# 软件工程

> 模块优先级：⭐⭐⭐⭐（分值中等，概念型为主，记忆量大）
> 考试题型：单选、多选、判断
> 难度：概念辨析为主，少量计算（PERT 图关键路径），不考代码实现

---

## 6.1 软件工程基本概念

### 软件是什么？

软件不仅仅是"程序代码"。软件 = **程序 + 数据 + 文档**。

**软件的特点**（和硬件对比）：
| 特点 | 解释 |
|------|------|
| 不会磨损 | 硬件用久了会坏，软件不会，但会"老化"（跟不上需求） |
| 逻辑实体 | 看不见摸不着，全靠抽象思维 |
| 手工开发 | 不像制造业有流水线，软件一直靠人写 |
| 维护复杂 | 改一处可能影响多处，越改越乱 |

### 软件危机

**什么是软件危机？** 不是"软件不好用"，而是要**开发**和**维护**软件时遇到的一系列严重问题。

| 表现 | 大白话 |
|------|--------|
| 开发成本超预算 | 钱花超了 |
| 开发进度拖延 | 时间一拖再拖 |
| 软件质量差 | Bug 多、不好用 |
| 维护困难 | 想改改不动，牵一发而动全身 |
| 用户不满意 | 做出来跟用户想象的不一样 |

**根本原因**：软件开发还是靠"手艺"，没有像工程那样有成熟的方法论。

### 软件工程三要素

软件工程 = 用**工程化**的方法来开发和维护软件。

> **类比**：盖房子有结构设计、施工规范、项目管理；写软件也应该有——这就是软件工程。

| 要素 | 解释 | 类比 |
|------|------|------|
| **方法** | 怎么做——技术上的"how" | 施工图纸 |
| **工具** | 用什么做——支撑方法的自动化系统 | 施工机械设备 |
| **过程** | 按什么顺序做——管理上的"when" | 施工流程管理 |

### 软件生命周期

软件从"想法"到"退役"的全过程，分为 7 个阶段：

| 阶段 | 做什么 | 产出物 |
|------|--------|--------|
| ① 问题定义 | 要解决什么问题？大概要花多少钱？ | 可行性报告 |
| ② 需求分析 | 用户到底要什么功能？ | SRS（需求规格说明书） |
| ③ 系统设计 | 怎么做？怎么搭架构？ | 设计文档 |
| ④ 编码实现 | 动手写代码 | 源代码 |
| ⑤ 软件测试 | 找 Bug，确认功能对 | 测试报告 |
| ⑥ 运行维护 | 上线后修 Bug、加功能 | 维护记录 |
| ⑦ 退役 | 软件不维护了，下线 | 退役报告 |

> **考试易错**：测试阶段在编码之后，不是在需求之后！需求分析阶段不能跳过直接去写代码。

## 6.2 软件开发过程管理

> 软件过程模型 = "做软件的一套流程"，不同模型适合不同场景。

### 瀑布模型

**核心思想**：像瀑布一样，一个阶段干完再干下一个，绝不回头。

```
需求分析 → 设计 → 编码 → 测试 → 维护
   ↓         ↓       ↓       ↓       ↓
上一阶段全部完成才进入下一阶段
```

| 优点 | 缺点 |
|------|------|
| 流程清晰，阶段分明 | 后期发现问题改不了（不能回头） |
| 文档齐全 | 用户前期必须把需求全说清楚（很难） |
| 适合需求固定的大项目 | 交付太晚，用户很久看不到东西 |

> **类比**：盖大楼，地基→框架→装修→验收，不能装了一半说要改地基。

### 原型模型

**核心思想**：先快速做一个"样板"给用户看，沟通清楚再正式做。

```
快速分析 → 建原型 → 用户试用 → 反馈 → 正式开发
```

| 优点 | 缺点 |
|------|------|
| 用户看得见、摸得着 | 用户可能把原型当成品 |
| 需求更准确 | 开发效率可能降低 |

> **原型分两种**：**抛弃型**（用完就扔）、**演化型**（在原型基础上改）。

### 增量模型

**核心思想**：把软件拆成多个"增量"，每个增量是一个可用的版本。

```
核心功能(增量1) → 加功能(增量2) → 再加功能(增量3) → ...
   ↓                 ↓                ↓
每个增量都是：需求→设计→编码→测试→交付
```

| 优点 | 缺点 |
|------|------|
| 用户能尽快看到可用版本 | 需要系统能拆分成模块 |
| 优先级高的先交付 | 后续增量可能破坏已交付部分 |

### 螺旋模型

**核心思想**：每个阶段都是"定目标 → 评估风险 → 开发 → 评审"的循环。**重点是风险管理**。

```
每个螺旋周期：
定目标 → 风险评估 → 开发实现 → 用户评审 → 进入下一圈
```

| 优点 | 缺点 |
|------|------|
| 强调风险管理 | 成本高 |
| 适合大型高风险项目 | 需要专业的风控能力 |

> **螺旋模型 = 原型模型 + 瀑布模型 + 风险分析**

### 4 种模型对比

| 模型 | 核心特点 | 适用场景 |
|------|---------|---------|
| 瀑布 | 严格按顺序，不可回头 | 需求明确不变的项目 |
| 原型 | 先做样版再正式做 | 需求模糊的项目 |
| 增量 | 拆模块逐个交付 | 核心功能优先的需求 |
| 螺旋 | 每圈都考虑风险 | 高风险大项目（航天、金融） |

### CMM / CMMI（软件能力成熟度模型）

用来**评估软件公司的开发能力**是几级。

| 级别 | 名称 | 特征 |
|------|------|------|
| 1 级 | **初始级** | 没流程，靠个人英雄 |
| 2 级 | **可重复级** | 有基本的项目管理 |
| 3 级 | **已定义级** | 有标准的开发流程 |
| 4 级 | **已管理级** | 用数据量化管理 |
| 5 级 | **优化级** | 持续改进优化 |

> **考试重点**：CMM 不是开发方法，是**能力评估标准**。级别越高，开发能力越成熟。

### 甘特图 vs PERT 图

项目管理的两种图形工具。

| 对比维度 | 甘特图 Gantt | PERT 图 |
|---------|-------------|---------|
| 形态 | 横向条形图 | 有向网络图 |
| 表示什么 | 任务 + 时间 + 进度 | 任务 + 依赖关系 |
| 能否看出任务依赖 | 不太直观 | 很直观（箭头表示） |
| 关键路径 | 不能直接看出 | 可以计算 |
| 用途 | 排期、跟进度 | 分析依赖、算工期 |

**PERT 图关键路径计算**：
- 关键路径 = 项目中**最长的**那条任务路径
- 关键路径上的任务一个都不能拖，拖了整体就延期
- 非关键路径上的任务可以适当延迟（有"浮动时间"）

> **类比**：甘特图像"日历表"，PERT 图像"任务依赖关系图"。

## 6.3 常见软件开发方法

### 结构化方法（面向过程）

**核心思想**：自顶向下，逐步求精。把大问题拆成小问题，小问题拆成更小的问题。

**DFD（数据流图）**是结构化分析的核心工具。

| DFD 元素 | 符号 | 含义 |
|----------|------|------|
| 外部实体（源头/终点） | 方框 | 谁提供数据 / 谁接收数据 |
| 处理（加工） | 圆/圆角矩形 | 对数据做什么处理 |
| 数据存储 | 开口矩形 | 数据存在哪里 |
| 数据流 | 箭头 | 数据从哪流向哪 |

**分层 DFD**：顶层（0 层）→ 1 层 → 2 层…逐步细化。

> **类比**：画"快递包裹从下单到签收的流转图"——谁下单、谁揽件、数据存哪、每步怎么处理。

### 面向对象方法（OOP/OOA/OOD）

**核心思想**：把事物看作"对象"，对象有属性和行为。

**三大特性**：
| 特性 | 解释 | 类比 |
|------|------|------|
| 封装 | 把数据和方法包在一起，对外隐藏细节 | 遥控器——你按按钮就行，不用管里面的电路 |
| 继承 | 子类自动拥有父类的属性和方法 | 继承房子——爸的房子自动归儿子用 |
| 多态 | 同一个接口，不同对象有不同表现 | "叫"——狗叫汪汪，猫叫喵喵，接口一样表现不同 |

### UML（统一建模语言）

UML 是面向对象分析设计的**图形化语言**，不是编程语言。

| 图类型 | 作用 | 一句话 |
|--------|------|--------|
| **用例图** | 描述"谁能做什么" | 用户和功能的关系 |
| **类图** | 描述"有哪些类及关系" | 静态结构 |
| **时序图** | 描述"对象间消息发来发去的顺序" | 时间上的交互过程 |
| 活动图 | 描述"业务流程" | 类似流程图 |
| 状态图 | 描述"对象状态怎么变化" | 从创建到销毁 |

### SOLID 五大设计原则

| 原则 | 含义 | 大白话 |
|------|------|--------|
| **S** - 单一职责 | 一个类只负责一件事 | 别让一个人干三份活 |
| **O** - 开闭原则 | 对扩展开放，对修改关闭 | 加功能可以，改旧代码不行 |
| **L** - 里氏替换 | 子类可以替换父类而不出问题 | 儿子能替爸爸干活 |
| **I** - 接口隔离 | 接口要小，不要一大坨 | 针对性给菜单，别给满汉全席 |
| **D** - 依赖倒置 | 依赖抽象，不依赖具体 | 依赖规范/接口，不依赖具体实现 |

### 敏捷开发

**核心思想**：不追求一次性做完美，小步快跑、频繁交付、随时调整。

**敏捷宣言**：
- **个体和互动** > 流程和工具
- **可工作的软件** > 详尽的文档
- **客户合作** > 合同谈判
- **响应变化** > 遵循计划

### Scrum（敏捷框架之一）

```
Sprint（冲刺 = 1~4 周）
│
├── Sprint 计划会 → 每日站会(15min) → Sprint 评审会 → Sprint 回顾会
│
角色：Product Owner(定需求) + Scrum Master(保障流程) + 开发团队
```

| Scrum 概念 | 解释 |
|-----------|------|
| Sprint | 一个迭代周期，通常 2 周 |
| Product Backlog | 需求列表，按优先级排 |
| Sprint Backlog | 当前 Sprint 要做的任务 |
| 每日站会 | 每天 15 分钟，昨天干了啥/今天干啥/有无障碍 |
| 燃尽图 | Sprint 剩余工作量可视化 |

### Kanban（看板）

**核心思想**：可视化工作流，限制"并行任务数"（WIP）。

```
待办 | 进行中(WIP ≤ 3) | 测试中 | 已完成
-----|----------------|--------|------
Task1 | Task2          | Task3  | Task4
      | Task5          |        |
```

> **Scrum vs Kanban**：Scrum 有固定 Sprint 周期；Kanban 是持续流动，没有固定时间框。

### XP（极限编程）

| 实践 | 解释 |
|------|------|
| 结对编程 | 两个人共用一台电脑写代码，一人写一人看 |
| TDD（测试驱动开发） | 先写测试再写代码 |
| 持续集成 | 频繁合代码，每次自动构建测试 |
| 小版本发布 | 尽可能频繁地交付可用版本 |

### DevOps

**核心思想**：打破开发（Dev）和运维（Ops）之间的墙。

```
代码提交 → 自动构建 → 自动测试 → 自动部署 → 监控反馈
    ↑_______________________________________________↓
                  持续改进循环
```

| 关键实践 | 解释 |
|---------|------|
| CI（持续集成） | 代码频繁合并，自动构建+测试 |
| CD（持续交付） | 代码随时可部署到生产 |
| CD（持续部署） | 代码通过测试后自动部署到生产 |
| 基础设施即代码 | 用代码管理服务器配置 |
| 监控与日志 | 实时监控系统运行状态 |

> **CI/CD 的关系**：CI → 持续集成（经常合代码），CD "D"可以是 Delivery（人工点发布）或 Deployment（自动发布）。

## 6.4 需求分析

### 功能需求 vs 非功能需求

| 类型 | 是什么 | 例子 |
|------|--------|------|
| **功能需求** | 系统**做什么** | "用户可以登录"、"购物车可添加商品" |
| **非功能需求** | 系统**做得怎么样** | "登录响应 < 1 秒"、"支持 1000 人同时在线"、"数据加密存储" |

**非功能需求的常见类型**：

| 类型 | 含义 | 例子 |
|------|------|------|
| 性能 | 快不快 | 响应时间 < 200ms |
| 可靠性 | 不容易挂 | 可用性 99.99% |
| 安全性 | 防不防攻击 | 密码加密、防 SQL 注入 |
| 可用性 | 好不好用 | 用户 5 分钟内学会基本操作 |
| 可维护性 | 好不好改 | 模块化设计、代码规范 |

### 需求获取方法

| 方法 | 解释 |
|------|------|
| 访谈 | 面对面问用户 |
| 问卷 | 发问卷收集大量用户的意见 |
| 用例分析 | 分析用户典型使用场景 |
| 原型法 | 做界面原型让用户试用反馈 |
| 观察法 | 直接看用户怎么工作的 |

### SRS（软件需求规格说明书）

**SRS 是需求阶段的产出物，是所有后续阶段的"宪法"**。

**SRS 应该有什么**：
- 功能描述（每个功能是什么）
- 数据描述（数据长什么样）
- 性能要求
- 约束条件（技术限制、法规要求等）
- 验收标准（怎么算"做好了"）

**SRS 的质量要求**：
| 属性 | 含义 |
|------|------|
| 正确性 | 描述的确实是用户想要的 |
| 无歧义 | 每个人读出来的意思都一样 |
| 完整性 | 所有需求都覆盖了 |
| 可验证 | 有明确的验证标准 |

## 6.5 系统设计

### 高内聚低耦合

这是软件设计的**核心原则**，也是考试**必考**概念。

> **类比**：一个部门（模块）内部配合紧密 = 高内聚；部门之间依赖少 = 低耦合。这样的公司效率最高。

### 内聚（模块内部元素联系的紧密程度）

**内聚越高越好**，从低到高排列：

| 级别 | 内聚类型 | 解释 | 好坏 |
|------|---------|------|------|
| 1 | 偶然内聚 | 模块内元素毫无关系，凑在一起的 | 最差 |
| 2 | 逻辑内聚 | 几个逻辑相似的功能放一起 | 差 |
| 3 | 时间内聚 | 同一时间执行的操作放一起 | 差 |
| 4 | 过程内聚 | 按特定顺序执行的功能放一起 | 中 |
| 5 | 通信内聚 | 操作同一数据集的功能放一起 | 中 |
| 6 | 顺序内聚 | 前一步输出是后一步输入 | 较好 |
| 7 | **功能内聚** | 模块只做一件完整的事 | **最好** |

> **记忆口诀**：偶逻时过通顺功（偶然→逻辑→时间→过程→通信→顺序→功能）

### 耦合（模块之间依赖的程度）

**耦合越低越好**，从高到低排列：

| 级别 | 耦合类型 | 解释 | 好坏 |
|------|---------|------|------|
| 1 | 内容耦合 | 一个模块直接修改另一个模块内部数据 | 最差 |
| 2 | 公共耦合 | 多个模块共享全局变量 | 差 |
| 3 | 外部耦合 | 共享外部规定（如通信协议） | 差 |
| 4 | 控制耦合 | 传控制信息影响另一个模块逻辑 | 中 |
| 5 | 标记耦合 | 传复杂数据结构（但只用其中一部分） | 中 |
| 6 | **数据耦合** | 只传简单的必要数据 | **最好** |

> **记忆口诀**：内公外控标数（内容→公共→外部→控制→标记→数据）

### 软件体系结构

#### 分层架构

```
┌─────────────────┐
│    表示层(UI)    │  ← 和用户交互
├─────────────────┤
│    业务逻辑层    │  ← 处理业务规则
├─────────────────┤
│    数据访问层    │  ← 读写数据库
├─────────────────┤
│     数据库       │
└─────────────────┘
```

> 每层只调用下一层，不能跨层调用。好处：改一层不影响其他层。

#### MVC 架构

| 字母 | 全称 | 职责 |
|------|------|------|
| **M** | Model（模型） | 数据 + 业务逻辑 |
| **V** | View（视图） | 展示给用户看 |
| **C** | Controller（控制器） | 接收用户输入，调度 M 和 V |

> **流程**：用户操作 → Controller 收到 → 调用 Model 处理 → 更新 View 展示

#### 微服务架构

**对比**：

| 对比维度 | 单体架构 | 微服务架构 |
|---------|---------|-----------|
| 结构 | 一个大的应用程序 | 多个小服务，各自独立 |
| 部署 | 整体打包部署 | 每个服务独立部署 |
| 通信 | 函数调用 | 网络调用（HTTP/RPC） |
| 扩展 | 整体扩展 | 哪个服务忙扩哪个 |
| 优点 | 开发简单 | 独立开发部署，技术栈灵活 |
| 缺点 | 越来越臃肿 | 分布式复杂性，运维成本高 |

> **类比**：单体架构像一个大超市（啥都有但改布局难），微服务像专卖店（各司其职，独立运营）。

## 6.6 系统开发

### 编码规范

写代码不只是"写出来就行"，还要让别人看得懂、好维护。

| 规范类型 | 内容 |
|---------|------|
| 命名规范 | 变量用驼峰（userName），常量全大写（MAX_SIZE），类名首字母大写 |
| 注释规范 | 解释为什么这么做，不只是翻译代码 |
| 代码格式 | 缩进对齐、换行规则、空格使用 |
| 错误处理 | 不要吞掉异常，要有日志记录 |
| 代码复用 | 不要复制粘贴，提取公共函数/类 |

### Git 基本操作

Git 是**分布式版本控制系统**。

**三个区**：

```
工作区 → git add → 暂存区 → git commit → 本地仓库 → git push → 远程仓库
  ↑                                                    ↓
  ←─────────────── git pull / git fetch ──────────────────
```

| 命令 | 作用 | 笔记 |
|------|------|------|
| `git init` | 初始化仓库 | 在当前目录创建 `.git` |
| `git clone <url>` | 克隆远程仓库 | 把远程仓库下载到本地 |
| `git status` | 查看状态 | 哪些改了、哪些暂存了 |
| `git add <file>` | 添加到暂存区 | 选哪些改动要提交 |
| `git commit -m "消息"` | 提交到本地仓库 | 生成一个版本快照 |
| `git push` | 推送本地提交到远程 | 上传到服务器 |
| `git pull` | 拉取远程更新 | = fetch + merge |
| `git log` | 查看提交历史 | 谁什么时候改了啥 |
| `git diff` | 查看具体改动内容 | 比较差异 |

### Git 分支操作

| 命令 | 作用 |
|------|------|
| `git branch` | 查看本地分支 |
| `git branch <name>` | 创建新分支 |
| `git checkout <name>` | 切换到指定分支 |
| `git checkout -b <name>` | 创建并切换到新分支 |
| `git merge <name>` | 将指定分支合并到当前分支 |
| `git branch -d <name>` | 删除分支 |

**分支工作流**：
```
main ──●───●───●───●───● (稳定主分支)
          \         /
feature    ●───●──●  (开发分支，开发完合并回 main)
```

> **类比**：Git 像一个"无限存档的游戏"——你可以随时存档（commit），回到任意之前的存档（checkout），开分支就像开了平行剧情线，打好了再合回主线（merge）。

## 6.7 软件测试

### 测试方法

#### 黑盒测试 vs 白盒测试

| 对比维度 | 黑盒测试 | 白盒测试 |
|---------|---------|---------|
| 是否看代码 | **不看**源代码 | **看**源代码 |
| 关注什么 | 输入→输出对不对 | 代码逻辑覆盖全不全 |
| 谁来测 | 测试人员 | 开发人员 |
| 类比 | 不拆开遥控器，只试按钮功能对不对 | 拆开机器，检查每个电路 |

#### 黑盒测试方法

| 方法 | 解释 | 示例 |
|------|------|------|
| **等价类划分** | 把输入分成有效/无效类，每类取代表 | 年龄输入 1~120 有效，选 30 测试；0 无效 |
| **边界值分析** | 测刚好在边界上的值 | 年龄 1~120，测 1、120、0、121 |
| 决策表 | 列出所有条件组合 | 各种 if-else 组合 |
| 因果图 | 分析输入和输出的因果关系 | |

> **边界值分析**是黑盒测试最有效的方法，因为错误往往出现在边界上。

#### 白盒测试方法（逻辑覆盖）

| 覆盖级别 | 解释 | 强度 |
|---------|------|------|
| 语句覆盖 | 每个语句至少执行一次 | 最弱 |
| 判定覆盖 | 每个判定的真假分支各执行一次 | 弱 |
| 条件覆盖 | 每个条件的真假各执行一次 | 中 |
| 判定/条件覆盖 | 判定覆盖 + 条件覆盖 | 较强 |
| 条件组合覆盖 | 所有条件真假组合都执行 | 强 |
| **路径覆盖** | 所有可能的执行路径都走过 | **最强** |

> **从弱到强**：语句 < 判定 < 条件 < 判定/条件 < 条件组合 < 路径

### 测试层次（V 模型）

```
需求分析 ──────────────→ 验收测试（用户来测）
    │                        │
    ↓                        ↓
系统设计 ──────────────→ 系统测试（测整个系统）
    │                        │
    ↓                        ↓
概要设计 ──────────────→ 集成测试（测模块之间）
    │                        │
    ↓                        ↓
详细设计 ──────────────→ 单元测试（测单个函数/类）
    │                        │
    ↓                        ↓
   编码 ←──────────────── 编码
```

| 层次 | 测试什么 | 谁来测 | 目的 |
|------|---------|--------|------|
| **单元测试** | 单个函数/类/模块 | 开发人员 | 确认每个小单元正确 |
| **集成测试** | 模块间的接口 | 开发/测试 | 确认模块间配合正确 |
| **系统测试** | 整个系统 | 测试人员 | 确认系统满足需求 |
| **验收测试** | 按需求验收 | 用户/客户 | 确认"这就是我想要的" |

### 回归测试

**定义**：改了代码后，重新跑一遍之前的测试，确保改一个新东西没把旧功能搞坏。

> **类比**：修好了一个房间的灯，把其他房间的灯也都检查一遍——确认没把别处搞短路。

**为什么要回归测试？** 软件各模块相互依赖，改 A 可能影响 B、C、D。

### 缺陷生命周期

```
新建(New) → 确认(Open) → 修复中(In Progress)
                            │
                            ↓
                        已修复(Fixed)
                            │
                            ↓
                        验证(Verify)
                           / \
                          /   \
                    通过        不通过
                     ↓           ↓
                  关闭(Closed)  重新打开(Reopen)
```

| 状态 | 含义 |
|------|------|
| New | 测试人员刚发现并提交 |
| Open | 开发确认确实是 Bug |
| In Progress | 开发正在修复 |
| Fixed | 开发说修好了 |
| Verified | 测试验证确实修好了 |
| Closed | 关单，Bug 生命周期结束 |
| Reopen | 测试验证发现没修好/又坏了，重新打开 |

## 6.8 软件交付与维护

### CI/CD

```
开发者提交代码
    │
    ↓
【CI 持续集成】
    ├── 自动拉取代码
    ├── 自动编译/构建
    ├── 自动运行单元测试
    ├── 自动代码扫描
    └── 如果通过
        │
        ↓
【CD 持续交付/部署】
    ├── 自动部署到测试环境
    ├── 自动运行集成测试
    ├── 自动部署到预发布环境
    └── 自动/手动部署到生产环境
```

| 概念 | 解释 | 关键点 |
|------|------|--------|
| CI 持续集成 | 频繁将代码合入主干，每次自动构建测试 | 发现问题越快越好 |
| 持续交付 CD | 代码随时处于可发布状态 | 需要手动点"发布" |
| 持续部署 CD | 通过测试后自动部署到生产 | 全自动，不需要人工确认 |

### 四种软件维护类型

| 类型 | 做什么 | 占比 | 例子 |
|------|--------|------|------|
| **改正性维护** | 修 Bug | ~21% | 登录按钮点了没反应，修这个 Bug |
| **适应性维护** | 适应外部环境变化 | ~25% | 系统从 Windows 迁移到 Linux |
| **完善性维护** | 加新功能、优化已有功能 | ~50% | 增加导出 PDF 功能；优化查询速度 |
| **预防性维护** | 防止将来出问题 | ~4% | 重构代码，即使现在没 Bug 也整理干净 |

> **考试重点**：完善性维护占比最高（约 50%），因为用户总想加新功能；预防性维护最少（约 4%）。

### 软件文档

| 文档类型 | 给谁看 | 内容 |
|---------|--------|------|
| 用户文档 | 最终用户 | 使用手册、帮助文档 |
| 开发文档 | 开发人员 | 需求规格、设计文档、代码注释 |
| 管理文档 | 项目经理 | 项目计划、进度报告 |

### 软件退役

软件生命周期结束——不再维护、不再使用、从服务器下线。原因可能是：技术过时、无商业价值、被新系统替代。

## 常见易错陷阱

1. **CMM 是能力评估标准，不是开发方法**——常考混淆
2. **螺旋模型的核心是风险分析**，不只是迭代
3. **内聚越高越好，耦合越低越好**——记住"高内聚低耦合"是目标
4. **黑盒测试不看代码**（等价类、边界值），**白盒测试看代码**（语句/判定/条件覆盖）
5. **单元测试是开发人员做的**，不是测试人员
6. **回归测试**不等于重复测试，特指"改了代码后重测确保没影响旧功能"
7. **完善性维护占 50%**，是最多的维护类型
8. **PERT 图的关键路径是项目中最长路径**，决定项目最短工期
9. **DevOps 的 CD 有两个含义**：Delivery（持续交付，手动发布）和 Deployment（持续部署，自动发布）
10. **敏捷不等于没有文档**，而是"可工作的软件 > 详尽的文档"
