## 知识点 45：人工智能基础

> **考频星级：必考 ⭐⭐⭐** | 机器学习分类判断、监督/无监督/强化学习的场景识别是每年必考题型

### 知识点 45：1 人工智能是什么？

人工智能（Artificial Intelligence，简称 AI）就是让计算机模仿人类的智能行为——学习、推理、感知、决策。

**类比**：教小孩认猫——先给他看很多猫的图片（这就是"数据"），他慢慢总结出猫的特征（"学习"），以后看见没见过的猫也能认出来（"泛化"）。AI 也是这个道理。

**三个层次划分**：

| 层次 | 含义 | 现状 |
|------|------|------|
| 弱人工智能（ANI） | 只会做一件特定的事 | 当前所有 AI 都在这个层次（AlphaGo、ChatGPT 都是） |
| 强人工智能（AGI） | 像人一样什么都能干的通用智能 | 尚未实现，是研究目标 |
| 超人工智能（ASI） | 在所有领域超过人类的智能 | 科幻范畴 |

> 考试记忆诀窍：当前所有 AI 都是弱人工智能（ANI），不是强人工智能（AGI）。

**真题 45-1-1（判断题）**：AlphaGo 战胜李世石属于强人工智能（AGI）的应用。（）

> 答案：错误。解析：AlphaGo 只会下围棋，属于"只会做一件事"的弱人工智能（ANI）。AGI 是指像人一样什么都能干的通用智能，目前尚未实现。关键词记忆："只会做一件事 = ANI"。

**真题 45-1-2（单选题）**：以下关于人工智能三个层次的描述，正确的是（）。
A. Siri 属于强人工智能（AGI）
B. 当前所有 AI 系统都属于弱人工智能（ANI）
C. ChatGPT 已经达到了强人工智能（AGI）水平
D. 超人工智能（ASI）已经在小范围内实现

> 答案：B。解析：Siri、ChatGPT、AlphaGo 等当前所有 AI 系统都只是弱人工智能（ANI），只能完成特定领域的任务。AGI（强人工智能）是研究目标，尚未实现；ASI（超人工智能）属于科幻范畴。

**常见陷阱**：
| 陷阱 | 错误认识 | 正确理解 |
|------|---------|---------|
| ChatGPT 很聪明 = AGI | 看到 ChatGPT 能聊天、写代码、翻译，就以为它是通用人工智能 | ChatGPT 的能力全部限于"文本处理"，离开文本领域什么都不会。它不是"什么都能干"，只是"在文本领域很能干" |

**记忆口诀**：
> "弱人工做一件事，强人工样样通，超人工科幻中"
> "考试铁律：当前所有 AI = 弱人工智能 ANI"

### 知识点 45：2 人工智能发展简史

```
1950 图灵测试 → 提出"机器能思考吗？"
1956 达特茅斯会议 → "人工智能"术语诞生
     ↓ （推理期：逻辑证明、问题求解）
1966-1974 第一次 AI 寒冬（算力不足，期望过高）
1980s 专家系统兴起 → 用规则库模拟专家决策（MYCIN 医疗诊断系统）
     ↓ （知识期：知识工程）
1987-1993 第二次 AI 寒冬（专家系统维护成本过高）
1990s 浅层机器学习 → SVM、决策树、随机森林
     ↓ （统计机器学习期）
2006 Hinton 提出深度学习 → 深层神经网络训练方法
2012 AlexNet 在 ImageNet 夺冠 → 深度学习爆发
2014 GAN 生成对抗网络诞生
2016 AlphaGo 战胜李世石
2017 Transformer 架构提出（论文 "Attention Is All You Need"）
2018 BERT / GPT-1 发布
2020 GPT-3（1750 亿参数）→ 大模型时代序幕
2022 ChatGPT → 大模型时代全面到来
2023 GPT-4、文心一言、通义千问等 → 多模态大模型
```

> 考试记忆诀窍："1956 诞生 → 1980s 专家系统 → 1987 二次寒冬 → 2012 深度学习爆发 → 2017 Transformer → 2022 大模型元年"

**真题 45-2-1（单选题）**：人工智能作为一门学科正式诞生的标志性事件是（）。
A. 1950 年图灵测试的提出
B. 1956 年达特茅斯会议
C. 1997 年深蓝战胜卡斯帕罗夫
D. 2012 年 AlexNet 在 ImageNet 夺冠

> 答案：B。解析：1956 年达特茅斯会议首次提出了"人工智能"（Artificial Intelligence）这一术语，标志着 AI 作为一门学科正式诞生。A 图灵测试虽早（1950），但只是提出了"机器能思考吗"的问题；C 是 AI 应用里程碑；D 是深度学习爆发的标志。

**真题 45-2-2（单选题）**：以下事件按时间顺序排列正确的是（）。
A. 图灵测试 → 达特茅斯会议 → AlphaGo 胜李世石 → AlexNet 夺冠
B. 达特茅斯会议 → 图灵测试 → AlexNet 夺冠 → AlphaGo 胜李世石
C. 图灵测试 → 达特茅斯会议 → AlexNet 夺冠 → AlphaGo 胜李世石
D. 达特茅斯会议 → 图灵测试 → AlphaGo 胜李世石 → AlexNet 夺冠

> 答案：C。解析：时间线：1950 图灵测试 → 1956 达特茅斯会议 → 2012 AlexNet → 2016 AlphaGo。记忆技巧：1950→1956 只差 6 年，2012→2016 也只差 4 年，按"先小后大"顺序不会错。

**常见陷阱**：
| 陷阱 | 错误认识 | 正确理解 |
|------|---------|---------|
| 图灵测试 = AI 诞生 | 图灵测试（1950）比达特茅斯会议（1956）早，误以为 AI 1950 年诞生 | 图灵测试只是提出了问题，达特茅斯会议才正式确立"Artificial Intelligence"这个学科名称 |
| 两次 AI 寒冬年代搞混 | 记不清第一次和第二次寒冬的时间 | 第一次：1966-1974（专家系统出现前），第二次：1987-1993（专家系统失败后）。口诀："六六到七四，八七到九三" |

**记忆口诀**：
> "五六诞生，八零专家，八七寒冬，一二爆发，一七变形金刚（Transformer），二二大模型元年"
> "图灵先问，达茅取名，两次寒冬，深度学习翻身"

### 知识点 45：3 机器学习三大范式

机器学习的核心公式：**数据 + 算法 = 模型**（模型遇到新数据时能做出预测或决策）

**机器学习关键术语速查**：

| 术语 | 含义 | 大白话 |
|------|------|--------|
| **特征（Feature）** | 描述数据的属性 | "这个人的年龄、收入、性别" |
| **标签（Label）** | 我们要预测的目标值 | "这个人会不会买（买/不买）" |
| **训练集（Training Set）** | 用来训练模型的数据 | "练习题" |
| **验证集（Validation Set）** | 用来调参和选模型的数据 | "模拟考" |
| **测试集（Test Set）** | 用来最终评估模型的数据 | "正式考试" |
| **泛化（Generalization）** | 模型在新数据上的表现能力 | "用学到的知识做新题" |
| **超参数（Hyperparameter）** | 人在训练前设置的参数（不是学出来的） | "学习率、网络层数、KNN的K值" |
| **epoch** | 模型把全部训练数据过了一遍 | "做完整本习题册一遍 = 一个 epoch" |
| **batch size** | 每次更新参数用的样本数 | "一次做多少道题才对照答案" |

#### 知识点 45：3.1 监督学习（Supervised Learning）

有"标准答案"（标签）的训练方式。

**类比**：老师教你做题，每道题都告诉你正确答案。做多了你就掌握了规律，遇到新题也能做出来。

| 要素 | 说明 |
|------|------|
| 输入 | 带标签的训练数据（特征 + 标签） |
| 目标 | 学到从"输入"到"输出"的映射关系 |
| 常见任务 | **分类**、**回归** |
| 常见算法 | KNN、决策树、随机森林、SVM、逻辑回归、线性回归、朴素贝叶斯 |
| 例子 | 垃圾邮件识别、房价预测、图像分类 |

**分类 vs 回归**：
- **分类（Classification）**：预测结果是离散的类别。如：这是猫还是狗？→ 猫/狗（有限的几个选项）
- **回归（Regression）**：预测结果是连续的数值。如：这房子卖多少钱？→ 500万（可以取任何数值）

**监督学习经典算法详解**：

| 算法 | 核心思想 | 优缺点 | 适用场景 |
|------|---------|--------|---------|
| **KNN（K近邻）** | 看离得最近的 K 个邻居，少数服从多数 | 简单直观，但计算量大、对异常值敏感 | 小数据集分类 |
| **决策树** | 像"流程图"一样逐级判断（if-else 树） | 可解释性强，但容易过拟合 | 客户分类、医疗诊断 |
| **随机森林** | 多棵决策树投票决定结果（集成学习） | 解决单棵树的过拟合问题，鲁棒性强 | 金融风控、生物信息 |
| **SVM（支持向量机）** | 找一个"最大间隔"的超平面把不同类分开 | 适合高维数据，但对大规模数据慢 | 文本分类、人脸识别 |
| **朴素贝叶斯** | 基于贝叶斯定理，假设特征之间相互独立 | 速度快，适合文本分类，但"独立性假设"现实中常不成立 | 垃圾邮件过滤、情感分析 |
| **逻辑回归** | 虽然叫"回归"，但用于二分类（输出 0~1 的概率） | 简单、可解释、输出概率值 | 信用评分、疾病预测 |
| **线性回归** | 用一条直线拟合数据点，预测连续值 | 最简单直观，但只能拟合线性关系 | 房价预测、销量预测 |

> 记忆诀窍：分类 = 选择题（ABCD），回归 = 填空题（填数字）

#### 知识点 45：3.2 无监督学习（Unsupervised Learning）

没有"标准答案"，让算法自己从数据中发现规律。

**类比**：给你一堆水果但不告诉你是谁买的，你自己按照颜色、大小、形状把苹果放一筐、橘子放一筐。

| 要素 | 说明 |
|------|------|
| 输入 | 无标签的数据（只有特征，没有标签） |
| 目标 | 发现数据内部的隐藏结构或分布 |
| 常见任务 | **聚类**、**降维**、**关联规则** |
| 常见算法 | K-Means、层次聚类、DBSCAN、PCA、Apriori |
| 例子 | 用户分群、异常检测、推荐系统"猜你喜欢" |

**聚类 vs 降维**：
- **聚类（Clustering）**：把相似的样本归为一组。如：把消费者分成高消费/中消费/低消费三群
- **降维（Dimensionality Reduction）**：把数据的特征数量压缩，保留核心信息。如：把人脸照片 1000 维数据压缩到 100 维，方便计算

**无监督学习经典算法详解**：

| 算法 | 核心思想 | 特点 |
|------|---------|------|
| **K-Means（K均值）** | 先随机选 K 个中心点，迭代把每个样本分配到最近的中心，不断修正中心点直到收敛 | 速度快，但需预先指定 K 值，对初始点敏感 |
| **层次聚类** | 自底向上（合并）或自顶向下（分裂）不断聚合/拆分 | 不需要指定 K，但计算量大，适合小数据集 |
| **DBSCAN（密度聚类）** | 基于密度：核心点周围密度高形成簇，密度低的是噪声 | 能发现任意形状簇、自动识别噪声，适合地理数据 |
| **PCA（主成分分析）** | 找到方差最大的方向（主成分），把高维数据投影到低维 | 最常用的降维方法，线性降维 |

#### 知识点 45：3.3 强化学习（Reinforcement Learning）

没有正确答案，算法通过和环境的互动，"试错"来学习最佳策略。

**类比**：训练小狗——做对了给零食（奖励），做错了不理它（惩罚）。狗狗会自己总结出怎么做才能得到更多零食。

| 要素 | 说明 |
|------|------|
| 核心概念 | **智能体（Agent）** 在 **环境（Environment）** 中执行 **动作（Action）**，获得 **奖励（Reward）** |
| 目标 | 找到让长期累积奖励最大的策略（Policy） |
| 关键要素 | 状态（State）、动作（Action）、奖励（Reward）、策略（Policy）、值函数（Value Function） |
| 典型算法 | Q-Learning、DQN（Deep Q-Network）、Policy Gradient、Actor-Critic |
| 典型例子 | AlphaGo 下围棋、自动驾驶、游戏 AI、机器人控制 |

**强化学习核心概念扩充**：

| 概念 | 含义 | 大白话 |
|------|------|--------|
| **探索（Exploration）** | 尝试新的动作，看看有没有更好的选择 | "试试没吃过的菜" |
| **利用（Exploitation）** | 根据已有的经验，选最好的动作 | "朋友说这家最好吃就去这家" |
| **值函数** | 评估在某个状态下长期能获得多少累计奖励 | "在路口 A 等待比在 B 等待更快到家" |
| **马尔可夫决策过程（MDP）** | 强化学习的数学框架：下一个状态只取决于当前状态和动作 | "未来只看现在，不看过去" |
| **Q-Learning** | 学习每个"状态-动作对"的价值（Q 表），选择 Q 值最大的动作 | "每个路口每个方向都打分，选最高分的走" |

> 强化学习不需要你预先准备"正确答案"，它自己边试边学。核心难点在于"探索与利用的平衡"——如果一直吃同一家店（过度利用），可能错过更好吃的店；如果天天换店（过度探索），永远找不到稳定好吃的店。

#### 知识点 45：3.4 机器学习三大范式——解题模板（国网考试必杀技）

国网考试中机器学习分类判断题有固定套路，掌握以下"三步法"可以秒杀所有场景题。

**三步法解题模板**：

```
第一步：看有没有"标签/标准答案"
  ├── 有标签（数据标注了正确结果）→ 监督学习，跳到第二步
  ├── 没有标签，但有"奖励/惩罚"信号 → 强化学习
  ├── 没有标签，也没有奖励信号 → 无监督学习，跳到第三步
  └── 少量标注 + 大量未标注 → 半监督学习

第二步：对监督学习，看预测目标是离散还是连续
  ├── 预测离散类别（猫/狗、买/不买、正常/欺诈）→ 分类
  └── 预测连续数值（价格、温度、销量）→ 回归

第三步：对无监督学习，看任务目标是分组还是压缩
  ├── 把数据分成几组（客户分群、商品归类）→ 聚类
  └── 减少特征数量（降维、特征提取）→ 降维
```

**国网考试场景关键词速查表**：

| 学习范式 | 题干关键词 | 秒选 |
|----------|-----------|------|
| **监督-分类** | "标注了""标签""已标记""已知类别""判断是否""识别" | 分类 |
| **监督-回归** | "预测价格""预测温度""预测销量""预测数值""预估" | 回归 |
| **无监督-聚类** | "自动分组""没有预定义""发现群体""自己分类""分群" | 聚类 |
| **无监督-降维** | "减少特征""压缩维度""降维""特征提取" | 降维 |
| **强化学习** | "试错""奖励""惩罚""自我对弈""与环境互动""策略" | 强化学习 |
| **半监督学习** | "少量标注"+"大量未标注" | 半监督学习 |

**三类学习方式深度对比**

| 对比维度 | 监督学习 | 无监督学习 | 强化学习 |
|----------|---------|-----------|---------|
| 有没有标签 | 有 | 没有 | 没有（但有奖励信号） |
| 学习方式 | 模仿正确答案 | 自己找规律 | 试错 + 奖励 |
| 反馈形式 | 直接给出正确结果 | 无反馈 | 延迟的奖励信号 |
| 典型任务 | 分类、回归 | 聚类、降维、关联规则 | 游戏、机器人控制、自动驾驶 |
| 关键算法 | KNN、SVM、决策树、随机森林、逻辑回归 | K-Means、层次聚类、PCA、DBSCAN | Q-Learning、DQN、Policy Gradient |
| 数据要求 | 需要大量标注数据 | 不需要标注 | 需要与环境交互的能力 |
| 类比 | 有答案的习题册 | 自己整理书架 | 训狗 |

### 知识点 45：4 深度学习三大网络结构

> **考频星级：高频 ⭐⭐** | CNN/RNN/Transformer 的适用场景和核心机制是常见考点

#### 知识点 45：4.1 CNN（卷积神经网络）

**专攻：图像处理**

**核心思想**：用"卷积核"（一个小窗口）在图片上滑动，提取局部特征。

**类比**：你在看一张猫的照片——不是一次性看整张照片，而是先看耳朵（局部特征），再看眼睛，再看尾巴，最后综合判断"这是一只猫"。

| 关键概念 | 含义 |
|----------|------|
| 卷积层（Convolution） | 用卷积核滑动，提取特征（边缘、纹理、形状） |
| 池化层（Pooling） | 压缩数据，保留最重要的信息（最大池化取窗口内最大值，平均池化取平均值） |
| 全连接层（FC） | 把前面提取的特征整合起来，做最后的分类判断 |
| 激活函数 | 常用 ReLU，引入非线性能力 |

**CNN 工作原理详解**：
1. 输入一张图片（如 224x224 像素的 RGB 图片）
2. 卷积层：用多个卷积核（如 3x3 大小）在图片上滑动，每个卷积核提取一种特征（如竖边、横边、纹理）
3. 池化层：把特征图缩小（如 2x2 窗口取最大值），减少计算量，同时保留重要特征
4. 堆叠多层（浅层提取简单特征如边缘，深层提取复杂特征如人脸、物体）
5. 全连接层 + Softmax：输出每个类别的概率

**CNN 两大核心特性**：

| 特性 | 含义 | 大白话 | 为什么重要 |
|------|------|--------|-----------|
| **局部感知（Local Receptive Field）** | 每个神经元只连接输入的一小块区域，不看全局 | "只关注眼前的一小块" | 大幅减少参数数量 |
| **权重共享（Weight Sharing）** | 同一个卷积核用相同的权重扫过整张图 | "用同一把尺子量遍整张图" | 无论特征出现在哪里都能检测到 |

**卷积核大小选择**：
- 3x3 是最常用的卷积核大小（VGGNet 全部使用 3x3）
- 两个 3x3 卷积堆叠的感受野 = 一个 5x5 卷积的感受野，但参数更少
- 1x1 卷积用于降维/升维（调整通道数，不改变空间尺寸）

**池化（Pooling）为什么重要？**
- 降维：减少计算量，加快训练
- 平移不变性：即使物体稍微移动，池化后特征仍然相似
- 防止过拟合：减少参数数量

**经典 CNN 模型**：

| 模型 | 年份 | 创新点 | 考试要点 |
|------|------|--------|---------|
| **LeNet-5** | 1998 | 最早的 CNN，手写数字识别 | CNN 鼻祖，确立了卷积+池化+全连接的基本结构 |
| **AlexNet** | 2012 | 用 GPU 训练，引入 ReLU + Dropout | 深度学习爆发的标志 |
| **VGGNet** | 2014 | 全部用 3x3 小卷积核，网络更深 | 结构简洁但参数多 |
| **ResNet** | 2015 | 引入"残差连接"（跳层连接），解决深层网络训练困难 | 可训练 152 层甚至更深的网络 |
| **Inception（GoogLeNet）** | 2014 | 同一层用多个不同大小的卷积核并行处理 | 宽度和深度同时扩展 |

**ResNet 残差连接详解**（考试高频）：
- 传统深层网络：越深越难训练（梯度消失），56 层网络错误率反而高于 20 层
- ResNet 方案：引入"短路连接"（Shortcut/Skip Connection），让输入直接跳过几层加到输出上
- 核心公式：输出 = F(x) + x（F(x) 是几层卷积的变换，x 是原始输入）
- 效果：即使 F(x) 学不到东西，至少还能保留原始输入 x，不会退化
- 这个设计让 ResNet 可以训练 152 层甚至 1000+ 层的网络

**CNN 典型应用**：图像分类（ImageNet 竞赛）、人脸识别（FaceID）、医学影像分析（CT/MRI 病灶识别）、自动驾驶中的物体检测（YOLO/SSD）、图像分割（U-Net）

> 记忆诀窍：CNN = 卷积核扫图 → 提取特征 → 池化压缩 → 全连接分类，核心就是"局部感知 + 权重共享"

#### 知识点 45：4.2 RNN（循环神经网络）

**专攻：序列数据处理**（数据前后有顺序关系）

**核心思想**：有一个"记忆单元"，把前一步的输出传递给后一步。

**类比**：你读一句话不会把每个字孤立理解，而是用前文来帮助理解后文的含义。"我今天心情很好，所以___"→ 你知道后面大概率是正面词汇。

**RNN 的数学本质**：
- 每一步的计算：h_t = f(W_h * h_{t-1} + W_x * x_t + b)
- h_t 是当前步的"隐藏状态"（记忆），h_{t-1} 是上一步的记忆，x_t 是当前输入
- 同一个权重矩阵 W_h 和 W_x 在所有时间步共享（参数共享）

**RNN 的两大核心问题**：

| 问题 | 原因 | 表现 | 解决方案 |
|------|------|------|---------|
| **梯度消失（Vanishing Gradient）** | 反向传播时梯度连乘，小于1的值越乘越小 | 无法学到长距离依赖关系，远处的信息传不过来 | LSTM、GRU（引入门控机制）、梯度裁剪 |
| **梯度爆炸（Exploding Gradient）** | 反向传播时梯度连乘，大于1的值越乘越大 | 模型参数剧烈震荡、loss 变 NaN | 梯度裁剪（Gradient Clipping，限制梯度最大值） |

> **类比**："传话游戏"——20个人传一句话，传到最后面目全非（梯度消失）；或者越传越夸张（梯度爆炸）。

| 变体 | 含义 |
|------|------|
| RNN（基础） | 能记住前面的信息，但太长的序列记不住（梯度消失/梯度爆炸） |
| LSTM（长短期记忆） | 引入三个"门"：遗忘门（决定丢掉什么旧信息）、输入门（决定存入什么新信息）、输出门（决定输出什么信息） |
| GRU（门控循环单元） | LSTM 的简化版，只有两个门（重置门 + 更新门），参数更少，训练更快 |
| Bi-RNN（双向 RNN） | 同时从前向后和从后向前处理序列，能利用上下文双向信息 |

**LSTM 三"门"详解**：

| 门 | 功能 | 大白话 |
|----|------|--------|
| **遗忘门** | 决定丢掉细胞状态中哪些旧信息 | "这段记忆不重要了，忘了吧" |
| **输入门** | 决定哪些新信息存入细胞状态 | "这个新信息很重要，记下来" |
| **输出门** | 决定当前时刻输出什么 | "现在该说什么（输出什么）" |

**RNN/LSTM 典型应用**：机器翻译（seq2seq 模型）、语音识别（声学模型）、文本生成（古诗、对联）、时间序列预测（股票走势、电力负荷）、手写识别

**为什么 RNN 系列逐渐被 Transformer 替代？**
- RNN 必须按顺序计算，第 t 步必须等第 t-1 步算完 → 无法并行，训练慢
- 长序列时梯度消失严重（LSTM/GRU 缓解但未根治）
- Transformer 的自注意力机制能直接建模任意两个位置的关系

> 记忆诀窍：RNN = 有记忆的神经网络，适合"前后有关系"的数据；LSTM = 加了三道门锁的记忆，不会忘事也不会乱记

#### 知识点 45：4.3 Transformer

**目前最主流的深度学习架构，ChatGPT/BERT/GPT-4 的基础**

**核心创新**：**自注意力机制（Self-Attention）**——让模型知道一句话里哪个词和哪个词有关系。

**类比**：读这句话："小明把苹果给了小红，她很高兴"。Transformer 的注意力机制能自动判断"她"指的是"小红"而不是"小明"。

| 关键概念 | 含义 |
|----------|------|
| 自注意力（Self-Attention） | 计算句子中每个词与其他所有词的关联度（Q=Query查询，K=Key键，V=Value值） |
| 多头注意力（Multi-Head） | 从多个角度（多个"头"）同时做注意力，不同"头"关注不同关系（语法/语义/指代等） |
| 位置编码（Positional Encoding） | 因为 Transformer 不像 RNN 那样天然有序，所以要额外告诉它词的顺序（常用正弦余弦编码） |
| Encoder（编码器） | 理解输入文本，输出上下文相关的表示向量 |
| Decoder（解码器） | 根据 Encoder 的输出，逐词生成输出文本 |

**Transformer 的 Q/K/V 机制（面试高频）**：

**类比**：你在图书馆查资料。
- **Query（Q/查询）**：你想知道什么？→ "猫的习性"
- **Key（K/键）**：每本书的标题/目录 → 用来匹配查询
- **Value（V/值）**：每本书的内容 → 匹配后实际读取的内容

计算过程：用 Query 和所有 Key 算相似度（点积），相似度越高权重越大，用权重加权求和所有 Value。相当于"先从书架上找到最相关的书，再重点看相关段落"。

**Encoder vs Decoder 分别用于哪些模型？**

| 架构组合 | 代表模型 | 适用任务 |
|----------|---------|---------|
| 只用 Encoder | BERT、RoBERTa | 文本理解（分类、问答、序列标注） |
| 只用 Decoder | GPT 系列（GPT-3/4、ChatGPT） | 文本生成（对话、写作、代码生成） |
| Encoder + Decoder | T5、BART、原始 Transformer | 序列到序列（翻译、摘要） |

**为什么 Transformer 替代了 RNN？**
- 可以**并行计算**（RNN 必须按顺序算，Transformer 可以同时算所有位置）
- 解决了长距离依赖问题（注意力机制直接连接任意两个词，路径长度恒为 O(1)）
- 可解释性更好（可以可视化"哪个词关注了哪个词"）

> 记忆诀窍：Transformer = 自注意力机制 + 位置编码 + 并行计算，是 GPT/BERT/文心一言的底层架构。2017 年 Google 发表的论文 "Attention Is All You Need" 标志着 Transformer 的诞生。

#### 三大网络结构终极对比

| 网络结构 | 擅长处理 | 核心机制 | 能否并行 | 长距离依赖 | 代表应用 |
|----------|---------|---------|---------|-----------|---------|
| CNN | 图像（网格数据） | 卷积 + 池化（局部感知 + 权重共享） | 可以 | 靠堆叠层数 | 人脸识别、物体检测、图像分割 |
| RNN/LSTM | 序列（时间有序） | 循环记忆单元 + 门控机制 | 不可以（串行） | LSTM/GRU 缓解但未根治 | 翻译、语音识别、股价预测 |
| Transformer | 序列（通用） | 自注意力 + 位置编码 | 可以（高度并行） | 完美解决（O(1) 路径） | GPT、BERT、ChatGPT、文心一言 |

**CNN vs RNN vs Transformer——解题模板**

国网考试中深度学习网络结构匹配题有固定套路：

```
网络选择诀窍——看到以下关键词直接选：

│   ├── 关键词：图像、图片、卷积、池化、人脸、CT影像、物体检测、特征提取
│   ├── 核心：卷积核扫图 + 局部感知 + 权重共享
│   └── 典型场景：人脸识别、医学影像、物体检测、图像分类

│   ├── 关键词：自注意力、GPT、BERT、大模型、ChatGPT、并行计算
```

### 知识点 45：5 机器学习/深度学习关键概念补充

#### 知识点 45：5.1 过拟合 vs 欠拟合

这是考试中极易混淆的概念，务必区分清楚。

| 概念 | 含义 | 表现 | 解决方法 |
|------|------|------|---------|
| **过拟合（Overfitting）** | 模型把训练数据"背"下来了，连噪声和异常点都记住了 | 训练集上表现极好，测试集上表现很差（泛化能力差） | 增加训练数据、正则化（L1/L2）、Dropout、早停法（Early Stopping）、降低模型复杂度 |
| **欠拟合（Underfitting）** | 模型太简单，连训练数据的基本规律都没学到 | 训练集和测试集上表现都很差 | 增加模型复杂度、增加特征、减少正则化、延长训练时间 |

**类比**：过拟合 = 死记硬背的学生——只会做原题，题目稍微变一下就不会了；欠拟合 = 根本没听课的学生——原题和变式题都不会做。

> 记忆口诀："过拟合 = 训练好测试差，欠拟合 = 两边都差"

#### 知识点 45：5.2 偏差 vs 方差

| 概念 | 含义 | 关联 |
|------|------|------|
| **偏差（Bias）** | 模型预测值与真实值之间的差距，反映"准不准" | 高偏差 → 欠拟合 |
| **方差（Variance）** | 模型在不同训练集上预测结果的波动程度，反映"稳不稳" | 高方差 → 过拟合 |

**偏差-方差权衡（Bias-Variance Tradeoff）**：模型复杂度增加 → 偏差降低、方差升高。最优模型需要在偏差和方差之间找到平衡点。

> 记忆：偏差 = 打靶打在靶心外面（偏了），方差 = 打靶子弹到处乱飞（不稳）

#### 知识点 45：5.3 常见激活函数

| 激活函数 | 公式特点 | 优点 | 缺点 | 适用场景 |
|----------|---------|------|------|---------|
| **Sigmoid** | f(x) = 1/(1+e^{-x})，输出 0~1 | 平滑、可解释为概率 | 容易梯度消失，输出不以 0 为中心 | 二分类输出层 |
| **Tanh** | f(x) = (e^x-e^{-x})/(e^x+e^{-x})，输出 -1~1 | 输出以 0 为中心 | 仍有梯度消失问题 | RNN 隐藏层 |
| **ReLU** | f(x) = max(0, x) | 计算简单，缓解梯度消失，收敛快 | 神经元可能"死亡"（负值恒输出 0） | 最常用的隐藏层激活函数 |
| **Leaky ReLU** | f(x) = max(0.01x, x) | 解决 ReLU 神经元死亡问题 | 引入额外超参数 | ReLU 的改进版 |
| **Softmax** | e^{z_i} / Σ e^{z_j}，输出多分类概率分布（和为 1） | 适合多分类 | 计算量略大 | 多分类输出层 |

> 记忆：Sigmoid/Tanh = S 形但会梯度消失；ReLU = 大于 0 原样输出，小于 0 就输出 0；Softmax = 多选一，谁大选谁

#### 知识点 45：5.4 常见损失函数

| 损失函数 | 用途 | 公式含义 |
|----------|------|---------|
| **均方误差（MSE）** | 回归任务 | 预测值和真实值差值的平方求平均 |
| **平均绝对误差（MAE）** | 回归任务 | 预测值和真实值差值的绝对值求平均（比 MSE 对异常值更鲁棒） |
| **交叉熵损失（Cross Entropy）** | 分类任务 | 衡量预测概率分布与真实概率分布之间的差异 |
| **二分类交叉熵（BCE）** | 二分类 | 交叉熵的特例，只有两个类别 |
| **Hinge Loss（合页损失）** | SVM 分类 | 不仅要求分对，还要求"分的够开" |

#### 知识点 45：5.5 精确率 vs 召回率 vs F1

| 指标 | 含义 | 公式 | 关注点 |
|------|------|------|--------|
| **精确率（Precision）** | 预测为正的样本中，真正为正的比例 | TP / (TP + FP) | "查得准不准" |
| **召回率（Recall）** | 真正的正样本中，被预测为正的比例 | TP / (TP + FN) | "查得全不全" |
| **准确率（Accuracy）** | 所有预测正确的样本比例 | (TP+TN) / 总样本 | 样本均衡时好用 |
| **F1 分数** | 精确率和召回率的调和平均 | 2 × P × R / (P + R) | 综合衡量 |

**混淆矩阵**（必须先理解这个）：

|  | 预测为正 | 预测为负 |
|--|---------|---------|
| **实际为正** | TP（真正例）| FN（假负例/漏报）|
| **实际为负** | FP（假正例/误报）| TN（真负例）|

**类比**：
- 警察抓了 10 个人，其中 8 个是真罪犯（TP），2 个是冤枉的（FP）→ 精确率 = 8/10 = 80%
- 总共 20 个罪犯，警察只抓到了 8 个（TP），漏了 12 个（FN）→ 召回率 = 8/20 = 40%

> 记忆：精确率 = 不冤枉好人；召回率 = 不放过坏人

### 知识点 45：6 自然语言处理（NLP）详解

让计算机理解、生成人类语言。

**NLP 任务分层**：

| 层次 | 任务 | 含义 | 例子 |
|------|------|------|------|
| 词法分析 | 分词 | 把句子切成词 | "我爱北京天安门" → "我/爱/北京/天安门" |
| 词法分析 | 词性标注 | 标注每个词的词性 | "我/代词 爱/动词 北京/名词" |
| 词法分析 | 命名实体识别（NER） | 识别人名、地名、机构名 | "马云 在 杭州 创立了 阿里巴巴" |
| 句法分析 | 依存句法分析 | 分析句中词语的语法关系 | 主语-谓语-宾语关系 |
| 语义分析 | 情感分析 | 判断文本情感倾向 | 好评/差评/中性 |
| 语义分析 | 文本分类 | 把文章归类 | 新闻分类：体育/财经/娱乐 |
| 语义分析 | 关系抽取 | 从文本中抽取实体间的关系 | "乔布斯是苹果公司创始人" |
| 生成任务 | 机器翻译 | 把一种语言翻译成另一种 | 中→英 翻译 |
| 生成任务 | 文本摘要 | 自动生成文章摘要 | 把长新闻压缩为三句话 |
| 生成任务 | 问答系统 | 根据文本回答问题 | "珠峰有多高？→ 8848米" |

**NLP 传统方法 vs 深度学习方法**：

| 阶段 | 代表方法 | 特点 |
|------|---------|------|
| 传统方法 | TF-IDF + 词袋模型（Bag of Words） + N-gram | 不考虑词序和上下文语义 |
| 静态词向量 | Word2Vec、GloVe | 每个词一个固定向量，但"苹果"（手机 vs 水果）无法区分 |
| 预训练语言模型 | BERT、GPT、ELMo | 根据上下文动态生成词向量，相同词在不同语境下向量不同 |
| 大语言模型（LLM） | GPT-4、文心一言、通义千问 | 超大规模参数，具备上下文学习（In-Context Learning）能力 |

#### 知识点 45：6.1 语音识别（ASR）

把人的说话声音转成文字。

**流程**：声波（模拟信号）→ 采样/量化（转为数字信号）→ 提取声学特征（MFCC/梅尔频谱）→ 声学模型（音素识别，把声音映射到发音单元）→ 语言模型（根据语言习惯纠错）→ 文字输出

**典型应用**：语音助手（Siri/小爱/天猫精灵）、语音输入法（讯飞）、会议实时转写、智能客服

#### 知识点 45：6.2 文字识别（OCR）

把图片中的文字提取出来。

**流程**：图片 → 预处理（去噪、二值化、倾斜校正）→ 文字区域检测（CTPN/East 算法找到字在哪里）→ 文字识别（CRNN/Attention 认出是什么字）→ 后处理纠错（语言模型/规则）

**典型应用**：身份证/银行卡识别、车牌识别、扫描文档转 Word/PDF、拍照翻译（Google 翻译）

#### 知识点 45：6.3 计算机视觉（Computer Vision / CV）

让计算机"看懂"图像和视频。

| 任务层级 | 含义 | 输入 → 输出 | 经典算法/模型 |
|----------|------|------------|-------------|
| **图像分类** | 判断图片里是什么 | 图片 → 类别标签 | ResNet、EfficientNet、ViT（Vision Transformer） |
| **目标检测** | 找到图片里有什么、在哪（画框） | 图片 → 多个框+类别 | R-CNN 系列、YOLO 系列、SSD |
| **图像分割** | 把图片中每个像素都分类 | 图片 → 每个像素的类别 | U-Net、Mask R-CNN、DeepLab |
| **实例分割** | 区分同一类别的不同个体 | 图片 → 每个实例的像素级 mask | Mask R-CNN、YOLACT |
| **图像生成** | 根据描述生成新图片 | 文本 → 图片 | GAN、VAE、Stable Diffusion、DALL-E |

### 知识点 45：7 大模型（LLM）深度解析

大模型（Large Language Model, LLM）是指参数规模巨大（通常十亿级别以上）的深度学习模型，通过海量文本数据训练，具备强大的语言理解和生成能力。

#### GPT 系列演进

| 版本 | 年份 | 参数量 | 核心突破 |
|------|------|--------|---------|
| GPT-1 | 2018 | 1.17亿 | 证明了"生成式预训练 + 任务微调"的有效性 |
| GPT-2 | 2019 | 15亿 | 展示零样本（Zero-shot）能力：不给样例也能做任务 |
| GPT-3 | 2020 | 1750亿 | 涌现上下文学习（In-Context Learning）：给几个样例就能学会新任务 |
| GPT-3.5 / ChatGPT | 2022 | 未公开 | 加入 RLHF（人类反馈强化学习），对齐人类偏好 |
| GPT-4 | 2023 | 未公开 | 多模态（文本+图像输入），推理能力大幅提升 |

#### 大模型关键概念

| 概念 | 含义 | 大白话 |
|------|------|--------|
| **涌现（Emergence）** | 模型大到一定程度后突然出现的能力（逻辑推理、代码生成等），小模型没有 | "量变引起质变" |
| **上下文学习（In-Context Learning）** | 不需要微调，只需在 Prompt 中给几个例子，模型就能学会做新任务 | "现学现卖" |
| **思维链（Chain-of-Thought）** | 提示模型一步步推理，能显著提高复杂问题准确率 | "把解题步骤写出来" |
| **RLHF（人类反馈强化学习）** | 用人类偏好训练奖励模型，再用强化学习优化模型输出 | "请人打分，让 AI 学会投其所好" |
| **幻觉（Hallucination）** | 模型自信地生成看似合理但实际错误的内容 | "一本正经地胡说八道" |
| **Scaling Law（缩放定律）** | 模型性能随参数、数据、算力的增长呈幂律提升 | "越大越聪明" |

#### 大模型训练三阶段（考试重点）

大模型的训练不是一步到位的，而是分阶段进行：

| 阶段 | 名称 | 做什么 | 数据需求 | 算力需求 |
|------|------|--------|---------|---------|
| **阶段1** | 预训练（Pre-training） | 在海量文本上做"下一个词预测"任务，学习语言的通用知识 | 海量无标注文本（TB/PB级） | 极高（数千GPU·月） |
| **阶段2** | 指令微调（Instruction Tuning / SFT） | 用高质量的"指令-回答"对来训练，让模型学会"按指令做事" | 数万~数十万条标注数据 | 中等 |
| **阶段3** | 人类反馈强化学习（RLHF） | 训练奖励模型（RM）判断回答好坏，再用PPO算法优化大模型 | 数万条人类偏好对比数据 | 中等 |

#### BERT 详解

BERT（Bidirectional Encoder Representations from Transformers）是 Google 2018 年发布的预训练语言模型。

**BERT 的核心创新**：

| 创新点 | 含义 | 与传统方法的区别 |
|--------|------|----------------|
| **双向编码** | 同时利用上下文（上文+下文）来理解词义 | GPT 只看上文（单向），ELMo 虽双向但浅层拼接 |
| **预训练 + 微调范式** | 先在大量无标注文本上预训练，再在具体任务上微调 | 开启了 NLP 的"预训练时代" |
| **MLM（掩码语言模型）** | 随机遮盖 15% 的词，让模型预测被遮盖的词（完形填空） | 这是 BERT 实现双向理解的关键训练任务 |
| **NSP（下一句预测）** | 判断句子 B 是否是句子 A 的下一句 | 训练模型理解句子间关系 |

**BERT 的输入表示**：
```
[CLS] 今天 天气 很好 [SEP] 我们 去 公园 吧 [SEP]
  ↑                    ↑                     ↑
 分类标记            分隔标记              分隔标记
  
每个词的最终输入 = Token Embedding（词向量）+ Segment Embedding（段落向量）+ Position Embedding（位置向量）
```

**BERT 的典型应用**：
- 文本分类（情感分析、新闻分类）
- 问答系统（给定问题和文章，找出答案片段）
- 命名实体识别（NER，识别文本中的人名/地名/机构名）
- 文本相似度计算（判断两句话意思是否相同）

#### GPT vs BERT 终极对比

| 对比维度 | GPT 系列 | BERT |
|----------|---------|------|
| 架构基础 | Transformer **Decoder**（单向） | Transformer **Encoder**（双向） |
| 预训练任务 | 自回归语言模型（预测下一个词） | MLM（掩码语言模型）+ NSP（下一句预测） |
| 信息流向 | 从左到右，单向 | 双向，同时看上文和下文 |
| 核心能力 | **文本生成**（"接着说"） | **文本理解**（"读懂了再答"） |
| 适用任务 | 对话、写作、代码生成、翻译 | 分类、问答、NER、情感分析 |
| 微调方式 | Prompt Engineering + 上下文学习 | 加分类头 + 任务特定微调 |
| 代表模型 | GPT-3/3.5/4、ChatGPT | BERT、RoBERTa、ALBERT、DeBERTa |

#### 思维链（Chain-of-Thought）深度解析

思维链是目前提升大模型推理能力的关键技术。

**核心思想**：不直接让模型输出答案，而是要求模型展示推理步骤，分步思考。

**例子**：
- 不用思维链："23 × 17 = ?" → 模型可能直接猜，容易出错
- 用思维链（Few-shot CoT）：
  ```
  问题：24 × 15 = ?
  推理：24 × 10 = 240，24 × 5 = 120，240 + 120 = 360
  答案：360
  
  问题：23 × 17 = ?
  推理：
  ```
  → 模型会模仿推理步骤，准确率大幅提升

**思维链的变体**：

| 变体 | 做法 | 适用场景 |
|------|------|---------|
| **Zero-shot CoT** | 只需加一句"Let's think step by step"（让我们一步步思考） | 通用场景，简单有效 |
| **Few-shot CoT** | 给几个带推理步骤的示例 | 复杂推理任务 |
| **Self-Consistency** | 多次生成推理路径，投票选出最一致的答案 | 数学题、逻辑推理 |
| **Tree-of-Thought** | 同时探索多个推理分支，剪枝不好的分支 | 需要创造性思维的复杂问题 |

> 考试注意：思维链（Chain-of-Thought）是让大模型**展示推理过程**来提升准确率，不是改变模型结构。这是 Prompt Engineering 的重要技巧。

#### 大模型部署的常见问题

| 问题 | 说明 | 解决方向 |
|------|------|---------|
| **推理成本高** | 大模型推理需要大量 GPU 资源 | 模型量化（INT8/INT4）、蒸馏（用大模型教小模型）、剪枝 |
| **推理延迟大** | 生成一个 token 需要大量计算 | KV-Cache 缓存、投机解码（小模型先猜，大模型验证） |
| **知识截止** | 模型训练数据有时间窗口，不知道最新信息 | RAG（检索增强生成，先查知识库再回答） |
| **可控性差** | 模型输出难以精确控制 | 约束解码（Constrained Decoding）、结构化输出 |

#### 提示工程（Prompt Engineering）

不重新训练模型，而是通过巧妙设计输入提示（Prompt），引导大模型产出更好的结果。

**核心技巧**：

| 技巧 | 说明 | 示例 |
|------|------|------|
| 角色设定 | 给 AI 一个明确身份 | "你是一位资深 Python 工程师" |
| 任务明确 | 说清楚要做什么 | "请帮我写一个函数，输入一个列表，返回去重排序后的结果" |
| 格式约束 | 指定输出格式 | "用 Markdown 表格输出，三列：方法名、时间复杂度、适用场景" |
| 分步引导 | 复杂任务拆成步骤 | "第一步：读懂代码逻辑；第二步：找出可能的 Bug；第三步：给出修复建议" |
| 少样本提示（Few-shot） | 给几个高质量示例 | "输入：天气真好 → 输出：积极 / 输入：烦死了 → 输出：消极 / 输入：还行吧 → 输出：？" |
| 思维链 | 要求展示推理过程 | "请一步步分析：1. 审题 2. 列出已知条件 3. 推导 4. 得出结论" |

**例子**：
- 差提示："写一封邮件"（太模糊）
- 好提示："你是一位专业的商务助理。请用正式礼貌的语气，写一封邮件给客户王总，提醒他明天下午 3 点有签约会议，地点在公司 12 楼会议室。邮件不超过 100 字。"（角色 + 任务 + 约束）

#### 生成式 AI vs 判别式 AI

不重新训练模型，而是通过巧妙设计输入提示（Prompt），引导大模型产出更好的结果。

#### 生成式 AI vs 判别式 AI

| 对比维度 | 生成式 AI（Generative） | 判别式 AI（Discriminative） |
|----------|------------------------|----------------------------|
| 核心思想 | 学习数据的联合分布 P(X, Y)，能"创造"新数据 | 学习决策边界 P(Y|X)，只做"判断" |
| 能力 | 生成新内容（文本、图片、代码、音乐） | 分类、预测、识别 |
| 代表模型 | GPT、Stable Diffusion、DALL-E、GAN | 逻辑回归、SVM、决策树、CNN 分类器 |
| 训练目标 | 最大化数据的似然（让生成的数据和真实数据越像越好） | 最小化分类错误率 |
| 一句话 | "画家"——会创作 | "鉴定师"——会判断 |

> 考试注意：ChatGPT/GPT 是生成式 AI，不是判别式。这是近年热点，常出现在单选/判断题中。

**例题 45-1（单选题）**：以下属于无监督学习的是（）。

**例题 45-2（单选题）**：过拟合的表现是（）。
A. 训练集和测试集表现都差  B. 训练集表现好但测试集表现差  C. 训练集和测试集表现都好  D. 训练集表现差但测试集表现好

> 答案：B。解析：过拟合 = 死记硬背，原题全会但变式不会。A 是欠拟合。

**例题 45-3（单选题）**：以下哪个模型基于 Transformer 的 Encoder 部分？（）
A. GPT-3  B. ChatGPT  C. BERT  D. GPT-4

> 答案：C。解析：GPT 系列基于 Decoder（单向生成），BERT 基于 Encoder（双向理解）。

**例题 45-4（单选题）**：CNN 中的"池化层"的主要作用是（）。
A. 提取特征  B. 压缩数据减少计算量  C. 做分类判断  D. 引入非线性

> 答案：错误。解析：ChatGPT 属于弱人工智能（ANI），只会做文本相关的特定任务。AGI 尚未实现。

### 知识点 45：真题实练——机器学习分类场景题

> 以下题目模拟国网考试真题风格，给场景判断属于哪种学习范式。

**真题 45-A（单选题）**：某电商平台想根据用户的历史购买记录，预测用户下一次是否会购买某类商品。系统使用了过去 100 万条标注了"已购买/未购买"的数据进行训练。这属于哪种学习方式？（）
A. 监督学习  B. 无监督学习  C. 强化学习  D. 半监督学习

> 答案：A。解析：数据被标注了"已购买/未购买"标签，有标准答案→监督学习（二分类问题）。解题关键词："标注了"。

**真题 45-B（单选题）**：某银行希望发现客户中自然存在的不同群体，以便针对性推送理财产品。银行并没有预先定义"哪些群体"，而是让算法根据客户的收入、年龄、消费习惯等自动分组。这属于哪种学习方式？（）
A. 监督学习-分类  B. 监督学习-回归  C. 无监督学习-聚类  D. 强化学习

> 答案：C。解析：没有预先定义的标签（没有"这个客户属于 A 类"这种标准答案），让算法自己找规律分组→无监督学习的聚类。解题关键词："没有预先定义""自动分组"。

**真题 45-C（单选题）**：AlphaGo 下围棋时，每走一步棋会根据当前局面评估"这一步对最终胜利有多大帮助"，通过大量自我对弈来不断优化走棋策略。这属于哪种学习方式？（）
A. 监督学习  B. 无监督学习  C. 强化学习  D. 迁移学习

> 答案：C。解析：没有标准答案（每步棋没有"正确走法"），通过与环境互动获得奖励（赢棋=正奖励，输棋=负奖励），逐步优化策略→强化学习。解题关键词："自我对弈""优化策略""奖励"。

**真题 45-D（单选题）**：某研究所想根据房屋的面积、地段、房龄等特征来预测房价。他们有 5000 套房子的历史成交数据，每套都有完整的特征和成交价格。这属于哪种学习方式？（）
A. 监督学习-分类  B. 监督学习-回归  C. 无监督学习  D. 半监督学习

> 答案：B。解析：有标签（成交价格），且预测的是连续数值→监督学习中的回归。解题关键词："预测房价"（连续值=回归）。若是"判断房子能否卖出去"（离散结果=分类）。

**真题 45-E（单选题）**：某图像识别系统只有少量标注的猫狗图片（约 200 张），但有大量未标注的动物图片（约 10000 张）。研究者先用大量未标注图片让模型学习图像的一般特征，再用少量标注图片进行精细分类训练。这种策略体现了哪种学习范式？（）
A. 纯监督学习  B. 纯无监督学习  C. 半监督学习  D. 强化学习

> 答案：C。解析：同时利用少量标注数据 + 大量未标注数据→半监督学习。解题关键词："少量标注""大量未标注"。这是现实中非常常见的场景，因为标注数据成本高昂。

> **应试技巧**：做这类题，先看"有没有标签"——有标签=监督（再判断结果是离散/连续→分类/回归），没标签=无监督（再判断是分组/压缩→聚类/降维），与环境互动+奖励=强化，少量标注+大量未标注=半监督。

### 知识点 45：真题实练——深度学习概念判断题

**真题 45-F（单选题）**：在以下场景中，最适合使用卷积神经网络（CNN）的是（）。
A. 股票价格走势预测  B. 中文到英文的机器翻译  C. 医学 CT 影像中的肿瘤识别  D. 围棋 AI 的走棋策略

> 答案：C。解析：CNN 专攻图像/网格数据处理，CT 影像属于图像数据。A 是时序数据→RNN/LSTM 更合适；B 是序列到序列→Transformer 最合适；D 是强化学习的典型场景。

**真题 45-G（单选题）**：以下哪个场景最适合使用循环神经网络（RNN/LSTM）？（）
A. 人脸识别门禁系统  B. 手写数字识别  C. 根据过去 30 天的气温预测未来 7 天的气温  D. 图片中物体的检测与定位

> 答案：C。解析：RNN/LSTM 专攻序列数据，气温是时间序列（前后有顺序关系）。A、B、D 都是图像相关任务→CNN 更合适。

**真题 45-H（单选题）**：关于 CNN 和 RNN 的比较，以下说法正确的是（）。
A. CNN 擅长处理序列数据，RNN 擅长处理图像数据
B. CNN 能并行计算，RNN 必须按顺序计算
C. RNN 的核心是卷积操作，CNN 的核心是循环连接
D. CNN 和 RNN 都可以完美解决长距离依赖问题

> 答案：B。解析：CNN 的卷积操作可以同时处理多个区域→可并行；RNN 的每个时间步依赖上一步的结果→必须串行。A 说反了（CNN 擅长图像，RNN 擅长序列）；C 说反了（CNN 核心是卷积，RNN 核心是循环）；D 错误（RNN 有梯度消失问题，长距离依赖是它的短板）。

**真题 45-I（单选题）**：Transformer 相对于 RNN 的核心优势是（）。
A. 计算更简单  B. 不需要训练数据  C. 可并行计算且能直接建模长距离依赖  D. 参数量更少

> 答案：C。解析：Transformer 的自注意力机制允许每个位置直接关注所有其他位置（路径长度 O(1)），且可以并行计算所有位置。A 错误（反而更复杂）；B 错误（需要大量训练数据）；D 错误（Transformer 参数量通常更大）。

**真题 45-J（判断题）**：BERT 模型基于 Transformer 的 Decoder 部分，擅长文本生成任务。（）

> 答案：错误。解析：BERT 基于 Transformer 的 Encoder（编码器）部分，擅长文本理解任务（分类、问答等）。基于 Decoder 的是 GPT 系列，擅长文本生成。判断方法：BERT=双向理解=Encoder；GPT=单向生成=Decoder。

> **应试技巧**：CNN vs RNN vs Transformer 的场景题——看到"图像/图片/人脸/CT"选 CNN；看到"时间/序列/语音/文本预测"选 RNN；看到"大模型/生成/BERT/GPT/翻译"选 Transformer。

| 陷阱编号 | 易错点 | 正确理解 |
|----------|--------|---------|
| 1 | 以为当前 AI 已经是 AGI | 当前所有 AI（含 ChatGPT/GPT-4）都是弱人工智能 ANI |

| 6 | 混淆偏差和方差 | 高偏差 → 欠拟合（不准）；高方差 → 过拟合（不稳） |

| 8 | 以为池化层是用来提取特征的 | 卷积层提取特征，池化层压缩数据 |

## 知识点 46：物联网基础

> **考频星级：高频 ⭐⭐** | 三层架构及职责匹配是核心考点，协议对比也常出现

### 知识点 46：1 物联网是什么？

物联网（Internet of Things，简称 IoT）就是把各种物理设备（传感器、家电、车辆、穿戴设备等）通过网络连接起来，实现"物与物"之间的数据交换和智能控制。

**核心公式**：传感器 + 网络 + 数据处理 = 物联网

**类比**：智能手机是人联网（人→手机→互联网→人），物联网是物联网（温度传感器→网关→互联网→空调控制器——温度高了自动开空调，人不用管）。

**物联网四大关键技术**：

| 关键技术 | 作用 | 说明 |
|----------|------|------|
| 感知与识别技术 | 感知物理世界信息 | 传感器、RFID、二维码 |
| 网络通信技术 | 把数据传输到目的地 | WiFi、5G、NB-IoT、LoRa |
| 计算处理技术 | 分析和处理海量数据 | 云计算、边缘计算、AI |
| 安全防护技术 | 保障设备、数据、网络安全 | 加密、认证、入侵检测 |

**物联网 vs 互联网**：

| 对比维度 | 互联网 | 物联网 |
|----------|--------|--------|
| 连接主体 | 人 ↔ 人 | 物 ↔ 物，物 ↔ 人 |
| 数据来源 | 人输入的 | 传感器自动采集的 |
| 终端设备 | 电脑、手机 | 传感器、智能家电、工业设备 |
| 数据量 | GB/TB 级 | PB/EB 级（海量） |
| 网络需求 | 高带宽、低时延可选 | 多需要低功耗、低速率即可 |

### 知识点 46：2 物联网三层架构（考试核心！）

这是考试的核心考点，必须记住三层及其职责。

```
┌──────────────────────────────────────────────────────────┐
│                    应用层（最上层）                         │
│  智能家居、智慧城市、工业物联网、车联网、智能穿戴、环境监测   │
│  核心职责：数据处理 + 提供服务 + 人机交互 + 决策与控制      │
│                       "做什么？"                          │
├──────────────────────────────────────────────────────────┤
│                    网络层（中间层）                         │
│  WiFi、4G/5G、NB-IoT、LoRa、ZigBee、蓝牙、以太网           │
│  核心职责：数据传输 + 路由转发 + 通信协议 + 网络管理         │
│                       "怎么传？"                          │
├──────────────────────────────────────────────────────────┤
│                    感知层（最下层）                         │
│  传感器、RFID、摄像头、GPS、执行器、二维码、条形码           │
│  核心职责：数据采集 + 物体识别 + 信息感知 + 物理执行         │
│                       "用什么感知？"                       │
└──────────────────────────────────────────────────────────┘
```

**三层架构深度解析**：

| 层次 | 别称 | 核心功能 | 典型设备/技术 | 大白话 | 考试常考细节 |
|------|------|---------|-------------|--------|------------|
| 感知层 | 传感层/感知互动层 | 数据采集 + 物体识别 + 执行控制 | 温度传感器、RFID 标签、摄像头、GPS、执行器（马达/开关） | "眼睛、耳朵和手" | 感知 + 执行一体！不仅有传感器（输入）还有执行器（输出） |
| 网络层 | 传输层/网络传输层 | 数据传输 + 路由转发 + 网络管理 | WiFi、4G/5G、NB-IoT、LoRa、ZigBee、蓝牙、以太网 | "神经系统" | 含接入网和核心网，负责把感知层数据可靠传给应用层 |
| 应用层 | 处理层/应用处理层 | 数据处理 + 智能决策 + 应用服务 | 智慧家居 APP、工业 MES 平台、智慧城市管理平台 | "大脑" | 不只存数据，还要分析数据、发出控制指令，形成闭环 |

> 记忆口诀："下面感知、中间传输、上面应用"——自下而上，信息越来越抽象。"眼耳（感知）→ 神经（网络）→ 大脑（应用），缺一不可。"

**数据流向**：
- 上行：感知层采集数据 → 网络层传输 → 应用层分析处理（"传感器上报"）
- 下行：应用层发指令 → 网络层传输 → 感知层执行器动作（"控制指令下发"）

**物联网三层架构——解题模板**

物联网三层架构匹配题是国网考试的高频考点，用以下"关键词匹配法"秒杀：

```
看到以下关键词 → 直接选对应层：
├── 感知层关键词：传感器、RFID、摄像头、GPS、执行器、二维码、条形码、采集、识别、感知
├── 网络层关键词：WiFi、5G、4G、NB-IoT、LoRa、ZigBee、蓝牙、路由器、网关、传输、协议
└── 应用层关键词：APP、平台、管理系统、智能家居系统、数据处理、决策、监控中心、人机交互
```

**三层架构易错辨析**：

| 易错设备/技术 | 常被误归为 | 正确归属 | 原因 |
|-------------|----------|---------|------|
| 网关（Gateway） | 感知层 | **网络层** | 网关负责协议转换和数据转发，属于"传输"范畴 |
| 摄像头 | 网络层 | **感知层** | 摄像头是图像采集设备，属于"感知"范畴 |
| WiFi 路由器 | 应用层 | **网络层** | 路由器负责数据传输，属于"传输"范畴 |
| 智能家居 APP | 网络层 | **应用层** | APP 提供人机交互和决策控制，属于"应用"范畴 |
| 执行器（马达/开关） | 网络层 | **感知层** | 执行器虽然"输出"而非"采集"，但仍属于感知层（感知+执行一体） |

**真题 46-2-1（单选题）**：在物联网三层架构中，以下哪项全部属于感知层设备？（）
A. 温度传感器、WiFi 路由器、智能家居 APP
B. RFID 标签、GPS 模块、摄像头
C. LoRa 网关、蓝牙模块、MQTT 协议
D. 智能家居 APP、环境监测平台、数据处理中心

> 答案：B。解析：RFID 标签（识别）、GPS 模块（定位）、摄像头（图像采集）全部是感知层设备。A 中 WiFi 路由器属于网络层、APP 属于应用层；C 中网关和协议属于网络层；D 全是应用层。

**真题 46-2-2（单选题）**：某智慧农业项目中，土壤湿度传感器采集数据后，通过 LoRa 无线模块将数据发送到网关，网关再通过 4G 网络上传到云平台，云平台分析后自动控制灌溉阀门开关。以下关于该场景的说法，正确的是（）。
A. 传感器和灌溉阀门都属于感知层
B. LoRa 模块和 4G 网络都属于感知层
C. 云平台数据分析属于网络层
D. 网关属于感知层

> 答案：A。解析：传感器（采集）和灌溉阀门/执行器（执行动作）都属于感知层。B 中 LoRa 和 4G 属于网络层；C 中云平台分析属于应用层；D 中网关属于网络层。关键点：感知层 = 感知 + 执行，所以阀门也属于感知层！

**常见陷阱**：
| 陷阱 | 错误认识 | 正确理解 |
|------|---------|---------|
| 执行器不在感知层 | 以为感知层只有传感器（输入） | 感知层包括传感器（输入）+ 执行器（输出），两者都直接与物理世界交互 |
| 网关属于感知层 | 网关在"设备旁边"就觉得是感知层 | 网关的核心功能是协议转换和数据转发，属于网络层 |
| 摄像头属于网络层 | 摄像头连网就觉得是网络层 | 分类看"核心功能"：采集图像 = 感知层，传输数据 = 网络层 |

**补充：物联网中的关键技术元件——执行器**

| 元件 | 分类 | 功能 | 与传感器的区别 |
|------|------|------|-------------|
| 传感器 | 输入设备 | 感知物理量，将其转换为电信号 | 物理世界 → 数字世界（"输入"） |
| 执行器 | 输出设备 | 接收电信号，将其转换为物理动作 | 数字世界 → 物理世界（"输出"） |

> 常见执行器：电机（开关窗/窗帘）、继电器（开关电路）、电磁阀（控制水/气）、扬声器（发声）

### 知识点 46：3 传感器与传感网络

#### 传感器（Sensor）

把物理世界的信息转化成电信号的设备——物联网的"五官"。

**传感器核心指标**：

| 指标 | 含义 | 考试注意 |
|------|------|---------|
| 灵敏度 | 输出变化量 / 输入变化量，越高越"敏感" | 灵敏度高 ≠ 好，可能把噪声也放大 |
| 精度 | 测量值与真实值的接近程度 | 精度和灵敏度是两回事 |
| 分辨率 | 能检测到的最小变化量 | 数字传感器的关键指标 |
| 量程 | 能测量的范围（最小值~最大值） | 超出量程可能损坏传感器 |
| 线性度 | 输入和输出的线性程度 | 越线性越容易校准 |
| 响应时间 | 从输入变化到输出稳定的时间 | 实时系统要求响应时间短 |

**灵敏度 vs 精度 vs 分辨率 区分详解**：

这三个概念是考试中的易混淆考点。

| 指标 | 类比——用体温计举例 | 大白话 |
|------|-------------------|--------|
| **灵敏度** | 温度每变化1度，水银柱升高多少毫米 | "反应有多敏感"——微小变化能不能被检测出来 |
| **精度** | 体温计测出来的是37.0度，真实体温也是37.0度 | "测得准不准"——测量值和真实值的接近程度 |
| **分辨率** | 体温计最小刻度是0.1度（能区分36.9和37.0） | "能分清多小的差别"——最小可检测的变化量 |

> 举个极端例子：一个体温计每次测都显示37.0度（高精度），但实际体温从36.5变到37.5它都不会变（灵敏度极低）。灵敏度高≠精度高，两者没必然关系。

**常见传感器分类**：

| 分类方式 | 类别 | 举例 |
|----------|------|------|
| 按测量对象 | 物理传感器 / 化学传感器 / 生物传感器 | 温度传感器 / 气体传感器 / 血糖传感器 |
| 按输出信号 | 模拟传感器（连续） / 数字传感器（离散） | 模拟温度计 / 数字温度计 |
| 按是否需电源 | 有源传感器 / 无源传感器 | 主动红外 / RFID 被动标签 |
| 按工作原理 | 电阻式 / 电容式 / 压电式 / 光电式 / 热电式 | 应变片 / 电容麦克风 / 压电加速度计 / 光敏电阻 / 热电偶 |

| 传感器类型 | 检测对象 | 工作原理 | 应用场景 |
|-----------|---------|---------|---------|
| 温度传感器 | 温度 | 热电效应/电阻变化 | 智能空调、冷链物流、体温计 |
| 湿度传感器 | 湿度 | 电容/电阻随湿度变化 | 农业大棚、粮仓监测、数据中心 |
| 光照传感器 | 光线强度 | 光电效应 | 智能灯光、农业补光、手机自动亮度 |
| 加速度传感器 | 运动/振动 | MEMS 微机电系统 | 计步器、地震监测、手机横竖屏切换 |
| 陀螺仪 | 角速度/旋转 | MEMS 角速度检测 | 无人机姿态控制、VR 头显 |
| GPS 模块 | 地理位置 | 卫星三角定位 | 车辆跟踪、物流追踪、导航 |
| 图像传感器 | 画面 | CMOS/CCD 光电转换 | 人脸识别门禁、安防监控、手机拍照 |
| 气体传感器 | 气体成分/浓度 | 化学反应 + 电信号 | 煤气泄漏报警、空气质量监测 |
| 压力传感器 | 压力 | 压阻/压电效应 | 胎压监测、血压计、工业管道 |

#### 无线传感网络（WSN）

Wireless Sensor Network，由大量微型传感器节点自组织形成的无线网络。

**WSN 完整架构**：

```
传感器节点（多）→ 汇聚节点（Sink）→ 网关 → Internet → 监控中心
  （采集+中继）     （收集+融合）   （协议转换）         （分析+展示）
```

| 组件 | 功能 | 特点 |
|------|------|------|
| 传感器节点 | 采集数据 + 中继转发（多跳路由中的"跳板"） | 算力弱、电量有限、大量部署 |
| 汇聚节点（Sink） | 汇集所有传感器节点的数据，做初步融合处理 | 算力较强、电量供给充足 |
| 网关 | 协议转换，连接 WSN 和外部网络（互联网） | 异构网络桥梁 |

| 特点 | 说明 |
|------|------|
| 自组织 | 节点能自己组建网络，不需要人工配置 |
| 多跳路由 | 数据通过多个节点"接力"传输到汇聚节点 |
| 低功耗 | 传感器节点通常靠电池供电，必须省电 |
| 大规模 | 一个网络可能有成百上千个节点 |
| 动态拓扑 | 节点可能移动、失效、新增，网络拓扑频繁变化 |
| 数据为中心 | 关注的是"数据本身"而非"哪个节点产生的" |

### 知识点 46：4 物联网常见通信协议与标准

#### 按传输距离分类

| 类别 | 典型协议 | 传输距离 | 速率 | 典型应用 |
|------|---------|---------|------|---------|
| 极近距离 | NFC | < 10cm | 106~424 kbps | 手机支付、门禁卡 |
| 近距离 | RFID、蓝牙 | 几厘米~100m | 低~中 | 物流仓储、穿戴设备 |
| 中距离（局域网） | WiFi、ZigBee | 几十米~200m | 11Mbps~Gbps | 智能家居、办公 |
| 远距离（广域网 LPWAN） | LoRa、NB-IoT | 2~15km | 0.3~250 kbps | 智慧城市、农业 |
| 超远距离 | 4G/5G、卫星 | 全球 | 高 | 自动驾驶、全球物流 |

**WiFi / 蓝牙 / ZigBee / LoRa / NB-IoT 深度对比**（考试重中之重！）：

| 协议 | 频段 | 速率 | 功耗 | 距离 | 组网方式 | 核心优势 | 典型场景 |
|------|------|------|------|------|---------|---------|---------|
| **WiFi（802.11）** | 2.4GHz/5GHz | 最高 Gbps | 高 | ~100m | 星型（AP为核心） | 高速率、普及度高 | 视频传输、上网、智能音箱 |
| **蓝牙 BLE** | 2.4GHz | 1~2 Mbps | 极低 | ~10m | 星型/点对点 | 功耗极低、手机标配 | 穿戴设备、耳机、键鼠 |
| **ZigBee** | 2.4GHz/868/915MHz | 20~250 kbps | 极低 | ~100m | Mesh（自组网） | 自组网、节点数量大 | 智能家居传感器网络 |
| **LoRa** | Sub-GHz（433/868/915MHz） | 0.3~50 kbps | 超低 | 2~15km | 星型 | 超远距离、免费频段 | 智能抄表、农业大田 |
| **NB-IoT** | 授权频段（运营商） | 60~250 kbps | 超低 | 1~10km | 蜂窝（基站） | 运营商级覆盖、无需网关 | 智慧城市、路灯、停车 |

> 记忆口诀："WiFi 快费电，蓝牙近省电，ZigBee 组网便宜省电，LoRa 远距离免费频段，NB-IoT 走运营商"

#### 协议详解

**MQTT（消息队列遥测传输）**
- 基于 **发布/订阅** 模式的轻量级通信协议
- 基于 TCP，协议头最小仅 2 字节，开销极小
- 支持三种服务质量（QoS）：QoS 0（至多一次/可能丢）、QoS 1（至少一次/可能重复）、QoS 2（恰好一次/最可靠）
- 特点：协议开销极小，适合低带宽、不可靠网络环境
- 典型应用：传感器数据传输、即时通讯推送（Facebook Messenger 也用过 MQTT）

> 记忆：MQTT = "发布/订阅 + 三种 QoS"——设备 A 发布消息，设备 B 订阅后就收到了。

**CoAP（受限应用协议）**
- 专为资源受限设备（内存小、算力弱）设计的类 HTTP 协议
- 基于 UDP，比 HTTP/TCP 更轻量，但通过重传机制保障可靠性
- 支持 RESTful 风格交互（GET/POST/PUT/DELETE）
- 支持"观察"模式（Observe）：客户端订阅资源，状态变化时服务端主动推送

> 记忆：CoAP = "瘦版 HTTP + UDP"，给内存和带宽都很小的设备用。MQTT = 多对多（发布/订阅），CoAP = 一对一（请求/响应）。

**MQTT vs CoAP 核心区别**：

| 对比 | MQTT | CoAP |
|------|------|------|
| 传输层 | TCP | UDP |
| 通信模式 | 发布/订阅（异步，多对多） | 请求/响应（同步，一对一） |
| 消息格式 | 二进制 | 二进制 + 支持 CBOR/JSON |
| 适用场景 | 推送类（传感器主动上报） | 查询类（客户端主动请求服务器资源） |

**ZigBee**
- 低速率、低功耗、低成本的无线通信标准
- 基于 IEEE 802.15.4 物理层和 MAC 层
- 支持三种拓扑：星型、树型、Mesh（网状），最大支持 65000+ 节点
- 三种设备角色：协调器（Coordinator，一个网络一个）、路由器（Router，转发）、终端设备（End Device，休眠省电）
- 典型应用：智能家居（小米/Philips Hue 智能灯泡用的就是 ZigBee）

> 记忆：ZigBee = "低功耗 Mesh 自组网"，适合智能灯泡、插座等大量小设备自组网。

**LoRa（远距离低功耗广域网）**
- 基于 CSS（线性调频扩频）调制技术，抗干扰能力强
- 工作在非授权频谱（Sub-GHz 免费频段，中国用 470-510MHz）
- 电池寿命可达 5~10 年
- 架构：终端节点 → LoRa 网关 → 网络服务器（LoRaWAN 协议）
- 特点：一个网关可覆盖几公里，但传输速率低（适合小数据量、低频次上报）

> 记忆：LoRa = "乡村广播"——距离远、省电，但说话慢、说不了太多内容。

**NB-IoT（窄带物联网）**
- 基于蜂窝网络（运营商 4G/5G 基站），可直接复用现有基站，部署成本低
- 特点：覆盖广（比 GSM 强 20dB，地下室也能覆盖）、连接多（一个小区可连 5-10 万设备）、功耗低（电池可用 10 年）
- 三种部署模式：独立部署（Stand-alone）、保护带部署（Guard-band）、带内部署（In-band）
- 带宽仅 180kHz，适合低频次小数据量上报

> 记忆：NB-IoT = "运营商的物联网专网"，穿墙能力强、连接数多，适合智慧城市。

**LoRa vs NB-IoT 终极对比**：

| 对比维度 | LoRa | NB-IoT |
|----------|------|--------|
| 部署方 | 自行部署网关 | 运营商基站（无需建网，有信号就能用） |
| 频谱 | 免费频段（Sub-GHz ISM） | 授权频段（需要运营商 SIM 卡） |
| 成本结构 | 初次部署网关成本高，后续免费 | 无部署成本，但持续按流量/连接付费 |
| QoS | 无服务质量保障 | 有运营商级 QoS 保障 |
| 适用场景 | 私有园区、偏远农田、工业厂区 | 城市市政、公共设施、运营商覆盖区域 |
| 数据速率 | < 50 kbps | < 250 kbps |

#### RFID 与 NFC（深度对比）

**RFID 标签类型详解**：

| 类型 | 供电方式 | 距离 | 成本 | 典型应用 |
|------|---------|------|------|---------|
| 低频（LF，125~134kHz） | 无源（靠阅读器电磁感应供电） | < 10cm | 低 | 动物识别、门禁卡 |
| 高频（HF，13.56MHz） | 无源 | ~1m | 低 | 图书馆、公交卡、身份证（NFC 在此频段） |
| 超高频（UHF，860~960MHz） | 无源/有源 | 1~12m | 中 | 物流仓储批量盘点、ETC |
| 有源 RFID | 自带电池 | 几十~上百米 | 高 | 车辆定位、大型设备跟踪 |

**RFID（射频识别）**完整架构：
- 标签（Tag）：贴在物体上，存唯一 ID 和数据，分有源/无源/半有源
- 阅读器（Reader）：发射射频信号，读取/写入标签数据
- 天线（Antenna）：收发射频信号
- 中间件：过滤、聚合原始 RFID 数据，对接上层应用

> 记忆：RFID = "电子标签"，不需要"看见"就能读取。优势是批量读取（一秒可读几十个标签）。

**NFC（近场通信）**
- RFID 的高频（13.56MHz）子类，距离极短（< 10cm），天然安全
- 支持 **双向通信**（普通 RFID 通常只是单向读取）
- 三种工作模式：

| 模式 | 说明 | 典型场景 |
|------|------|---------|
| 卡模拟模式 | NFC 设备模拟成一张智能卡 | Apple Pay、公交卡刷卡 |
| 读写器模式 | NFC 设备读取 NFC 标签信息 | 读取商品 NFC 标签、获取信息 |
| 点对点模式 | 两台 NFC 设备之间数据交换 | Android Beam 传文件、一碰传 |

> 记忆：NFC = "贴一下"——卡模式（被读）、读模式（读别人）、点对点（互相传）

**RFID vs NFC 核心区别**：

| 对比维度 | RFID | NFC |
|----------|------|-----|
| 通信距离 | 几厘米~几十米（甚至上百米） | < 10cm |
| 通信方向 | 多为单向（阅读器读标签） | 双向通信 |
| 工作频率 | 多频段（低频/高频/超高频） | 固定 13.56MHz（HF） |
| 并发读取 | 支持批量读取（一秒几十个） | 一对一 |
| 典型场景 | 仓储批量盘点、ETC 不停车收费 | 手机支付、公交卡、一碰传 |
| 手机集成 | 较少 | 几乎所有智能手机都内置 NFC |

> 记忆诀窍：NFC 是 RFID 的"高端定制版"——距离短但能双向，天然适合做支付。

#### 协议速记总表

| 协议 | 关键词记忆 | 频段/传输层 | 组网方式 | 适用场景 |
|------|-----------|-----------|---------|---------|
| MQTT | 发布/订阅、TCP、三种 QoS | 应用层协议 | Broker 中转 | 传感器数据推送 |
| CoAP | 瘦版 HTTP、UDP、RESTful | 应用层协议 | 点对点 | 受限设备查询 |
| 蓝牙 BLE | 低功耗、点对点 | 2.4GHz | 星型 | 穿戴设备 |
| ZigBee | 低功耗、Mesh、65000+ 节点 | 2.4GHz/868/915MHz | Mesh | 智能家居 |
| LoRa | 超远距离、免费频段、电池 10 年 | Sub-GHz ISM | 星型(LoRaWAN) | 抄表、农业 |
| NB-IoT | 运营商基站、授权频段、SIM 卡 | 蜂窝 4G/5G | 蜂窝 | 智慧城市 |
| RFID | 电子标签、批量读取、有源/无源 | 多频段 | 一对多 | 物流、ETC |
| NFC | 近距离、双向、三种模式 | 13.56MHz | 一对一 | 支付、公交卡 |

**物联网通信协议——解题模板**

国网考试中协议匹配题有固定套路：

```
协议选择三步法：
第一步：看"需不需要 SIM 卡/运营商"
  ├── 需要 SIM 卡 → NB-IoT（走运营商基站）
  └── 不需要 SIM 卡 → 跳到第二步

第二步：看"通信距离和场景"
  ├── < 10cm、手机支付 → NFC
  ├── 几厘米~几十米、批量读取 → RFID
  ├── ~10m、穿戴设备 → 蓝牙 BLE
  ├── ~100m、智能家居传感器网 → ZigBee
  ├── ~100m、高速上网/视频 → WiFi
  ├── 2~15km、农田/抄表 → LoRa
  └── 城市级、运营商覆盖 → NB-IoT

第三步：看"传输层协议特征"
  ├── 基于 TCP、发布/订阅 → MQTT
  ├── 基于 UDP、类 HTTP、RESTful → CoAP
  └── 基于 TCP、客户端-服务器 → HTTP
```

**协议对比高频易错点**：

| 易错对比 | 关键区别 | 口诀 |
|----------|---------|------|
| MQTT vs CoAP | MQTT = TCP + 发布订阅；CoAP = UDP + 请求响应 | "MQTT 多对多发，CoAP 一对一查" |
| LoRa vs NB-IoT | LoRa = 免费频段 + 自建网关；NB-IoT = 运营商 + SIM 卡 | "LoRa 自己盖，NB 租房子" |
| ZigBee vs 蓝牙 | ZigBee = Mesh 自组网 + 大网络；蓝牙 = 点对点 + 小范围 | "ZigBee 像蜘蛛网，蓝牙像一根线" |
| RFID vs NFC | RFID = 远距离 + 单向 + 批量；NFC = 近距离 + 双向 + 一对一 | "NFC 是 RFID 的支付特化版" |

### 知识点 46：5 边缘计算 vs 雾计算 vs 云计算

这是重要且易混淆的对比考点。

| 概念 | 计算位置 | 响应延迟 | 算力 | 适用场景 | 一句话 |
|------|---------|---------|------|---------|--------|
| **云计算** | 数据中心（远端几千里外） | 慢（几十~几百 ms） | 强（可弹性扩展） | 大规模数据分析、AI 模型训练、长期存储 | 所有数据打包送到"云端"处理 |
| **雾计算** | 网络边缘（局域网网关/路由器/基站） | 中等（几~几十 ms） | 中 | 本地数据过滤聚合、实时性要求中的场景 | 在"局域网网关"先处理一波，重要的再传云 |
| **边缘计算** | 设备端/最近端（传感器、摄像头本地） | 极快（< 1ms） | 弱/中 | 实时控制、图像实时处理、AR/VR | 数据在"设备旁边"直接处理，不传出去 |

**类比（一栋楼的摄像头系统）**：
- 云计算 = 所有视频传到几千里外的数据中心分析，发现可疑行为再发报警 → 延迟大，黄花菜凉了
- 雾计算 = 在楼里的局域网服务器先过滤（丢弃没人的视频片段），可疑片段才上传云 → 快了，省带宽
- 边缘计算 = 摄像头自带的 AI 芯片直接在本地做人脸识别和行为分析 → 最快，且不上传原始视频保护隐私

**三者关系**：不是替代关系，而是分层协作。"云-雾-边缘"三层架构 = 边缘做实时处理 + 雾做近端聚合 + 云做全局分析和模型训练。

> 记忆口诀："边缘设备端（最近最快算力弱），雾在局域网关（中间），云在数据中心（最远最强）"

**边缘计算 vs 雾计算 vs 云计算——解题模板**

```
"谁离数据最近"判断法：
├── 数据在设备本地就处理了（不传出去）→ 边缘计算
├── 数据传到局域网网关/服务器才处理 → 雾计算
└── 数据传到远端数据中心才处理 → 云计算

"延迟要求"判断法：
├── 要求 < 1ms、实时控制 → 边缘计算
├── 要求几~几十 ms、近实时 → 雾计算
└── 几秒~几分钟都可以接受 → 云计算

"算力需求"判断法：
├── 需要大规模 GPU 集群、AI 训练 → 云计算
├── 需要中等算力、本地过滤 → 雾计算
└── 算力需求低、单设备即可 → 边缘计算
```

**真题 46-5-1（单选题）**：自动驾驶汽车需要在毫秒级内对障碍物做出反应，场景最适合使用哪种计算模式？（）
A. 云计算  B. 雾计算  C. 边缘计算  D. 网格计算

> 答案：C。解析：自动驾驶要求毫秒级响应，数据必须在车辆本地（边缘端）立即处理，不能等数据传到云端再回来——那可能已经撞上了。关键词："毫秒级""车上"→边缘计算。

**真题 46-5-2（判断题）**：边缘计算将取代云计算，成为未来唯一的计算模式。（）

> 答案：错误。解析：三者不是替代关系，而是分层协作。边缘做实时处理，雾做近端聚合，云做全局分析和模型训练。它们各有各的适用场景，未来是"云边协同"的模式。

**常见陷阱**：
| 陷阱 | 错误认识 | 正确理解 |
|------|---------|---------|
| 边缘计算替代云计算 | 以为边缘计算更强所以会淘汰云 | 三者是互补关系，不是替代关系。边缘算力弱但快，云算力强但慢 |
| 雾计算和边缘计算是一回事 | 混淆两者 | 边缘 = 设备端（最近），雾 = 局域网网关（中间），云 = 数据中心（最远） |

### 知识点 46：6 物联网安全

物联网设备数量大、算力弱、分布广，安全问题突出。

| 安全层次 | 威胁 | 防护措施 |
|----------|------|---------|
| 感知层安全 | 节点被物理捕获/篡改、假冒节点注入假数据、信号干扰 | 硬件加密芯片、身份认证、防拆设计 |
| 网络层安全 | 数据窃听、中间人攻击、DDoS（Mirai 僵尸网络利用了数百万 IoT 设备） | 传输加密（TLS/DTLS）、网络隔离 |
| 应用层安全 | 数据泄露、未授权访问、隐私侵犯 | 访问控制、数据脱敏、审计日志 |
| 设备安全 | 固件漏洞、默认密码、远程攻击 | 固件签名验证、安全启动、远程 OTA 升级 |

**Mirai 病毒（考试热点）**：2016 年史上最大 DDoS 攻击，利用数百万未修改默认密码的 IoT 设备（摄像头、路由器）组成僵尸网络，攻击 DNS 服务商 Dyn，导致 Twitter、Netflix 等大面积瘫痪。

> 考点：物联网安全中最常见的问题 = 设备弱口令/默认密码未修改 + 固件未及时更新。

### 知识点 46：7 物联网典型应用与热点

| 应用领域 | 场景举例 | 涉及技术 | 关键特点 |
|----------|---------|---------|---------|
| 智能家居 | 智能灯控、智能门锁、智能空调、扫地机器人 | ZigBee、WiFi、语音识别 | 消费级、Mesh 组网、手机 APP 控制 |
| 智慧城市 | 智能路灯、智能停车、垃圾桶满溢监测、环境监测 | NB-IoT、LoRa、大数据 | 市政级、海量设备、运营商网络 |
| 工业物联网（IIoT） | 设备状态监控、预测性维护、数字孪生 | 传感器、MQTT、边缘计算 | 高可靠、低延迟、恶劣环境 |
| 智能穿戴 | 智能手表、健康手环、心率/血氧监测 | 蓝牙 BLE、加速度传感器 | 超低功耗、人体交互 |
| 车联网（V2X） | 车与车(V2V)、车与路(V2I)、自动驾驶 | GPS、5G、边缘计算 | 超低延迟（1ms）、高可靠性 |
| 智慧农业 | 土壤湿度监测、自动灌溉、无人机巡检 | LoRa、传感器 | 广覆盖、电池长寿命、户外 |
| 数字孪生 | 在虚拟世界创建物理实体的实时数字镜像 | 传感器 + 3D 建模 + AI | 实时映射、仿真优化 |

**热点：AIoT（人工智能物联网）= AI + IoT**

AIoT 让物联网设备不仅"感知"，还能"思考"和"自主决策"。

| 场景 | AI 角色 | IoT 角色 | 效果 |
|------|--------|---------|------|
| 智能音箱 | NLP 语音识别 + NLU 理解语义 | 麦克风阵列 + 联网控制家电 | "天猫精灵，开空调" |
| 智能摄像头 | 人脸识别 + 行为分析（跌倒检测） | 图像传感器 + 联网报警 | 老人跌倒自动报警 |
| 预测性维护 | 机器学习分析振动/温度趋势预测故障 | 振动/温度传感器采集数据 | 提前一周知道设备要坏 |

### 知识点 46：例题精练

**例题 46-1（单选题）**：物联网三层架构中，负责数据采集的是（）。
A. 应用层  B. 网络层  C. 感知层  D. 传输层

> 答案：C。解析：感知层 = 传感器采集数据，是最底层。"传输层"是网络层的别称，但选项中 C 和 D 同时出现时，首选标准名称"感知层"。

**例题 46-2（单选题）**：以下哪种协议使用运营商基站、需要 SIM 卡？（）
A. LoRa  B. WiFi  C. ZigBee  D. NB-IoT

> 答案：D。解析：NB-IoT 基于运营商蜂窝网络（4G/5G 基站），需 SIM 卡。LoRa 用免费频段自行部署网关。

**例题 46-3（单选题）**：NFC 的三个工作模式不包括（）。
A. 卡模拟模式  B. 读写器模式  C. 广播模式  D. 点对点模式

> 答案：C。解析：NFC 三种模式 = 卡模拟（被读）+ 读写器（读别人）+ 点对点（互相传）。没有"广播模式"。

**例题 46-4（单选题）**：边缘计算相对于云计算的最大优势是（）。
A. 算力更强  B. 存储更大  C. 响应延迟更低  D. 成本更低

> 答案：C。解析：边缘计算的核心优势 = 数据在设备附近处理，延迟极低（毫秒级）。云计算的算力和存储反而更强，边缘计算的算力比云弱。

**例题 46-5（判断题）**：MQTT 协议基于 UDP，CoAP 协议基于 TCP。（）

> 答案：错误。解析：正好说反了！MQTT 基于 TCP（可靠传输），CoAP 基于 UDP（轻量）。

### 知识点 46：真题实练——物联网三层架构匹配题

**真题 46-A（单选题）**：物联网体系架构中，负责数据采集和物体识别的是哪一层？（）
A. 应用层  B. 网络层  C. 感知层  D. 平台层

> 答案：C。解析：感知层是物联网的最底层，负责通过传感器、RFID、摄像头等设备采集物理世界的数据并识别物体。"用什么感知？"→感知层。

**真题 46-B（单选题）**：在智能家居系统中，用户通过手机 APP 远程开关家里的灯。这个场景中，手机 APP 属于物联网架构中的哪一层？（）
A. 感知层  B. 网络层  C. 应用层  D. 物理层

> 答案：C。解析：手机 APP 提供人机交互界面，进行数据处理和服务提供→应用层。"做什么？"→应用层。灯的开关控制器属于感知层的执行器，WiFi 属于网络层。

**真题 46-C（单选题）**：以下设备/技术中，属于物联网感知层的是（）。  
① WiFi 路由器 ② 温度传感器 ③ RFID 电子标签 ④ 智能家居 APP ⑤ GPS 模块
A. ①④  B. ②③⑤  C. ①②③  D. ③④⑤

> 答案：B。解析：感知层=传感器/识别设备/定位设备。① WiFi 路由器属于网络层（传输数据），④ 智能家居 APP 属于应用层（提供服务）。②③⑤ 分别是传感器、射频识别和定位模块→全部属于感知层。

**真题 46-D（判断题）**：在物联网三层架构中，网络层不仅负责数据传输，还负责路由转发和网络管理。（）

> 答案：正确。解析：网络层是"神经系统"，负责把感知层数据可靠地传输到应用层，包括数据路由转发、通信协议处理、网络管理等所有传输相关功能。它的核心问题就是"怎么传？"。

> **应试技巧**：三层架构题记住口诀——"下面感知（眼耳手）、中间传输（神经）、上面应用（大脑）"。关键技巧：看到"传感器/RFID/GPS/摄像头/执行器"→感知层；看到"WiFi/5G/路由器/网关/协议"→网络层；看到"APP/平台/管理系统/数据处理"→应用层。

| 陷阱编号 | 易错点 | 正确理解 |
|----------|--------|---------|
| 1 | 物联网三层顺序搞反 | 自下而上：感知层（最下）→ 网络层（中间）→ 应用层（最上） |

| 8 | 以为传感器只负责"感知" | 感知层不仅有传感器（输入），还有执行器（输出），负责"感知+执行" |

## 知识点 47：大数据基础

> **考频星级：必考 ⭐⭐⭐** | 4V/5V 特征含义区分、Hadoop 三大组件、Apriori 算法计算都是高频必考点

### 知识点 47：1 大数据是什么？

大数据（Big Data）是指数据量太大、太复杂，传统工具无法在合理时间内处理的数据集合。

**一句话**：大到传统数据库/Excel 搞不定的数据，就叫大数据。

**大数据 vs 传统数据**：

| 对比维度 | 传统数据 | 大数据 |
|----------|---------|--------|
| 数据量 | MB/GB 级 | TB/PB/EB 级 |
| 数据类型 | 以结构化为主（表格） | 结构化 + 半结构化 + 非结构化混合 |
| 处理工具 | 单机数据库（MySQL/Oracle） | 分布式集群（Hadoop/Spark） |
| 处理模式 | 事后批处理 | 批处理 + 实时流处理 |
| 存储成本 | 高（需要高性能存储） | 低（普通 PC 服务器即可） |
| 数据价值 | 价值密度高 | 价值密度低，需要"沙里淘金" |

### 知识点 47：2 大数据的 4V/5V 特征（考试必考！）

> ⚠️ **4V vs 5V 口径辨析（重点！）**：华图讲义及部分教材采用 **4V** 口径——**Volume（大量）、Velocity（高速）、Variety（多样）、Value（价值）**，**不含 Veracity（真实性）**。5V 是在 4V 基础上追加 Veracity 得到的（IBM 提出）。国网考试若按华图口径出题，应选 4V；若按 5V 出题，才包含 Veracity。**两种口径都要掌握**，做题时先看题干/选项是 4V 还是 5V。

| 特征（英文） | 中文 | 含义 | 考试要点 |
|------------|------|------|---------|
| **Volume** | 大量 | 数据量巨大，从 TB 到 PB、EB、ZB 级别 | 量级换算：1PB=1024TB，1EB=1024PB |
| **Velocity** | 高速 | 数据生成速度快，需要实时或准实时处理 | 每秒数百万条数据涌入，传统批处理来不及 |
| **Variety** | 多样 | 数据类型多样：结构化+半结构化+非结构化 | 结构化=表格，半结构化=XML/JSON，非结构化=图片/视频/文本(占80%+) |
| **Value** | 低价值密度 | 海量数据中有价值的信息比例低 | 不是"价值高"！是"价值密度低"——容易误解 |
| **Veracity** | 真实性/准确性 | 数据质量参差不齐，需要清洗验证 | 数据来源多、格式乱、噪声大（⚠️ 5V 特有，4V 口径不含此项） |

> 记忆口诀："大数据 4 个 V（华图口径）"——Volume 量大、Velocity 速快、Variety 多样、Value 价值密度低；5V 再追加 Veracity 不准。先记 4V，再看题干要不要加 Veracity。

**大数据 5V 特征——解题模板**

国网考试中 5V 特征匹配题是必考题型，用"关键词秒杀法"：

```
看到以下关键词 → 直接选对应 V：
├── Volume（大量）：TB/PB/EB/ZB、海量、数据量大、存储容量
├── Velocity（高速）：每秒、实时、快速、流式、毫秒级、双十一、高频
├── Variety（多样）：结构化/半结构化/非结构化、图片+视频+文本、多种格式、JSON/XML
├── Value（低价值密度）：沙里淘金、价值密度低、关键信息少、有用信息比例低
└── Veracity（真实性/准确性）：噪声、不准、质量差、错误数据、重复、缺失
```

**5V 高频易错辨析**：

| 场景描述 | 容易误选 | 正确选项 | 辨析 |
|----------|---------|---------|------|
| "每天产生 50TB 数据" | Velocity（因为有"每天"） | **Volume** | "每天"只是描述产生频率，核心是强调数据量达到了 TB 级别 |
| "视频监控中只有几秒是关键画面" | Veracity（以为是数据不准） | **Value** | "有价值信息比例低"是价值密度问题，不是准确性问题 |
| "传感器数据有噪声和漂移" | Value（以为噪声=价值低） | **Veracity** | "噪声和漂移"是数据质量/准确性问题，不是价值密度问题 |
| "每秒几十万笔交易需要实时处理" | Volume（因为"几十万"） | **Velocity** | "每秒"+"实时"强调速度，不是因为数据量大 |

**5V 详细解析**：

**1. Volume（大量）**：从 TB 到 PB 到 EB。
- 淘宝每天产生约 50TB 的新数据
- 大型强子对撞机每年产生约 30PB 数据
- 全球数据总量预计到 2025 年达 175ZB

**2. Velocity（高速）**：数据产生和流动的速度极快。
- 双十一每秒几十万笔交易
- 微博热点事件每秒数万条评论
- 需要实时/准实时处理，而非"T+1 报表"

**3. Variety（多样）**：数据格式五花八门。

| 数据类型 | 说明 | 占比 | 例子 |
|----------|------|------|------|
| 结构化数据 | 有固定格式，行和列明确 | ~10% | 数据库表格、Excel |
| 半结构化数据 | 有标签/标记但结构不固定 | ~10% | XML、JSON、HTML、YAML |
| 非结构化数据 | 没有预定义格式 | ~80% | 图片、视频、音频、文本、日志 |

> 考试重点：非结构化数据占比最大（约 80%），但最难以处理和分析。

**4. Value（低价值密度）**：
- 几小时的监控视频中，可能只有几秒是关键画面
- 千万条日志中，可能只有几条是异常告警
- 核心挑战：如何从海量数据中"沙里淘金"

**5. Veracity（真实性/准确性）**：
- 传感器数据可能有噪声和漂移
- 用户填写的问卷可能不真实
- 网络爬虫抓取的数据可能有重复和错误
- 需要进行数据清洗和质量管理

**类比**（一座山的比喻）：
- Volume = 一座山（数据量大得惊人）
- Velocity = 山还在不停地长（数据源源不断涌入）
- Variety = 山里有石头、泥土、树、动物（各种类型的数据混杂）
- Value = 山里只有几块金子（有价值的信息很少，需要挖掘）
- Veracity = 里面还有假石头和垃圾（数据有噪声、不准确，需要清洗）

### 知识点 47：3 数据处理全流程

```
数据采集 → 数据预处理 → 数据分析 → 数据挖掘 → 可视化
```

#### 知识点 47：3.1 数据采集

从各种来源把数据汇聚起来。

| 采集方式 | 说明 | 工具/技术 | 例子 |
|----------|------|----------|------|
| 日志采集 | 从服务器日志中收集用户行为数据 | Flume、Logstash、Filebeat | 网页点击日志、APP 操作日志 |
| 传感器采集 | 从物联网设备收集物理数据 | MQTT、CoAP | 温度、湿度、定位 |
| 网络爬虫 | 自动从网页抓取数据 | Scrapy、Selenium、Nutch | 电商比价、舆情监控 |
| API 接口 | 通过程序接口获取数据 | RESTful API、SDK | 调用第三方开放平台 |
| 数据库同步 | 从业务数据库抽取数据 | Sqoop、DataX、Canal | 将 MySQL 数据同步到数仓 |

#### 知识点 47：3.2 数据预处理

**原始数据 = 脏数据**（有缺失、有重复、有错误），必须先"洗干净"。

| 步骤 | 操作 | 具体方法 | 大白话 |
|------|------|---------|--------|
| 1. 数据清洗 | 处理缺失值、异常值、重复数据 | 缺失值：删除/填充均值/中位数/众数；异常值：3-sigma 原则/箱线图；重复：去重 | "去脏东西" |
| 2. 数据集成 | 把多个来源的数据合并到一起 | 实体识别（同一实体不同表）、冗余处理（相关分析去冗余）、冲突处理（单位不一致） | "拼积木" |
| 3. 数据变换 | 统一数据格式、规范化处理 | 归一化（Min-Max 缩到 0~1）、标准化（Z-score 转标准正态分布）、离散化（连续值分桶） | "统一度量衡" |
| 4. 数据规约 | 压缩数据量，保持核心信息 | 维度规约（PCA 降维）、数量规约（采样）、数据压缩（编码） | "浓缩精华" |

> 口诀：洗→合→变→缩（清洗 → 集成 → 变换 → 规约）

**缺失值处理详解**（考试高频）：

| 处理方法 | 操作 | 适用场景 |
|----------|------|---------|
| 删除 | 直接删除含缺失值的行/列 | 缺失比例高且不重要 |
| 均值填充 | 用该列均值填充 | 数值型、正态分布 |
| 中位数填充 | 用该列中位数填充 | 数值型、有偏分布（有异常值） |
| 众数填充 | 用该列出现最多的值填充 | 类别型数据 |
| 模型预测 | 用其他特征训练模型预测缺失值 | 缺失值有规律可循 |

#### 知识点 47：3.3 数据分析

| 分析类型 | 含义 | 核心问题 | 方法举例 |
|----------|------|---------|---------|
| 描述性分析 | 描述"发生了什么" | 昨天销售额是多少？ | 均值、方差、分布、占比 |
| 诊断性分析 | 分析"为什么会发生" | 为什么昨天销售额下降？ | 下钻分析、相关性分析、归因分析 |
| 预测性分析 | 预测"未来会发生什么" | 下个月销售额会是多少？ | 回归、时间序列、机器学习 |
| 规范性分析 | 建议"应该怎么办" | 怎么做才能提升下月销售额？ | 优化算法、仿真模拟、推荐系统 |

> 记忆：描述 → 诊断 → 预测 → 规范（由浅到深，从"知道"到"行动"）

#### 知识点 47：3.4 数据仓库建模

数据模型是数据组织和存储的蓝图，决定了数据如何被结构化以便分析。最常见的是**维度建模**。

**维度建模核心概念**：

| 概念 | 含义 | 大白话 |
|------|------|--------|
| 事实（Fact） | 业务过程的度量值，可累加 | "卖了多少钱"、"卖了多少件" |
| 维度（Dimension） | 描述事实的上下文，用来"切分"和"筛选" | "什么时间"、"哪个门店"、"哪个产品" |
| 粒度（Granularity） | 事实表中每一行代表什么级别的数据 | 一行 = 一笔交易？还是一天汇总？ |
| 度量（Measure） | 事实表中的数值型字段 | 金额、数量、次数 |

**星型模型 vs 雪花模型深度对比**：

| 对比维度 | 星型模型 | 雪花模型 |
|----------|---------|---------|
| 结构 | 一个事实表连接多个维度表（维度表不拆分） | 事实表连维度表，维度表进一步规范化拆分 |
| 维度表数量 | 少（每个维度一张表） | 多（维度被拆成多张子表） |
| 数据冗余 | 高（维度表有大量重复数据） | 低（通过拆分减少冗余） |
| 查询性能 | 快（JOIN 少，通常 1-2 次 JOIN） | 慢（JOIN 多，需要多次关联） |
| 维护复杂度 | 低（结构简单，便于理解） | 高（表多，关系复杂） |
| 适用场景 | 查询性能优先，存储成本不敏感 | 存储成本敏感，维度层级多 |

**星型模型示意图**：
```
              ┌──────────────┐
              │   时间维度表   │
              └──────┬───────┘
                     │
    ┌──────────────┐ │ ┌──────────────┐
    │   产品维度表   │ │ │   门店维度表   │
    └──────┬───────┘ │ └──────┬───────┘
           │         │        │
           ▼         ▼        ▼
         ┌──────────────────────┐
         │      销售事实表        │
         │  （时间ID、产品ID、    │
         │   门店ID、销售金额、   │
         │     销售数量）         │
         └──────────────────────┘
```

**雪花模型示意**：维度表进一步拆分
```
    产品维度表 → 产品类别子表（类别ID、类别名称、父类别）
    门店维度表 → 城市子表 → 省份子表 → 区域子表
```

> 类比：星型 = 一个中心枢纽（事实表）直接连各个卫星（维度表）；雪花 = 卫星还有自己的卫星（维度表再拆分）。星型快但冗余，雪花省空间但慢。

**事实表 vs 维度表**：

| 类型 | 存什么 | 特点 | 数据量 | 增长 | 类比 |
|------|--------|------|--------|------|------|
| 事实表 | 业务度量值（金额、数量、次数） | 多为数值型、可累加 | 大（亿级） | 增长快 | 账本——记录每一笔交易 |
| 维度表 | 描述性信息（时间、地点、产品、客户） | 多为文本型、相对稳定 | 小（万级） | 增长慢 | 字典——查"这是什么" |

**缓慢变化维（SCD）**：维度表的数据虽然变化慢，但也会变。处理维度变化的三类方式：

| 类型 | 策略 | 例子 |
|------|------|------|
| SCD Type 1 | 直接覆盖旧值（不保留历史） | 客户换手机号，直接更新 |
| SCD Type 2 | 新增一行记录（保留历史） | 客户搬家，新增一条地址记录，旧记录保留 |
| SCD Type 3 | 新增一列保留旧值（保留一次历史） | 客户升级会员等级，新列"当前等级"，旧列"原等级" |

#### 知识点 47：3.5 数据挖掘

从大量数据中发现隐藏的模式和规律。

**数据挖掘四大任务**：

| 挖掘方法 | 含义 | 典型算法 | 典型场景 |
|----------|------|---------|---------|
| 关联规则 | 发现事物之间的关联关系 | Apriori、FP-Growth | "买了尿布的人通常也买啤酒"（购物篮分析） |
| 分类 | 判断数据属于哪一类 | 决策树、SVM、朴素贝叶斯、逻辑回归 | 判断一笔交易是正常还是欺诈 |
| 聚类 | 把相似的数据归为一组 | K-Means、层次聚类、DBSCAN | 把消费者分为不同群体精准营销 |
| 回归 | 预测连续数值 | 线性回归、多项式回归 | 根据房屋面积、地段预测房价 |

**Apriori 算法详解（关联规则经典算法，考试重点！）**：

Apriori 用于发现频繁项集（经常一起出现的东西）。

**核心概念**：
| 概念 | 公式 | 含义 | 大白话 |
|------|------|------|--------|
| 支持度（Support） | P(A∩B) = 同时含 A 和 B 的记录数 / 总记录数 | A 和 B 同时出现的概率 | "多常见" |
| 置信度（Confidence） | P(B|A) = 同时含 A 和 B 的记录数 / 含 A 的记录数 | 买了 A 的人中有多少也买了 B | "多可靠" |
| 提升度（Lift） | Confidence / P(B) = P(A∩B) / (P(A)×P(B)) | A 的出现是否提升了 B 的出现概率 | "A 对 B 的促进效果" |
| 频繁项集 | 支持度 >= 最小支持度阈值的项集 | 出现次数足够多的商品组合 | "经常一起买的组合" |

> Lift > 1：正相关（A 促进 B）；Lift = 1：独立（无关）；Lift < 1：负相关（A 抑制 B）

**Apriori 计算例题**（考试必会！）：

假设有 5 笔交易，最小支持度 = 40%（即至少 2 笔交易），最小置信度 = 60%：

| 交易ID | 购买商品 |
|--------|---------|
| T1 | 牛奶、面包、尿布 |
| T2 | 牛奶、尿布 |
| T3 | 面包、尿布、啤酒 |
| T4 | 牛奶、面包、尿布 |
| T5 | 牛奶、面包、啤酒 |

**第一步：找频繁 1-项集**（支持度 >= 40% = 2/5）：
- 牛奶：4/5 = 80% >= 40% ✓ → 频繁
- 面包：4/5 = 80% >= 40% ✓ → 频繁
- 尿布：4/5 = 80% >= 40% ✓ → 频繁
- 啤酒：2/5 = 40% >= 40% ✓ → 频繁

**第二步：找频繁 2-项集**（由频繁 1-项集组合，支持度 >= 2/5）：
- {牛奶,面包}：3/5 = 60% ✓
- {牛奶,尿布}：4/5 = 80% ✓
- {牛奶,啤酒}：1/5 = 20% ✗
- {面包,尿布}：3/5 = 60% ✓
- {面包,啤酒}：2/5 = 40% ✓
- {尿布,啤酒}：1/5 = 20% ✗

**第三步：找频繁 3-项集**（由频繁 2-项集组合）：
- {牛奶,面包,尿布}：3/5 = 60% ✓

**第四步：生成关联规则**（置信度 >= 60%）：
- {牛奶,面包} → {尿布}：置信度 = 3/3 = 100% ✓
- {牛奶,尿布} → {面包}：置信度 = 3/4 = 75% ✓
- {面包,尿布} → {牛奶}：置信度 = 3/3 = 100% ✓
- {牛奶} → {面包,尿布}：置信度 = 3/4 = 75% ✓

> Apriori 核心原理：如果一个项集是频繁的，则它的所有子集也是频繁的（**先验性质**）。反之，如果一个项集是非频繁的，则它的所有超集也是非频繁的（**剪枝依据**）。

**Apriori 计算题解题模板**（国网考试必考计算题）：

```
给定：N 笔交易 + 最小支持度阈值 + 最小置信度阈值

步骤1：统计每个单项出现的次数 → 计算支持度 → 排除不满足最小支持度的
步骤2：用频繁1-项集两两组合 → 统计每个2-项集出现的次数 → 排除不满足的
步骤3：重复"组合→统计→排除"直到没有新的频繁项集
步骤4：从频繁项集生成关联规则 → 计算置信度 → 筛选满足最小置信度的规则

关键公式速记：
  支持度(A) = 含A的交易数 / 总交易数
  支持度(A→B) = 同时含A和B的交易数 / 总交易数
  置信度(A→B) = 同时含A和B的交易数 / 含A的交易数 = 支持度(A∪B) / 支持度(A)
  提升度(A→B) = 置信度(A→B) / 支持度(B)
```

**真题 47-3-1（计算题）**：4 笔交易：{A,B,C}、{A,C,D}、{B,C,D}、{A,B,C,D}。最小支持度 = 50%，最小置信度 = 70%。求 {A} → {B} 的置信度。

> 答案：
> - 含 A 的交易：T1、T2、T4 共 3 笔，支持度(A) = 3/4 = 75%
> - 同时含 A 和 B 的交易：T1、T4 共 2 笔，支持度(A,B) = 2/4 = 50%
> - 置信度(A→B) = 2/3 = 66.7% < 70%，不满足最小置信度，该规则不成立。
> 解析：置信度不是 2/4=50%！分母是"含 A 的交易数"（3），不是"总交易数"（4）。这是最容易出错的地方。

**真题 47-3-2（计算题）**：6 笔交易：{牛奶,面包}、{牛奶,尿布,啤酒}、{面包,尿布,啤酒}、{牛奶,面包,尿布,啤酒}、{牛奶,面包,尿布}、{牛奶,面包,啤酒}。求 {牛奶,面包} → {啤酒} 的置信度和提升度。

> 答案：
> - 含{牛奶,面包}的交易：T1、T4、T5、T6 共 4 笔
> - 同时含{牛奶,面包,啤酒}的交易：T4、T6 共 2 笔
> - 置信度 = 2/4 = 50%
> - 支持度(啤酒) = 4/6 ≈ 66.7%
> - 提升度 = 50% / 66.7% = 0.75 < 1
> 解析：提升度 < 1 说明 {牛奶,面包} 的出现反而降低了购买啤酒的概率——买了牛奶和面包的人，比一般人更不愿意买啤酒。这是一种负相关关系。

**常见陷阱**：
| 陷阱 | 错误做法 | 正确做法 |
|------|---------|---------|
| 置信度分母用错 | 用总交易数做分母 | 置信度分母 = 前件出现的次数（含 A 的交易数），不是总交易数 |
| 忘记频繁项集的先验性质 | 直接用所有可能的组合去算 | 先剪枝：非频繁项集的超集一定是非频繁的，不需要计算 |
| 提升度计算用错分母 | 提升度 = 置信度 / 支持度(前件) | 提升度 = 置信度(A→B) / 支持度(B)，分母是后件的支持度 |

**Apriori 算法步骤口诀**：
1. 扫描数据库，统计每个单项的支持度，排除不频繁的
2. 频繁项两两组合，再次扫描统计支持度，排除不频繁的
3. 重复组合-扫描-排除，直到没有新的频繁项集产生
4. 从频繁项集生成关联规则，计算置信度，筛选满足最小置信度的规则

### 知识点 47：4 大数据平台技术栈

#### 知识点 47：4.1 Hadoop 生态详解

Hadoop 是大数据处理的"鼻祖"框架，核心是三大组件 + 周边生态。

**Hadoop 三大核心组件**：

| 组件 | 全称 | 功能 | 版本 | 类比 |
|------|------|------|------|------|
| **HDFS** | Hadoop Distributed File System | 分布式文件存储 | 1.0/2.0/3.0（3.0 支持纠删码） | "超大仓库" |
| **MapReduce** | Map + Reduce | 分布式计算模型 | 1.0（JobTracker）/ 2.0（YARN） | "分锅做饭" |
| **YARN** | Yet Another Resource Negotiator | 资源管理和任务调度 | Hadoop 2.0 引入 | "项目经理" |

**Hadoop 三大组件——解题模板**：

```
看到以下关键词 → 直接选对应组件：
├── HDFS 关键词：存储、文件系统、NameNode、DataNode、分块、副本、Block、128MB、一次写入多次读取
├── MapReduce 关键词：计算、Map、Reduce、Shuffle、WordCount、分布式计算、并行处理
├── YARN 关键词：资源管理、任务调度、ResourceManager、NodeManager、Container、分配CPU/内存
└── HBase 关键词：列式存储、NoSQL、实时读写、Region、HMaster
```

**Hadoop 生态工具——关键词匹配表**：

| 工具 | 功能关键词 | 一句话 |
|------|-----------|--------|
| Hive | SQL、数据仓库、HQL、翻译成 MapReduce | "SQL 翻译成 MapReduce" |
| HBase | 列式存储、NoSQL、实时随机读写、Region | "HDFS 上的 BigTable" |
| Zookeeper | 协调、分布式锁、Leader 选举、配置管理 | "分布式协调员" |
| Sqoop | 导入导出、MySQL ↔ Hadoop、批量传输 | "MySQL ↔ Hadoop 搬运工" |
| Flume | 日志采集、Agent、Source→Channel→Sink | "日志收集管道" |
| Kafka | 消息队列、发布订阅、Topic、Partition、Producer、Consumer | "数据高速公路" |

**真题 47-4-1（单选题）**：在 Hadoop 生态中，Hive 的主要功能是（）。
A. 提供分布式文件存储
B. 提供类 SQL 查询功能，将 SQL 编译成 MapReduce 任务执行
C. 提供分布式协调服务
D. 提供实时流数据处理

> 答案：B。解析：Hive 是数据仓库工具，核心功能是提供 HQL（类 SQL）语言，将 SQL 查询编译成 MapReduce/Tez/Spark 任务执行。A 是 HDFS 的功能，C 是 Zookeeper 的功能，D 是 Spark Streaming/Flink 的功能。

**真题 47-4-2（单选题）**：以下关于 Hadoop 三大组件的描述，错误的是（）。
A. HDFS 采用"一次写入、多次读取"的模式
B. MapReduce 的 Map 阶段负责拆分并行处理，Reduce 阶段负责汇总结果
C. YARN 在 Hadoop 1.0 中就已经引入
D. HDFS 默认数据块大小为 128MB（Hadoop 2.0+）

> 答案：C。解析：YARN 是 Hadoop 2.0 才引入的资源管理框架，Hadoop 1.0 中资源管理由 MapReduce 框架自带的 JobTracker 负责，JobTracker 既管资源又管任务，压力大、扩展性差。A、B、D 均为正确描述。

**真题 47-4-3（单选题）**：以下关于 HDFS 数据块副本放置策略的描述，正确的是（）。
A. 三个副本全部放在同一机架上以提高传输速度
B. 第一个副本放在客户端所在节点，第二个副本放在不同机架，第三个副本放在第二个副本所在机架
C. 三个副本随机放置以提高容错性
D. 第一个副本放在 NameNode 所在节点

> 答案：B。解析：HDFS 默认 3 副本策略：第1个→客户端所在节点（就近）；第2个→与第1个不同机架（防机架故障）；第3个→与第2个同机架不同节点（传输快+容错）。A 全都同机架一损俱损；C 随机放置效率低；D NameNode 只存元数据不存数据块。

**常见陷阱**：
| 陷阱 | 错误认识 | 正确理解 |
|------|---------|---------|
| NameNode 存数据 | 以为 NameNode 存文件数据 | NameNode 只存元数据（目录树+块映射），实际数据存在 DataNode 上 |
| Secondary NameNode 是备份 | 以为它是 NameNode 的热备/替代品 | 它只是"秘书"（定期合并 FsImage 和 EditLog），NameNode 挂了它不能自动接管 |
| Hadoop 2.0 就有 YARN | 记混了版本 | Hadoop 1.0 = JobTracker，Hadoop 2.0 才引入 YARN |
| HDFS 适合小文件 | 以为分布式文件系统什么都能存 | 大量小文件会撑爆 NameNode 内存（每个文件约 150 字节元数据） |

**HDFS 核心特点**：
- 主从架构：NameNode（主节点，存元数据/目录树）+ DataNode（从节点，存实际数据块）
- 数据分块存储（默认 128MB/块，Hadoop 1.0 为 64MB），每块存多个副本（默认 3 份）
- **一次写入，多次读取**：写完后不改，适合存日志、存数据分析的原始数据
- 机架感知：优先把副本放到不同机架，提高容错
- 不适合低延迟访问，不适合大量小文件（小文件会撑爆 NameNode 内存）

**HDFS 架构详解**（考试重点）：

**1. NameNode（名称节点/主节点）**

NameNode 是 HDFS 的"大脑"，负责管理整个文件系统的元数据。

| 职责 | 详细说明 |
|------|---------|
| 管理文件系统的命名空间（目录树） | 维护文件→块的映射关系：哪个文件由哪些块组成 |
| 管理数据块的位置信息 | 记录每个块存储在哪些 DataNode 上 |
| 处理客户端请求 | 客户端读写文件前都要先找 NameNode 要"路条" |
| 监控 DataNode 状态 | 通过心跳机制确认 DataNode 是否存活 |

**NameNode 存储的内容（元数据）**：
- **FsImage（文件系统镜像）**：文件系统某一时刻的完整快照（目录结构、文件属性、块映射）
- **EditLog（编辑日志）**：记录自上次 FsImage 以来的所有变更操作（创建文件、删除文件等）
- 启动时：NameNode 加载 FsImage + 重放 EditLog → 得到当前最新状态

**NameNode 单点故障问题**：
- Hadoop 1.0：只有一台 NameNode，挂了整个集群不可用
- Hadoop 2.0：引入 **HA（高可用）**，通过两台 NameNode（Active + Standby）+ JournalNode 集群实现自动故障切换
- Hadoop 3.0：支持多 NameNode 联邦（Federation），每个 NameNode 管理一部分目录

**2. DataNode（数据节点/从节点）**

DataNode 是 HDFS 的"手脚"，负责实际存储数据。

| 职责 | 详细说明 |
|------|---------|
| 存储实际数据块 | 每个数据块以文件形式存储在本地磁盘上 |
| 执行读写操作 | 客户端直接从 DataNode 读取/写入数据（不经过 NameNode） |
| 定期向 NameNode 汇报 | 心跳（默认 3 秒一次）+ 块报告（Block Report，默认 6 小时一次） |
| 执行 NameNode 指令 | 复制块到其他节点、删除块、恢复块 |

**DataNode 与 NameNode 的交互**：
- 心跳机制：DataNode 每 3 秒向 NameNode 发送心跳信号，证明自己"还活着"
- 如果 NameNode 连续 10 分钟没收到某 DataNode 的心跳，标记该节点为"死亡"
- 死节点上的块副本需要从其他副本重新复制，恢复到设定的副本数

**3. Secondary NameNode（辅助名称节点）**

**不是 NameNode 的热备份！** 这个常考易错。

| 误解 | 正确理解 |
|------|---------|
| Secondary NameNode 是 NameNode 的备份？ | **不是！** 它不能替代 NameNode 工作 |
| 它的真正作用 | 定期合并 FsImage 和 EditLog，防止 EditLog 过大 |
| 合并过程 | 获取 NameNode 的 FsImage + EditLog → 在本地合并 → 传回新的 FsImage 给 NameNode |

> 记忆：Secondary NameNode = "秘书"——帮 NameNode 整理文件，但不能替代 NameNode 工作。NameNode 挂了，Secondary NameNode 不能自动接管。

**4. HDFS 数据块（Block）**

| 属性 | 说明 |
|------|------|
| 默认块大小 | Hadoop 2.0/3.0：**128MB**（Hadoop 1.0：64MB） |
| 为什么块这么大？ | 减少寻址开销（磁盘寻道时间 >> 数据传输时间，大块=少寻道） |
| 副本数 | 默认 **3** 份（可配置） |
| 比磁盘块大的原因 | 为了最小化寻址开销，需要让传输时间远大于寻道时间 |

**5. 副本放置策略（机架感知）**

HDFS 默认副本数 = 3，放置策略如下（以 Hadoop 3.0 为例）：

| 副本 | 放置位置 | 原因 |
|------|---------|------|
| 第1个副本 | 客户端所在节点（如果客户端在集群内）或随机节点 | 就近写入，减少网络开销 |
| 第2个副本 | 与第1个副本**不同机架**的节点 | 防止单机架故障导致数据丢失 |
| 第3个副本 | 与第2个副本**相同机架**的另一个节点 | 同机架内传输快，同时保证容错 |
| 更多副本 | 随机选择，但要满足机架均衡 | 负载均衡 |

**6. HDFS 读写流程**

**写入流程（考试理解即可）**：
```
客户端 → NameNode（请求创建文件）→ NameNode（返回DataNode列表）
→ 客户端向第一个DataNode写入 → 第一个DataNode传给第二个 → 第二个传给第三个
→ 每个DataNode写入完成后向上游确认 → 最终确认回到客户端
```

**读取流程**：
```
客户端 → NameNode（请求读取文件）→ NameNode（返回块位置列表，按"就近原则"排序）
→ 客户端从最近的DataNode读取块1 → 读取块2 → ... → 按顺序读取所有块
```

**7. HDFS 适用与不适用场景**

| 适用场景 | 不适用场景 |
|---------|-----------|
| 大文件存储（GB/TB/PB 级） | 大量小文件（几 MB 以下） |
| 流式数据访问（一次写入、多次读取） | 随机读写、频繁修改 |
| 批处理分析（MapReduce/Spark） | 低延迟数据访问（毫秒级） |
| 高吞吐量优先（而非低延迟） | 需要实时交互式查询 |

> 大量小文件的问题：每个文件的元数据约 150 字节存在 NameNode 内存中。1 亿个小文件 → 150 亿字节 ≈ 15GB 内存仅存元数据，NameNode 内存撑不住。

**MapReduce 计算流程详解**：

```
输入数据 → InputFormat（切片）→ RecordReader（读成 key-value）
         → Map 阶段（每个 key-value 调用一次 map 函数，输出中间 key-value）
         → Shuffle 阶段（分区+排序+合并+分组）【最耗时阶段】
         → Reduce 阶段（每个 key 调用一次 reduce 函数，聚合输出）
         → OutputFormat（写回 HDFS）
```

**MapReduce 经典 WordCount 示例**：

输入："Hello World Hello Hadoop"
```
Map 阶段：
  (0, "Hello World Hello Hadoop") → ("Hello",1), ("World",1), ("Hello",1), ("Hadoop",1)

Shuffle 阶段（按 key 分组）：
  "Hadoop" → [1]
  "Hello"  → [1, 1]
  "World"  → [1]

Reduce 阶段（对每个 key 的 value 列表求和）：
  ("Hadoop", 1), ("Hello", 2), ("World", 1)
```

> 考试记忆：MapReduce = Map（拆分+映射，并行处理）→ Shuffle（中间结果混洗排序）→ Reduce（聚合汇总）。Map 输出是中间结果，Reduce 输出是最终结果。

**Hadoop 周边生态工具**：

| 工具 | 功能 | 详细原理 | 一句话 |
|------|------|---------|--------|
| Hive | 数据仓库工具 | 提供类 SQL 语言（HQL），编译成 MapReduce/Tez/Spark 任务执行。元数据存于关系型数据库（如 MySQL） | "SQL 翻译成 MapReduce 执行" |
| HBase | 基于 HDFS 的列式 NoSQL 数据库 | 支持实时随机读写，按行键范围扫描。底层用 LSM 树（Log-Structured Merge-Tree）实现高写入吞吐 | "Hadoop 上的 BigTable" |
| Zookeeper | 分布式协调服务 | 提供配置管理、命名服务、分布式锁、Leader 选举。基于 ZAB 协议（类似 Paxos）保证一致性 | "分布式系统的协调员" |
| Sqoop | 批量数据传输 | 用 MapReduce 在关系型数据库和 Hadoop 之间批量导入/导出数据 | "MySQL ↔ Hadoop 的搬运工" |
| Flume | 日志采集 | Agent 模式：Source（收集）→ Channel（缓冲）→ Sink（输出），可靠地采集和传输日志 | "日志收集管道" |
| Kafka | 高吞吐分布式消息队列 | 基于发布/订阅模式，Producer → Broker集群 → Consumer。数据按 Topic 分区，支持消息持久化 | "数据高速公路" |

**HBase 架构核心要点**：
- 基于 HDFS 存储，使用 LSM 树实现高写入吞吐（先写内存 MemStore → 定期刷磁盘 HFile）
- **Region** 是数据分布的最小单元，一个表可拆分为多个 Region
- **RegionServer** 管理多个 Region，负责处理客户端读写请求
- **HMaster** 负责 Region 的分配和负载均衡
- 行键设计决定查询性能——行键相鄰的数据物理存储在一起

**Kafka 核心概念**：

| 概念 | 含义 | 类比 |
|------|------|------|
| **Topic** | 消息分类（如订单 Topic、日志 Topic） | 不同的"分类频道" |
| **Partition** | Topic 的物理分区，每个 Partition 是一个有序不可变的消息序列 | 把同一个频道的消息分到多个"子频道" |
| **Producer** | 发送消息的生产者 | "发消息的人" |
| **Consumer** | 接收消息的消费者 | "收消息的人" |
| **Consumer Group** | 一组 Consumer 共同消费一个 Topic（每条消息只被组内一个 Consumer 消费） | "轮班制"——一条消息只由组内一个人处理 |
| **Broker** | Kafka 集群中的一个节点 | "快递站"——收发和存储消息 |
| **Offset** | 消息在 Partition 中的位置编号 | "消息编号"——方便回溯和重读

#### 知识点 47：4.2 Spark 详解

Spark 是比 MapReduce 更快的新一代大数据计算框架。

| 对比维度 | Hadoop MapReduce | Spark |
|----------|-----------------|-------|
| 计算方式 | 磁盘 I/O（中间结果写磁盘，慢） | 内存计算（中间结果放内存，快） |
| 速度 | 慢 | 快（比 MapReduce 快 10~100 倍） |
| 适用场景 | 批量离线处理 | 批量处理 + 实时流处理 + 机器学习 + 图计算 |
| 编程语言 | Java 为主 | 支持 Java/Scala/Python/R |
| 容错机制 | 任务失败重跑 | 基于 RDD 的血统（Lineage）重算 |
| 交互式查询 | 不支持 | 支持（Spark Shell） |

**Spark 核心概念 RDD（弹性分布式数据集）**：
- 不可变的分布式数据集合，可分区并行计算
- 血统（Lineage）：记录每个 RDD 是怎么从上一个 RDD 转换来的，某个分区丢失时可按血统重算
- 两大操作类型：Transformation（转换，惰性不立即执行，如 map/filter）和 Action（动作，触发实际计算，如 count/collect）

**RDD 五大核心特性**：

| 特性 | 含义 | 大白话 |
|------|------|--------|
| **分区列表（Partitions）** | RDD 被切分成多个分区，分布到不同节点并行计算 | "把大任务切成小块分给大家做" |
| **计算函数（Compute Function）** | 每个分区怎么算——从父 RDD 到子 RDD 的转换逻辑 | "每块怎么做" |
| **依赖关系（Dependencies）** | 记录这个 RDD 依赖哪些父 RDD | "知道数据是怎么一步步算出来的" |
| **分区器（Partitioner）** | 可选，指定数据如何分区（Hash Partitioner / Range Partitioner） | "决定数据怎么分配到各节点" |
| **首选位置（Preferred Locations）** | 数据在哪台机器上，计算就在哪台机器上做（数据本地性） | "把计算搬到数据旁边，而不是搬数据" |

**Transformation vs Action 详解**：

RDD 的操作为什么分两类？因为 Spark 采用**惰性计算（Lazy Evaluation）**：遇到 Transformation 时只记录操作但不执行，遇到 Action 时才触发从头到尾的所有计算。

| 对比维度 | Transformation（转换） | Action（动作） |
|----------|----------------------|---------------|
| 执行时机 | **不立即执行**（惰性） | **立即触发执行** |
| 返回值 | 返回一个新的 RDD | 返回一个普通值/写入外部存储 |
| 是否生成 DAG | 生成新的 DAG 节点 | 触发 DAG 执行 |
| 常见操作 | map、filter、flatMap、groupByKey、reduceByKey、join、sort | count、collect、take、reduce、saveAsTextFile、foreach |
| 类比 | 制定食谱（只写不炒） | 开火做菜（真正执行） |

**常见 Transformation 操作**：

| 操作 | 含义 | 举例 |
|------|------|------|
| map(func) | 对每个元素应用函数，返回新 RDD | rdd.map(x => x*2) |
| filter(func) | 保留满足条件的元素 | rdd.filter(x => x>0) |
| flatMap(func) | 对每个元素产生多个输出（展平） | rdd.flatMap(s => s.split(" ")) |
| reduceByKey(func) | 按 Key 聚合（MapReduce 的 Reduce 操作） | pairs.reduceByKey((a,b) => a+b) |
| groupByKey() | 按 Key 分组 | pairs.groupByKey() |
| sortByKey() | 按 Key 排序 | pairs.sortByKey() |

> **reduceByKey vs groupByKey**（考试高频）：reduceByKey 先在每个分区内局部聚合再 shuffle（Map 端预聚合，数据量小），groupByKey 直接 shuffle 所有数据。**reduceByKey 效率远高于 groupByKey**。

**常见 Action 操作**：

| 操作 | 含义 | 注意 |
|------|------|------|
| count() | 返回 RDD 中元素个数 | — |
| collect() | 将 RDD 所有数据拉回 Driver | 数据量大时 Driver 内存可能不够，慎用 |
| take(n) | 返回 RDD 前 n 个元素 | 比 collect() 安全，只拉少量数据 |
| reduce(func) | 聚合所有元素 | 如 rdd.reduce((a,b) => a+b) |
| saveAsTextFile(path) | 保存到文件 | 每个分区输出一个文件 |
| foreach(func) | 对每个元素执行操作 | 常用于写入外部系统（如 Redis） |

**RDD 依赖关系**：

| 依赖类型 | 含义 | 特点 | 例子 |
|----------|------|------|------|
| **窄依赖（Narrow Dependency）** | 每个父 RDD 分区**最多**被一个子 RDD 分区使用 | 可以流水线执行（pipeline），一个节点就能完成 | map、filter、union |
| **宽依赖（Shuffle Dependency）** | 每个父 RDD 分区**可能**被多个子 RDD 分区使用 | 需要跨节点 shuffle 数据，开销大 | groupByKey、reduceByKey、join |

> 窄依赖 = 不需要 shuffle，快；宽依赖 = 需要 shuffle，慢。优化方向：尽量减少宽依赖，用 reduceByKey 代替 groupByKey。

**Spark 作业执行流程**：
1. Action 触发 → SparkContext 构建 DAG（有向无环图）
2. DAGScheduler 将 DAG 划分为 Stage（遇到宽依赖就切分新 Stage）
3. TaskScheduler 将 Stage 内的任务分发给 Executor 执行
4. Executor 执行任务并返回结果

**Spark 核心模块**：

| 模块 | 功能 | 替代什么 |
|------|------|---------|
| Spark Core | 基础计算引擎（RDD、任务调度、内存管理） | MapReduce 核心 |
| Spark SQL | 用 SQL 查询结构化数据，支持 DataFrame/Dataset API | Hive（但比 Hive 快得多） |
| Spark Streaming | 实时流数据处理（微批处理模式） | Storm（但吞吐更高） |
| Structured Streaming | 新一代流处理引擎（基于 Spark SQL 引擎） | Flink 的竞品 |
| MLlib | 机器学习库（分类、回归、聚类、推荐等） | Mahout |
| GraphX | 图计算（PageRank、连通分量、三角计数） | Giraph |

**Hadoop vs Spark 怎么选？**
- 预算有限、数据量极大、只需要离线批处理 → Hadoop MapReduce
- 需要快速迭代、交互式分析、机器学习 → Spark
- 实际项目中常两者配合：HDFS 存储 + Spark 计算 + YARN 调度

#### 知识点 47：4.3 批处理 vs 流处理

| 处理类型 | 处理方式 | 延迟 | 数据范围 | 代表框架 | 典型场景 |
|----------|---------|------|---------|---------|---------|
| **批处理（Batch）** | 先攒一批数据，再统一处理 | 分钟~小时级 | 有界数据（固定大小） | Hadoop MapReduce、Spark | 日终报表、月度统计 |
| **流处理（Stream）** | 数据来一条处理一条（真正实时） | 毫秒~秒级 | 无界数据（持续流入） | Storm、Flink、Kafka Streams | 实时风控、股票交易 |
| **微批处理（Micro-batch）** | 小批次实时处理（折中方案） | 秒~分钟级 | 小批次 | Spark Streaming | 近实时日志分析 |

> 记忆：批处理 = 攒一筐再洗（慢但吞吐高），流处理 = 来一个洗一个（快但更复杂）

#### 知识点 47：4.4 NoSQL 数据库分类

> **考频星级：高频 ⭐⭐** | NoSQL 四种类型及其代表产品匹配是常见考题

NoSQL = Not Only SQL，非关系型数据库，解决传统关系型数据库在大数据场景下的扩展性瓶颈。

| 类型 | 数据模型 | 代表数据库 | 特点 | 适用场景 |
|------|---------|-----------|------|---------|
| **键值存储（Key-Value）** | Key → Value | Redis、Memcached、DynamoDB | 极快、简单，但查询能力弱 | 缓存、会话管理、购物车 |
| **列族存储（Column-Family）** | 行键 + 列族 + 列 | HBase、Cassandra | 稀疏存储、按列压缩、高写入吞吐 | 时序数据、日志、物联网数据 |
| **文档存储（Document）** | JSON/BSON 文档 | MongoDB、CouchDB、Elasticsearch | 灵活 Schema、嵌套结构、支持索引 | 内容管理、用户画像、商品目录 |
| **图数据库（Graph）** | 节点 + 边 | Neo4j、JanusGraph | 擅长处理复杂关系 | 社交网络、推荐系统、知识图谱 |

**NoSQL 的 CAP 选择**：

| 数据库 | CAP 选择 | 解释 |
|--------|----------|------|
| MySQL（单机） | CA（无 P） | 单机不涉及分区容错，保证一致性和可用性 |
| HBase | CP | 优先一致性和分区容错，Master 挂了短暂不可用 |
| MongoDB（默认） | CP | 优先一致性 |
| Cassandra | AP | 优先可用性，最终一致性（可能读到旧数据） |
| Redis（单机） | CA（无 P） | 单机 |
| Redis Cluster | AP | 分布式 Redis 优先可用性 |

> CAP 定理核心：分布式系统必须保证 P（分区容错性），只能在 C（一致性）和 A（可用性）之间取舍。CP 系统在网络分区时牺牲可用性（暂时不可访问），AP 系统牺牲一致性（可能读到旧数据）。

**NoSQL 数据库分类——解题模板**

```
NoSQL 选型"场景关键词"秒杀法：

├── 键值存储（Redis）
│   ├── 关键词：缓存、session、极快、key-value、购物车、验证码
│   └── 一句话：最快最简单，但只能按 key 查
│
├── 文档存储（MongoDB）
│   ├── 关键词：JSON、灵活 Schema、字段不固定、嵌套结构、内容管理
│   └── 一句话：像存 JSON 文件一样存数据，结构灵活
│
├── 列族存储（HBase）
│   ├── 关键词：时序数据、海量写入、设备数据、传感器、日志、按时间范围查
│   └── 一句话：列式存储，写得多查得少，适合海量时序数据
│
└── 图数据库（Neo4j）
    ├── 关键词：好友关系、社交网络、推荐、关联查询、多跳查询、知识图谱
    └── 一句话：专治各种"关系"，查几层好友效率极高
```

**CAP 定理——解题模板**

```
CAP 题目解题口诀：
1. 分布式系统必须选 P（分区容错性）——这是铁律！
2. 在 C（一致性）和 A（可用性）之间二选一
3. 记住常见数据库的 CAP 选择：
   ├── CP（要一致，允许短暂不可用）：HBase、MongoDB
   ├── AP（要可用，允许短暂不一致）：Cassandra、DynamoDB、Redis Cluster
   └── CA（单机才有，分布式不可能）：MySQL（单机版）、Redis（单机版）
```

**真题 47-4-4（单选题）**：某电商平台使用 Redis 存储用户登录后的 session 信息，设置过期时间为 30 分钟。这种场景选择 Redis 的主要原因是（）。
A. Redis 支持 SQL 查询  B. Redis 是文档型数据库，存储灵活  C. Redis 读写速度极快，且支持 key-value 模式  D. Redis 支持复杂的图查询

> 答案：C。解析：Redis 是键值存储数据库，读写速度极快（微秒级），天然适合缓存和 session 管理。A 错误（Redis 不支持 SQL）；B 是 MongoDB 的特点；D 是 Neo4j 的特点。

**真题 47-4-5（单选题）**：根据 CAP 定理，以下关于分布式数据库的说法，正确的是（）。
A. 分布式系统可以同时满足 C、A、P 三个特性
B. 分布式系统必须保证 P，只能在 C 和 A 之间取舍
C. HBase 选择了 AP，优先保证可用性
D. Cassandra 选择了 CP，优先保证一致性

> 答案：B。解析：CAP 定理的核心结论——分布式系统必须保证 P，只能在 C 和 A 之间取舍。C 和 D 说反了：HBase 是 CP（优先一致性），Cassandra 是 AP（优先可用性）。

**常见陷阱**：
| 陷阱 | 错误认识 | 正确理解 |
|------|---------|---------|
| CAP 可以三选三 | 以为分布式系统可以同时满足 C、A、P | 分布式系统只能三选二，且必须选 P |
| 单机数据库也选 AP 或 CP | 把 CAP 用到单机数据库上 | 单机不存在网络分区问题，所以没有 P，是 CA |
| NoSQL = 完全不用 SQL | 以为 NoSQL 就是"不要 SQL" | NoSQL = Not Only SQL（不仅仅是 SQL），不同场景用不同数据库类型 |

#### 知识点 47：4.5 数据仓库 vs 数据湖 vs 数据集市

| 概念 | 存什么 | 数据质量 | 处理方式 | 主要用户 | 类比 |
|------|--------|---------|---------|---------|------|
| **数据湖（Data Lake）** | 所有原始数据（结构化+半结构化+非结构化） | 低（原始态） | 读时处理（Schema-on-Read） | 数据科学家、算法工程师 | 大水库，什么水都存 |
| **数据仓库（Data Warehouse）** | 经过清洗、结构化后的"干净"数据 | 高 | 写时处理（Schema-on-Write） | 业务分析师、决策层 | 自来水厂，净化后供人使用 |
| **数据集市（Data Mart）** | 数据仓库的子集，面向特定业务部门 | 高 | 写时处理 | 某个业务部门 | 小区的直饮水站 |

**数据湖 vs 数据仓库关键区别**：

| 对比 | 数据湖 | 数据仓库 |
|------|--------|---------|
| 数据 | 原始数据，保留所有细节 | 加工后的汇总数据 |
| Schema | Schema-on-Read（读时定义结构） | Schema-on-Write（写时定义结构） |
| 灵活性 | 高（随时可按新需求读取原始数据） | 低（修改 ETL 流程成本高） |
| 查询速度 | 慢（需要解析原始数据） | 快（数据已优化） |
| 代表技术 | Hadoop HDFS、AWS S3、Azure Data Lake | Hive、Teradata、Snowflake、ClickHouse |

#### 知识点 47：4.6 OLTP vs OLAP

| 对比维度 | OLTP（联机事务处理） | OLAP（联机分析处理） |
|----------|---------------------|---------------------|
| 关注点 | 日常业务操作（增删改查） | 数据分析与决策支持 |
| 操作类型 | 大量短事务（增删改查） | 大量复杂查询（SELECT + 聚合 + GROUP BY） |
| 数据特点 | 当前数据，实时更新，行式存储 | 历史数据，定期批量更新，列式存储 |
| 每秒操作量 | 几千~几万次事务 | 几十~几百次查询 |
| 数据库类型 | MySQL、Oracle、PostgreSQL | Hive、ClickHouse、Doris、Kylin |
| 数据量 | GB~TB | TB~PB |
| 范式 | 高度规范化（3NF） | 反规范化（星型/雪花模型） |
| 一句话 | "处理业务——收银台" | "做分析——财报" |

> 记忆：OLTP = 一笔一笔交易处理（高频低延迟），OLAP = 汇总分析大量数据（低频高吞吐）

#### 知识点 47：4.7 ETL vs ELT

| 对比维度 | ETL（传统） | ELT（现代云数仓） |
|----------|------------|-------------------|
| 顺序 | 先转换（Transform）→ 再加载（Load） | 先加载（Load）→ 再转换（Transform） |
| 转换位置 | 在中间 ETL 服务器完成 | 在目标数据仓库中完成 |
| 原始数据 | 转换后废弃，不保留 | 保留在数仓/数据湖中 |
| 适用场景 | 数据量小、计算资源有限 | 云数仓、大数据平台 |
| 代表工具 | Informatica、DataStage、Kettle | dbt + Snowflake、BigQuery |
| 灵活性 | 低（转换后原始数据没了） | 高（原始数据在，随时可按新逻辑重新转换） |

> 记忆：ETL = 先洗再存（传统），ELT = 先存再洗（现代）。关键区别 = 在哪做转换 + 保不保留原始数据。

#### 知识点 47：4.8 Lambda 架构 vs Kappa 架构

| 架构 | 核心思想 | 优点 | 缺点 |
|------|---------|------|------|
| **Lambda 架构** | 同时维护"批处理层"（准确性）+ "速度层"（实时性）+ "服务层"（合并） | 兼顾准确性和实时性 | 需要维护两套代码，运维复杂 |
| **Kappa 架构** | 只用流处理，所有数据都当作流，批处理是流的"回放" | 架构简单，一套代码 | 对消息队列（Kafka）依赖高，历史数据重算代价大 |

> 记忆：Lambda = 批+流两套（复杂但稳妥），Kappa = 全部用流（简单但有局限）

#### 知识点 47：4.9 大数据热点方向

| 热点 | 说明 | 核心价值 |
|------|------|---------|
| 数据中台 | 统一数据服务，打破数据孤岛，提供 OneData 体系 | 数据复用、口径统一、降本增效 |
| 用户画像 | 基于行为数据打标签（年龄/性别/偏好/消费力） | 精准推荐、精细化运营 |
| 实时计算 | Flink 成为主流流计算引擎 | 实时风控、实时大屏、实时数仓 |
| 数据治理 | 数据质量、元数据管理、数据血缘、数据安全 | 数据可信、合规、可追溯 |
| 隐私计算 | 联邦学习、多方安全计算、差分隐私 | 保护隐私前提下利用数据 |
| 湖仓一体（Lakehouse） | 数据湖 + 数据仓库融合，兼具灵活性和高性能 | Delta Lake、Iceberg、Hudi |

### 知识点 47：例题精练

**例题 47-1（单选题）**：大数据的 5V 特征中，表示"价值密度低"的是（）。
A. Volume  B. Velocity  C. Variety  D. Value

> 答案：D。解析：注意 Value 不是"价值高"，而是"价值密度低"——海量数据中有价值的信息比例很低，需要"沙里淘金"。

**例题 47-2（单选题）**：在 Apriori 关联规则中，支持度（Support）的含义是（）。
A. 买了 A 的人中有多少也买了 B  B. A 和 B 同时出现的概率  C. A 的出现使 B 的概率提升了多少  D. 规则的准确率

> 答案：B。解析：A 是置信度（Confidence），B 是支持度（Support），C 是提升度（Lift）。

**例题 47-3（单选题）**：Hadoop 生态中，负责资源管理和任务调度的组件是（）。
A. HDFS  B. MapReduce  C. YARN  D. HBase

> 答案：C。解析：HDFS = 存，MapReduce = 算，YARN = 管资源（项目经理），HBase = 列式数据库。

**例题 47-4（单选题）**：以下哪种 NoSQL 数据库最适合存储社交网络中的好友关系？（）
A. Redis  B. MongoDB  C. HBase  D. Neo4j

> 答案：D。解析：社交网络的好友关系 = 图结构（节点=人，边=好友关系），用图数据库 Neo4j 最合适。Redis 是键值缓存，MongoDB 是文档存储，HBase 是列族存储。

**例题 47-5（计算题）**：5 笔交易：{A,B,C}、{A,C}、{A,B}、{B,C}、{A,B,C}。求 {A,B} → {C} 的置信度。

> 答案：{A,B} 出现在 T1、T3、T5 共 3 笔交易中。同时含 {A,B,C} 的出现在 T1、T5 共 2 笔。置信度 = 2/3 = 66.7%。解析：置信度 = 同时含 A、B、C 的交易数 / 含 A、B 的交易数。

### 知识点 47：真题实练——大数据 5V 特征判断题

**真题 47-A（单选题）**：大数据的 5V 特征中，用来描述数据来源格式多样、包括结构化/半结构化/非结构化数据的是（）。
A. Volume  B. Velocity  C. Variety  D. Veracity

> 答案：C。解析：Variety（多样性）描述数据类型繁多——结构化（数据库表）、半结构化（XML/JSON）、非结构化（图片/视频/文本）。关键词记忆：Variety = Variety of data types（多种多样）。

**真题 47-B（单选题）**：淘宝双十一每秒产生几十万笔交易，需要实时处理这些数据。这体现了大数据的哪个特征？（）
A. Volume  B. Velocity  C. Value  D. Variety

> 答案：B。解析：Velocity（高速性）描述数据产生和流动的速度极快，需要实时/准实时处理。"每秒几十万笔"强调的就是"速度"。关键词记忆：Velocity = 速度快。

**真题 47-C（单选题）**：大数据的 5V 特征中，"Value"的正确理解是（）。
A. 数据的商业价值很高
B. 海量数据中有价值的信息密度很低
C. 数据越多价值越高
D. 所有数据都具有同等价值

> 答案：B。解析：Value 不是"价值高"，而是"价值密度低"——几小时监控视频中可能只有几秒是关键画面，核心挑战是如何"沙里淘金"。这是最高频的易错点！

**真题 47-D（单选题）**：某物联网项目每天产生 50TB 的传感器数据，公司需要建设 PB 级别的存储系统。这主要体现了大数据的哪个特征？（）
A. Volume  B. Value  C. Veracity  D. Velocity

> 答案：A。解析：Volume（大量）描述数据量巨大，从 TB→PB→EB 级别。关键词："50TB""PB 级别"= 数量大。记忆：Volume = 容量/数量。

**真题 47-E（多选题）**：以下属于大数据的 5V 特征的有（）。
A. Volume（大量）  B. Velocity（高速）  C. Variety（多样）  D. Value（高价值）  E. Veracity（真实性）

> 答案：ABCE。解析：5V 的 V 分别是 Volume（大量）、Velocity（高速）、Variety（多样）、Value（低价值密度）、Veracity（真实性/准确性）。D 的错误在于 Value 不是"高价值"，而是"价值密度低"。多选题要注意 Value 的这个陷阱！

> **应试技巧**：5V 判断题——看到"50TB/PB/海量/数据量大"选 Volume；看到"每秒/实时/快速/流式"选 Velocity；看到"结构不同/图片视频/多种格式"选 Variety；看到"价值密度低/沙里淘金/关键信息少"选 Value；看到"数据不准/噪声/质量差"选 Veracity。

### 知识点 47：真题实练——NoSQL 数据库分类匹配题

**真题 47-F（单选题）**：某互联网公司需要存储用户的会话信息（session），要求读写速度极快，数据结构简单，每个 session 对应一个 key。最适合使用哪种 NoSQL 数据库？（）
A. MongoDB  B. HBase  C. Redis  D. Neo4j

> 答案：C。解析：Key-Value 存储，读写极快，适合缓存和会话管理→Redis。场景关键词："key-value""极快""简单"。MongoDB 是文档存储，HBase 是列族存储，Neo4j 是图数据库。

**真题 47-G（单选题）**：某内容管理平台需要存储各种格式的文章数据，每篇文章的字段结构可能不同（有的有图片字段、有的有视频字段），且需要支持按多个字段灵活查询。最适合使用哪种 NoSQL 数据库？（）
A. Redis  B. HBase  C. MongoDB  D. Neo4j

> 答案：C。解析：灵活 Schema（字段结构不固定），支持嵌套结构→文档存储 MongoDB。场景关键词："字段结构不同""JSON/文档格式""灵活查询"。

**真题 47-H（单选题）**：某物联网平台需要存储海量的传感器时序数据（设备ID + 时间戳 + 温度 + 湿度），写入吞吐量要求极高，查询时通常按设备ID和时间范围获取。以下哪种数据库最适合？（）
A. Redis  B. MongoDB  C. Neo4j  D. HBase

> 答案：D。解析：时序数据、高写入吞吐、按行键范围查询→列族存储 HBase。HBase 擅长按行键连续读写，适合存储"设备ID+时间戳"这类有序的海量数据。场景关键词："时序数据""海量写入""按ID连续读取"。

**真题 47-I（单选题）**：以下 NoSQL 数据库与类型的对应关系中，正确的是（）。
A. Redis——文档存储  B. MongoDB——键值存储  C. HBase——列族存储  D. Neo4j——文档存储

> 答案：C。解析：正确对应——Redis=键值存储，MongoDB=文档存储，HBase=列族存储，Neo4j=图数据库。这道题检验四种 NoSQL 类型与代表产品的对应关系，是高频考点。

**真题 47-J（单选题）**：某社交平台想实现"你可能认识的人"推荐功能，需要高效查询用户之间的好友关系网络（"A 是 B 的好友"、"B 是 C 的好友"这类关联查询）。最适合使用哪种数据库？（）
A. Redis  B. MongoDB  C. HBase  D. Neo4j

> 答案：D。解析：好友关系是典型的图结构（节点=用户，边=好友关系），需要高效的图遍历查询（如"找到用户A的所有好友的好友"）→图数据库 Neo4j。场景关键词："好友关系""推荐""关联网络""多跳查询"。

> **应试技巧**：NoSQL 分类题——看到"缓存/session/key-value/极快"→键值存储（Redis）；看到"JSON/灵活Schema/字段不同/文档"→文档存储（MongoDB）；看到"时序/海量写入/列式/设备数据"→列族存储（HBase）；看到"好友关系/社交网络/推荐/关联查询"→图数据库（Neo4j）。

### 知识点 47：易错陷阱表

| 陷阱编号 | 易错点 | 正确理解 |
|----------|--------|---------|
| 1 | 以为大数据的 Value 是"价值高" | Value = 价值密度低，需要沙里淘金 |
| 2 | 混淆支持度和置信度 | 支持度 = "多常见"（A 和 B 同时出现的概率）；置信度 = "多可靠"（买了 A 的人中买 B 的比例） |
| 3 | 混淆星型模型和雪花模型 | 星型 = 维度表不分拆（JOIN 少，快）；雪花 = 维度表规范化拆分（JOIN 多，省空间） |
| 4 | 混淆 OLTP 和 OLAP | OLTP = 处理业务交易（增删改）；OLAP = 做数据分析（查询聚合） |
| 5 | 混淆 ETL 和 ELT 的顺序 | ETL = 先转换再加载（传统）；ELT = 先加载再转换（现代） |
| 6 | 以为 Spark 比 MapReduce 快是因为算法更好 | 快在内存计算，不是算法更优。MapReduce 中间结果写磁盘，Spark 中间结果放内存 |
| 7 | 混淆 Hadoop 三大组件功能 | HDFS = 存（分布式文件系统），MapReduce = 算（分布式计算），YARN = 管（资源调度） |
| 8 | 以为 NoSQL 是完全替代关系型数据库 | NoSQL = Not Only SQL，不是 No SQL。不同场景用不同类型的数据库 |
| 9 | 混淆数据仓库和数据湖 | 数仓 = 洗干净的结构化数据（自来水厂），数据湖 = 所有原始数据（大水库） |
| 10 | CAP 中以为可以不选 P | 分布式系统必须保证 P（分区容错性），只能在 C 和 A 之间取舍 |

## 常见易错陷阱

1. **当前所有 AI 都是弱人工智能（ANI），不是强人工智能（AGI）**
2. **监督学习需要标签，无监督学习不需要标签**——这是两者最本质的区别
3. **分类输出离散类别，回归输出连续数值**——不要搞混
4. **CNN 用于图像，RNN/LSTM 用于序列**——不要交叉使用
5. **GPT 是单向生成，BERT 是双向理解**——GPT = "接着说"，BERT = "读懂再答"
6. **物联网三层：感知层在最下面、网络层在中间、应用层在最上面**——顺序不能乱
7. **NFC 是 RFID 的子集**——距离更短、支持双向通信
8. **LoRa 用免费频段、NB-IoT 用运营商基站**——部署方式完全不同
9. **大数据的 Value 是指"价值密度低"，不是价值高**——容易被误解
10. **Hadoop 的 HDFS 是"一次写入、多次读取"**——不适合频繁修改的文件
11. **Spark 比 MapReduce 快是因为内存计算**——不是算法更优，而是减少磁盘 I/O
12. **Map = 拆分处理，Reduce = 汇总结果**——方向不要搞反

   - GPT 基于 Transformer 的 Decoder 部分（单向），擅长文本生成（"接着说"）

1. 物联网三层架构（自下而上）：
   - 感知层（传感层）：数据采集 + 物体识别，类比"眼睛和耳朵"，典型设备：传感器、RFID、摄像头
   - 网络层（传输层）：数据传输 + 路由转发，类比"神经系统"，典型技术：WiFi、4G/5G、NB-IoT、LoRa
   - 应用层（处理层）：数据处理 + 提供服务，类比"大脑"，典型应用：智能家居 APP、工业监控平台
2. MQTT vs CoAP：
   - MQTT：基于发布/订阅模式的轻量级协议，适合低带宽、不可靠网络，用于传感器数据推送
   - CoAP：类 HTTP 的受限应用协议，基于 UDP，适合资源受限设备，支持 RESTful 风格
   RFID vs NFC：
   - RFID：电子标签，无线射频识别，距离几厘米到几十米，多为单向一对多通信，用于仓储物流
   - NFC：RFID 的子集，距离 < 10cm，支持双向一对一通信，频率固定 13.56MHz，用于手机支付/公交卡

</details>

**自测 47**：

1. 大数据的 5V 特征分别是什么？其中 Value 指的是什么（容易误解题）？
2. 数据预处理的四个步骤是什么？Hadoop 的三大核心组件及其功能分别是什么？

<details><summary>参考答案</summary>

1. 大数据 5V：
   - Volume（大量）：数据量巨大，PB/EB 级别
   - Velocity（高速）：数据生成和处理速度快，需要实时或准实时处理
   - Variety（多样）：数据类型多样，结构化 + 半结构化 + 非结构化
   - Value（低价值密度）：注意不是"价值高"，而是"价值密度低"——海量数据中有价值的信息比例很低，需要"沙里淘金"
   - Veracity（真实性/准确性）：数据质量参差不齐，需要清洗验证
2. 数据预处理四步骤：清洗 → 集成 → 变换 → 规约（洗→合→变→缩）
   Hadoop 三大核心组件：
   - HDFS（分布式文件系统）：负责存储，大文件分块存到多台机器，每块存多副本（默认 3 份），"一次写入、多次读取"
   - MapReduce（分布式计算）：Map 拆分任务并行处理，Reduce 汇总结果
   - YARN（资源管理）：统一分配 CPU、内存给各个任务，相当于"项目经理"

</details>

### 一、人工智能（AI）考点补充

#### 考点 1：过拟合 vs 欠拟合

这是考试中极易混淆的概念，务必区分清楚。

| 概念 | 含义 | 表现 | 解决方法 |
|------|------|------|---------|
| **过拟合（Overfitting）** | 模型把训练数据"背"下来了，连噪声和异常点都记住了 | 训练集上表现极好，测试集上表现很差（泛化能力差） | 增加训练数据、正则化（L1/L2）、Dropout、早停法（Early Stopping）、降低模型复杂度 |
| **欠拟合（Underfitting）** | 模型太简单，连训练数据的基本规律都没学到 | 训练集和测试集上表现都很差 | 增加模型复杂度、增加特征、减少正则化、延长训练时间 |

**类比**：
- 过拟合 = 死记硬背的学生——只会做原题，题目稍微变一下就不会了
- 欠拟合 = 根本没听课的学生——原题和变式题都不会做

> 记忆口诀："过拟合 = 训练好测试差，欠拟合 = 两边都差"

#### 考点 2：偏差 vs 方差

| 概念 | 含义 | 关联 |
|------|------|------|
| **偏差（Bias）** | 模型预测值与真实值之间的差距，反映模型的"准不准" | 高偏差 → 欠拟合 |
| **方差（Variance）** | 模型在不同训练集上预测结果的波动程度，反映模型的"稳不稳" | 高方差 → 过拟合 |

**偏差-方差权衡（Bias-Variance Tradeoff）**：模型复杂度增加 → 偏差降低，方差升高。最优模型在偏差和方差之间取平衡点。

> 记忆：偏差 = 打靶打在靶心外面（偏了），方差 = 打靶子弹到处乱飞（不稳）

#### 考点 3：常见激活函数

| 激活函数 | 公式特点 | 优点 | 缺点 | 适用场景 |
|----------|---------|------|------|---------|
| **Sigmoid** | 输出 0~1，S 形曲线 | 平滑、可解释为概率 | 容易梯度消失，输出不以 0 为中心 | 二分类输出层 |
| **Tanh** | 输出 -1~1，S 形曲线 | 输出以 0 为中心 | 仍有梯度消失问题 | RNN 隐藏层 |
| **ReLU** | f(x) = max(0, x) | 计算简单，缓解梯度消失，收敛快 | 神经元可能"死亡"（负数输出恒为 0） | 最常用的隐藏层激活函数 |
| **Softmax** | 输出多分类概率分布（所有输出之和 = 1） | 适合多分类 | 计算量大 | 多分类输出层 |

> 记忆：Sigmoid/Tanh = S 形曲线但会梯度消失；ReLU = 大于 0 就原样输出，小于 0 就输出 0；Softmax = 多选一，谁大选谁

#### 考点 4：常见损失函数

| 损失函数 | 用途 | 一句话 |
|----------|------|--------|
| 均方误差（MSE） | 回归任务 | 预测值和真实值差值的平方求平均 |
| 交叉熵损失（Cross Entropy） | 分类任务 | 衡量两个概率分布之间的差异 |
| 二分类交叉熵（BCE） | 二分类 | 交叉熵的特例，只有两个类别 |

#### 考点 5：精确率 vs 召回率

| 指标 | 含义 | 公式 | 关注点 |
|------|------|------|--------|
| **精确率（Precision）** | 预测为正的样本中，真正为正的比例 | TP / (TP + FP) | "查得准不准" |
| **召回率（Recall）** | 真正的正样本中，被预测为正的比例 | TP / (TP + FN) | "查得全不全" |
| **F1 分数** | 精确率和召回率的调和平均值 | 2 × P × R / (P + R) | 综合衡量 |

**类比**：
- 精确率 = 警察抓了 10 个人，其中 8 个是真罪犯 → 精确率 = 80%
- 召回率 = 总共 20 个罪犯，警察只抓到了 8 个 → 召回率 = 40%

> 记忆：精确率 = 不冤枉好人，召回率 = 不放过坏人

#### 考点 6：生成式 AI 与判别式 AI

| 对比维度 | 生成式 AI（Generative） | 判别式 AI（Discriminative） |
|----------|------------------------|----------------------------|
| 核心思想 | 学习数据的联合分布 P(X, Y)，能"创造"新数据 | 学习决策边界 P(Y\|X)，只做"判断" |
| 能力 | 生成新内容（文本、图片、代码） | 分类、预测、识别 |
| 代表 | GPT、Stable Diffusion、GAN | 逻辑回归、SVM、决策树、CNN 分类器 |

> 考试注意：ChatGPT/GPT 是生成式 AI，不是判别式。这是近年热点，常出现在单选题中。

#### 考点 7：AI 热点应用（近年热点）

| 热点方向 | 典型应用 | 涉及技术 |
|----------|---------|---------|
| AIGC（AI 生成内容） | ChatGPT 对话、AI 绘画、AI 作曲 | 大语言模型（LLM）、扩散模型（Diffusion）、GAN |
| 自动驾驶 | 环境感知、路径规划、决策控制 | 计算机视觉、强化学习、传感器融合 |
| 智能客服 | 自动问答、意图识别、情绪分析 | NLP、语音识别、情感计算 |
| AI 医疗 | 医学影像辅助诊断、药物研发 | 图像分割、深度学习 |
| 具身智能 | 人形机器人、机械臂操作 | 强化学习、多模态感知 |

### 二、物联网（IoT）考点补充

#### 考点 1：边缘计算 vs 雾计算 vs 云计算

这是重要且易混淆的对比考点。

| 概念 | 计算位置 | 响应速度 | 适用场景 | 一句话 |
|------|---------|---------|---------|--------|
| **云计算（Cloud Computing）** | 数据中心（远端） | 慢（几百毫秒） | 大规模数据分析、模型训练 | 所有数据都送到"云端"处理 |
| **雾计算（Fog Computing）** | 网络边缘（局域网网关/路由器） | 中等 | 本地数据分析、过滤 | 在"局域网网关"处先处理一波 |
| **边缘计算（Edge Computing）** | 设备端/最近端 | 极快（毫秒级） | 实时控制、图像实时处理 | 数据直接在"设备旁边"就处理了 |

**类比**：一栋楼的摄像头
- 云计算 = 所有视频传到几千里外的数据中心分析 → 延迟大
- 雾计算 = 在楼里的局域网服务器先分析 → 快一些
- 边缘计算 = 摄像头自带芯片直接在本地分析 → 最快

> 记忆：数据越靠近数据源头处理，速度越快，延迟越低。三者不是取代关系，而是互相配合。

#### 考点 2：物联网安全

| 安全问题 | 说明 |
|---------|------|
| 设备认证 | 确保只有合法设备能接入网络 |
| 数据加密 | 传输中的数据（传感器数据）必须加密，防止窃听 |
| 固件安全 | 终端设备固件需防篡改、可远程升级 |
| 隐私保护 | 传感器采集的个人数据（位置、健康数据）需合规保护 |
| DDoS 攻击 | 大量 IoT 设备被劫持形成僵尸网络（如 Mirai 病毒） |

#### 考点 3：蓝牙 vs ZigBee vs WiFi 对比

| 协议 | 速率 | 功耗 | 距离 | 典型场景 |
|------|------|------|------|---------|
| 蓝牙（BLE） | 低 | 极低 | ~10m | 穿戴设备、耳机 |
| ZigBee | 低 | 极低 | ~100m（Mesh） | 智能家居传感器网络 |
| WiFi | 高 | 高 | ~100m | 视频传输、上网 |

#### 考点 4：物联网热点应用（近年热点）

| 热点 | 说明 |
|------|------|
| 智慧城市 | 智能交通、智慧路灯、环境监测，NB-IoT 为主力连接技术 |
| 工业物联网（IIoT） | 工厂设备预测性维护、数字孪生（Digital Twin） |
| 车联网（V2X） | 车与车、车与路的通信，依赖 5G + 边缘计算 |
| 智能穿戴 | 健康监测手环/手表，心率、血氧、睡眠监测 |
| 数字孪生 | 在虚拟世界中创建物理实体的实时数字镜像，用于仿真和优化 |

### 三、大数据考点补充

#### 考点 1：批处理 vs 流处理 vs 实时处理

| 处理类型 | 处理方式 | 延迟 | 代表框架 | 典型场景 |
|----------|---------|------|---------|---------|
| **批处理（Batch）** | 先攒一批数据，再统一处理 | 分钟~小时级 | Hadoop MapReduce | 日终报表、月度统计 |
| **流处理（Stream）** | 数据来一条处理一条（真正实时） | 毫秒~秒级 | Storm、Flink | 实时风控、股票交易 |
| **微批处理（Micro-batch）** | 小批次实时处理（折中方案） | 秒~分钟级 | Spark Streaming | 近实时日志分析 |

> 记忆：批处理 = 攒一筐再洗，流处理 = 来一个洗一个

#### 考点 2：Lambda 架构 vs Kappa 架构

| 架构 | 核心思想 | 优点 | 缺点 |
|------|---------|------|------|
| **Lambda 架构** | 同时维护"批处理层"（保证准确性）+ "速度层"（保证实时性）+ "服务层"（合并结果） | 兼顾准确性和实时性 | 需要维护两套代码，运维复杂 |
| **Kappa 架构** | 只用流处理，所有数据都当作流来处理，批处理是流处理的"回放" | 架构简单，一套代码 | 对消息队列依赖高，历史数据重算代价大 |

> 记忆：Lambda = 批+流两套，Kappa = 全部用流

#### 考点 3：数据仓库 vs 数据湖 vs 数据集市

| 概念 | 存什么 | 数据质量 | 用户 |
|------|--------|---------|------|
| **数据仓库（Data Warehouse）** | 经过清洗、结构化后的"干净"数据 | 高 | 业务分析师、决策层 |
| **数据湖（Data Lake）** | 所有原始数据（结构化 + 半结构化 + 非结构化） | 低（原始状态） | 数据科学家、算法工程师 |
| **数据集市（Data Mart）** | 数据仓库的子集，面向特定业务部门 | 高 | 某个业务部门 |

**类比**：
- 数据湖 = 一个大水库，什么水都往里放（原生态）
- 数据仓库 = 自来水厂，把水库的水净化处理后供人使用
- 数据集市 = 某个小区的直饮水站，只服务特定人群

#### 考点 4：OLTP vs OLAP

| 对比维度 | OLTP（联机事务处理） | OLAP（联机分析处理） |
|----------|---------------------|---------------------|
| 关注点 | 日常业务操作（增删改查） | 数据分析与决策支持 |
| 操作类型 | 大量短事务（INSERT/UPDATE/DELETE） | 大量复杂查询（SELECT + 聚合） |
| 数据特点 | 当前数据，实时更新 | 历史数据，定期更新 |
| 数据库类型 | 关系型数据库（MySQL、Oracle） | 数据仓库（Hive、ClickHouse） |
| 一句话 | "处理业务" | "做分析" |

> 记忆：OLTP = 收银台（一笔一笔交易处理），OLAP = 财报分析（汇总分析大量数据）

#### 考点 5：ETL vs ELT

| 对比维度 | ETL（传统） | ELT（现代） |
|----------|------------|------------|
| 顺序 | 先转换（Transform）→ 再加载（Load） | 先加载（Load）→ 再转换（Transform） |
| 转换位置 | 在中间 ETL 服务器完成 | 在目标数据仓库中完成 |
| 适用场景 | 数据量较小、计算资源有限的传统数仓 | 云数仓、大数据平台（靠数仓自身的算力） |
| 原始数据 | 不保留在数仓中 | 保留在数仓中（数据湖理念） |

> 记忆：ETL = 先洗再存，ELT = 先存再洗

#### 考点 6：CAP 定理与 NoSQL

分布式系统无法同时满足三个特性，只能三选二：

| 特性 | 含义 | 放弃后的问题 |
|------|------|------------|
| **C（一致性）** | 所有节点在同一时刻数据一致 | 可能读到旧数据 |
| **A（可用性）** | 系统始终能响应请求（不宕机） | 某些情况下可能无法访问 |
| **P（分区容错性）** | 网络出问题时系统仍能运行 | 分布式系统必须保证 P，所以只能在 C 和 A 之间选 |

> 考试关键：**分布式系统必须保证 P（分区容错性）**，所以实际选择是 CP 或 AP。

| 数据库类型 | CAP 选择 | 代表 |
|-----------|----------|------|
| 传统关系型数据库（单机） | CA（无 P） | MySQL、Oracle |
| MongoDB、HBase | CP | MongoDB、HBase |
| Cassandra、DynamoDB | AP | Cassandra、DynamoDB |

#### 考点 7：大数据热点应用（近年热点）

| 热点 | 说明 |
|------|------|
| 数据中台 | 统一数据服务，打破数据孤岛，提供"OneData"体系 |
| 用户画像（User Profile） | 基于用户行为数据打标签，支撑精准推荐 |
| 实时计算 | Flink 成为主流流计算引擎，用于实时风控、实时大屏 |
| 数据治理 | 数据质量、元数据管理、数据血缘、数据安全 |
| 隐私计算 | 联邦学习、多方安全计算，在保护隐私前提下利用数据 |

### 四、跨领域综合考点

#### 考点 1：AI + IoT = AIoT（人工智能物联网）

AIoT 是 AI 和 IoT 融合的产物，让物联网设备不仅"感知"，还能"思考"。

| 应用场景 | AI 角色 | IoT 角色 |
|----------|--------|---------|
| 智能音箱 | 语音识别 + NLU（理解你说的话） | 麦克风阵列 + 联网控制家电 |
| 智能摄像头 | 人脸识别 + 行为分析 | 图像传感器 + 联网报警 |
| 预测性维护 | 机器学习分析设备数据预测故障 | 振动/温度传感器采集数据 |

#### 考点 2：大数据 + AI = 数据驱动 AI

大数据是 AI 的"燃料"——AI 模型需要海量数据来训练，数据量越大，模型效果通常越好。

> 记忆：IoT 产生数据 → 大数据平台存储和处理数据 → AI 利用数据做智能决策，三者形成闭环。

#### 考点 3：典型考题样例

**单选题示例**：

1. 以下属于无监督学习的是（）。
   A. 垃圾邮件分类 B. 房价预测 C. 客户聚类分析 D. AlphaGo 下围棋
   > 答案：C。A 是分类（监督学习），B 是回归（监督学习），D 是强化学习。

2. 物联网三层架构中，负责数据采集的是（）。
   A. 应用层 B. 网络层 C. 感知层 D. 传输层
   > 答案：C。感知层 = 传感器采集数据，是最底层。

3. 大数据的 5V 特征中，指"价值密度低"的是（）。
   A. Volume B. Velocity C. Variety D. Value
   > 答案：D。注意 Value 不是"价值高"，而是"价值密度低"。

4. 以下哪种协议工作在授权频段、需要运营商 SIM 卡？（）
   A. LoRa B. ZigBee C. NB-IoT D. WiFi
   > 答案：C。NB-IoT 基于运营商基站，需要 SIM 卡。LoRa 用免费频段。

5. Hadoop 生态中，负责资源管理和任务调度的组件是（）。
   A. HDFS B. MapReduce C. YARN D. HBase
   > 答案：C。YARN = "项目经理"。

**判断题示例**：

1. 当前 ChatGPT 属于强人工智能（AGI）。（）
   > 答案：错误。ChatGPT 是弱人工智能（ANI），只会做特定任务。AGI 尚未实现。

2. NFC 是 RFID 的一个子集，支持双向通信。（）
   > 答案：正确。NFC 是 RFID 的高频子类，距离更短但支持双向通信。

3. 监督学习和无监督学习最本质的区别在于是否有标签数据。（）
   > 答案：正确。有标签 = 监督学习，无标签 = 无监督学习。

4. Spark 比 MapReduce 快是因为算法更优。（）
   > 答案：错误。Spark 快是因为基于内存计算，减少了磁盘 I/O，不是算法更优。

5. 大数据预处理中，数据清洗的目的是把数据压缩变小。（）
   > 答案：错误。数据清洗是处理缺失值、异常值、重复数据。把数据压缩变小是"数据规约"。

### 五、易混淆概念终极对比速查

#### AI 领域

| 易混淆组合 | 关键区别 |
|-----------|---------|
| 过拟合 vs 欠拟合 | 过拟合 = 训练好测试差（太复杂）；欠拟合 = 训练和测试都差（太简单） |
| 偏差 vs 方差 | 偏差 = 不准（瞄准偏了）；方差 = 不稳（子弹乱飞） |
| 分类 vs 回归 | 分类 = 离散类别（选择题）；回归 = 连续数值（填空题） |
| 聚类 vs 分类 | 聚类 = 无监督，没标签自己分；分类 = 有监督，有标签学完后分 |
| 精确率 vs 召回率 | 精确率 = 查得准不准；召回率 = 查得全不全 |
| GPT vs BERT | GPT = 单向 Decoder，生成；BERT = 双向 Encoder，理解 |
| 生成式 vs 判别式 | 生成式 = 能创造新内容；判别式 = 只做判断 |
| CNN vs RNN vs Transformer | CNN = 图像（卷积）；RNN = 序列（循环记忆）；Transformer = 序列（注意力） |
| Sigmoid vs Softmax | Sigmoid = 二分类输出；Softmax = 多分类输出 |
| 强化学习 vs 监督学习 | 强化学习 = 试错+奖励（无标签）；监督学习 = 有标签模仿 |

#### 物联网领域

| 易混淆组合 | 关键区别 |
|-----------|---------|
| 感知层 vs 网络层 vs 应用层 | 感知层 = 采数据（最下）；网络层 = 传数据（中间）；应用层 = 用数据（最上） |
| RFID vs NFC | RFID = 长距离，单向；NFC = 短距离（<10cm），双向，RFID 的子集 |
| LoRa vs NB-IoT | LoRa = 免费频段，自建网关；NB-IoT = 运营商基站，需要 SIM 卡 |
| MQTT vs CoAP | MQTT = 发布/订阅模式；CoAP = 类 HTTP 的 RESTful 风格，基于 UDP |
| ZigBee vs 蓝牙 | ZigBee = Mesh 自组网，智能家居；蓝牙 = 点对点，穿戴设备 |
| 边缘计算 vs 雾计算 | 边缘 = 设备端/最近；雾 = 局域网网关；云 = 数据中心 |
| 传感器 vs 执行器 | 传感器 = 感知（输入）；执行器 = 动作（输出，如马达、开关） |

#### 大数据领域

| 易混淆组合 | 关键区别 |
|-----------|---------|
| 5V 之 Value | 不是"价值高"，而是"价值密度低"，需要沙里淘金 |
| 批处理 vs 流处理 | 批处理 = 攒一筐再处理（慢）；流处理 = 来一条处理一条（快） |
| Lambda vs Kappa 架构 | Lambda = 批+流两套；Kappa = 全部用流一套 |
| 数据仓库 vs 数据湖 | 数据仓库 = 洗干净的结构化数据；数据湖 = 所有原始数据都存 |
| OLTP vs OLAP | OLTP = 处理业务交易（增删改）；OLAP = 做数据分析（查询聚合） |
| ETL vs ELT | ETL = 先转换再加载；ELT = 先加载再转换 |
| Hadoop vs Spark | Hadoop = 基于磁盘（慢）；Spark = 基于内存（快 10~100 倍） |
| HDFS vs MapReduce | HDFS = 存文件；MapReduce = 算数据 |
| 事实表 vs 维度表 | 事实表 = 存数据（金额、次数）；维度表 = 存描述（时间、地点、产品） |
| 星型模型 vs 雪花模型 | 星型 = 维度表不拆分；雪花 = 维度表再拆分（规范化） |
| CAP 之 CP vs AP | 分布式系统必须保证 P，数据库在 C 和 A 之间取舍 |

### 六、考前冲刺记忆口诀

**AI 部分**：
- "当前 AI 都是弱，AGI 还没实现"
- "有标签是监督，无标签是非监督，试错奖励是强化"
- "分类选择题，回归填空题"
- "CNN 看图像，RNN 看序列，Transformer 靠注意力"
- "GPT 接着说，BERT 读懂了"
- "过拟合背题，欠拟合没学"
- "精确率不冤枉，召回率不放过"

**物联网部分**：
- "下面采数据，中间传数据，上面用数据"
- "MQTT 发布订阅，CoAP 瘦版 HTTP"
- "ZigBee 低功耗 Mesh，LoRa 远距离免费，NB-IoT 走运营商"
- "NFC 是 RFID 儿子，距离短但能双向"
- "边缘在设备，雾在局域网，云在数据中心"

**大数据部分**：
- "5V：量大速快种类多，价值密度低，还不准"
- "预处理：洗 → 合 → 变 → 缩"
- "分析层次：描述 → 诊断 → 预测 → 规范（越来越高级）"
- "Hadoop 三件套：HDFS 存、MapReduce 算、YARN 管"
- "Spark 快在内存，不是算法"
- "数据湖是水库，数据仓库是自来水厂"
- "ETL 先洗再存，ELT 先存再洗"
- "分布式必须 P，CP 要一致，AP 要可用"
