## 知识点 10：数据库基本概念

### 10.1 DB / DBMS / DBS 三个概念怎么区分？

这三个概念的关系就像是"仓库、仓库管理员、仓库管理系统"：

| 术语 | 全称 | 大白话 | 类比 |
|------|------|--------|------|
| **DB**（数据库） | Database | 存放数据的"大仓库" | 仓库里的货物 |
| **DBMS**（数据库管理系统） | Database Management System | 管理数据的"仓库管理员"（软件） | 仓库管理员 |
| **DBS**（数据库系统） | Database System | "仓库 + 管理员 + 规章制度"的整体 | 仓库、管理员、操作手册加在一起 |

**记忆口诀**：DB 是数据本身，DBMS 是管理软件，DBS = DB + DBMS + 人 + 规则，是更大的概念。

---

#### 易错点 1："DBMS 就是数据库" ❌

很多初学者把 DBMS 说成"数据库"，比如"我装了一个 MySQL 数据库"——严格说，MySQL 是 DBMS，里面管理的那个数据仓库才是 DB。考试里要注意区分。

---

### 10.2 数据库系统 vs 文件系统

"为什么不直接用 Excel 存数据，非要搞数据库？"

| 对比维度 | 文件系统 | 数据库系统 |
|----------|----------|------------|
| 数据冗余 | 各文件各自存，重复多 | 集中管理，冗余少 |
| 数据一致性 | 一个数据改多处容易遗漏 | DBMS 自动维护一致性 |
| 数据独立性 | 程序直接操作文件，换个格式代码就要改 | 程序和数据结构分离，改了表不影响程序 |
| 并发访问 | 多个程序同时改一个文件容易出错 | 有事务和锁机制，安全 |
| 数据共享 | 格式不统一，不易共享 | 统一接口（SQL），方便共享 |

**大白话总结**：数据库系统的核心优势就是"数据独立、集中管理、并发安全"。

---

### 10.3 数据模型——怎么描述数据？

数据模型就是"画蓝图"的工具，用数学化、标准化的方式描述数据叫什么、长什么样、之间什么关系。

#### 三类数据模型对比

| 模型类型 | 别称 | 干什么用的 | 举例 |
|----------|------|-----------|------|
| **概念模型** | 信息模型 | 跟用户沟通，画业务逻辑 | E-R 图 |
| **逻辑模型** | 结构模型 | 程序员看的，决定数据怎么存 | 关系模型、层次模型、网状模型 |
| **物理模型** | 存储模型 | 数据库底层，决定数据在硬盘的位置 | 索引、文件组织 |

**关系**：概念模型（E-R 图）→ 转换成 → 逻辑模型（关系表）→ 落地成 → 物理模型（磁盘文件）。

**当前主流**：逻辑模型以**关系模型**（二维表）绝对主导，层次模型和网状模型基本被淘汰。

---

### 10.4 E-R 模型（实体-联系模型）

E-R 模型是概念模型的最常用工具，核心就是三个要素：

| 要素 | 符号/表示 | 大白话 | 例子 |
|------|----------|--------|------|
| **实体**（Entity） | 矩形框 | 一个"东西/对象" | 学生、课程 |
| **属性**（Attribute） | 椭圆 | 实体的特征 | 学生的学号、姓名 |
| **联系**（Relationship） | 菱形 | 实体之间怎么关联 | 学生"选课" |

#### 联系的三种类型

| 类型 | 表示 | 大白话 | 例子 |
|------|------|--------|------|
| 1 : 1（一对一） | `1——1` | 你有一个我，我有一个你 | 一个学生有一个学号 |
| 1 : N（一对多） | `1——N` | 你有多个我，我只有一个你 | 一个班级有多个学生 |
| M : N（多对多） | `M——N` | 你有多个我，我有多个你 | 一个学生选多门课，一门课有多个学生 |

> **关键规则**：M : N 联系必须拆成两张"两张 1 : N 联系"才能在关系模型里存。这是考试大题必考点！

---

### 10.5 三级模式两级映像 ⭐

这是数据库系统的核心架构，考试高频考点。

#### 三层模式（自上而下）

```
┌─────────────────────────┐
│  外模式（用户模式）        │  ← 用户看到的视图（View），可以有多个
│  针对不同用户定制的"视野"   │
├─────────────────────────┤
│  模式（概念模式/逻辑模式）   │  ← 数据库的全局逻辑结构，只有一个
│  所有数据的全局逻辑蓝图      │
├─────────────────────────┤
│  内模式（存储模式）         │  ← 数据在磁盘上怎么存的，只有一个
│  物理存储细节               │
└─────────────────────────┘
```

**大白话类比**：
- **内模式**：仓库的货架怎么摆、货物编号怎么编（只有仓管知道）——物理层
- **模式**：仓库里一共有多少种货、各放哪个区（管理员心中有全局）——逻辑层
- **外模式**：每个前台只能看到自己负责的那部分货（不同人看到不同视图）——视图层

#### 两级映像（保证数据独立性的关键）

| 映像 | 映射关系 | 大白话作用 |
|------|----------|-----------|
| **外模式/模式映像** | 外模式 ↔ 模式 | 改了全局表结构，用户看到的视图可以不变 → **逻辑数据独立性** |
| **模式/内模式映像** | 模式 ↔ 内模式 | 改了物理存储方式，全局表结构不变 → **物理数据独立性** |

**一句话核心**：两级映像是"缓冲层"，让你改底层时不用改上层。这就是数据库"数据独立性"的底层实现原理。

---

#### 易错点 2："模式只有一个，外模式可以有多个"

- **模式**（概念模式）是唯一的，描述了整个数据库的逻辑结构
- **外模式**可以有多个，因为不同用户有不同的权限和需求
- **内模式**也是唯一的（一个数据库只有一个物理存储结构）

## 知识点 11：关系数据库基本理论

### 11.1 关系数据库的基本概念

**大白话**：关系模型就是把数据存成一张张**二维表**（行 + 列）。

| 术语 | 大白话 | 表格对应 |
|------|--------|----------|
| **关系** | 一张表 | 整张表 |
| **元组**（Tuple）| 一行数据 | 行 / 一条记录 |
| **属性**（Attribute）| 一列数据 | 列 / 字段 |
| **分量** | 某个元组在某个属性上的值 | 某一个单元格 |
| **候选码**（Candidate Key）| 能唯一标识一行的属性（组）| 比如学号 |
| **主码**（Primary Key）| 从候选码中选一个当"正式代表" | 主键 |
| **外码**（Foreign Key）| 别的表的主码，引用来建立联系 | 外键 |
| **域**（Domain）| 属性的取值范围 | 年龄：0 ~ 150 |
| **关系模式** | 表的结构定义 | `学生(学号, 姓名, 年龄)` |

#### 关系的性质（判断题常考）

- 每一列（属性）**不可再分**（满足 1NF）
- 每一列有**唯一的属性名**
- 行的**顺序无关紧要**，列的顺序也无关紧要
- 任意两行**不能完全相同**（关系是元组的集合）

---

#### 易错点 3："行顺序无关"是关系数据库的核心特征

关系数据库中的行是无序的集合，如果你想让查询结果**有序**，必须使用 `ORDER BY`——不加 ORDER BY 的查询结果，数据库可以按任意顺序返回。

---

### 11.2 关系代数 ⭐

关系代数是"对表进行运算"的数学语言，SQL 就是它的具体实现。

#### 传统集合运算

| 运算 | 符号 | 条件 | 大白话 |
|------|------|------|--------|
| **并**（Union）| ∪ | 两个表的列数和类型必须相同 | 两张表摞在一起，去重 |
| **差**（Difference）| − | 同上 | 在表 A 里但不在表 B 里的行 |
| **交**（Intersection）| ∩ | 同上 | 两张表都有的行 |
| **笛卡尔积**（Cartesian Product）| × | 无要求 | 表 A 每一行 × 表 B 每一行（全组合） |

#### 专门的关系运算 ⭐

| 运算 | 符号 | 大白话 | SQL 对应 |
|------|------|--------|----------|
| **选择**（Selection）| σ | 按条件筛选行（横向切） | `WHERE` |
| **投影**（Projection）| π | 只取某些列（纵向切） | `SELECT 列名` |
| **连接**（Join）| ⋈ | 两张表按某条件拼成一张 | `JOIN ... ON` |
| **除**（Division）| ÷ | 找出满足"所有"条件的元组 | 没有直接对应 |

---

#### 易错点 4：选择 vs 投影，别搞混

- **选择 σ**：横向操作，筛**行**（对应 SQL 的 `WHERE`）
- **投影 π**：纵向操作，选**列**（对应 SQL 的 `SELECT` 后指定列名）

记忆方法：**选行投列**——"选择"就是"筛选行"，"投影"就是"选取列"。

---

#### 自然连接 vs 等值连接

| 类型 | 大白话 | 关键区别 |
|------|--------|----------|
| **等值连接** | 按某个条件（比如相等）把两张表拼起来 | 保留两个表的连接列（会有重复列） |
| **自然连接** | 自动找两张表中**同名的属性**，按这些属性相等来连接 | **自动去掉重复列** |

**自然连接 = 等值连接 + 去除重复列**。考试特别注意"自然连接会去掉重复属性"这句话。

---

### 11.3 三大完整性约束 ⭐⭐⭐

完整性约束 = 数据的"交通规则"，保证数据不乱七八糟。

| 约束类型 | 大白话 | 核心要求 | 例子 |
|----------|--------|----------|------|
| **实体完整性** | 每行数据必须能唯一找出来 | 主码不能是 NULL，且唯一 | 学号不能为空 |
| **参照完整性** | 外键引用的值必须存在 | 外键要么是 NULL，要么等于被引用表中主键的某个值 | 选课表里的学号，必须在学生表里存在 |
| **用户定义完整性** | 业务上的额外规则 | 用户自己定的约束 | 年龄 ≥ 0，性别只能是"男"或"女" |

#### 参照完整性中的级联操作

| 策略 | 大白话 | 例子 |
|------|--------|------|
| **CASCADE**（级联） | 主表变了，从表跟着变 | 删除学生，他选的课也自动删除 |
| **SET NULL** | 主表变了，从表外键设为空 | 删除学生，选课记录变孤儿（学号字段置空） |
| **RESTRICT / NO ACTION** | 主表有"孩子"时禁止删除 | 如果有课选了某学生，就不让删这个学生 |

---

#### 易错点 5：实体完整性要求主码"非空且唯一"，不是"非空或唯一"

- 必须是**既非空又唯一**，缺一不可。
- 如果主码由多个属性组成（复合主键），则**每个分量都不能为空**。

> A. 数据之间的关联  B. 一张二维表  C. 字段之间的对应关系  D. E-R 图中的联系
>
> **答案**：B。在关系模型中，"关系"对应的就是一张二维表。

> **例题 4**：设关系 R 有 3 个属性 4 个元组，关系 S 有 2 个属性 5 个元组，则 R × S 有 \_\_\_ 个属性，\_\_\_ 个元组。
>
> **答案**：5 个属性（3 + 2）、20 个元组（4 × 5）。笛卡尔积属性相加、元组相乘。

>
> **答案**：笛卡尔积。因为没有公共属性就无法做属性相等匹配，只能是全组合。

## 知识点 12：关系数据库标准语言 SQL

### 12.1 SQL 四大分类

| 类别 | 全称 | 功能 | 核心命令 |
|------|------|------|----------|
| **DDL** | Data Definition Language（数据定义语言）| 建表、修改表结构、删表 | `CREATE`, `ALTER`, `DROP` |
| **DML** | Data Manipulation Language（数据操纵语言）| 增删改数据 | `INSERT`, `UPDATE`, `DELETE` |
| **DQL** | Data Query Language（数据查询语言）| 查询数据 | `SELECT` |
| **DCL** | Data Control Language（数据控制语言）| 权限管理 | `GRANT`, `REVOKE` |

**记忆口诀**：DDL 管结构、DML 管数据、DQL 管查询、DCL 管权限。

---

### 12.2 DDL——建表和改表

```sql
-- 建表
CREATE TABLE 学生 (
    学号 CHAR(10) PRIMARY KEY,    -- 主键约束
    姓名 VARCHAR(20) NOT NULL,    -- 非空约束
    年龄 INT CHECK(年龄 >= 0 AND 年龄 <= 150),  -- 检查约束
    性别 CHAR(2) DEFAULT '未知'   -- 默认值
);

-- 改表：加一列
ALTER TABLE 学生 ADD 手机号 VARCHAR(11);

-- 删表
DROP TABLE 学生;
```

---

### 12.3 DML——增删改

```sql
-- 插入
INSERT INTO 学生(学号, 姓名, 年龄) VALUES ('2024001', '张三', 20);

-- 更新（一定要加 WHERE，否则全表更新！）
UPDATE 学生 SET 年龄 = 21 WHERE 学号 = '2024001';

-- 删除（同样一定要加 WHERE）
DELETE FROM 学生 WHERE 学号 = '2024001';
```

---

#### 易错点 6：DELETE vs DROP vs TRUNCATE

| 命令 | 分类 | 作用 | 能回滚吗 | 删的是 |
|------|------|------|----------|--------|
| `DELETE` | DML | 删除数据行 | 可以（事务回滚）| 行数据 |
| `TRUNCATE` | DDL | 清空整张表 | 不能回滚 | 所有行 |
| `DROP` | DDL | 删除整张表（表都没了）| 不能回滚 | 表结构 + 数据 |

---

### 12.4 DQL——查询（最重要，考试占比最高）

#### 基本查询

```sql
-- 最基本的查询
SELECT 学号, 姓名 FROM 学生 WHERE 年龄 >= 18;

-- 去重
SELECT DISTINCT 性别 FROM 学生;

-- LIKE 模糊查询
-- % 匹配任意长度字符，_ 匹配单个字符
SELECT * FROM 学生 WHERE 姓名 LIKE '张%';   -- 姓张的
SELECT * FROM 学生 WHERE 姓名 LIKE '张_';   -- 张某（单名）
```

#### 聚合函数

| 函数 | 作用 | 注意 |
|------|------|------|
| `COUNT(*)` | 统计行数 | 包括 NULL 行 |
| `COUNT(列名)` | 统计某列非空值的个数 | 不算 NULL |
| `SUM(列名)` | 求和 | 忽略 NULL |
| `AVG(列名)` | 平均值 | 忽略 NULL |
| `MAX(列名)` | 最大值 | — |
| `MIN(列名)` | 最小值 | — |

#### GROUP BY 和 HAVING ⭐

**大白话**：GROUP BY 把行按某列分堆，然后每堆单独做聚合运算；HAVING 是"分组后的 WHERE"，用来筛选分组结果。

```sql
-- 查询每个系的学生人数，只要人数超过 50 的系
SELECT 系名, COUNT(*) AS 学生人数
FROM 学生
GROUP BY 系名
HAVING COUNT(*) > 50;
```

---

#### 易错点 7：WHERE 和 HAVING 的执行时机不同

| | WHERE | HAVING |
|------|-------|--------|
| **作用对象** | 原始行（分组前）| 分组后的聚合结果 |
| **能用聚合函数吗** | 不能 ❌ | 可以 ✅ |
| **执行顺序** | 先 WHERE 筛选 → 再 GROUP BY 分组 → 再 HAVING 筛选 |

**典型错误**：把 `WHERE COUNT(*) > 50` 写在 SQL 里——WHERE 不能跟聚合函数，必须用 HAVING。

---

#### 连接查询（JOIN）⭐

| JOIN 类型 | 大白话 | 图示理解 |
|-----------|--------|----------|
| **INNER JOIN**（内连接）| 两边都有的才留下 | 交集 |
| **LEFT JOIN**（左外连接）| 左边全保留，右边能配上的就配上，配不上填空 | 左表所有行 |
| **RIGHT JOIN**（右外连接）| 右边全保留，左边能配上的就配上，配不上填空 | 右表所有行 |
| **FULL JOIN**（全外连接）| 两边都保留，配不上的填空 | 并集 |

```sql
-- 内连接：查询选了课的学生信息
SELECT 学生.姓名, 选课.课程号
FROM 学生 INNER JOIN 选课 ON 学生.学号 = 选课.学号;

-- 左外连接：所有学生都显示，没选课的课程号填 NULL
SELECT 学生.姓名, 选课.课程号
FROM 学生 LEFT JOIN 选课 ON 学生.学号 = 选课.学号;
```

---

#### 易错点 8：INNER JOIN 和 WHERE 连接的区别

早期 SQL 中 `FROM A, B WHERE A.id = B.id` 等价于 `INNER JOIN`，但现代标准推荐用 `JOIN ... ON`，逻辑更清晰。考试中两种写法都认识。

---

#### 子查询（嵌套查询）

子查询就是"查询里面套查询"，有三种典型用法：

| 类型 | 关键字 | 大白话 | 例子 |
|------|--------|--------|------|
| 带 `IN` 的子查询 | `IN` / `NOT IN` | 判断值在不在子查询结果里 | 查选了"数据库"课的学生 |
| 带比较运算符 | `>`, `=`, `<` 等 | 子查询返回**单个值**，进行比较 | 查年龄大于平均年龄的学生 |
| 带 `EXISTS` | `EXISTS` / `NOT EXISTS` | 判断子查询有没有结果（返回布尔值）| 查至少选了一门课的学生 |

```sql
-- 子查询示例：查询选了"数据库"课程的学生姓名
SELECT 姓名 FROM 学生
WHERE 学号 IN (
    SELECT 学号 FROM 选课
    WHERE 课程号 = (
        SELECT 课程号 FROM 课程 WHERE 课程名 = '数据库'
    )
);

-- EXISTS 示例：查询至少选了一门课的学生
SELECT 姓名 FROM 学生
WHERE EXISTS (
    SELECT * FROM 选课 WHERE 选课.学号 = 学生.学号
);
```

---

#### 易错点 9：EXISTS vs IN 的区别

- `IN`：子查询先执行，返回结果集，再外层匹配
- `EXISTS`：外层每查一行，就拿到子查询里问一句"有没有"，关联子查询
- `NOT IN` 有坑：如果子查询结果中有 NULL，则整条 `NOT IN` 返回空（NULL 跟任何值比较结果都是 UNKNOWN）

---

### 12.5 DCL——权限管理

```sql
-- 授权
GRANT SELECT, INSERT ON 学生 TO 用户A;
-- 把"学生"表的查询和插入权限给用户A

-- 回收权限
REVOKE INSERT ON 学生 FROM 用户A;
```

**考试注意**：`GRANT` 和 `REVOKE` 属于 DCL，不要归到 DDL。

## 知识点 13：事务处理和并发控制

### 13.1 事务是什么？

**大白话**：事务就是"一组操作，要么全部成功，要么全部撤销"。就像银行转账——从 A 扣钱、给 B 加钱，这两步必须绑在一起做。

#### 事务的四个特性：ACID ⭐⭐⭐

| 特性 | 全称 | 大白话 | 类比 |
|------|------|--------|------|
| **A** — 原子性 | Atomicity | 要么全做，要么全不做 | 签合同，不能签半张 |
| **C** — 一致性 | Consistency | 数据从一种正确状态变到另一种正确状态 | 转账前后，总金额不变 |
| **I** — 隔离性 | Isolation | 并发事务互不干扰 | 你在编辑文档，别人不能同时改同一段 |
| **D** — 持久性 | Durability | 提交成功的数据永远不丢 | 签完字盖了章，白纸黑字跑不掉 |

**记忆口诀**：ACI 是事务执行时的保证，D 是提交后的保证。

---

### 13.2 并发带来的问题

多个事务同时跑，如果不加控制，会出三种"脏事"：

| 并发问题 | 英文名 | 大白话 | 严重程度 |
|----------|--------|--------|----------|
| **丢失修改** | Lost Update | 你先改了我没看到，我覆盖了你的修改 | 最严重 |
| **脏读** | Dirty Read | 读到了一个还没提交的修改，结果人家回滚了 | 你读了个"假消息" |
| **不可重复读** | Non-repeatable Read | 同一事务内两次读同一数据，结果不一样（别人中间改了） | 中等 |
| **幻读** | Phantom Read | 同一事务内两次查同一条件，结果**行数**不一样（别人插/删了数据） | 中等 |

#### 类比理解"不可重复读 vs 幻读"

- **不可重复读**：数据**内容**被改了（你读的是同一行，值变了）
- **幻读**：数据**条数**变了（突然多了几行或少了几行）

---

### 13.3 封锁机制——解决并发问题的手段

封锁 = 给数据上"通行证"。核心是两种锁：

| 锁类型 | 符号 | 英文 | 大白话 | 兼容性 |
|--------|------|------|--------|--------|
| **共享锁** | S 锁 | Share Lock | "大家都能看，但不能改"（读锁）| S 与 S 兼容，S 与 X 不兼容 |
| **排他锁** | X 锁 | Exclusive Lock | "我一个人用，别人不能看也不能改"（写锁）| X 与任何锁都不兼容 |

#### 锁的兼容矩阵

|  | 已有 S 锁 | 已有 X 锁 |
|------|-----------|-----------|
| 申请 S 锁 | ✅ 可以 | ❌ 不行 |
| 申请 X 锁 | ❌ 不行 | ❌ 不行 |

---

### 13.4 隔离级别 ⭐⭐

数据库提供四种隔离级别，从低到高越来越安全，但也越来越慢：

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 性能 | 默认使用 |
|----------|------|-----------|------|------|----------|
| **读未提交**（Read Uncommitted）| 可能 | 可能 | 可能 | 最快 | 几乎不用 |
| **读已提交**（Read Committed）| 解决 | 可能 | 可能 | 快 | Oracle 默认 |
| **可重复读**（Repeatable Read）| 解决 | 解决 | 可能 | 中等 | MySQL InnoDB 默认 |
| **可串行化**（Serializable）| 解决 | 解决 | 解决 | 最慢 | 极少使用 |

**MySQL InnoDB 的特殊之处**：在"可重复读"级别下，通过**间隙锁**（Gap Lock）也解决了幻读问题。

---

### 13.5 两段锁协议（2PL）

**大白话**：事务分两段——第一阶段只加锁不解锁，第二阶段只解锁不加锁。

```
开始 → [不断加锁（扩张阶段）] → 封锁点 → [不断解锁（收缩阶段）] → 结束
```

**2PL 的意义**：遵守两段锁协议的事务，其并发调度一定是**可串行化**的。

---

#### 易错点 10：2PL 保证可串行化，但不防止死锁

两段锁协议只是规定了加锁和解锁的顺序，但两个事务如果交叉等待对方的锁，还是会产生死锁。死锁需要额外的检测和恢复机制（如超时、等待图等）。

---

### 13.6 例题

> **例题 8**：事务的隔离性是指 \_\_\_\_\_\_。
> A. 事务执行结果必须使数据库从一种一致性状态变到另一种
> B. 一个事务内部操作及使用的数据对并发的其他事务是隔离的
> C. 事务一旦提交，对数据库的改变是永久的
> D. 事务中包括的所有操作要么都做，要么都不做
>
> **答案**：B。A 是一致性，C 是持久性，D 是原子性。

> **例题 9**：设有两个事务 T1 和 T2，T1 对数据 A 加了 X 锁，此时 T2 申请对 A 加 S 锁，则 \_\_\_\_\_\_。
>
> **答案**：T2 必须等待（阻塞），直到 T1 释放 X 锁。因为 X 锁和 S 锁不兼容。

> **例题 10**：解决"丢失修改"问题，至少需要把隔离级别设为 \_\_\_\_\_\_。
>
> **答案**：读未提交（Read Uncommitted）以上即可。实际上 Read Uncommitted 需要配合写锁才能防丢失修改——通常任何隔离级别下数据库都会对写操作加排他锁。

## 知识点 14：备份和恢复

### 14.1 故障类型

数据库会出哪些"意外"？

| 故障类型 | 大白话 | 严重程度 | 举例 |
|----------|--------|----------|------|
| **事务内部故障** | 单个事务自身出错 | 轻 | 违反约束，事务回滚 |
| **系统故障** | 数据库软件/操作系统崩了（内存数据丢了）| 中 | 断电、死机 |
| **介质故障** | 硬盘坏了 | 重 | 磁盘损坏 |
| **计算机病毒** | 恶意攻击 | 重 | 勒索病毒 |

**关键区别**：系统故障只丢**内存**中的数据（正在跑的事务），介质故障丢的是**磁盘**上持久化的数据。

---

### 14.2 数据转储（备份）

数据转储就是定期把数据库复制一份存起来：

| 转储方式 | 大白话 | 优点 | 缺点 |
|----------|--------|------|------|
| **静态转储**（冷备份）| 数据库停下来，完整复制 | 简单，数据一致性好 | 需要停机 |
| **动态转储**（热备份）| 数据库一边跑一边备份 | 不用停机 | 数据可能不一致 |
| **完全转储**（全量备份）| 每次把所有数据都备份一遍 | 恢复简单 | 慢，占空间 |
| **增量转储**（增量备份）| 只备份上次备份之后变动的部分 | 快，省空间 | 恢复时要拼多个备份 |

---

### 14.3 日志和恢复

#### WAL（Write-Ahead Logging，预写日志）

**大白话**：对一个数据的修改，**先记日志，再写数据**。这样即使写到一半断电了，日志还在，可以根据日志恢复。

**WAL 两条规则**：
1. 日志记录必须在数据修改之前写入磁盘
2. 事务提交时，日志必须已经写入磁盘

#### 恢复策略

| 恢复策略 | 适用场景 | 操作方法 |
|----------|----------|----------|
| **UNDO（撤销）** | 事务没提交就崩了 | 根据日志把数据改回去 |
| **REDO（重做）** | 事务已提交但数据还没写盘 | 根据日志把操作再做一遍 |

**记忆诀窍**：UNDO 是"反悔"，REDO 是"补做"。

---

### 14.4 安全控制

| 控制手段 | 大白话 | 例子 |
|----------|--------|------|
| **身份验证** | 证明"你是谁" | 用户名 + 密码 |
| **存取控制** | 规定"你能做什么" | GRANT/REVOKE 授权 |
| **审计** | 记录"你做了什么" | 操作日志 |
| **加密** | 数据"上锁" | 存储加密、传输加密 |
| **视图** | 只给看该看的 | 敏感字段不出现 |

## 知识点 15：数据库应用系统设计与开发

### 15.1 数据库设计的六个阶段

设计一个数据库，不是上来就建表，而是分六个阶段有序推进：

| 阶段 | 做什么 | 产出物 | 大白话 |
|------|--------|--------|--------|
| **1. 需求分析** | 搞清楚用户要什么 | 需求说明书、数据流图 | "你需要什么功能？" |
| **2. 概念结构设计** | 用 E-R 图画业务逻辑 | E-R 图 | "现实世界长什么样？" |
| **3. 逻辑结构设计** | E-R 图转换成关系表 | 关系模式（表结构）| "数据怎么用表存？" |
| **4. 物理结构设计** | 确定存储方式、索引 | 物理存储方案 | "表存在硬盘哪里更高效？" |
| **5. 数据库实施** | 写 SQL 建表、编程序 | 建好的数据库 | "开工干活！" |
| **6. 运行与维护** | 上线后调优修改 | 维护记录 | "后续服务" |

**记忆口诀**：需求 → 概念 → 逻辑 → 物理 → 实施 → 维护（需概逻物实维）。

---

### 15.2 E-R 图转关系模式（考试重点）⭐

#### 转换规则

| E-R 要素 | 怎么转 | 说明 |
|-----------|--------|------|
| **实体** | 每个实体 → 一张表 | 实体的属性 → 表的列 |
| **1 : 1 联系** | 合并到任意一方，或单独建表 | 通常合并进去即可 |
| **1 : N 联系** | 把"1"方的主键放到"N"方作为外键 | N 方的表里加一个外键字段 |
| **M : N 联系** | **必须单独建一张联系表** | 包含双方主键，共同组成复合主键 |

#### 转换示例

假设 E-R 图中有：学生（学号、姓名）、课程（课程号、课程名），学生与课程是 M : N 联系（选课，含成绩）。

转换结果——三张表：

```
学生表（学号, 姓名）            ← 实体
课程表（课程号, 课程名）         ← 实体
选课表（学号, 课程号, 成绩）     ← M : N 联系转成独立表
```

---

#### 易错点 11：M : N 联系必须单独建表

很多同学会把 M : N 联系直接合并到某一方，这是**绝对不可以**的。M : N 联系必须有自己的一张表，主键由双方的主键共同组成。

---

### 15.3 范式（Normalization）⭐⭐⭐

#### 为什么要学范式？

**大白话**：范式就是"表格设计有没有把事说清楚"的检查标准。范式越高，数据冗余越少，但查询可能越慢。

#### 三大范式的逐级递进关系

**不规范的原始表 → 一步步拆成规范的表**

---

##### 第一范式（1NF）：原子性

**要求**：每一列的值都是不可分割的原子项。

| 错误示例（违反 1NF）| 修正后（满足 1NF）|
|---------------------|-------------------|
| 电话：13800138000, 13900139000 | 分拆成"电话1"和"电话2"两列，或另建一张电话表 |

**大白话**：一个格子里不能塞两个值。

---

##### 第二范式（2NF）：消除部分函数依赖

**前置条件**：先满足 1NF。

**要求**：非主属性必须**完全函数依赖**于候选码（不能只依赖候选码的一部分）。

| 错误示例 | 问题 | 修正方案 |
|----------|------|----------|
| 选课表（学号, 课程号, 学生姓名, 课程名, 成绩）| 候选码 =（学号, 课程号），但"学生姓名"只依赖于"学号"（部分依赖）| 拆成：学生表（学号, 姓名）+ 课程表（课程号, 课程名）+ 选课表（学号, 课程号, 成绩）|

**大白话**：一个字段不应该描述主键的一部分，而应该描述整个主键。

---

##### 第三范式（3NF）：消除传递函数依赖

**前置条件**：先满足 2NF。

**要求**：非主属性不能**传递函数依赖**于候选码。

| 错误示例 | 问题 | 修正方案 |
|----------|------|----------|
| 学生表（学号, 姓名, 系号, 系名, 系主任）| 学号 → 系号 → 系名（传递依赖）| 拆成：学生表（学号, 姓名, 系号）+ 系表（系号, 系名, 系主任）|

**大白话**：如果列 A 依赖列 B，列 B 又依赖主键，那列 A 就不应该跟主键放一张表。

---

#### 三大范式一句话总结

| 范式 | 核心要求 | 记法 |
|------|----------|------|
| **1NF** | 列不可再分 | "一格一值" |
| **2NF** | 消除部分依赖 | "全依赖码" |
| **3NF** | 消除传递依赖 | "不依赖非码" |

---

#### 易错点 12：BCNF 不是范式化的终点

除了 1NF、2NF、3NF 之外，还有 BCNF（Boyce-Codd 范式，3NF 的加强版）、4NF、5NF。国网考试偶尔涉及 BCNF，但重点在 1NF、2NF、3NF。

**BCNF 和 3NF 的区别**：3NF 只要求非主属性不传递依赖，BCNF 更进一步，要求**所有主属性**也不能存在部分依赖或传递依赖。

**经典案例**：在关系 R(S, J, T) 中，S=学生, J=课程, T=老师，假设每位老师只教一门课、一门课有多个老师、学生选课配老师。此时：候选码为 (S, J) 和 (S, T)。但 T → J 说明存在主属性对候选码的部分依赖 → 属于 3NF 但不属于 BCNF。

| 存储内容 | 举例 |
|----------|------|
| 表定义 | 表名、列名、数据类型 |
| 视图定义 | 视图的 SELECT 语句 |
| 索引信息 | 索引名、索引列 |
| 约束信息 | 主键、外键、检查约束 |
| 权限信息 | 谁对哪些表有什么权限 |

### 15.5 例题

> **例题 13**：在 E-R 图转换为关系模式时，一个 M : N 联系应该转换为 \_\_\_\_\_\_。
>
> **答案**：一个独立的关系模式（单独一张表），主键由两端实体的主键共同组成。

> **例题 14**：关系模式 R（学号, 课程号, 成绩, 教师姓名）中，候选码为（学号, 课程号），教师姓名依赖于课程号，则 R 最高满足 \_\_\_ 范式。
>
> **答案**：1NF。
> - 1NF：满足（每个属性都不可再分）
> - 2NF：不满足，因为"教师姓名"只依赖于"课程号"（候选码的一部分）——存在**部分函数依赖**
> - 因此最高只到 1NF

> **例题 15**：关系模式 R（学号, 姓名, 系名, 系主任）中，学号 → 系名 → 系主任，存在 \_\_\_\_\_\_ 依赖，不满足 \_\_\_\_\_\_ 范式。
>
> **答案**：传递函数依赖，不满足 3NF。

### 一、SQL 典型真题（至少 3 道）

#### 真题 1：多表 JOIN + 聚合 + HAVING 综合题

> **题目**：有学生表 `S(sid, sname, age, sex)`，选课表 `SC(sid, cid, score)`，课程表 `C(cid, cname, teacher)`。查询"平均成绩大于 80 分的学生姓名和平均成绩"，按平均成绩降序排列。

```sql
SELECT S.sname, AVG(SC.score) AS avg_score
FROM S
INNER JOIN SC ON S.sid = SC.sid
GROUP BY S.sid, S.sname
HAVING AVG(SC.score) > 80
ORDER BY avg_score DESC;
```

**考点拆解**：
- `INNER JOIN`：学生表关联选课表（只取有选课记录的学生）
- `GROUP BY`：按学生分组，对每个学生的成绩做聚合
- `HAVING`：筛选分组后的聚合结果（不能用 WHERE，因为 AVG 是聚合函数）
- `ORDER BY`：降序排列

**易错陷阱**：`GROUP BY S.sid, S.sname` 中两个字段都要写——因为 `sname` 在 SELECT 中出现了且不是聚合函数的参数，必须出现在 GROUP BY 中（SQL 标准要求）。

---

#### 真题 2：NOT EXISTS 双重否定（关系除法）

> **题目**：查询"选修了所有课程的学生姓名"。

```sql
SELECT sname FROM S
WHERE NOT EXISTS (
    SELECT * FROM C
    WHERE NOT EXISTS (
        SELECT * FROM SC
        WHERE SC.sid = S.sid AND SC.cid = C.cid
    )
);
```

**大白话翻译**：
- 内层 `NOT EXISTS`："不存在一门课程，这个学生选了它" → 这个学生选了所有课程
- 外层 `NOT EXISTS`："不存在一门课程，这个学生没选它" → 选了全部课程

**考点拆解**：
- 这是关系代数中"除法（÷）"的 SQL 实现
- 双重 `NOT EXISTS` 是经典写法，考试大题常考
- `EXISTS` 是关联子查询：内层引用外层 `S.sid` 和 `C.cid`

**易错陷阱**：单层 `NOT EXISTS` 只能判断"存在/不存在"，要表达"全部"必须用双重否定。

---

#### 真题 3：自连接 + LEFT JOIN 找 NULL

> **题目**：有员工表 `Emp(eid, ename, mid)`，其中 `mid` 是上级领导的员工编号（自引用外键）。查询"没有下属的员工姓名"。

```sql
SELECT DISTINCT e1.ename
FROM Emp e1
LEFT JOIN Emp e2 ON e1.eid = e2.mid
WHERE e2.eid IS NULL;
```

**大白话理解**：拿每个员工 e1，去匹配"谁的上司是我"，如果匹配不到（e2.eid IS NULL），说明没人叫他上司。

**考点拆解**：
- 自连接：同一张表起两个别名，自己连自己
- `LEFT JOIN`：保留左表全部行，右表匹配不上的填 NULL
- `WHERE e2.eid IS NULL`：利用外连接"右表全 NULL"来找出"没有匹配"的行

**易错陷阱**：`WHERE e2.eid = NULL`（单等号）是错的！NULL 不能用 `=` 比较，必须用 `IS NULL` / `IS NOT NULL`。

---

#### 真题 4：子查询 + IN + 聚合

> **题目**：查询"比本系平均年龄大的学生"。

```sql
SELECT s1.*
FROM S s1
WHERE s1.age > (
    SELECT AVG(s2.age)
    FROM S s2
    WHERE s2.dept = s1.dept
);
```

**考点拆解**：关联子查询 —— 外层每读一行，子查询就用当前学生的系别去算该系的平均年龄。

### 二、SQL 易错陷阱速查

| 陷阱 | 错误写法 | 正确写法 | 原因 |
|------|----------|----------|------|
| WHERE 中用聚合函数 | `WHERE COUNT(*) > 3` | `HAVING COUNT(*) > 3` | WHERE 在分组前执行，聚合函数还不能用 |
| NULL 比较 | `WHERE col = NULL` | `WHERE col IS NULL` | NULL 代表"未知"，不能用等号比较 |
| NOT IN + NULL | `WHERE id NOT IN (SELECT ...)` | 子查询中排除 NULL 或用 NOT EXISTS | 子查询结果有 NULL 时，NOT IN 返回空集 |
| DELETE 忘加 WHERE | `DELETE FROM 表` | `DELETE FROM 表 WHERE 条件` | 不加 WHERE 会清空整张表 |
| 聚合列与普通列混用 | `SELECT name, MAX(score) FROM SC` | 必须加 `GROUP BY name` | 聚合列和非聚合列不能同时出现在 SELECT 中（除非 GROUP BY） |
| COUNT(*) vs COUNT(列) | 混淆 | `COUNT(*)` 统计行数（含 NULL）；`COUNT(列)` 统计非空值个数 | 算总人数用 COUNT(*)，统计某列有效值用 COUNT(列) |
| 忘记 JOIN 条件 | `FROM A JOIN B` | `FROM A JOIN B ON A.id = B.id` | 没有 ON 条件会退化为笛卡尔积 |

### 三、事务并发高频考点

#### 3.1 四种并发问题对比（必考选择/判断题）

| 并发问题 | 现象 | 发生条件 | 类比 |
|----------|------|----------|------|
| **丢失修改**（Lost Update） | 两个事务同时读同一行，各自修改后提交，后提交的覆盖先提交的 | 没有写锁 | 你我在同一个 Word 文档上各改各的，最后保存的人覆盖了前一个人的修改 |
| **脏读**（Dirty Read） | T1 读到 T2 未提交的修改，T2 随后回滚，T1 读到了"不存在"的数据 | Read Uncommitted | 听到小道消息当真了，结果人家辟谣了 |
| **不可重复读**（Non-repeatable Read） | 同一事务内两次读同一行，**值**不一样（别人 UPDATE 了） | Read Committed 及以下 | 你隔 5 分钟查同一行数据，发现字段值变了 |
| **幻读**（Phantom Read） | 同一事务内两次查同一条件，**行数**不一样（别人 INSERT/DELETE 了） | Repeatable Read 及以下（MySQL InnoDB 除外） | 你隔 5 分钟查同一条件，发现多出了几行 |

#### 3.2 隔离级别速查表（必考填表/选择题）

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 实现方式 | 默认使用 |
|----------|------|-----------|------|----------|----------|
| 读未提交（Read Uncommitted） | 允许 | 允许 | 允许 | 不加锁 | 几乎不用 |
| 读已提交（Read Committed） | 禁止 | 允许 | 允许 | 快照/MVCC | Oracle、PostgreSQL |
| 可重复读（Repeatable Read） | 禁止 | 禁止 | 允许(标准) | MVCC | MySQL InnoDB |
| 可串行化（Serializable） | 禁止 | 禁止 | 禁止 | 表锁/范围锁 | 极少使用 |

**MySQL InnoDB 特殊之处**：在"可重复读"级别下，InnoDB 通过**间隙锁（Gap Lock）+ 临键锁（Next-Key Lock）**解决了幻读问题。所以 MySQL 的"可重复读"实际上对幻读也是禁止的。

#### 3.3 封锁（Lock）核心考点

**锁的兼容矩阵（必考）**：

|  | 已持有 S 锁 | 已持有 X 锁 |
|--|------------|------------|
| 申请 S 锁 | ✅ 兼容 | ❌ 冲突（等待） |
| 申请 X 锁 | ❌ 冲突（等待） | ❌ 冲突（等待） |

**记忆口诀**：S 锁=共享锁=读锁（大家都能读）；X 锁=排他锁=写锁（只能一个人用）。S 只跟 S 兼容，X 跟谁都不兼容。

**两段锁协议（2PL）高频考点**：
- 2PL 规定：事务分两段 —— 扩张阶段（只加锁不解锁）→ 收缩阶段（只解锁不加锁）
- 2PL **保证**可串行化调度
- 2PL **不防止**死锁（死锁需要额外的检测机制）
- 注意区别：一次封锁法（一次性申请所有锁）可以防止死锁，但 2PL 不行

**死锁的预防与检测**：
- 预防：一次封锁法、顺序封锁法
- 检测：等待图（Wait-for Graph），检测到环 → 存在死锁
- 恢复：选一个事务回滚（牺牲者），释放它持有的锁

#### 3.4 事务并发判断速解技巧

**题目类型**："以下调度是否可串行化？"解题步骤：
1. 画出调度序列中每个事务的读/写操作
2. 检查是否存在冲突操作（对同一数据，一个写另一个读/写）且顺序不一致
3. 如果冲突操作形成环 → 不可串行化
4. 如果 2PL 满足 → 一定可串行化

### 四、范式判断技巧

#### 4.1 范式判断三步法（国网大题必考）

**步骤**：
1. **先看 1NF**：有没有列包含多个值？有 → 不满足 1NF，不用往下看
2. **再看 2NF**：找候选码（主键），然后看每个非主属性是否"完全函数依赖"于候选码。如果某非主属性只依赖候选码的一部分 → 不满足 2NF
3. **最后看 3NF**：非主属性之间有没有传递依赖？即 非主属性 A → 非主属性 B → 候选码 这种链？有 → 不满足 3NF

#### 4.2 函数依赖速查

| 依赖类型 | 定义 | 大白话 | 范式关系 |
|----------|------|--------|----------|
| 完全函数依赖 | 非主属性依赖整个候选码，缺任何一个属性都不行 | 必须用完整主键才能确定这个值 | 满足 2NF 的前提 |
| 部分函数依赖 | 非主属性只依赖候选码的**一部分** | 主键的某一部分就够确定这个值了 | 违反 2NF |
| 传递函数依赖 | 非主属性 A → 非主属性 B → 候选码 这种链 | A 不直接依赖主键，而是通过 B 间接依赖 | 违反 3NF |

#### 4.3 范式判断快速模板

**给定关系模式 R(A, B, C, D)，函数依赖集 F = {A→B, B→C, ...}，判断最高满足第几范式。**

```
第1步：求候选码 → 闭包法
第2步：列出所有非主属性
第3步：检查非主属性是否完全函数依赖于候选码（2NF）
第4步：检查非主属性之间是否存在传递依赖（3NF）
```

#### 4.4 范式判断经典例题

> **例题**：关系模式 R(学号, 课程号, 成绩, 教师姓名, 教师职称)，F = { (学号,课程号)→成绩, (学号,课程号)→教师姓名, 课程号→教师姓名, 教师姓名→教师职称 }，候选码为 (学号, 课程号)。
>
> **判断**：
> - 1NF：✅（所有属性原子性）
> - 2NF：❌，因为"教师姓名"只依赖于"课程号"（候选码的一部分），存在部分函数依赖
> - 最高满足 **1NF**

> **例题**：关系模式 R(学号, 姓名, 系号, 系主任)，F = { 学号→姓名, 学号→系号, 系号→系主任 }，候选码为 学号。
>
> **判断**：
> - 1NF：✅
> - 2NF：✅（候选码是单属性，不存在部分依赖问题）
> - 3NF：❌，因为 学号→系号→系主任，存在传递函数依赖
> - 最高满足 **2NF**

#### 4.5 BCNF 判断速解

**BCNF 是 3NF 的加强版**：3NF 只要求非主属性不传递依赖，BCNF 要求**所有决定因素都必须是候选码**。

**判断口诀**：看函数依赖集的**左边**（决定因素）是否都是候选码。如果存在一个函数依赖 `X→Y`，其中 X 不是候选码 → 不满足 BCNF。

**经典 BCNF 例题**：R(S, J, T)，S=学生, J=课程, T=老师，F = { SJ→T, T→J }。候选码为 (S,J) 和 (S,T)。
- 3NF：✅（没有非主属性——所有属性都是主属性）
- BCNF：❌，因为 T→J 中 T 不是候选码
- 最高满足 **3NF**

#### 4.6 范式易错陷阱

| 陷阱 | 错误认知 | 正确认知 |
|------|----------|----------|
| 单属性候选码 = 自动满足 2NF | 以为 2NF 一定满足 | 对！单属性候选码不存在"部分依赖"问题，自动满足 2NF |
| 1NF 是默认满足的 | 忽略检查 | 考试中默认关系都满足 1NF，除非题目明确说某个属性不原子 |
| 3NF 比 BCNF 宽松 | 混淆关系 | BCNF ⊂ 3NF ⊂ 2NF ⊂ 1NF（BCNF 最严格） |
| 认为 NULL 影响范式判断 | 混入无关概念 | 范式判断只看函数依赖，跟 NULL 和具体数据无关 |
| 混淆"传递依赖"和"间接依赖" | 把任何间接关系都叫传递依赖 | 传递依赖特指：非主属性 A → 非主属性 B。如果 A 是主属性则不叫传递依赖（那是 BCNF 的范畴） |
