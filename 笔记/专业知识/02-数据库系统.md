## 知识点 10：数据库基本概念

> ⭐中频 —— 三级模式两级映像、DB/DBMS/DBS 概念辨析是基础题

### 10.1 数据的四级概念——从底层到顶层

这是数据库系统中最基础也最容易混淆的四个概念，必须逐层区分清楚：

```
数据（Data）
  └── 数据库（DB, Database）
        └── 数据库管理系统（DBMS, Database Management System）
              └── 数据库系统（DBS, Database System）
```

#### 逐层解析

| 层级 | 术语 | 定义 | 大白话 | 类比 |
|------|------|------|--------|------|
| 第一层 | **数据（Data）** | 描述事物的符号记录，是信息的载体 | 最原始的数字、文字、图片等 | 仓库里的一件件货物 |
| 第二层 | **数据库（DB）** | 长期存储在计算机内、有组织、可共享的大量数据的集合 | 把数据按照一定结构存起来的"大仓库" | 整座仓库 |
| 第三层 | **数据库管理系统（DBMS）** | 位于用户与操作系统之间的一层数据管理软件，负责科学地组织和存储数据、高效地获取和维护数据 | 管理仓库的"管理员软件" | 仓库管理员（管理软件） |
| 第四层 | **数据库系统（DBS）** | 由数据库、DBMS、应用程序、数据库管理员（DBA）组成的整体系统 | 仓库 + 管理员 + 操作手册 + 人的总和 | 仓库、管理员、操作手册加在一起 |

**易错点**：很多人说"装了一个数据库"，严格来说装的是 DBMS（如 MySQL）。数据库（DB）是 DBMS 管理下的数据集合。考试中要注意选项的精确表述。

**记忆口诀**：数据是原材料 → DB 是仓库 → DBMS 是管理员 → DBS 是整个体系。

---

### 10.2 DBMS 的主要功能 ⭐

DBMS（数据库管理系统）是数据库系统的核心软件，它位于用户和操作系统之间，负责对数据库进行统一管理和控制。考试中常考 DBMS 的六大功能：

| 功能 | 大白话 | 具体内容 | 关键命令/机制 |
|------|--------|---------|-------------|
| **数据定义** | 建表、定义结构 | 提供数据定义语言（DDL），定义数据库中的各种对象 | `CREATE`、`ALTER`、`DROP` |
| **数据操纵** | 增删改查 | 提供数据操纵语言（DML/DQL），对数据进行增删改查 | `INSERT`、`UPDATE`、`DELETE`、`SELECT` |
| **数据库运行管理** | 保证安全、稳定 | 并发控制、安全性检查、完整性约束检查、日志记录 | 事务管理、封锁机制、WAL |
| **数据库建立和维护** | 日常保养 | 数据装载、转储、恢复、重组、性能监控 | 备份恢复、性能调优 |
| **数据组织、存储和管理** | 底层存储 | 数据字典、索引、数据文件的组织方式 | B+树索引、聚簇、分区 |
| **通信功能** | 与外界交互 | 与操作系统联机处理、分时系统、远程作业输入 | 网络协议、ODBC/JDBC |

**考试重点**：DBMS 是"位于用户和操作系统之间的一层数据管理软件"，是数据库系统的**核心**。数据定义和操纵是最基本的两大功能。

**记忆口诀**：DBMS 六大功能——定义（DDL）、操纵（DML）、运行管理（事务/安全）、维护（备份/恢复）、存储管理（索引/字典）、通信（网络）。

### 10.2b 三种数据模型详细对比（层次 vs 网状 vs 关系）⭐

数据模型是数据库系统的核心和基础。逻辑数据模型主要有三种类型，考试中常考它们的对比：

| 对比维度 | 层次模型（Hierarchical） | 网状模型（Network） | 关系模型（Relational） |
|----------|------------------------|-------------------|----------------------|
| **数据结构** | 树形结构（有根节点，一个子节点只能有一个父节点） | 图结构（有向图，一个子节点可以有多个父节点） | 二维表（行 + 列） |
| **表示方式** | 倒立的树，节点表示记录型 | 结点 + 有向边（系，set） | 关系 = 表，元组 = 行，属性 = 列 |
| **数据联系** | 一对多（1:N）为主 | 多对多（M:N）可以直接表示 | 通过外键（Foreign Key）关联 |
| **查询方式** | 从根节点逐层向下导航 | 沿着指针链路导航 | 声明式 SQL（告诉系统"要什么"而不是"怎么找"） |
| **数据独立性** | 差（物理存储细节暴露给用户） | 较差（导航路径依赖物理存储） | 好（三级模式两级映像机制） |
| **典型代表** | IMS（IBM 1968） | DBTG（CODASYL 1971） | Oracle、MySQL、PostgreSQL |
| **优点** | 结构简单清晰，查询效率高（适合1:N固定查询） | 能直接描述现实世界中多对多的复杂关系，存取效率高 | 数据结构简单（表），有严格的数学理论（关系代数），数据独立性高 |
| **缺点** | 不能直接表示 M:N 关系；插入删除异常多；查询必须从根开始 | 结构复杂，DBA 和程序员负担重；编写应用程序困难 | 语义表达能力有限（不如 E-R 图直观）；查询效率可能不如导航式 |
| **当前状态** | 已淘汰 | 已淘汰 | **绝对主流** |

**易错点**：
- 层次模型的"一个子节点只能有一个父节点"是核心限制，这导致 M:N 关系必须拆成多个树
- 网状模型突破了层次模型的限制，但复杂度太高，最终被关系模型取代
- 关系模型用的是"二维表"而非"树"或"图"，这是判断数据模型类型的速解方法

**记忆口诀**：层次像家族树（一个爹），网状像蜘蛛网（多个爹），关系像 Excel 表（二维格）。

**典型例题**：

> **例题 1**：在数据库技术中，用二维表结构表示实体以及实体间联系的数据模型是（ ）。
> A. 层次模型  B. 网状模型  C. 关系模型  D. 面向对象模型
>
> **答案**：C。关系模型的核心数据结构是二维表（行 + 列），层次模型是树形结构，网状模型是图结构。

> **例题 2**：下列关于层次模型的说法，正确的是（ ）。
> A. 层次模型可以直接表示 M:N 关系
> B. 层次模型中一个子节点可以有多个父节点
> C. 层次模型的查询效率高，适合 1:N 固定查询
> D. 层次模型的数据独立性是最好的
>
> **答案**：C。层次模型是树形结构，一个子节点只能有一个父节点（B错），不能直接表示 M:N（A错），数据独立性差（D错）。但层次模型结构简单，在 1:N 固定查询场景下效率高。

> **例题 3**：网状模型与层次模型相比，最大的进步是（ ）。
> A. 用二维表表示数据  B. 允许一个子节点有多个父节点  C. 有数据独立性  D. 查询效率更高
>
> **答案**：B。网状模型用图结构代替树结构，允许一个子节点有多个父节点，从而可以直接表示 M:N 关系。这是网状模型相对于层次模型最大的突破（但复杂度也大幅增加）。

**常见陷阱**：
- 陷阱1："层次模型、网状模型、关系模型是按抽象层次分类的"——错！这是按**逻辑模型类型**分类的。按抽象层次分类是概念模型→逻辑模型→物理模型。
- 陷阱2："网状模型已经完全被淘汰了，没有任何价值"——错！网状模型直接表示 M:N 的能力被后续模型继承，它的思想影响了后来的数据库设计。
- 陷阱3："关系模型是因为查询效率最高才成为主流的"——不完全对。关系模型成为主流的主要原因是**结构简单（二维表）、有严格数学理论（关系代数）、数据独立性高**，而不是单纯的查询效率。

**对比表格速记**：
```
层次 → 树 → 一个爹 → 1:N 为主 → IMS → 已淘汰
网状 → 图 → 多个爹 → M:N 直接 → DBTG → 已淘汰
关系 → 表 → 外键连 → 声明式 → MySQL → 绝对主流
```

### 10.3 DB / DBMS / DBS 三者关系

这三个概念的关系就像是"仓库、仓库管理员、仓库管理系统"：

| 术语 | 全称 | 大白话 | 类比 |
|------|------|--------|------|
| **DB**（数据库） | Database | 存放数据的"大仓库" | 仓库里的货物 |
| **DBMS**（数据库管理系统） | Database Management System | 管理数据的"仓库管理员"（软件） | 仓库管理员 |
| **DBS**（数据库系统） | Database System | "仓库 + 管理员 + 规章制度"的整体 | 仓库、管理员、操作手册加在一起 |

**记忆口诀**：DB 是数据本身，DBMS 是管理软件，DBS = DB + DBMS + 人 + 规则，是更大的概念。

---

#### 易错点 1："DBMS 就是数据库" ❌

很多初学者把 DBMS 说成"数据库"，比如"我装了一个 MySQL 数据库"——严格说，MySQL 是 DBMS，里面管理的那个数据仓库才是 DB。考试里要注意区分。

### 10.4 数据库系统 vs 文件系统 ⭐

"为什么不直接用 Excel 存数据，非要搞数据库？"

| 对比维度 | 文件系统 | 数据库系统 |
|----------|----------|------------|
| **数据冗余** | 各文件各自存，同一数据多处重复存储 | 集中管理，数据共享，冗余度小 |
| **数据一致性** | 一个数据改多处容易遗漏，不一致 | DBMS 通过完整性约束自动维护一致性 |
| **数据独立性** | 程序直接操作文件，文件格式一变代码就要改 | 程序和数据结构分离（三级模式两级映像），改了表不影响程序 |
| **并发访问** | 多个程序同时改一个文件容易出错，无锁机制 | 有事务和锁机制，保证并发安全 |
| **数据共享** | 格式不统一，不易共享，需要知道文件格式 | 统一接口（SQL），结构化查询，方便共享 |
| **数据安全性** | 安全性差，只能靠操作系统权限保护 | 多层次安全控制（用户认证、权限管理、审计） |
| **数据完整性** | 无约束检查，可能出现无效数据 | 实体完整性、参照完整性、域完整性、用户定义完整性 |
| **查询能力** | 需要程序员自己编写查询逻辑 | 声明式 SQL 查询，无需关心实现细节 |
| **数据恢复** | 没有自动恢复能力，文件丢失就是永久丢失 | 日志文件 + 检查点 + 备份恢复机制 |
| **数据粒度** | 以文件为单位，粗粒度 | 以记录（行）为最小访问单位，细粒度 |

#### 数据库系统的核心优势（三个关键词）

1. **数据结构化**：所有数据按照统一的数据模型组织，不是一盘散沙
2. **数据共享性高、冗余度低**：多个用户可以同时访问同一数据，减少重复存储
3. **数据独立性高**：应用程序与数据的物理存储和逻辑结构分离

#### 数据库系统 vs 文件系统：本质区别

| 本质区别 | 文件系统 | 数据库系统 |
|----------|----------|------------|
| **数据模型** | 无（文件是流式数据） | 有（关系模型 / 层次模型等） |
| **数据联系** | 由程序显式定义 | 由数据模型隐式定义 |
| **操作方式** | 过程化（告诉系统"怎么做"） | 非过程化（告诉系统"要什么"） |

**大白话总结**：数据库系统相比文件系统的核心优势是"数据独立、集中管理、并发安全、结构统一"。文件系统就像每个人自己管自己的文件柜，数据库系统是一个专业仓库管理员统一管理所有货物。

**考试常见判断题**：
- "数据库系统和文件系统没有本质区别" ❌
- "数据库系统中数据与程序完全独立，毫无关系" ❌（数据独立性是指逻辑和物理结构独立，不是说数据与程序无关）
- "文件系统也能实现并发控制" ❌（文件系统没有锁机制，无法保证并发安全）

### 10.5 数据模型——怎么描述数据？

数据模型就是"画蓝图"的工具，用数学化、标准化的方式描述数据叫什么、长什么样、之间什么关系。

#### 数据模型的三要素

每个数据模型都由以下三个要素组成：

| 要素 | 含义 | 大白话 | 例子（关系模型） |
|------|------|--------|---------------|
| **数据结构** | 数据对象的集合及它们之间的联系 | 数据长什么样，怎么组织 | 二维表（行+列） |
| **数据操作** | 对数据库中各种数据允许执行的操作 | 能对数据做什么 | 增删改查（CRUD） |
| **完整性约束** | 数据必须满足的约束条件 | 数据不能违反什么规则 | 实体完整性、参照完整性 |

#### 概念模型 vs 逻辑模型 vs 物理模型（按抽象层次分）

| 模型类型 | 别称 | 干什么用的 | 面向谁 | 举例 | 与 DBMS 关系 |
|----------|------|-----------|--------|------|:---:|
| **概念模型** | 信息模型 | 跟用户沟通，画业务逻辑，不涉及技术细节 | 用户、需求分析师 | E-R 图、对象模型 | 独立于 DBMS |
| **逻辑模型** | 结构模型 | 程序员看的，决定数据怎么存、表之间关系 | 数据库设计人员、程序员 | 关系模型、层次模型、网状模型、面向对象模型 | 依赖 DBMS 类型 |
| **物理模型** | 存储模型 | 数据库底层，决定数据在硬盘的位置和存取方式 | DBA、系统程序员 | 索引、文件组织、分区、聚簇 | 依赖具体 DBMS 和硬件 |

**三个层次的关系**：概念模型（E-R 图）→ 转换 → 逻辑模型（关系表）→ 实现 → 物理模型（磁盘文件）。

**考试重点**：
- 概念模型用于**信息世界**建模，逻辑模型用于**计算机世界**建模
- 概念模型中最常用的是**实体-联系方法（E-R 方法）**
- 逻辑模型中最常用的是**关系模型**
- 物理模型依赖于具体的 DBMS 和硬件

#### 数据模型的分类维度总结

| 分类维度 | 分类结果 | 说明 |
|----------|----------|------|
| 按抽象层次 | 概念模型 → 逻辑模型 → 物理模型 | 从高到低越来越具体 |
| 按逻辑模型类型 | 层次模型、网状模型、关系模型、面向对象模型 | 关系模型是当前主流 |
| 按数据模型三要素 | 数据结构 + 数据操作 + 完整性约束 | 任何数据模型都必须包含这三个要素 |

> 注意：10.2b 节中讲的"层次/网状/关系"是**逻辑模型**层面的三种类型，而 10.5 节说的是模型按抽象层次分三类（概念→逻辑→物理），两者是不同的分类维度。简单说：概念模型画 E-R 图，逻辑模型从 E-R 图转成关系表，物理模型把关系表存到磁盘。

**记忆口诀**：
```
数据模型三要素：结构（长什么样）、操作（能做什么）、约束（不能违反什么）
抽象层次三级别：概念（画 E-R 图）→ 逻辑（转关系表）→ 物理（存磁盘）
```

### 10.6 E-R 模型（实体-联系模型）⭐

E-R 模型（Entity-Relationship Model，实体-联系模型）是概念模型的最常用工具，由 P.P.Chen 于 1976 年提出。核心就是三个要素：

| 要素 | 符号/表示 | 大白话 | 例子 |
|------|----------|--------|------|
| **实体**（Entity） | 矩形框 | 一个"东西/对象" | 学生、课程 |
| **属性**（Attribute） | 椭圆 | 实体的特征 | 学生的学号、姓名 |
| **联系**（Relationship） | 菱形 | 实体之间怎么关联 | 学生"选课" |

#### 实体类型

| 实体类型 | 大白话 | 例子 |
|----------|--------|------|
| **强实体** | 独立存在，不依赖其他实体 | 学生、课程 |
| **弱实体** | 依赖于其他实体存在，没有自己的主键 | 订单明细（依赖订单）、家属（依赖员工） |

**弱实体考试要点**：弱实体用**双矩形框**表示，其联系用**双菱形**表示。弱实体的主键 = 强实体主键 + 弱实体的部分键。

#### 属性类型（考试辨析）

| 属性类型 | 大白话 | 例子 |
|----------|--------|------|
| **简单属性**（原子属性） | 不可再分的属性 | 年龄、性别 |
| **复合属性** | 可以再分的属性 | 地址（省+市+区），姓名（姓+名） |
| **单值属性** | 只有一个值 | 学号、身份证号 |
| **多值属性** | 可以有多个值，用**双椭圆**表示 | 电话号码（一个人有多个号） |
| **派生属性** | 可以从其他属性算出来的，用**虚线椭圆**表示 | 年龄（由出生日期算出）、总成绩（由各科成绩算出） |
| **NULL 属性** | 值未知或不存在 | 备注信息 |

#### 联系的三种类型

| 类型 | 表示 | 大白话 | 例子 |
|------|------|--------|------|
| 1 : 1（一对一） | `1——1` | 你有一个我，我有一个你 | 一个班级有一个班主任，一个班主任管一个班级 |
| 1 : N（一对多） | `1——N` | 你有多个我，我只有一个你 | 一个班级有多个学生，一个学生属于一个班级 |
| M : N（多对多） | `M——N` | 你有多个我，我有多个你 | 一个学生选多门课，一门课有多个学生选 |

> **关键规则**：M : N 联系必须拆成两个"1 : N 联系"才能在关系模型里存。这是考试大题必考点！

#### E-R 图设计常见错误

| 错误 | 正确做法 |
|------|----------|
| 把 M:N 联系合并到某一端 | M:N 联系**必须单独建表** |
| 把联系属性放到实体中 | 联系属性应放在联系对应的表中 |
| 把复合属性当作原子属性 | 复合属性应拆分为多个简单属性 |
| 忽略弱实体 | 弱实体用双矩形框，需要标注依赖关系 |

#### E-R 图与 UML 类图的区别

| 对比维度 | E-R 图 | UML 类图 |
|----------|--------|----------|
| 用途 | 数据库概念设计 | 面向对象软件设计 |
| 核心概念 | 实体、属性、联系 | 类、属性、方法、关联 |
| 关联表示 | 菱形（联系） | 连线（关联） |
| 支持操作 | 不支持 | 支持（方法） |
| 产生阶段 | 概念结构设计 | 需求分析/系统设计 |

**E-R 模型典型例题**：

> **例题 1**：在 E-R 图中，若一个学生可以选修多门课程，一门课程可被多个学生选修，则学生与课程之间的联系类型是（ ）。
> A. 1:1  B. 1:N  C. M:N  D. 以上都不对
>
> **答案**：C。两边的实体都是"多个对应多个"，典型 M:N 联系。这种联系必须单独建表。

> **例题 2**：E-R 模型是数据库设计的什么阶段产生的？
> A. 需求分析阶段  B. 概念结构设计阶段  C. 逻辑结构设计阶段  D. 物理结构设计阶段
>
> **答案**：B。E-R 模型是概念结构设计阶段的产物，独立于具体的 DBMS。

> **例题 3**：在 E-R 图中，如果一个属性可以有多个值（如一个人有多个电话号码），该属性称为（ ），用（ ）表示。
> A. 复合属性，椭圆  B. 派生属性，虚线椭圆  C. 多值属性，双椭圆  D. NULL 属性，虚线椭圆
>
> **答案**：C。多值属性用**双椭圆**表示。复合属性是可再分的属性（如地址），派生属性是可从其他属性计算出来的（如年龄），NULL 属性表示值未知或不存在。

**常见陷阱**：
- 陷阱1：E-R 图属于**概念模型**，不是逻辑模型。概念模型独立于 DBMS，逻辑模型依赖 DBMS 类型。
- 陷阱2：弱实体用**双矩形**，弱实体的联系用**双菱形**。这两个符号容易混淆——记忆：弱实体是"弱势的实体"，所以实体符号（矩形）加强（双线）。
- 陷阱3：派生属性（虚线椭圆）和 NULL 属性（也是虚线椭圆）容易混淆。派生属性侧重于"可以推导出来"，NULL 属性侧重于"值未知或不存在"。

### 10.7 三级模式两级映像 ⭐⭐⭐

这是数据库系统的核心架构，考试高频考点，每年必出 1-2 题。

#### 三层模式（自上而下）

```
┌──────────────────────────────────────┐
│  外模式（External Schema / 子模式）   │  ← 用户看到的视图（View），可以有多个
│  针对不同用户定制的"视野"             │     应用程序的接口，每个应用有自己的外模式
│  数目：多个                          │
├──────────────────────────────────────┤
│  模式（Conceptual Schema / 逻辑模式）  │  ← 数据库的全局逻辑结构，只有一个
│  所有数据的全局逻辑蓝图               │     定义所有表、字段、类型、约束
│  数目：唯一                          │
├──────────────────────────────────────┤
│  内模式（Internal Schema / 存储模式）  │  ← 数据在磁盘上怎么存的，只有一个
│  物理存储细节                        │     定义文件组织、索引方式、数据压缩
│  数目：唯一                          │
└──────────────────────────────────────┘
```

#### 每层详细说明

| 层次 | 别名 | 描述 | 谁关心 | 例子 |
|------|------|------|--------|------|
| **外模式** | 子模式、用户模式 | 用户看到的数据视图，是模式的子集 | 应用程序员、最终用户 | HR系统只能看到员工表，看不到工资表 |
| **模式** | 概念模式、逻辑模式 | 数据库中全体数据的逻辑结构和特征 | 数据库管理员（DBA） | 定义所有表、字段类型、约束、关系 |
| **内模式** | 存储模式 | 数据的物理存储方式 | 系统程序员 | 数据文件如何存放、用什么索引结构 |

**大白话类比**：
- **内模式**：仓库的货架怎么摆、货物编号怎么编（只有仓管知道）——物理层
- **模式**：仓库里一共有多少种货、各放哪个区（管理员心中有全局）——逻辑层
- **外模式**：每个前台只能看到自己负责的那部分货（不同人看到不同视图）——视图层

#### 两级映像（保证数据独立性的关键）

| 映像 | 映射关系 | 定义 | 大白话作用 | 保证的独立性 |
|------|----------|------|-----------|------------|
| **外模式/模式映像** | 外模式 ↔ 模式 | 定义外模式与模式之间的对应关系 | 改了全局表结构（如加一列），用户看到的视图可以不变 | **逻辑数据独立性** |
| **模式/内模式映像** | 模式 ↔ 内模式 | 定义模式与内模式之间的对应关系 | 改了物理存储方式（如换索引），全局表结构不变 | **物理数据独立性** |

**逻辑独立性 vs 物理独立性**：

| 对比维度 | 逻辑数据独立性 | 物理数据独立性 |
|----------|-------------|-------------|
| **定义** | 当模式改变时，外模式不变，应用程序不变 | 当内模式改变时，模式不变，应用程序不变 |
| **映像** | 外模式/模式映像 | 模式/内模式映像 |
| **场景** | 表结构中增加字段、修改字段类型 | 数据文件迁移、更换索引结构、更换存储设备 |
| **谁修改** | DBA 修改外模式/模式映像 | DBA 修改模式/内模式映像 |

**考试常见干扰项**：
- "外模式/模式映像保证物理独立性" ❌ → 保证的是**逻辑**独立性
- "模式/内模式映像保证逻辑独立性" ❌ → 保证的是**物理**独立性
- 两个映像的维持工作由**数据库管理员（DBA）**负责

**一句话核心**：两级映像是"缓冲层"，让你改底层时不用改上层。这就是数据库"数据独立性"的底层实现原理。

#### 三级模式结构在数据库系统中的体现

| 三级模式 | 在实际 DBMS 中的体现 |
|----------|-------------------|
| **外模式** | 视图（View）、应用程序的查询接口 |
| **模式** | 基本表（Base Table）的定义 |
| **内模式** | 存储文件、索引文件、数据字典 |

**记忆口诀**：
```
三个模式记清楚：外多模一内也一
两级映像分得清：外模保逻辑，模内保物理
外模式是窗外看，模式是全局图，内模式是仓库底
```

**三级模式两级映像典型例题**：

> **例题 1**：数据库系统的三级模式结构中，外模式又称（ ），有（ ）个。
> A. 存储模式，1个  B. 子模式/用户模式，多个  C. 概念模式，1个  D. 逻辑模式，1个
>
> **答案**：B。外模式又称子模式/用户模式，面向不同用户，可以有多个。模式（概念模式）和内模式（存储模式）各只有一个。

> **例题 2**：保证数据库物理数据独立性的是（ ）。
> A. 外模式/模式映像  B. 模式/内模式映像  C. 外模式/内模式映像  D. 用户/模式映像
>
> **答案**：B。模式/内模式映像保证物理数据独立性（当内模式改变时，模式不变）。外模式/模式映像保证逻辑数据独立性。注意：A和B正好相反，考试常混着考。

> **例题 3**：在数据库三级模式结构中，直接面向用户的是（ ）。
> A. 内模式  B. 模式  C. 外模式  D. 存储模式
>
> **答案**：C。外模式是用户看到的视图，是用户与数据库的接口。内模式是物理存储，模式是全局逻辑结构，用户不直接接触。

**常见陷阱**：
- 陷阱1："外模式/模式映像保证物理独立性"——这是故意把 A 和 B 的作用说反，考试最爱考这个混淆。
- 陷阱2："外模式只有一个"——错！外模式可以有多个（不同用户看到不同视图），模式和内模式才各只有一个。
- 陷阱3："三级模式两级映像可以直接在 DBMS 中看到"——不完全对。在实际 DBMS 中，外模式对应**视图（View）**，模式对应**基本表（Base Table）**，内模式对应**存储文件**。视图是实打实的 SQL 对象，但"映像"是 DBMS 内部机制，用户看不到。

---

#### 易错点 2："模式只有一个，外模式可以有多个"

- **模式**（概念模式）是唯一的，描述了整个数据库的逻辑结构
- **外模式**可以有多个，因为不同用户有不同的权限和需求
- **内模式**也是唯一的（一个数据库只有一个物理存储结构）

---

### 10.8 例题（5道选择题）

> **例题 1**：数据库系统的核心是 \_\_\_\_\_\_。
> A. 数据模型  B. 数据库管理系统  C. 数据库  D. 数据库管理员
>
> **答案**：B。DBMS 是数据库系统的核心软件，负责所有管理操作。DBMS 是位于用户和操作系统之间的一层数据管理软件。

> **例题 2**：在数据库的三级模式结构中，描述数据库中全体数据的全局逻辑结构和特征的是 \_\_\_\_\_\_。
> A. 外模式  B. 内模式  C. 存储模式  D. 模式
>
> **答案**：D。模式（也称概念模式、逻辑模式）是数据库中全体数据的逻辑结构和特征的描述，是所有用户的公共数据视图，只有一个。

> **例题 3**：两级映像中的"外模式/模式映像"保证了数据库的 \_\_\_\_\_\_。
> A. 物理数据独立性  B. 逻辑数据独立性  C. 数据安全性  D. 数据完整性
>
> **答案**：B。当模式改变时（如增加新的关系、增加新的属性等），数据库管理员修改外模式/模式映像，使外模式保持不变，从而应用程序不必修改，保证了数据与程序的逻辑独立性。

> **例题 4**：层次模型与网状模型相比，层次模型的特点是 \_\_\_\_\_\_。
> A. 允许一个节点有多个父节点  B. 一个子节点只能有一个父节点  C. 用二维表表示数据  D. 数据独立性最高
>
> **答案**：B。层次模型的核心特征是树形结构，一个子节点只能有一个父节点（除根节点外）。网状模型突破了这一限制，允许一个子节点有多个父节点。

> **例题 5**：关于数据库系统的数据独立性，下列说法正确的是 \_\_\_\_\_\_。
> A. 数据独立性是指数据与程序之间互不依赖、相互独立
> B. 物理独立性是指当数据的存储结构改变时，应用程序不变
> C. 逻辑独立性是指当数据的逻辑结构改变时，应用程序也不变
> D. 以上说法都正确
>
> **答案**：D。数据独立性是数据库系统的重要特征，包括物理独立性（内模式改变不影响模式和应用程序）和逻辑独立性（模式改变不影响外模式和应用程序），两级映像机制是实现数据独立性的关键。

### 10.9 易错陷阱

| 陷阱 | 错误认知 | 正确认知 |
|------|----------|----------|
| 数据库 vs DBMS | "MySQL 是数据库" | MySQL 是 DBMS（数据库管理系统），它管理的数据集合才是数据库（DB） |
| 模式数量 | "外模式只有一个" | 外模式可以有多个（不同用户看到不同视图），模式和内模式各只有一个 |
| 两级映像对应关系 | "外模式/模式映像保证物理独立性" | 外模式/模式映像保证**逻辑**独立性，模式/内模式映像保证**物理**独立性，正好反过来 |
| 层次模型限制 | "层次模型可以直接表示 M:N" | 层次模型不能直接表示 M:N，必须拆成多个树；网状模型可以直接表示 M:N |
| 数据独立性 | "数据独立性 = 数据不依赖任何东西" | 数据独立性是指应用程序不依赖于数据的物理存储和逻辑结构，不是说数据本身独立 |

```
四级概念层层套：数据→DB→DBMS→DBS
三种模型比一比：层次是树、网状是图、关系是表
三级模式记清楚：外多模一内也一
两级映像分得清：外模保逻辑，模内保物理
```

### 10.11 自测题

1. DB、DBMS、DBS 三者之间是什么关系？
2. 三级模式分别叫什么？各自有几个？
3. "一个学生可以借多本书，一本书可以被多个学生借"——这是什么类型的联系？
4. 两级映像分别保证什么独立性？
5. 概念模型最常用的工具是什么？它的三个基本要素是什么？

**自测题答案：**

1. **DB（数据库）**是存放数据的集合（仓库）；**DBMS（数据库管理系统）**是管理数据的软件（管理员）；**DBS（数据库系统）**= DB + DBMS + 应用程序 + 数据库管理员（DBA），是包含人、数据、软件、硬件在内的完整体系。关系：DBS 包含 DBMS，DBMS 管理 DB。

2. **外模式**（子模式/用户模式）：可以有多个，是用户看到的局部数据视图；**模式**（概念模式/逻辑模式）：只有1个，是全局逻辑结构；**内模式**（存储模式）：只有1个，是物理存储结构。

3. **M:N（多对多）联系**。"一个学生可以借多本书"=N，"一本书可以被多个学生借"=M，所以是 M:N。

4. **外模式/模式映像**保证**逻辑数据独立性**（模式变了，外模式可以不变）；**模式/内模式映像**保证**物理数据独立性**（内模式变了，模式可以不变）。

5. 概念模型最常用的工具是**E-R 模型（实体-联系模型）**。三个基本要素：**实体**（矩形框）、**属性**（椭圆）、**联系**（菱形）。

## 知识点 11：关系数据库基本理论

> ⭐⭐高频 —— 关系代数运算、完整性约束是必考基础，除运算和自然连接是难点

### 11.1 关系数据库的基本概念

**大白话**：关系模型就是把数据存成一张张**二维表**（行 + 列）。

| 术语 | 大白话 | 表格对应 |
|------|--------|----------|
| **关系** | 一张表 | 整张表 |
| **元组**（Tuple）| 一行数据 | 行 / 一条记录 |
| **属性**（Attribute）| 一列数据 | 列 / 字段 |
| **分量** | 某个元组在某个属性上的值 | 某一个单元格 |
| **候选码**（Candidate Key）| 能唯一标识一行的属性（组）| 比如学号 |
| **主码**（Primary Key）| 从候选码中选一个当"正式代表" | 主键 |
| **外码**（Foreign Key）| 别的表的主码，引用来建立联系 | 外键 |
| **域**（Domain）| 属性的取值范围 | 年龄：0 ~ 150 |
| **关系模式** | 表的结构定义 | `学生(学号, 姓名, 年龄)` |

#### 关系的性质（判断题常考）

- 每一列（属性）**不可再分**（满足 1NF）
- 每一列有**唯一的属性名**
- 行的**顺序无关紧要**，列的顺序也无关紧要
- 任意两行**不能完全相同**（关系是元组的集合）

---

#### 易错点 3："行顺序无关"是关系数据库的核心特征

关系数据库中的行是无序的集合，如果你想让查询结果**有序**，必须使用 `ORDER BY`——不加 ORDER BY 的查询结果，数据库可以按任意顺序返回。

---

### 11.2 关系代数 ⭐

关系代数是"对表进行运算"的数学语言，SQL 就是它的具体实现。关系代数分为两大类：传统集合运算（4种）和专门的关系运算（4种），共 8 种基本运算（交可用差表示，所以基本运算实际是 5 种：并、差、笛卡尔积、选择、投影）。

#### 一、传统集合运算（4种）

| 运算 | 符号 | 条件 | 大白话 | 例子 |
|------|------|------|--------|------|
| **并**（Union）| ∪ | 两个表的列数和类型必须相同（并相容） | 两张表摞在一起，去重 | R ∪ S = 所有在 R 中或在 S 中的元组 |
| **差**（Difference）| − | 同上 | 在表 A 里但不在表 B 里的行 | R − S = 在 R 中但不在 S 中的元组 |
| **交**（Intersection）| ∩ | 同上 | 两张表都有的行 | R ∩ S = 同时在 R 和 S 中的元组 |
| **笛卡尔积**（Cartesian Product）| × | 无要求 | 表 A 每一行 × 表 B 每一行（全组合） | R 有 m 行, S 有 n 行 → R × S 有 m×n 行 |

**注意**：交运算可以用差运算表示：R ∩ S = R − (R − S)，所以交不是基本运算。

#### 笛卡尔积详细例子

设有关系 R 和 S：
```
R:           S:
┌───┬───┐    ┌───┬───┐
│ A │ B │    │ C │ D │
├───┼───┤    ├───┼───┤
│ 1 │ 2 │    │ x │ y │
│ 3 │ 4 │    │ z │ w │
└───┴───┘    └───┴───┘
```

R × S 的结果（2×2=4 行，2+2=4 列）：
```
┌───┬───┬───┬───┐
│ A │ B │ C │ D │
├───┼───┼───┼───┤
│ 1 │ 2 │ x │ y │
│ 1 │ 2 │ z │ w │
│ 3 │ 4 │ x │ y │
│ 3 │ 4 │ z │ w │
└───┴───┴───┴───┘
```

---

#### 二、专门的关系运算（4种）⭐

| 运算 | 符号 | 大白话 | SQL 对应 |
|------|------|--------|----------|
| **选择**（Selection）| σ<sub>条件</sub>(R) | 按条件筛选行（横向切） | `WHERE` |
| **投影**（Projection）| π<sub>属性列表</sub>(R) | 只取某些列（纵向切），自动去重 | `SELECT DISTINCT 列名` |
| **连接**（Join）| R ⋈<sub>条件</sub> S | 两张表按某条件拼成一张 | `JOIN ... ON` |
| **除**（Division）| R ÷ S | 找出满足"所有"条件的元组 | 没有直接对应 |

##### 选择的例子

σ<sub>年龄>20</sub>(学生) —— 从学生表中选出年龄大于 20 的行。结果的行数 ≤ 原表的行数，列数不变。

##### 投影的例子

π<sub>学号, 姓名</sub>(学生) —— 从学生表中只取"学号"和"姓名"两列。结果的行数可能少于原表（因为自动去重），列数缩减。

##### 外连接详解（重点中的难点）

外连接（Outer Join）与内连接的区别在于：内连接只保留匹配的行，外连接会保留"悬浮元组"（匹配不上的行），匹配不上的列填 NULL。

**三种外连接对比**：

| 外连接类型 | SQL 写法 | 保留哪边 | 不匹配的列填什么 |
|-----------|----------|---------|---------------|
| **左外连接** | `LEFT OUTER JOIN` / `LEFT JOIN` | 保留左表所有行 | 右表列填 NULL |
| **右外连接** | `RIGHT OUTER JOIN` / `RIGHT JOIN` | 保留右表所有行 | 左表列填 NULL |
| **全外连接** | `FULL OUTER JOIN` / `FULL JOIN` | 保留两表所有行 | 不匹配的列填 NULL |

**外连接详细例子**：

```
学生表 S:              选课表 SC:
┌──────┬──────┐        ┌──────┬──────┬───────┐
│ 学号 │ 姓名 │        │ 学号 │ 课程 │ 成绩  │
├──────┼──────┤        ├──────┼──────┼───────┤
│ 001  │ 张三 │        │ 001  │ 数学 │  85   │
│ 002  │ 李四 │        │ 001  │ 英语 │  90   │
│ 003  │ 王五 │        │ 003  │ 数学 │  78   │
└──────┴──────┘        └──────┴──────┴───────┘

内连接（INNER JOIN）结果：
┌──────┬──────┬──────┬───────┐
│ 学号 │ 姓名 │ 课程 │ 成绩  │
├──────┼──────┼──────┼───────┤
│ 001  │ 张三 │ 数学 │  85   │
│ 001  │ 张三 │ 英语 │  90   │
│ 003  │ 王五 │ 数学 │  78   │
└──────┴──────┴──────┴───────┘
-- 李四(002)没有选课记录，被丢弃了

左外连接（LEFT JOIN）结果：
┌──────┬──────┬──────┬───────┐
│ 学号 │ 姓名 │ 课程 │ 成绩  │
├──────┼──────┼──────┼───────┤
│ 001  │ 张三 │ 数学 │  85   │
│ 001  │ 张三 │ 英语 │  90   │
│ 002  │ 李四 │ NULL │ NULL  │  ← 李四保留，右边填 NULL
│ 003  │ 王五 │ 数学 │  78   │
└──────┴──────┴──────┴───────┘

右外连接（RIGHT JOIN）结果：
┌──────┬──────┬──────┬───────┐
│ 学号 │ 姓名 │ 课程 │ 成绩  │
├──────┼──────┼──────┼───────┤
│ 001  │ 张三 │ 数学 │  85   │
│ 001  │ 张三 │ 英语 │  90   │
│ 003  │ 王五 │ 数学 │  78   │
└──────┴──────┴──────┴───────┘
-- 注意：右表（SC）所有行都有匹配，所以结果同内连接

全外连接（FULL JOIN）结果：
┌──────┬──────┬──────┬───────┐
│ 学号 │ 姓名 │ 课程 │ 成绩  │
├──────┼──────┼──────┼───────┤
│ 001  │ 张三 │ 数学 │  85   │
│ 001  │ 张三 │ 英语 │  90   │
│ 002  │ 李四 │ NULL │ NULL  │  ← 左表悬浮元组
│ 003  │ 王五 │ 数学 │  78   │
└──────┴──────┴──────┴───────┘
```

**外连接考试常考应用场景**：
- "查询所有学生及其选课信息（包括没选课的学生）" → 左外连接
- "查询所有课程及其被选情况（包括没人选的课）" → 右外连接
- "查询所有学生和所有课程，不管有没有选课关系" → 全外连接 |

##### 自然连接详细例子

```
R:               S:               R ⋈ S（自然连接）:
┌───┬───┬───┐    ┌───┬───┬───┐    ┌───┬───┬───┬───┐
│ A │ B │ C │    │ B │ C │ D │    │ A │ B │ C │ D │
├───┼───┼───┤    ├───┼───┼───┤    ├───┼───┼───┼───┤
│ 1 │ 2 │ 3 │    │ 2 │ 3 │ x │    │ 1 │ 2 │ 3 │ x │
│ 4 │ 5 │ 6 │    │ 5 │ 6 │ y │    │ 4 │ 5 │ 6 │ y │
│ 7 │ 8 │ 9 │    │ 8 │ 9 │ z │    │ 7 │ 8 │ 9 │ z │
└───┴───┴───┘    └───┴───┴───┘    └───┴───┴───┴───┘
公共属性 B, C 自动匹配，结果中 B, C 只出现一次（去重列）
```

##### 除运算详解（难点）⭐⭐⭐

**除运算** R ÷ S：假设 R(X, Y) 和 S(Y)，则 R ÷ S = { t[X] | 对任意 t[Y] ∈ S，都有 (t[X], t[Y]) ∈ R }

**大白话**：找出 R 中那些"与 S 中所有值都匹配"的 X 值。

**例子**：R(学生, 课程) = 选课记录，S(课程) = 全部课程，则 R ÷ S = 选了所有课程的学生。

```
R（选课表）:         S（全部课程）:      R ÷ S:
┌──────┬──────┐     ┌──────┐          ┌──────┐
│ 学生 │ 课程 │     │ 课程 │          │ 学生 │
├──────┼──────┤     ├──────┤          ├──────┤
│ 张三 │ 数学 │     │ 数学 │          │ 张三 │
│ 张三 │ 英语 │     │ 英语 │          └──────┘
│ 张三 │ 语文 │     │ 语文 │
│ 李四 │ 数学 │     └──────┘          （张三选了全部3门课，李四只选了2门）
│ 李四 │ 英语 │
└──────┴──────┘
```

**手算除运算的步骤（必考大题）**：

步骤1：求 R 在 X 上的投影 π<sub>学生</sub>(R) = {张三, 李四}
步骤2：对每个 X 值，找其对应的 Y 值集合：
   - 张三 → {数学, 英语, 语文}
   - 李四 → {数学, 英语}
步骤3：检查谁的 Y 值集合"包含"S 的全部值{数学, 英语, 语文} → 只有张三
步骤4：结果 R ÷ S = {张三}

**通用手算步骤（5步法）**：

1. 列出 R 中所有 X 值（消除重复）
2. 列出 S 中所有 Y 值
3. 对每个 X 值，找出它在 R 中对应的所有 Y 值，形成集合 Y<sub>X</sub>
4. 检查 Y<sub>X</sub> 是否**包含** S 中的所有 Y 值（即 S ⊆ Y<sub>X</sub>）
5. 满足条件的 X 值就是结果

**除运算的三种等价理解**：

| 理解方式 | 大白话 | 适用场景 |
|----------|--------|----------|
| 包含法 | "X 的 Y 集合包含 S 的全部 Y" | 手算时最直观 |
| 差运算法 | R÷S = π<sub>X</sub>(R) − π<sub>X</sub>((π<sub>X</sub>(R)×S) − R) | 关系代数理论推导 |
| 双重 NOT EXISTS | SQL 中用双重否定实现 | SQL 编程 |

**除运算在 SQL 中的实现（双重 NOT EXISTS）**：

```sql
-- 查询"选了所有课程的学生"
SELECT DISTINCT 学生 FROM R AS R1
WHERE NOT EXISTS (
    SELECT * FROM S
    WHERE NOT EXISTS (
        SELECT * FROM R AS R2
        WHERE R2.学生 = R1.学生 AND R2.课程 = S.课程
    )
);
```

**除法运算常见变体**：

| 变体 | 大白话 | 例子 |
|------|--------|------|
| 基本除法 | 包含S中全部值 | 选了所有课程的学生 |
| 至少除法 | 包含S中至少这些值 | 至少选了数学和英语的学生 |
| 精确除法 | 恰好包含S中的值（不多不少） | 恰好选了数学和英语（没选其他课）的学生 |

**考试注意事项**：
- 除法运算要求 S 的属性集必须是 R 的属性集的子集
- R 的属性集 = X ∪ Y，S 的属性集 = Y，结果只有 X 属性
- 结果的元组数 ≤ R 的元组数
- 如果 S 是空集，除法结果 = π<sub>X</sub>(R)（所有 X 值都满足"空条件"）

---

#### 易错点 4：选择 vs 投影，别搞混

- **选择 σ**：横向操作，筛**行**（对应 SQL 的 `WHERE`）
- **投影 π**：纵向操作，选**列**（对应 SQL 的 `SELECT` 后指定列名）

记忆方法：**选行投列**——"选择"就是"筛选行"，"投影"就是"选取列"。

---

#### 自然连接 vs 等值连接

| 类型 | 大白话 | 关键区别 |
|------|--------|----------|
| **等值连接** | 按某个条件（比如相等）把两张表拼起来 | 保留两个表的连接列（会有重复列） |
| **自然连接** | 自动找两张表中**同名的属性**，按这些属性相等来连接 | **自动去掉重复列** |

**自然连接 = 等值连接 + 去除重复列**。考试特别注意"自然连接会去掉重复属性"这句话。

**特殊情况**：当两个关系没有公共属性时，自然连接退化为**笛卡尔积**。

### 11.3 关系演算基本概念

关系演算是关系数据模型的另一种查询表示方式，与关系代数不同，它用**谓词逻辑**来描述查询。

#### 关系代数 vs 关系演算

| 对比维度 | 关系代数 | 关系演算 |
|----------|----------|----------|
| **表达方式** | 过程化（告诉系统"怎么做"） | 非过程化（告诉系统"要什么"） |
| **理论基础** | 集合论 | 数理逻辑（谓词演算） |
| **核心概念** | 运算符（σ, π, ⋈, ×, ∪, −, ÷） | 谓词公式（∀, ∃, ∧, ∨, ¬） |
| **典型代表** | — | 元组关系演算、域关系演算 |
| **查询风格** | 指定操作步骤 | 指定目标条件 |
| **SQL 关系** | SQL 同时包含两种风格（关系代数+关系演算） | SQL 的 WHERE 子句本质就是谓词公式 |

#### 关系代数 vs 关系演算：大白话类比

- **关系代数**：像厨师做菜，一步步告诉你"先切菜、再下锅、再翻炒、最后出锅"
- **关系演算**：像你点菜，直接说"我要一盘鱼香肉丝"，厨师自己知道怎么做

#### 元组关系演算（ALPHA 语言）

格式：`{t | P(t)}`，表示"所有满足谓词 P 的元组 t 的集合"。

**元组变量**：t 代表一个元组（一行），`t.属性名` 表示取元组 t 中某个属性的值。

**例子**：
- 查询所有男学生：`{t | 学生(t) ∧ t.性别 = '男'}`
  - 解读：t 是学生表中的元组，且 t 的性别属性值为"男"
- 查询选了"数据库"课程的学生：`{t | ∃u(选课(u) ∧ u.课程名 = '数据库' ∧ t.学号 = u.学号)}`
  - 解读：存在一个选课元组 u，它的课程名是"数据库"，且它的学号与 t 的学号相同
- 查询选了所有课程的学生：`{t | ∀u(课程(u) → ∃v(选课(v) ∧ v.课程号 = u.课程号 ∧ v.学号 = t.学号))}`
  - 解读：对任意课程 u，都存在一个选课记录 v，使得 v 的课程号是 u 的课程号，且 v 的学号是 t 的学号

**元组关系演算中的常用逻辑符号**：

| 符号 | 含义 | 大白话 |
|------|------|--------|
| ∧ | 与（AND） | "并且" |
| ∨ | 或（OR） | "或者" |
| ¬ | 非（NOT） | "不是" |
| ∃ | 存在量词 | "存在……使得" |
| ∀ | 全称量词 | "对所有的……都有" |
| → | 蕴含 | "如果……则……" |

#### 域关系演算（QBE 语言）

按域（属性值）来查询，格式：`{<x1, x2, ..., xn> | P(x1, x2, ..., xn)}`

**元组关系演算 vs 域关系演算**：

| 对比维度 | 元组关系演算 | 域关系演算 |
|----------|------------|------------|
| 基本变量 | 元组（行） | 域变量（列值） |
| 语法 | `{t \| P(t)}` | `{<x1, x2, ...> \| P(x1, x2, ...)}` |
| 典型语言 | ALPHA | QBE（Query By Example） |
| 查询方式 | 以元组为单位 | 以属性值为单位 |

**结论**：关系代数、元组关系演算和域关系演算三者在表达能力上是**等价**的（考试常考这个结论）。

**三者表达能力等价关系**：

```
关系代数 ⟺ 元组关系演算 ⟺ 域关系演算

三种方式都能表达相同的查询，只是表达风格不同：
- 关系代数：过程化（怎么做）
- 关系演算：非过程化（要什么）
```

**考试重点**：三个是等价的，不能说"关系代数比关系演算更强大"或"关系演算不能表达某些查询"。

### 11.4 四类完整性约束 ⭐⭐⭐

完整性约束 = 数据的"交通规则"，保证数据不乱七八糟。关系模型提供了**四类完整性约束**（注意：不同教材有"三类"和"四类"两种说法，华图讲义采用"四类"——在实体、参照、用户定义之外，单独把**域完整性**列出来，国网考试以四类为准）：

| 约束类型 | 核心规则 | 约束对象 | 由谁保证 | 违反后果 |
|----------|---------|---------|---------|---------|
| **实体完整性** | 主属性（主码）不能是 NULL，且必须唯一 | 基本关系（基本表） | DBMS 自动检查 | 插入/更新操作被拒绝 |
| **域完整性** | 列必须满足特定的数据类型、取值范围、精度 | 基本关系的属性（列） | DBMS 约束（CHECK/DEFAULT/NOT NULL） | 插入/更新操作被拒绝 |
| **参照完整性** | 外码要么是 NULL，要么等于被引用表中主码的某个值 | 基本关系（基本表） | DBMS 自动检查 | 操作被拒绝或触发级联操作 |
| **用户定义完整性** | 用户针对具体应用自定义的约束条件 | 具体应用 | 应用程序 + DBMS 约束 | 根据约束类型拒绝或警告 |

> **华图重点**：实体完整性和参照完整性约束条件合称为**关系的两个不变性**——即无论数据库怎么变，这两条规则都必须始终成立。
>
> **关于"三类" vs "四类"的说明**：很多教材把完整性约束归纳为"实体、参照、用户定义"三类（本笔记旧版也是三类）。华图讲义把"域完整性"单独列为一类，形成四类。两者的**本质内容是一致的**——域完整性要求列满足数据类型和取值范围，这部分内容在"三类"说法里通常被归入"用户定义完整性"。考试若考"关系模型有几类完整性约束"，按华图/国网口径答**四类**；若考"关系的两个不变性"，答**实体完整性 + 参照完整性**。

#### 实体完整性 - 详解

| 方面 | 说明 |
|------|------|
| **规则** | 如果属性 A 是关系 R 的主属性（属于候选码），则 A 不能取空值（NULL） |
| **原因** | 主码用于唯一标识每个元组，如果主码为空，就无法区分哪个元组是哪个 |
| **适用范围** | 只适用于**基本表**（Base Table），不适用于视图 |
| **复合主键** | 如果主码由多个属性组成，则**每个分量都不能为空** |
| **检查时机** | 插入（INSERT）和更新（UPDATE）时自动检查 |

**考试常见判断题**：
- "实体完整性要求主键不能重复" ✅（唯一性）
- "实体完整性要求主键不能为空" ✅（非空性）
- "实体完整性要求外键不能为空" ❌（那是参照完整性，外键可以为空）
- "实体完整性也适用于视图" ❌（只适用于基本表）

#### 域完整性 - 详解（华图新增，三类说法中常并入用户定义完整性）

| 方面 | 说明 |
|------|------|
| **规则** | 数据库表中的每一列必须满足特定的数据类型、取值范围、精度等约束，保证取值"合法" |
| **本质** | 限定某一列的值只能落在某个"合法域"（Domain）内 |
| **典型实现** | `CHECK`（取值范围）、`DEFAULT`（默认值）、`NOT NULL`（非空）、`FOREIGN KEY`（外键也属于域完整性范畴）、数据类型声明（如 INT、VARCHAR 的精度） |
| **例子** | 成绩列 `CHECK(成绩 >= 0 AND 成绩 <= 100)`；性别列只能是 '男'/'女'；年龄列 `CHECK(年龄 >= 0 AND 年龄 <= 150)` |

**NULL 的正确理解（华图重点）**：实体完整性要求主属性不能取空值 NULL。**NULL 不是 0、不是空格、不是空字符串**，而是表示"没有值 / 不知道 / 无意义"。考试常考"NULL 和 0 的区别"——0 是一个具体的数值，NULL 是"值不存在"。

**域完整性 vs 用户定义完整性**：两者容易混淆。华图把"列的数据类型、取值范围、精度"这类**针对单列取值合法性**的约束归为**域完整性**；把"用户针对具体业务自定义的、更复杂的规则"归为**用户定义完整性**（也称域完整性规则）。简单理解：域完整性管"这列能填什么类型的值"，用户定义完整性管"业务上还额外要求什么"。

#### 参照完整性 - 详解

| 方面 | 说明 |
|------|------|
| **规则** | 如果关系 R 的外码 F 引用关系 S 的主码 K，则 F 的每个值必须满足：要么等于 NULL，要么等于 S 中某个元组的 K 值 |
| **原因** | 保证引用关系之间的逻辑一致性，不会出现"引用不存在的数据"的情况 |
| **外码允许 NULL** | 外码可以为 NULL（表示"未知"或"不引用任何记录"） |
| **被引用表要求** | 被引用的属性必须是主码或具有唯一性约束 |
| **自引用** | 外码可以引用同一个表的主码（如：员工的上级领导编号） |

**级联操作（参照完整性触发规则）**：

| 策略 | 触发时机 | 动作 | 大白话 |
|------|---------|------|--------|
| **CASCADE**（级联） | 主表删除/更新 | 从表对应行自动删除/更新 | "主表变了，从表跟着变" |
| **SET NULL** | 主表删除/更新 | 从表外码字段设为 NULL | "主表记录没了，从表外键变空" |
| **RESTRICT**（限制） | 主表删除/更新 | 如果从表有引用，拒绝操作 | "有孩子就不能删" |
| **NO ACTION** | 主表删除/更新 | 同 RESTRICT，但检查时机在事务结束时 | "等事务结束再检查" |
| **SET DEFAULT** | 主表删除/更新 | 从表外码字段设为默认值 | "主表记录没了，从表外键用默认值" |

**级联操作例子**：
- 删除一个学生（学号 001），选课表中的 001 记录怎么办？
  - CASCADE：选课表中 001 的记录也自动删除
  - SET NULL：选课表中 001 的记录学号变为 NULL
  - RESTRICT：如果选课表中有 001 的记录，拒绝删除该学生

#### 用户定义完整性 - 详解

| 约束方式 | 说明 | SQL 实现 |
|----------|------|----------|
| **NOT NULL** 约束 | 某列不允许为空 | `姓名 VARCHAR(20) NOT NULL` |
| **UNIQUE** 约束 | 某列值必须唯一 | `身份证号 CHAR(18) UNIQUE` |
| **CHECK** 约束 | 自定义条件检查 | `CHECK(年龄 >= 0 AND 年龄 <= 150)` |
| **DEFAULT** 约束 | 默认值 | `性别 CHAR(2) DEFAULT '未知'` |
| **触发器（Trigger）** | 复杂的业务规则 | 自定义触发器 |

#### 四类完整性约束对比总结

| 对比维度 | 实体完整性 | 域完整性 | 参照完整性 | 用户定义完整性 |
|----------|-----------|---------|-----------|-------------|
| 约束对象 | 主码 | 列（属性） | 外码 | 任何属性 |
| 核心要求 | 非空 + 唯一 | 取值落在合法域内（类型/范围/精度） | 要么 NULL，要么真实存在 | 用户自定义规则 |
| 检查时机 | INSERT / UPDATE | INSERT / UPDATE | INSERT / UPDATE / DELETE | INSERT / UPDATE |
| 定义方式 | PRIMARY KEY | CHECK / DEFAULT / NOT NULL / 类型声明 | FOREIGN KEY ... REFERENCES | CHECK / NOT NULL / UNIQUE / 触发器 |
| 谁定义 | DBA 建表时 | DBA 建表时 | DBA 建表时 | 用户根据需要定义 |
| 举例 | 学号不能为空不能重复 | 成绩必须在 0-100 之间 | 选课表学号必须在学生表中存在 | 年龄在 0-150 之间 |

**记忆口诀**：
```
完整性约束四兄弟：
  实体看主键（非空唯一）
  域看列取值（类型、范围、精度合法）
  参照看外键（要么空，要么真实存在）
  用户自己定（业务规则，CHECK/NOT NULL/UNIQUE）

两个不变性要牢记：实体完整性 + 参照完整性
```

---

#### 易错点 5：实体完整性要求主码"非空且唯一"，不是"非空或唯一"

- 必须是**既非空又唯一**，缺一不可。
- 如果主码由多个属性组成（复合主键），则**每个分量都不能为空**。

### 11.5 例题（5道选择题）

> **例题 1**：关系数据库中的"关系"指的是 \_\_\_\_\_\_。
> A. 数据之间的关联  B. 一张二维表  C. 字段之间的对应关系  D. E-R 图中的联系
>
> **答案**：B。在关系模型中，"关系"正式定义是域的笛卡尔积的子集，直观上对应一张二维表。

> **例题 2**：设关系 R 有 3 个属性 4 个元组，关系 S 有 2 个属性 5 个元组，则 R × S 有 \_\_\_ 个属性，\_\_\_ 个元组。
> A. 5, 9  B. 5, 20  C. 6, 20  D. 6, 9
>
> **答案**：B。5 个属性（3 + 2）、20 个元组（4 × 5）。笛卡尔积属性相加、元组相乘。

> **例题 3**：自然连接中，当两个关系没有公共属性时，自然连接退化为 \_\_\_\_\_\_。
> A. 等值连接  B. 外连接  C. 笛卡尔积  D. θ 连接
>
> **答案**：C。因为没有公共属性就无法做属性相等匹配，只能是全组合（笛卡尔积）。

> **例题 4**：关系代数的五种基本运算是 \_\_\_\_\_\_。
> A. 并、差、交、选择、投影  B. 并、差、笛卡尔积、选择、投影  C. 并、交、笛卡尔积、连接、除  D. 并、差、选择、投影、连接
>
> **答案**：B。五种基本运算：并、差、笛卡尔积、选择、投影。交（∩）可以用差（−）表示：R∩S = R−(R−S)，所以交不是基本运算。连接和除也都是可由基本运算组合而成的。

> **例题 5**：在关系数据库中，当外码 F 是关系 R 的属性，且 F 引用关系 S 的主码 K 时，F 的值 \_\_\_\_\_\_。
> A. 可以为空  B. 不能为空  C. 为空或等于 S 中某个 K 值  D. 必须等于 S 中某个 K 值
>
> **答案**：C。参照完整性规定：外码要么为空（NULL），要么等于被引用关系中某个主码值。注意与实体完整性（主码不能为空）区分。

### 11.6 易错陷阱

| 陷阱 | 错误认知 | 正确认知 |
|------|----------|----------|
| 基本运算包含交 | 五种基本运算 = 并、差、交、笛卡尔积、选择 | 交可以用差表示，所以基本运算是"并、差、笛卡尔积、选择、投影" |
| 自然连接 vs 等值连接 | "自然连接就是等值连接" | 自然连接 = 等值连接 + 自动去掉重复列，是不等价的 |
| 投影是否去重 | "投影就是取几列，行数不变" | 投影会自动去重！π 的结果行数 ≤ 原表行数 |
| 除运算的理解 | 混淆 R÷S 中谁除谁 | R÷S 中，S 的属性必须是 R 的属性的子集，结果是 R 中那些"满足 S 所有值"的元组在剩余属性上的投影 |
| 外码能否为空 | "外码不能为空" | 外码可以为 NULL！参照完整性规定外码要么为空要么等于被引用主码值。主码才不能为空。 |

### 11.8 自测题

1. "候选码"和"主码"有什么区别？
2. 关系的哪几个基本性质是关系模型和其他模型的核心区别？
3. 关系代数中 σ 和 π 分别代表什么运算？它们在 SQL 中对应什么？
4. 自然连接和等值连接的关系是什么？
5. 如果一个学生转学了，他在选课表中的记录怎么处理？——这涉及什么完整性约束？

**自测题答案：**

1. **候选码**是能唯一标识一个元组的属性或属性组，一个关系可能有多个候选码（如学号、身份证号都是候选码）。**主码**是从候选码中选出的一个作为"正式代表"，一个关系只有一个主码。候选码和主码都必须满足"非空且唯一"。

2. 关系模型的核心性质：①每一列（属性）**不可再分**（满足1NF）；②每一列有**唯一的属性名**；③行的顺序和列的顺序**无关紧要**；④任意两行**不能完全相同**（关系是元组的集合）。这些性质是关系模型区别于层次/网状模型的核心——因为关系是"元组的集合"（数学概念），所以有集合的无序性、无重复性。

3. **σ（选择）**：横向操作，筛选**行**，对应 SQL 的 `WHERE`；**π（投影）**：纵向操作，选取**列**，对应 SQL 的 `SELECT 列名`（且自动去重，对应 `SELECT DISTINCT`）。

4. **自然连接 = 等值连接 + 去除重复列**。自然连接自动匹配**同名属性**并合并重复列，等值连接需要显式指定连接条件且保留重复列。当两个关系没有公共属性时，自然连接退化为**笛卡尔积**。

5. 涉及**参照完整性**约束。如果选课表中的学号是外键（引用学生表的主键），处理方式取决于级联策略：**CASCADE**=自动删除选课记录；**SET NULL**=选课记录中学号变NULL；**RESTRICT**=如果还有选课记录则拒绝删除学生。

## 知识点 12：关系数据库标准语言 SQL

> ⭐⭐⭐必考 —— SQL SELECT 执行顺序、GROUP BY+HAVING、JOIN 五种类型是得分核心

### 12.1 SQL 四大分类

| 类别 | 全称 | 功能 | 核心命令 |
|------|------|------|----------|
| **DDL** | Data Definition Language（数据定义语言）| 建表、修改表结构、删表 | `CREATE`, `ALTER`, `DROP` |
| **DML** | Data Manipulation Language（数据操纵语言）| 增删改数据 | `INSERT`, `UPDATE`, `DELETE` |
| **DQL** | Data Query Language（数据查询语言）| 查询数据 | `SELECT` |
| **DCL** | Data Control Language（数据控制语言）| 权限管理 | `GRANT`, `REVOKE` |

**记忆口诀**：DDL 管结构、DML 管数据、DQL 管查询、DCL 管权限。

---

### 12.2 DDL——建表和改表

```sql
-- 建表
CREATE TABLE 学生 (
    学号 CHAR(10) PRIMARY KEY,    -- 主键约束
    姓名 VARCHAR(20) NOT NULL,    -- 非空约束
    年龄 INT CHECK(年龄 >= 0 AND 年龄 <= 150),  -- 检查约束
    性别 CHAR(2) DEFAULT '未知'   -- 默认值
);

-- 改表：加一列
ALTER TABLE 学生 ADD 手机号 VARCHAR(11);

-- 删表
DROP TABLE 学生;
```

**DDL 典型例题**：

> **例题 1**：在 SQL 中，以下哪个命令用于修改表结构（如添加列）？
> A. UPDATE  B. ALTER  C. INSERT  D. MODIFY
>
> **答案**：B。ALTER 属于 DDL，用于修改表结构（添加列、删除列、修改列类型）。UPDATE 是 DML，用于修改数据行。

> **例题 2**：以下 SQL 语句中，属于 DDL 的是（ ）。
> A. SELECT * FROM 学生  B. INSERT INTO 学生 VALUES(...)  C. CREATE TABLE 课程(...)  D. GRANT SELECT ON 学生 TO user1
>
> **答案**：C。A 是 DQL，B 是 DML，D 是 DCL。只有 C 是 DDL（CREATE TABLE）。

**常见陷阱**：
- 陷阱1：`ALTER TABLE` 属于 DDL，不是 DML。因为它是修改**表结构**（元数据），不是修改**表数据**。
- 陷阱2：`CREATE`、`ALTER`、`DROP` 都是 DDL，它们操作的是数据库对象（表、视图、索引），不是数据行。
- 陷阱3：DDL 语句执行后**自动提交**（不能回滚），这与 DML 不同（DML 可以回滚）。

---

### 12.3 DML——增删改

```sql
-- 插入
INSERT INTO 学生(学号, 姓名, 年龄) VALUES ('2024001', '张三', 20);

-- 更新（一定要加 WHERE，否则全表更新！）
UPDATE 学生 SET 年龄 = 21 WHERE 学号 = '2024001';

-- 删除（同样一定要加 WHERE）
DELETE FROM 学生 WHERE 学号 = '2024001';
```

**DML 典型例题**：

> **例题 1**：在 SQL 中，将学生表中所有学生的年龄加 1 岁，正确的语句是（ ）。
> A. `UPDATE 学生 SET 年龄 = 年龄 + 1`  B. `UPDATE 学生 SET 年龄 = 年龄 + 1 WHERE *`  C. `ALTER 学生 SET 年龄 = 年龄 + 1`  D. `MODIFY 学生 SET 年龄 = 年龄 + 1`
>
> **答案**：A。UPDATE 是 DML 修改语句，不加 WHERE 就是对全表操作。B 的 WHERE * 语法错误，C 的 ALTER 只能改表结构，D 的 MODIFY 语法不存在。

> **例题 2**：以下关于 DELETE 和 TRUNCATE 的说法，**错误**的是（ ）。
> A. DELETE 是 DML，TRUNCATE 是 DDL
> B. DELETE 可以加 WHERE 条件，TRUNCATE 不能
> C. DELETE 删除后可以回滚，TRUNCATE 删除后不能回滚
> D. TRUNCATE 比 DELETE 慢，因为它需要记录日志
>
> **答案**：D。TRUNCATE 比 DELETE **快**（不是慢），因为 TRUNCATE 不记录每行删除的日志，直接释放数据页。A、B、C 都是正确的。

**常见陷阱**：
- 陷阱1：`UPDATE` 不加 `WHERE` → 全表更新！这是最常见的 DML 操作失误。写 UPDATE/DELETE 前务必确认 WHERE 条件是否正确。
- 陷阱2：`DELETE` 可以回滚（DML），`TRUNCATE` 不能回滚（DDL）。考试常考这个区别。
- 陷阱3：`INSERT INTO` 可以省略列名列表，但此时 VALUES 必须按表的列顺序提供所有列的值（含自增列和默认值列）。

---

#### 易错点 6：DELETE vs DROP vs TRUNCATE

| 命令 | 分类 | 作用 | 能回滚吗 | 删的是 |
|------|------|------|----------|--------|
| `DELETE` | DML | 删除数据行 | 可以（事务回滚）| 行数据 |
| `TRUNCATE` | DDL | 清空整张表 | 不能回滚 | 所有行 |
| `DROP` | DDL | 删除整张表（表都没了）| 不能回滚 | 表结构 + 数据 |

---

### 12.4 DQL——查询（最重要，考试占比最高）

#### SELECT 语句的完整语法和执行顺序 ⭐⭐⭐

**语法顺序**（我们写 SQL 时的顺序）：
```sql
SELECT [DISTINCT] 列名, 聚合函数        -- 第5步执行
FROM 表名 [JOIN 其他表 ON 条件]          -- 第1步执行
WHERE 条件                               -- 第2步执行
GROUP BY 分组列                          -- 第3步执行
HAVING 分组后条件                        -- 第4步执行
ORDER BY 排序列 [ASC|DESC]               -- 第6步执行
LIMIT 数量;                              -- 第7步执行
```

**执行顺序**（数据库实际处理的顺序，考试高频考点）：

```
FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT
  (1)    (2)       (3)        (4)       (5)        (6)       (7)
```

**每一步做了什么**：

| 步骤 | 关键字 | 做什么 | 大白话 |
|------|--------|--------|--------|
| 1 | FROM + JOIN | 加载表，执行连接，生成初始行集 | "把要用的表都拿出来" |
| 2 | WHERE | 对每一行做条件过滤 | "把不符合条件的行扔掉" |
| 3 | GROUP BY | 按指定列分组，每组变成一个"聚合行" | "把同类行堆成一摞" |
| 4 | HAVING | 对分组后的结果做条件过滤 | "把不符合条件的分组扔掉" |
| 5 | SELECT | 计算表达式、聚合函数，选出要显示的列 | "决定最终显示哪些列" |
| 6 | ORDER BY | 对结果排序 | "按你说的顺序排好" |
| 7 | LIMIT | 截取前 N 行 | "只要前几行" |

**关键推论**（考试高频考点）：
- `WHERE` 中不能使用 `SELECT` 中定义的**列别名**（因为 WHERE 在 SELECT 之前执行）
- `ORDER BY` 中可以使用列别名（因为 ORDER BY 在 SELECT 之后执行）
- `WHERE` 中不能使用**聚合函数**（因为聚合发生在 GROUP BY 阶段，WHERE 在它之前）
- `HAVING` 中可以使用聚合函数

**例子**：
```sql
-- 正确：别名用在 ORDER BY（在 SELECT 之后）
SELECT 系名, COUNT(*) AS 人数 FROM 学生 GROUP BY 系名 ORDER BY 人数 DESC;

-- 错误：别名用在 WHERE（在 SELECT 之前）
SELECT 学号, 成绩*1.1 AS 加权成绩 FROM 选课 WHERE 加权成绩 > 90;  -- 报错！
SELECT 学号, 成绩*1.1 AS 加权成绩 FROM 选课 WHERE 成绩*1.1 > 90;  -- 正确
```

#### 基本查询

```sql
-- 最基本的查询
SELECT 学号, 姓名 FROM 学生 WHERE 年龄 >= 18;

-- 去重
SELECT DISTINCT 性别 FROM 学生;

-- LIKE 模糊查询
-- % 匹配任意长度字符，_ 匹配单个字符
SELECT * FROM 学生 WHERE 姓名 LIKE '张%';   -- 姓张的
SELECT * FROM 学生 WHERE 姓名 LIKE '张_';   -- 张某（单名）
```

#### 聚合函数

| 函数 | 作用 | 注意 |
|------|------|------|
| `COUNT(*)` | 统计行数 | 包括 NULL 行 |
| `COUNT(列名)` | 统计某列非空值的个数 | 不算 NULL |
| `SUM(列名)` | 求和 | 忽略 NULL |
| `AVG(列名)` | 平均值 | 忽略 NULL |
| `MAX(列名)` | 最大值 | — |
| `MIN(列名)` | 最小值 | — |

#### GROUP BY 和 HAVING ⭐

**大白话**：GROUP BY 把行按某列分堆，然后每堆单独做聚合运算；HAVING 是"分组后的 WHERE"，用来筛选分组结果。

```sql
-- 查询每个系的学生人数，只要人数超过 50 的系
SELECT 系名, COUNT(*) AS 学生人数
FROM 学生
GROUP BY 系名
HAVING COUNT(*) > 50;
```

---

#### 易错点 7：WHERE 和 HAVING 的执行时机不同

| | WHERE | HAVING |
|------|-------|--------|
| **作用对象** | 原始行（分组前）| 分组后的聚合结果 |
| **能用聚合函数吗** | 不能 ❌ | 可以 ✅ |
| **执行顺序** | 先 WHERE 筛选 → 再 GROUP BY 分组 → 再 HAVING 筛选 |

**典型错误**：把 `WHERE COUNT(*) > 50` 写在 SQL 里——WHERE 不能跟聚合函数，必须用 HAVING。

---

#### 连接查询（JOIN）⭐

##### 五种连接类型详细对比

| JOIN 类型 | SQL 写法 | 大白话 | 结果说明 |
|-----------|----------|--------|----------|
| **交叉连接**（CROSS JOIN） | `FROM A CROSS JOIN B` | 笛卡尔积，每一行 × 每一行 | 无 ON 条件，结果行数 = 左表行数 × 右表行数 |
| **内连接**（INNER JOIN） | `FROM A INNER JOIN B ON 条件` | 两边都匹配的才留下 | 只返回匹配行，不匹配的行丢弃 |
| **左外连接**（LEFT OUTER JOIN） | `FROM A LEFT JOIN B ON 条件` | 左表全保留，右表配不上填 NULL | 左表所有行都在，右表没有匹配的列填 NULL |
| **右外连接**（RIGHT OUTER JOIN） | `FROM A RIGHT JOIN B ON 条件` | 右表全保留，左表配不上填 NULL | 右表所有行都在，左表没有匹配的列填 NULL |
| **全外连接**（FULL OUTER JOIN） | `FROM A FULL JOIN B ON 条件` | 两边都保留，配不上的填空 | 左表和右表所有行都保留，没有匹配的列填 NULL |

##### 详细例子

假设有两张表：
```
学生表 S:              选课表 SC:
┌──────┬──────┐        ┌──────┬──────┬───────┐
│ 学号 │ 姓名 │        │ 学号 │ 课程 │ 成绩  │
├──────┼──────┤        ├──────┼──────┼───────┤
│ 001  │ 张三 │        │ 001  │ 数学 │  85   │
│ 002  │ 李四 │        │ 001  │ 英语 │  90   │
│ 003  │ 王五 │        │ 003  │ 数学 │  78   │
└──────┴──────┘        └──────┴──────┴───────┘
```

**内连接结果**（INNER JOIN ON S.学号 = SC.学号）：
```
┌──────┬──────┬──────┬───────┐
│ 学号 │ 姓名 │ 课程 │ 成绩  │
├──────┼──────┼──────┼───────┤
│ 001  │ 张三 │ 数学 │  85   │
│ 001  │ 张三 │ 英语 │  90   │

└──────┴──────┴──────┴───────┘
-- 李四(002)没有选课记录，被丢弃了
```

**左外连接结果**（LEFT JOIN ON S.学号 = SC.学号）：
```

```

**交叉连接结果**（CROSS JOIN）—— 3×3 = 9 行，全排列：
```

│ 001  │ 张三 │ 003  │ 数学 │  78   │
```

#### 易错点 8：INNER JOIN 和 WHERE 连接的区别

早期 SQL 中 `FROM A, B WHERE A.id = B.id` 等价于 `INNER JOIN`，但现代标准推荐用 `JOIN ... ON`，逻辑更清晰。考试中两种写法都认识。

**注意**：`CROSS JOIN` 不加 ON 就是笛卡尔积。标准 SQL 中 `INNER JOIN` 必须带 ON 条件，不写 ON 会报语法错误（MySQL 例外，允许省略并退化为笛卡尔积）。

#### 子查询（嵌套查询）—— 相关子查询 vs 非相关子查询 ⭐

子查询就是"查询里面套查询"。按执行方式分为两类：

##### 非相关子查询（独立子查询）

子查询**不依赖**外层查询，先执行子查询得到结果，外层再使用这个结果。

```sql
-- 查询年龄大于平均年龄的学生
SELECT * FROM 学生
WHERE 年龄 > (SELECT AVG(年龄) FROM 学生);

-- 子查询只需执行一次，结果是一个数值，外层用这个数值过滤
```

**特点**：子查询只执行一次，效率较高。

##### 相关子查询（关联子查询）

子查询**依赖**外层查询的列值，外层每处理一行，子查询就执行一次。

```sql
-- 查询比本系平均年龄大的学生
SELECT * FROM 学生 s1
WHERE 年龄 > (
    SELECT AVG(年龄) FROM 学生 s2
    WHERE s2.系名 = s1.系名       -- 引用了外层的 s1.系名！
);

-- 对于外层每一行，先取出该学生的系名，再算该系的平均年龄，然后比较
```

**特点**：子查询多次执行，不能独立运行。

##### 对比总结

| 对比维度 | 非相关子查询 | 相关子查询 |
|----------|------------|------------|
| 能否独立运行 | 能 | 不能（依赖于外层） |
| 执行次数 | 1 次 | 外层每行执行 1 次 |
| 效率 | 通常较高 | 通常较低 |
| 典型关键字 | IN, 比较运算符 | EXISTS, NOT EXISTS |
| 例子 | `WHERE id IN (SELECT ...)` | `WHERE EXISTS (SELECT ... WHERE 外层.列 = 内层.列)` |

##### 子查询的三种典型用法

| 类型 | 关键字 | 大白话 | 例子 |
|------|--------|--------|------|
| 带 `IN` 的子查询 | `IN` / `NOT IN` | 判断值在不在子查询结果里 | 查选了"数据库"课的学生 |
| 带比较运算符 | `>`, `=`, `<` 等 | 子查询返回**单个值**，进行比较 | 查年龄大于平均年龄的学生 |
| 带 `EXISTS` | `EXISTS` / `NOT EXISTS` | 判断子查询有没有结果（返回布尔值）| 查至少选了一门课的学生 |

```sql
-- IN 子查询示例：查询选了"数据库"课程的学生姓名
SELECT 姓名 FROM 学生
WHERE 学号 IN (
    SELECT 学号 FROM 选课
    WHERE 课程号 = (
        SELECT 课程号 FROM 课程 WHERE 课程名 = '数据库'
    )
);

-- EXISTS 示例（相关子查询）：查询至少选了一门课的学生
SELECT 姓名 FROM 学生
WHERE EXISTS (
    SELECT * FROM 选课 WHERE 选课.学号 = 学生.学号
);
```

---

#### 易错点 9：EXISTS vs IN 的区别

- `IN`：子查询先执行，返回结果集，再外层匹配
- `EXISTS`：外层每查一行，就拿到子查询里问一句"有没有"，关联子查询
- `NOT IN` 有坑：如果子查询结果中有 NULL，则整条 `NOT IN` 返回空（NULL 跟任何值比较结果都是 UNKNOWN）
- 如果子查询结果集很大，`EXISTS` 通常比 `IN` 效率高（EXISTS 找到第一个匹配就返回 TRUE，不用扫描全部结果）

#### 集合操作（UNION / INTERSECT / EXCEPT）⭐

集合操作把两个查询的结果当作集合来处理：

| 操作 | 关键字 | 大白话 | 要求 |
|------|--------|--------|------|
| **并** | `UNION` / `UNION ALL` | 两个结果摞在一起 | 列数和类型一致 |
| **交** | `INTERSECT` | 两个结果都有的行 | 列数和类型一致 |
| **差** | `EXCEPT`（或 `MINUS`，Oracle 用 MINUS） | 在第一个结果但不在第二个结果中的行 | 列数和类型一致 |

**UNION vs UNION ALL**：
- `UNION`：自动去重（结果中不出现重复行）
- `UNION ALL`：不去重，保留所有行（效率更高）

```sql
-- 查询选了"数学"或"英语"的学生学号（去重）
SELECT 学号 FROM 选课 WHERE 课程 = '数学'
UNION
SELECT 学号 FROM 选课 WHERE 课程 = '英语';

-- 查询同时选了"数学"和"英语"的学生学号
SELECT 学号 FROM 选课 WHERE 课程 = '数学'
INTERSECT
SELECT 学号 FROM 选课 WHERE 课程 = '英语';

-- 查询选了"数学"但没选"英语"的学生学号
SELECT 学号 FROM 选课 WHERE 课程 = '数学'
EXCEPT
SELECT 学号 FROM 选课 WHERE 课程 = '英语';
```

**注意**：并非所有 DBMS 都支持 INTERSECT 和 EXCEPT（MySQL 5.x 不支持，需用 JOIN 或子查询替代；MySQL 8.0+ 已支持）。

#### 视图（View）⭐

**定义**：视图是从一个或几个基本表（或视图）导出的**虚表**。数据库中只存放视图的定义，不存放视图对应的数据。

**大白话**：视图就是一个"保存好的查询"，每次用视图时，数据库自动执行背后的 SELECT 语句。

```sql
-- 创建视图：学生选课汇总（隐藏了敏感字段）
CREATE VIEW 学生选课汇总 AS
SELECT S.学号, S.姓名, C.课程名, SC.成绩
FROM 学生 S
JOIN 选课 SC ON S.学号 = SC.学号
JOIN 课程 C ON SC.课程号 = C.课程号;

-- 使用视图：像查普通表一样查视图
SELECT * FROM 学生选课汇总 WHERE 成绩 > 80;

-- 删除视图
DROP VIEW 学生选课汇总;
```

##### 视图的作用

| 作用 | 大白话 | 例子 |
|------|--------|------|
| **简化查询** | 把复杂的 JOIN 封装成一个"虚拟表" | 建一个汇总视图，以后直接查 |
| **安全保护** | 隐藏敏感列，只暴露需要的数据 | 视图里不含身份证号、工资等敏感字段 |
| **逻辑独立性** | 基表结构变了，修改视图定义即可，应用程序不用改 | 拆分了大表，视图保持旧结构不变 |

##### 视图的更新条件 ⭐（考试高频考点）

**并非所有视图都可以更新**（INSERT/UPDATE/DELETE）。视图可更新的条件：

| 条件 | 说明 |
|------|------|
| 视图由**单个基本表**导出 | 涉及多表 JOIN 的视图通常不可更新 |
| 视图的列来自**基本表的列**，不是聚合函数或表达式 | 含 `COUNT(*)`、`AVG(列)`、`列*2` 的列不可更新 |
| 视图的行与基本表的行**一一对应** | 含 `GROUP BY`、`HAVING`、`DISTINCT` 的视图不可更新 |
| 视图定义中**没有** `UNION`、`INTERSECT`、`EXCEPT` 等集合操作 | 有集合操作的视图不可更新 |

**结论**：大多数 DBMS 只允许对**行列子集视图**（从单个基本表导出的、只包含某些行和某些列的简单视图）进行更新。

```sql
-- 可更新的视图：单表，无聚合，无 GROUP BY
CREATE VIEW 计算机系学生 AS
SELECT 学号, 姓名, 年龄 FROM 学生 WHERE 系名 = '计算机';

-- 不可更新的视图：有 GROUP BY + 聚合函数
CREATE VIEW 各系人数 AS
SELECT 系名, COUNT(*) AS 人数 FROM 学生 GROUP BY 系名;
```

### 12.5 DCL——权限管理

```sql
-- 授权
GRANT SELECT, INSERT ON 学生 TO 用户A;
-- 把"学生"表的查询和插入权限给用户A

-- 回收权限
REVOKE INSERT ON 学生 FROM 用户A;
```

**考试注意**：`GRANT` 和 `REVOKE` 属于 DCL，不要归到 DDL。

**DCL 典型例题**：

> **例题 1**：在 SQL 中，授予用户权限的命令 `GRANT` 属于（ ）。
> A. DDL  B. DML  C. DCL  D. DQL
>
> **答案**：C。`GRANT`（授权）和 `REVOKE`（回收权限）都属于 DCL（Data Control Language，数据控制语言）。这是考试中经常用来迷惑的考点——很多人误把 GRANT 归到 DDL。

> **例题 2**：SQL 语言中，`GRANT` 和 `REVOKE` 语句用于实现数据库的（ ）。
> A. 完整性控制  B. 安全性控制  C. 并发控制  D. 恢复控制
>
> **答案**：B。GRANT/REVOKE 实现的是**自主存取控制（DAC）**，属于数据库安全性控制。完整性控制靠主键/外键/CHECK约束实现，并发控制靠锁/MVCC实现，恢复控制靠日志/备份实现。

> **例题 3**：关于 `WITH GRANT OPTION` 的说法，正确的是（ ）。
> A. 允许被授权用户将权限再授予其他用户
> B. 自动授予所有权限
> C. 只能和 SELECT 权限一起使用
> D. 撤销权限时必须使用 CASCADE
>
> **答案**：A。`WITH GRANT OPTION` 允许被授权用户将获得的权限**转授**给其他用户。回收时如果用了 `WITH GRANT OPTION`，通常需要用 `CASCADE` 级联回收。

**常见陷阱**：
- 陷阱1：GRANT/REVOKE 属于 DCL，不是 DDL！这是考试最高频的分类题陷阱。
- 陷阱2：DCL 实现的是**安全性**控制（存取控制），不是完整性控制（完整性=约束）、不是并发控制（并发=锁/MVCC）、不是恢复控制（恢复=日志/备份）。
- 陷阱3：`REVOKE` 默认只回收直接授予的权限，如果被授权者又转授给了别人，需要加 `CASCADE` 才能级联回收。

### 12.5b 索引 ⭐⭐

索引是数据库中对表中一列或多列的值进行排序的一种存储结构，类似于书的**目录**——帮你快速定位内容，不用逐页翻。

#### 索引的作用和代价

| | 作用 | 大白话 |
|------|------|--------|
| **好处** | 大大加快数据检索速度 | 查字典不用一页页翻，先看拼音索引 |
| | 加速表之间的 JOIN 操作 | 连接时用索引列匹配，效率翻倍 |
| | 保证数据的唯一性（唯一索引） | 插入重复值会报错 |
| | 加快 ORDER BY 和 GROUP BY 操作 | 索引本身就是排好序的 |
| **代价** | 占用额外的存储空间 | 建了索引就要多占磁盘 |
| | INSERT/UPDATE/DELETE 会变慢 | 每次改数据都要同时维护索引 |

**考试判断题**：
- "索引一定能加速查询" ❌ → 如果查询返回大量行（超过表的 30%），全表扫描可能比索引更快
- "索引越多越好" ❌ → 索引多了反而降低增删改的性能
- "索引列可以为 NULL" ✅（除了主键索引）

#### 索引的四种分类

**（一）按物理存储分：聚集索引 vs 非聚集索引**

| 对比维度 | 聚集索引（Clustered Index） | 非聚集索引（Non-clustered Index） |
|----------|-------------------------|-------------------------------|
| **定义** | 数据行按索引键的顺序物理存储 | 索引结构和数据行分开存储 |
| **类比** | 拼音查字典——字的编排顺序就是拼音顺序 | 偏旁部首查字典——检字表中找到页码，再翻到那一页 |
| **叶节点内容** | 叶子节点 = 数据行本身 | 叶子节点 = 指向数据行的指针（行定位器） |
| **表可有几个** | **1 个**（数据只能按一种顺序排列） | **多个**（索引可以建多个） |
| **查询效率** | 直接拿到数据，更高 | 查到指针后还需一次 IO 才能拿到数据（回表） |
| **默认实现** | 主键自动创建聚集索引（InnoDB） | 普通索引、唯一索引默认是非聚集的 |

**（二）按逻辑功能分**

| 索引类型 | 说明 | 举例 |
|----------|------|------|
| **主键索引** | 为主键自动创建的索引，默认是聚集索引 | PRIMARY KEY 自动有索引 |
| **唯一索引** | 索引列的所有值必须唯一（允许 NULL） | 身份证号、邮箱 |
| **普通索引** | 没有任何限制，单纯加速查询 | 为经常查询的列建索引 |
| **复合索引** | 多个列组成一个索引 | 为 (地区, 年龄) 建复合索引 |
| **全文索引** | 对文本内容进行关键词搜索 | 搜索文章标题和正文 |

#### B+ 树索引原理 ⭐⭐⭐（必考）

**为什么用 B+ 树而不是红黑树？**

| 对比维度 | 红黑树（二叉树） | B 树 | B+ 树 |
|----------|----------------|------|-------|
| 每个节点存的键数 | 1 个 | 多个（阶数-1） | 多个（阶数-1） |
| 树的高度 | 高 | 矮 | 矮 |
| 磁盘 IO 次数 | 多 | 少 | 少 |
| 叶子节点存储 | 数据 | 数据 | **全部数据** |
| 非叶子存储 | 数据 | 数据 + 索引键 | **只存索引键** |
| 叶子节点链表 | 无 | 无 | **有（双向链表）** |
| 范围查询 | 需要中序遍历（多次 IO） | 需要中序遍历 | 叶子链表直接扫描（快） |

**B+ 树的核心特点（考试必考）**：
1. **所有数据都在叶子节点**，非叶子节点只存索引键值
2. **叶子节点之间用双向链表连接**，支持高效的范围查询（`BETWEEN`、`>`、`<`）
3. **所有叶子节点在同一层**，每次查询的 IO 次数相同（稳定）
4. **树的高度很低**（3-4层就能存上亿数据），查询效率高

```
B+ 树结构示意图：

                 [30 | 60]           ← 根节点（只存索引键）
                /    |    \
         [10|20]  [40|50]  [70|80]   ← 内部节点（只存索引键）
          / | \    / | \    / | \
        [1]→[10]→[20]→[30]→[40]→...→[80]  ← 叶子节点（存全部数据，链表连接）
```

**B+ 树查询过程**：从根节点出发，通过索引键值层层定位到叶子节点，在叶子节点中找到目标数据。每次查询的路径长度 = 树的高度。

**为什么数据库索引几乎都用 B+ 树而不用 B 树？**
- B+ 树的数据全在叶子，非叶子只存键 → 非叶子可以存更多键 → 树更矮 → IO 更少
- B+ 树叶子有链表 → 范围查询直接扫描链表（快）
- B+ 树查询效率稳定（每次都到叶子）

#### 最左前缀原则 ⭐⭐⭐（必考）

**定义**：对于复合索引（多列索引），查询条件必须从索引的最左边列开始匹配，且不能跳过中间的列，索引才会被使用。

**示例**：有一个复合索引 `INDEX idx_abc (a, b, c)`，相当于创建了三个索引：
- `(a)`
- `(a, b)`
- `(a, b, c)`

| 查询条件 | 是否使用索引 | 原因 |
|----------|:---:|------|
| `WHERE a = 1` | ✅ | 使用最左列 a |
| `WHERE a = 1 AND b = 2` | ✅ | 使用 (a, b) |
| `WHERE a = 1 AND b = 2 AND c = 3` | ✅ | 使用完整索引 (a, b, c) |
| `WHERE a = 1 AND c = 3` | ✅（部分） | 只用到 a 列（b 被跳过，c 用不上） |
| `WHERE b = 2` | ❌ | 没从最左列 a 开始 |
| `WHERE b = 2 AND c = 3` | ❌ | 没从最左列 a 开始 |
| `WHERE c = 3` | ❌ | 没从最左列 a 开始 |
| `WHERE a > 1 AND b = 2` | ✅（部分） | a 用范围查询，b 用不上索引 |

**最左前缀匹配原理**：复合索引按 (a, b, c) 的顺序构建 B+ 树——先按 a 排序，a 相同时按 b 排序，b 相同时按 c 排序。所以必须从 a 开始才能利用这个排序。

**设计建议**：
- 把等值查询条件中**区分度高**的列放在最左边
- 把范围查询（`>`, `<`, `BETWEEN`）的列放在复合索引的最后
- 复合索引的列数一般不超过 3-4 个

#### EXPLAIN 详解 ⭐⭐

`EXPLAIN` 是 SQL 查询分析工具，用来看一条 SQL 是怎么执行的——是否用了索引、扫描了多少行、连接顺序等。

```sql
EXPLAIN SELECT * FROM 学生 WHERE 姓名 = '张三';
```

**EXPLAIN 输出关键字段**：

| 字段 | 含义 | 关键值 | 说明 |
|------|------|--------|------|
| **id** | SELECT 执行顺序 | 数字越大越先执行 | 同 id 从上到下执行 |
| **select_type** | 查询类型 | SIMPLE / SUBQUERY / DERIVED | SIMPLE=简单查询，SUBQUERY=子查询 |
| **table** | 当前操作的表名 | — | — |
| **type** | **访问类型（重要！）** | 从好到差：system > const > eq_ref > ref > range > index > ALL | ALL=全表扫描（要优化） |
| **possible_keys** | 可能用到的索引 | 索引名 | 理论上可选的索引 |
| **key** | **实际使用的索引** | 索引名 / NULL | NULL 表示没用到索引（需要优化） |
| **key_len** | 索引使用的字节数 | 数字 | 越小说明用的索引列越少 |
| **ref** | 与索引比较的列或常量 | const / 列名 | 显示索引的哪一列被使用了 |
| **rows** | **预计扫描的行数** | 数字 | 越小越好，大说明效率低 |
| **Extra** | 额外信息 | Using index / Using filesort / Using temporary | Using index=覆盖索引（最优） |

**type 访问类型详解（从最优到最差）**：

| type 值 | 含义 | 大白话 | 例子 |
|---------|------|--------|------|
| **system** | 表中只有一行数据 | const 的特殊情况 | 系统表 |
| **const** | 通过主键或唯一索引查到一行 | 用唯一键查一行 | `WHERE id = 1` |
| **eq_ref** | 连接查询中被驱动表用主键匹配 | 连表查时对方用主键 | `JOIN ON b.id = a.id` |
| **ref** | 非唯一索引等值匹配 | 普通索引的等值查询 | `WHERE name = '张三'` |
| **range** | 索引范围扫描 | 用索引做范围查询 | `WHERE age > 18` |
| **index** | 全索引扫描（比全表好一点） | 扫描整个索引 | 查询的列全在索引里 |
| **ALL** | 全表扫描（最差） | 逐行扫描全表 | 没有任何索引可用 |

**Extra 关键值**：

| Extra 值 | 含义 | 好坏 |
|----------|------|:---:|
| **Using index** | 使用了覆盖索引（不需要回表） | 最优 ✅ |
| **Using where** | 使用了 WHERE 条件过滤 | 正常 ✅ |
| **Using index condition** | 使用了索引下推（ICP） | 较好 ✅ |
| **Using filesort** | 需要额外排序（没用到索引排序） | 需要优化 ⚠️ |
| **Using temporary** | 使用了临时表（GROUP BY 或 DISTINCT 导致） | 需要优化 ⚠️ |

#### 覆盖索引（Covering Index）

**定义**：查询所需的所有列都在索引中，不需要回表到主键索引中取数据。

**大白话**：索引里就有你要的所有数据，不用再去翻原表。

```sql
-- 假设有复合索引 idx_name_age (姓名, 年龄)
-- 覆盖索引！只查姓名和年龄，都在索引里
SELECT 姓名, 年龄 FROM 学生 WHERE 姓名 = '张三';

-- 不是覆盖索引！成绩不在索引里，需要回表查
SELECT 姓名, 年龄, 成绩 FROM 学生 WHERE 姓名 = '张三';
```

**覆盖索引 vs 回表**：
- 覆盖索引：Extra 显示 `Using index`，只访问索引就够了
- 回表查询：在二级索引中找不到所需列，要到聚集索引（主键索引）中取完整数据行

#### 创建索引的原则（考试常考）

| 应该创建索引 | 不应该创建索引 |
|-------------|---------------|
| 主键和外键列 | 很少使用的列 |
| 频繁出现在 WHERE 条件中的列 | 数据量很小的表 |
| 频繁出现在 JOIN ON 条件中的列 | 频繁增删改的列 |
| 频繁出现在 ORDER BY / GROUP BY 中的列 | 取值很少的列（如性别只有男/女，区分度低） |
| 复合索引优先考虑（而非多个单列索引） | 大字段（如 TEXT、BLOB 类型） |

**索引优化原则**：
1. **选择区分度高的列**建索引（如身份证号 > 性别）
2. **避免在索引列上使用函数或表达式**（如 `WHERE YEAR(日期) = 2024` 会导致索引失效）
3. **避免使用 SELECT ***（尽量用覆盖索引）
4. **复合索引注意最左前缀原则**
5. **小表不建索引**（全表扫描可能更快）

### 12.6 例题（5道选择题）

> **例题 1**：SQL 的 SELECT 语句中，下列子句的执行顺序正确的是 \_\_\_\_\_\_。
> A. SELECT → FROM → WHERE → GROUP BY → HAVING
> B. FROM → WHERE → GROUP BY → HAVING → SELECT
> C. FROM → GROUP BY → WHERE → HAVING → SELECT
> D. WHERE → FROM → GROUP BY → SELECT → HAVING
>
> **答案**：B。执行顺序为 FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY。

> **例题 2**：在 SQL 中，要查询"没有选任何课程的学生"，应使用 \_\_\_\_\_\_。
> A. `SELECT * FROM 学生 WHERE 学号 NOT IN (SELECT 学号 FROM 选课)`
> B. `SELECT * FROM 学生 WHERE 学号 IN (SELECT 学号 FROM 选课)`
> C. `SELECT * FROM 学生 LEFT JOIN 选课 ON 学生.学号 = 选课.学号`
> D. `SELECT * FROM 学生 WHERE EXISTS (SELECT * FROM 选课 WHERE 选课.学号 = 学生.学号)`
>
> **答案**：A。NOT IN 找出不在选课表中的学生。注意如果选课表的学号列有 NULL，NOT IN 可能返回空，此时需要用 NOT EXISTS。

> **例题 3**：关于视图，下列说法**错误**的是 \_\_\_\_\_\_。
> A. 视图是一个虚拟表，不存储实际数据
> B. 视图可以简化复杂的查询操作
> C. 包含 GROUP BY 的视图也可以进行更新操作
> D. 视图是数据库三级模式中外模式的实现方式之一
>
> **答案**：C。包含 GROUP BY、聚合函数、DISTINCT 等操作的视图是不可更新的。

> **例题 4**：SQL 中，UNION 和 UNION ALL 的区别是 \_\_\_\_\_\_。
> A. UNION 不去重，UNION ALL 去重
> B. UNION 去重，UNION ALL 不去重
> C. UNION 要求列名相同，UNION ALL 不要求
> D. 没有区别
>
> **答案**：B。UNION 自动消除重复行，UNION ALL 保留所有行（包括重复行），UNION ALL 效率更高。

> **例题 5**：以下子查询中，属于相关子查询的是 \_\_\_\_\_\_。
> A. `SELECT * FROM S WHERE age > (SELECT AVG(age) FROM S)`
> B. `SELECT * FROM S WHERE id IN (SELECT sid FROM SC WHERE score > 80)`
> C. `SELECT * FROM S WHERE EXISTS (SELECT * FROM SC WHERE SC.sid = S.id)`
> D. `SELECT * FROM S WHERE age = (SELECT MAX(age) FROM S)`
>
> **答案**：C。只有 C 中的子查询引用了外层 S.id，属于相关子查询。A、B、D 的子查询都可以独立执行。

### 12.7 易错陷阱

| 陷阱 | 错误认知 | 正确认知 |
|------|----------|----------|
| SELECT 执行顺序 | "SELECT 先执行，所以 WHERE 可以用别名" | SELECT 在第5步执行，WHERE 在第2步执行，WHERE 中不能用 SELECT 定义的别名 |
| WHERE vs HAVING | "WHERE count > 3" | WHERE 不能跟聚合函数！聚合函数的过滤必须用 HAVING |
| NOT IN + NULL | "NOT IN 总是返回正确结果" | 子查询结果中含有 NULL 时，NOT IN 返回空集（NULL 比较结果是 UNKNOWN） |
| 相关子查询判断 | "子查询中引用了外层的表就是相关子查询" | 正确！关联子查询的特征是内层子查询中使用了外层表的列 |
| 视图可更新 | "所有视图都能像表一样增删改" | 只有行列子集视图（单表、无聚合、无 GROUP BY）可以更新 |
| UNION vs UNION ALL | "用哪个都一样" | UNION 去重（额外排序开销大），UNION ALL 不去重（更快）。大多数场景用 UNION ALL 更高效 |
| 交叉连接 | "INNER JOIN 不加 ON 报错" | 标准 SQL 中 INNER JOIN 必须带 ON，漏写是语法错误；MySQL 是例外允许省略 |
| DDL vs DML vs DCL | "GRANT 属于 DDL" | GRANT/REVOKE 属于 DCL（数据控制语言），CREATE/ALTER/DROP 才是 DDL |

### 12.8 记忆口诀

```
SQL 执行有顺序：
  一 FROM 来二 WHERE 选
  三 GROUP BY 来分组
  四 HAVING 把组筛
  五 SELECT 定显示
  六 ORDER BY 排好队
  七 LIMIT 取前几

SQL 类别：
  DDL 管建表（CREATE/ALTER/DROP）
  DML 管数据（INSERT/UPDATE/DELETE）
  DQL 只查（SELECT）
  DCL 管权限（GRANT/REVOKE）

连接五种记心间：
  交叉笛积全组合
  内连只留匹配对
  左外全留左、右填 NULL
  右外全留右、左填 NULL
  全外两边都保留

子查询分两种：
  非相关独立先执行（IN）
  相关关联每行跑（EXISTS）
```

### 12.9 自测题

1. `SELECT` 属于 SQL 的哪个子语言？`GRANT` 呢？
2. `WHERE COUNT(*) > 3` 这种写法错在哪？
3. `LEFT JOIN` 和 `INNER JOIN` 的区别是什么？
4. 聚合函数中哪几个会忽略 NULL？
5. 用 `IN` 和 `EXISTS` 都能实现"查询至少选了一门课的学生"吗？写法分别是什么？
6. SELECT 语句中 FROM 和 SELECT 谁先执行？这意味着什么？
7. 包含 GROUP BY 的视图能更新吗？为什么？

**自测题答案：**

1. `SELECT` 属于 **DQL**（数据查询语言）；`GRANT` 属于 **DCL**（数据控制语言）。注意区分：CREATE/ALTER/DROP 是 DDL，INSERT/UPDATE/DELETE 是 DML。

2. **WHERE 子句中不能使用聚合函数**（COUNT、SUM、AVG、MAX、MIN）。聚合函数只能在 HAVING 子句中使用。正确写法：`HAVING COUNT(*) > 3`。原因：WHERE 在 GROUP BY 之前执行，此时还没有分组，聚合函数无法计算。

3. **INNER JOIN**（内连接）：只返回两表都匹配的行，不匹配的行丢弃。**LEFT JOIN**（左外连接）：返回左表的所有行，右表匹配不上的列填 NULL。口诀："内连只留匹配对，左外全留左、右填 NULL"。

4. 所有聚合函数**除 COUNT(\*)** 外都忽略 NULL：`SUM(列)`、`AVG(列)`、`MAX(列)`、`MIN(列)`、`COUNT(列)` 都忽略 NULL 值。只有 `COUNT(*)` 不忽略 NULL（统计所有行）。

5. 都能实现。

   **IN 写法**（非相关子查询）：
   ```sql
   SELECT 姓名 FROM 学生
   WHERE 学号 IN (SELECT DISTINCT 学号 FROM 选课);
   ```
   **EXISTS 写法**（相关子查询）：
   ```sql
   SELECT 姓名 FROM 学生
   WHERE EXISTS (SELECT * FROM 选课 WHERE 选课.学号 = 学生.学号);
   ```

6. **FROM 先执行，SELECT 后执行**（执行顺序：FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT）。这意味着：① WHERE 中不能用 SELECT 中定义的别名；② ORDER BY 中可以用别名（ORDER BY 在 SELECT 之后）。

7. **不能更新**。原因：包含 GROUP BY 的视图不是"行列子集视图"——视图的一行可能对应基表的**多行聚合结果**，DBMS 无法确定更新操作应该修改基表的哪一行。视图可更新的条件是：单表、无聚合函数、无 GROUP BY、无 DISTINCT、无集合操作。

## 知识点 13：事务与并发控制

> ⭐⭐⭐必考 —— ACID 四个特性定义、四种隔离级别对应关系是数据库最高频考点，每年必出1-2题

### 13.1 事务的 ACID 特性 ⭐⭐⭐

**事务**是用户定义的一个数据库操作序列，要么全做，要么全不做，是一个不可分割的工作单位。

**事务的定义（SQL 方式）**：
```sql
BEGIN TRANSACTION;     -- 开始事务
  操作1;
  操作2;
  ...
COMMIT;                -- 提交（确认所有修改）
-- 或
ROLLBACK;              -- 回滚（撤销所有修改）
```

#### ACID 四大特性详解

| 特性 | 全称 | 大白话 | 类比 | 底层实现机制 |
|------|------|--------|------|------------|
| **A** — 原子性 | Atomicity | 要么全做，要么全不做 | 转账：A扣100+B加100，两步必须一起成或一起败 | **Undo Log**（回滚日志），记录旧值用于撤销 |
| **C** — 一致性 | Consistency | 数据从一种正确状态变到另一种正确状态 | A+B总金额转账前后不变 | **程序员的业务逻辑** + DBMS 完整性约束检查 |
| **I** — 隔离性 | Isolation | 并发事务互不干扰 | 多个窗口同时办理业务，互不影响 | **锁机制**（S锁/X锁）+ **MVCC**（多版本并发控制） |
| **D** — 持久性 | Durability | 提交成功的数据永远不会丢 | 钱转到账就是真到账了，断电也不丢 | **Redo Log**（重做日志）+ **WAL原则**（先写日志后写数据） |

#### ACID 深入理解 ⭐

**（一）原子性（Atomicity）—— 靠 Undo Log 实现**

- 事务执行过程中，每次修改前先把旧值写入 Undo Log
- 如果事务需要回滚，就从 Undo Log 中取出旧值恢复
- **注意**：原子性是通过**撤销（UNDO）**实现的，不是"锁"实现的

**（二）一致性（Consistency）—— 是目标，不是手段**

- 一致性是保证原子性、隔离性、持久性的**最终目标**
- 原子性、隔离性、持久性都是实现一致性的**手段**
- 一致性的保证来自于：数据库的完整性约束 + 程序员正确编写的事务逻辑
- 如果程序员逻辑写错了（如转账只扣不加），DBMS 无法保证一致性

**（三）隔离性（Isolation）—— 靠锁和 MVCC 实现**

- 锁机制：S 锁（共享读锁）、X 锁（排他写锁）
- MVCC（多版本并发控制）：不通过加锁，而是保存数据历史版本实现并发
- 不同隔离级别 = 隔离程度的不同层次

**（四）持久性（Durability）—— 靠 Redo Log + WAL 实现**

- WAL（Write-Ahead Logging）原则：先写日志到磁盘，再修改数据
- 事务提交时，先把 Redo Log 刷到磁盘（持久化），才算提交成功
- 断电恢复时，可以通过 Redo Log 重做已提交的事务

#### ACID 特性易混淆辨析

| 常见混淆 | 纠正 |
|----------|------|
| "原子性就是事务不可分割" | 正确，但更多强调"要么全做要么全不做" |
| "一致性靠 DBMS 自动保证" | 不完全对，一致性也需要程序员写正确的事务逻辑 |
| "原子性靠锁实现" | 错！原子性靠 **Undo Log** 实现，锁是用来保证隔离性的 |
| "持久性 = 数据存到磁盘" | 不完全对，持久性靠 **Redo Log + WAL** 保证，不是直接写数据到磁盘 |

**类比**：银行转账——A 扣 100 元、B 加 100 元。
- **原子性**：A 扣款和 B 加款要么都做要么都不做（UNDO 撤消半途而废的）
- **一致性**：总金额 1000 → 转账后还是 1000（业务规则保证）
- **隔离性**：转账时别人不能同时操作 A 或 B 账号（锁 + MVCC）
- **持久性**：转账提交后，钱就真的到账了，断电也不丢（REDO 重做）

### 13.2 并发操作带来的四种问题（重点）⭐⭐⭐

当多个事务并发执行时，如果不加以控制，会产生以下四种问题。这四种问题是数据库中最高频的考点之一。

#### 13.2.1 丢失修改（Lost Update）—— 写-写冲突

**场景演示**：两个事务同时读取同一行并修改，后提交的覆盖前提交的。

| 时间 | 事务 T1 | 事务 T2 |
|------|--------|--------|
| t1 | `READ(A)` → 读到 1000 | |
| t2 | | `READ(A)` → 读到 1000 |
| t3 | A = A - 100 → `WRITE(A, 900)` | |
| t4 | COMMIT | |
| t5 | | A = A - 200 → `WRITE(A, 800)` |
| t6 | | COMMIT |

**最终**：A = 800，但正确结果应该是 1000 - 100 - 200 = 700。T1 的 -100 被 T2 覆盖消失了！

**本质**：写-写冲突。两个事务改了同一数据，后面的事务不知道前面的事务修改过。

**解决方案**：
- 加**排他锁（X 锁）**：T1 读 A 时就加 X 锁，T2 必须等 T1 释放锁后才能读
- 或使用**乐观锁**（版本号机制）

#### 13.2.2 脏读（Dirty Read）—— 读到了未提交的"脏"数据

**场景演示**：T1 读到了 T2 修改但未提交的数据，后来 T2 回滚了。

| 时间 | 事务 T1 | 事务 T2 |
|------|--------|--------|
| t1 | | `READ(A)` → 读到 1000 |
| t2 | | A = 2000 → `WRITE(A, 2000)`（未提交） |
| t3 | `READ(A)` → 读到 2000 ← 读到脏数据！ | |
| t4 | | **ROLLBACK**（回滚，A 恢复为 1000） |

T1 读到的 2000 是"脏数据"——它来自于一个后来回滚的事务，实际上 A 的值一直是 1000。

**本质**：读到了其他事务**未提交**的修改。

**解决方案**：将隔离级别设为**读已提交（Read Committed）**或更高。

#### 13.2.3 不可重复读（Non-repeatable Read）—— 同一行两次读，值不同

**场景演示**：T1 两次读同一行数据，中间 T2 修改并提交了该行。

| 时间 | 事务 T1 | 事务 T2 |
|------|--------|--------|
| t1 | `READ(A)` → 读到 1000 | |
| t2 | | `READ(A)` → 读到 1000 |
| t3 | | A = 2000 → `WRITE(A, 2000)` |
| t4 | | **COMMIT** |
| t5 | `READ(A)` → 读到 2000 ← 值变了！ | |

T1 在同一个事务内，两次读 A 得到不同的值（1000 vs 2000）。第二次读是在 T2 提交后。

**本质**：同一事务内，同一行数据被其他事务**修改并提交**（UPDATE 操作），导致两次读的值不同。

**解决方案**：将隔离级别设为**可重复读（Repeatable Read）**或更高。

#### 13.2.4 幻读（Phantom Read）—— 两次查同一条件，行数不同

**场景演示**：T1 两次查同一条件，中间 T2 插入了一行新数据并提交。

| 时间 | 事务 T1 | 事务 T2 |
|------|--------|--------|
| t1 | `SELECT COUNT(*) FROM 学生 WHERE 年龄>20` → 结果：5 行 | |
| t2 | | `INSERT INTO 学生 VALUES('006', '赵六', 21)` |
| t3 | | **COMMIT** |
| t4 | `SELECT COUNT(*) FROM 学生 WHERE 年龄>20` → 结果：6 行 ← 多了一行！ | |

T1 的两次查询结果行数不同——第二次多了一行"幻影"数据。

**本质**：同一事务内，同一条件查询的结果集行数被其他事务的 **INSERT/DELETE** 操作改变。

**解决方案**：将隔离级别设为**可串行化（Serializable）**。MySQL InnoDB 在可重复读级别通过**间隙锁（Gap Lock）**也解决了幻读。

#### 四种并发问题对比总结 ⭐

| 并发问题 | 冲突类型 | 触发操作 | 现象 | 最低防范级别 |
|----------|---------|---------|------|------------|
| **丢失修改** | 写-写冲突 | 两个事务同时写同一行 | 后提交的覆盖先提交的修改 | 所有隔离级别都能防（通过写锁） |
| **脏读** | 读-写冲突 | 读到别人未提交的修改 | 读到了"不存在"的数据 | Read Committed |
| **不可重复读** | 读-写冲突 | 别人UPDATE并提交后重读 | 同一行两次读值不同 | Repeatable Read |
| **幻读** | 读-写冲突 | 别人INSERT/DELETE后重查 | 同一条件两次查行数不同 | Serializable（MySQL RR 通过间隙锁也可防） |

**不可重复读 vs 幻读的核心区别（考试必考）**：

| 对比 | 不可重复读 | 幻读 |
|------|-----------|------|
| **操作类型** | UPDATE（修改已有行） | INSERT / DELETE（新增/删除行） |
| **变化内容** | 同一行数据的**值**变了 | 结果集的**行数**变了 |
| **侧重** | "读到的数据不一样了" | "读到的数据变多了/变少了" |
| **锁什么** | 行锁（锁定被修改的行） | 间隙锁 / 表锁（锁定行之间的间隙） |
| **谁说解决了** | Repeatable Read | Serializable（标准）；MySQL InnoDB RR（间隙锁） |

**考试记忆窍门**：
- 脏读 = T2 没提交，T1 就读了（回滚后数据"脏"了）
- 不可重复读 = T2 **提交后**，T1 再读同行的值变了（重点：**值**变了）
- 幻读 = T2 **提交后**，T1 再查行数多了/少了（重点：**行数**变了）

### 13.3 封锁机制 ⭐⭐⭐

封锁是并发控制最基本的手段。一个事务在操作数据之前，先对数据加锁，阻止其他事务操作该数据。

#### 两种基本锁类型

| 锁类型 | 全称 | 符号 | 含义 | 作用对象 | 兼容性 |
|--------|------|------|------|---------|--------|
| **共享锁** | Shared Lock | **S 锁** | "大家都能看，不能改"（读锁） | 只允许读操作 | S 与 S 兼容，S 与 X 不兼容 |
| **排他锁** | Exclusive Lock | **X 锁** | "我一个人用，别人不能看也不能改"（写锁） | 读+写都禁止他人 | X 与任何锁都不兼容 |

#### 锁兼容矩阵（必背）⭐

|  | 已持有 **S 锁** | 已持有 **X 锁** |
|--|:---:|:---:|
| 申请 **S 锁** | ✅ 兼容（可以同时读） | ❌ 冲突（要等待） |
| 申请 **X 锁** | ❌ 冲突（要等待） | ❌ 冲突（要等待） |

**记忆口诀**：S 锁只跟 S 锁兼容，X 锁跟谁都不兼容。

#### 封锁协议（Locking Protocol）

封锁协议是在运用 S 锁和 X 锁时约定的规则。三级封锁协议逐步解决不同的并发问题：

| 封锁协议 | 规则 | 解决的并发问题 | 不能解决的问题 |
|----------|------|:---:|:---:|
| **一级封锁协议** | 修改数据前先加 X 锁，事务结束后释放 | 丢失修改 ✅ | 脏读、不可重复读、幻读 |
| **二级封锁协议** | 一级 + 读数据前加 S 锁，读完即释放 | 丢失修改 ✅、脏读 ✅ | 不可重复读、幻读 |
| **三级封锁协议** | 一级 + 读数据前加 S 锁，事务结束后释放 | 丢失修改 ✅、脏读 ✅、不可重复读 ✅ | 幻读 |

#### 两段锁协议（2PL, Two-Phase Locking）⭐⭐⭐

**定义**：事务分为两个阶段——加锁阶段和释放锁阶段。
- **第一阶段（扩张阶段/加锁阶段）**：只能申请加锁，不能释放锁
- **第二阶段（收缩阶段/释放锁阶段）**：只能释放锁，不能申请加锁

**2PL 核心定理（考试必考）**：
- 遵守**两段锁协议**的事务，其并发的调度一定是**可串行化的**
- **可串行化**不一定满足两段锁协议（2PL 是充分条件，非必要条件）
- 2PL **不防止死锁**（可能死锁！）

**例子**（符合 2PL）：
```
事务 T：
  S_lock(A)  ← 扩张阶段
  X_lock(B)  ← 
  ...操作...  ← 
  Unlock(B)  ← 收缩阶段
  Unlock(A)  ← 
```
先集中加锁，再集中释放——这就是 2PL 的本质。

**例题判断**："如果一个并发调度的所有事务都遵守两段锁协议，则该调度一定是可串行化的"——正确 ✅

**2PL vs 一次封锁法**：

| 封锁方法 | 核心思想 | 优点 | 缺点 |
|----------|---------|------|------|
| **一次封锁法** | 事务开始时一次性申请所有需要的锁 | 不会死锁 | 锁的持有时间长，并发度低 |
| **两段锁协议（2PL）** | 分两阶段加锁和释放 | 保证可串行化，并发度高 | 可能死锁 |
| **顺序封锁法** | 所有事务按固定顺序申请锁 | 不会死锁 | 维护顺序困难 |

#### 封锁粒度 ⭐

| 粒度级别 | 封锁对象 | 并发度 | 系统开销 | 适用场景 |
|----------|---------|:---:|:---:|----------|
| **表级锁** | 整张表 | 低 | 小（只需管理几个锁） | 大量更新、全表操作 |
| **页面锁** | 磁盘页 | 中等 | 中等 | 中间选择 |
| **行级锁** | 表中的一行 | 高 | 大（需要管理大量锁） | 频繁的单行操作 |
| **字段锁** | 表中的某个字段 | 最高 | 极大 | 极少使用 |

**多粒度封锁**：现代 DBMS 支持同时在多个粒度上加锁（表锁+行锁）。通常采用**意向锁**（IS/IX）来实现多粒度锁的快速冲突检测。

| 意向锁类型 | 含义 |
|-----------|------|
| **IS 锁**（意向共享锁） | "我打算在孙子节点上加 S 锁" |
| **IX 锁**（意向排他锁） | "我打算在孙子节点上加 X 锁" |

### 13.4 隔离级别（重点）⭐⭐⭐

隔离级别定义了并发事务之间互相隔离的程度。SQL 标准定义了四种隔离级别，从低到高越来越严格。

| 隔离级别 | 丢失修改 | 脏读 | 不可重复读 | 幻读 | 实现方式 | 默认使用 |
|----------|:---:|:---:|:---:|:---:|----------|------|
| **READ UNCOMMITTED**（读未提交） | ❌ 防 | 允许 | 允许 | 允许 | 不加锁 | 几乎不用 |
| **READ COMMITTED**（读已提交） | ❌ 防 | ❌ 防 | 允许 | 允许 | MVCC（每次SELECT生成新ReadView） | Oracle 默认、PostgreSQL 默认 |
| **REPEATABLE READ**（可重复读） | ❌ 防 | ❌ 防 | ❌ 防 | 允许（标准） | MVCC（事务期间复用同一ReadView） | MySQL InnoDB 默认 |
| **SERIALIZABLE**（可串行化） | ❌ 防 | ❌ 防 | ❌ 防 | ❌ 防 | 表锁/范围锁，所有事务串行执行 | 极少使用 |

**说明**：丢失修改通过写锁（X 锁）在所有隔离级别都能防止，所以全部标注为"防"。

#### MySQL InnoDB 的特殊之处

MySQL InnoDB 的 **REPEATABLE READ** 级别通过**间隙锁（Gap Lock）+ 临键锁（Next-Key Lock）**也解决了幻读，优于 SQL 标准的要求。

| 锁类型 | 锁范围 | 解决的并发问题 |
|--------|--------|:---:|
| **Record Lock**（记录锁） | 锁定索引中的某一条记录 | 防止该行被修改（不可重复读） |
| **Gap Lock**（间隙锁） | 锁定记录之间的"间隙" | 防止在该间隙插入新数据（幻读） |
| **Next-Key Lock**（临键锁） | Record Lock + Gap Lock | 同时防止不可重复读和幻读 |

**Next-Key Lock 范围**：(上一个记录, 当前记录]，左开右闭。

#### 各隔离级别下的事务行为演示

假设有 100 行数据。T1 执行 `SELECT COUNT(*) WHERE age > 20`，T2 同时执行 `INSERT INTO students VALUES (101, '赵六', 21)`。

| 隔离级别 | T1 第一次读 | T2 INSERT | T1 第二次读 | 结果是否一致 |
|----------|-----------|-----------|-----------|:---:|
| READ UNCOMMITTED | 5 行 | 插入但未提交 | 6 行（脏读） | 不一致 |
| READ COMMITTED | 5 行 | 插入并提交 | 6 行（幻读） | 不一致 |
| REPEATABLE READ（MySQL） | 5 行 | 插入（被间隙锁阻塞） | 5 行 | 一致 |
| SERIALIZABLE | 5 行 | 插入（被表锁阻塞） | 5 行 | 一致 |

#### 设置隔离级别的 SQL

```sql
-- 查看当前隔离级别
SELECT @@transaction_isolation;   -- MySQL 8.0+
SELECT @@tx_isolation;            -- MySQL 5.x

-- 设置隔离级别
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SET SESSION TRANSACTION ISOLATION LEVEL SERIALIZABLE;
```

### 13.5 MVCC（多版本并发控制）⭐⭐

MVCC（Multi-Version Concurrency Control，多版本并发控制）是现代数据库（如 MySQL InnoDB、PostgreSQL）实现高并发读写的核心技术。

#### MVCC 的核心思想

**大白话**：不通过"加锁"来控制并发，而是给每条数据保留多个"历史版本"。每个事务读取时，读到的是**数据的一个快照版本**，而不是最新版本。这样读操作不会阻塞写操作，写操作也不会阻塞读操作。

**类比**：像 Git 的版本控制——每次修改都会创建新版本，你可以随时切换到某个历史版本查看，别人继续修改也不影响你看到的版本。

#### MVCC 的实现机制

每条数据记录有两个隐藏列：

| 隐藏列 | 名称 | 含义 | 大小 |
|--------|------|------|------|
| **trx_id** | 事务 ID | 最近修改这条记录的事务 ID | 6 字节 |
| **roll_pointer** | 回滚指针 | 指向这条记录的上一个版本（Undo Log 中） | 7 字节 |

#### ReadView（读视图/快照）⭐

每个事务在执行快照读时会生成一个 **ReadView**，包含三个关键信息：

| 字段 | 含义 |
|------|------|
| **m_ids** | 生成 ReadView 时，当前活跃的（未提交的）事务 ID 列表 |
| **min_trx_id** | m_ids 中的最小值 |
| **max_trx_id** | 当前系统已分配的最大事务 ID + 1 |
| **creator_trx_id** | 生成这个 ReadView 的事务自己的 ID |

#### 可见性判断规则

对于一条数据的某个版本（trx_id = data_trx_id），当前事务能否看到：

| 条件 | 能/不能看到 | 原因 |
|------|:---:|------|
| `data_trx_id == creator_trx_id` | ✅ 能看到 | 自己修改的当然能看 |
| `data_trx_id < min_trx_id` | ✅ 能看到 | 修改这条数据的事务在 ReadView 创建前就提交了 |
| `data_trx_id >= max_trx_id` | ❌ 不能看 | 修改这条数据的事务在 ReadView 创建后才开始 |
| `min_trx_id <= data_trx_id < max_trx_id` 且该事务在 m_ids 中 | ❌ 不能看 | 修改这条数据的事务在 ReadView 创建时还未提交 |
| `min_trx_id <= data_trx_id < max_trx_id` 且该事务不在 m_ids 中 | ✅ 能看到 | 修改这条数据的事务在 ReadView 创建时已经提交了 |

**如果当前版本不可见，就沿着 roll_pointer 找到上一个版本，继续判断，直到找到可见版本。**

#### READ COMMITTED vs REPEATABLE READ 在 MVCC 中的区别

| 对比 | READ COMMITTED（读已提交） | REPEATABLE READ（可重复读） |
|------|-------------------------|--------------------------|
| **ReadView 生成时机** | 每次 SELECT 都生成一个**新的** ReadView | 只在**第一次 SELECT** 时生成 ReadView，后续复用同一个 |
| **效果** | 每次读都能看到最新已提交的数据 | 整个事务期间看到的都是同一个快照 |
| **能否防止不可重复读** | 不能 ❌ | 能 ✅ |

**这解释了为什么 REPEATABLE READ 能防止不可重复读**：ReadView 只生成一次，后续再用同一个视图去判断可见性，所以读到的数据始终一致。

#### MVCC 的三大优势（vs 纯锁机制）

| 优势 | 说明 |
|------|------|
| **读写不互斥** | 读操作（快照读）不加锁，不阻塞写操作 |
| **高并发性能** | 多个事务可以同时读取数据的不同版本 |
| **一致性和性能兼得** | 在保证一致性的前提下，避免了大量加锁开销 |

### 13.6 死锁（Deadlock）⭐⭐

#### 死锁的概念

两个或多个事务互相等待对方释放锁，形成循环等待，导致所有事务都无法继续执行。

**死锁例子**：

| 时间 | 事务 T1 | 事务 T2 |
|------|--------|--------|
| t1 | 给 A 加 X 锁 ✅ | |
| t2 | | 给 B 加 X 锁 ✅ |
| t3 | 请求给 B 加 X 锁 → **等待 T2 释放** | |
| t4 | | 请求给 A 加 X 锁 → **等待 T1 释放** |
| 结果 | T1 等 T2 放 B，T2 等 T1 放 A → 死锁！ |

#### 死锁的四个必要条件

| 条件 | 说明 | 在数据库中的体现 |
|------|------|---------------|
| **互斥条件** | 资源不能共享，一时刻只能一个事务使用 | X 锁的排他性 |
| **请求保持条件** | 已持有资源，又申请新资源，被拒绝后不释放已有资源 | T1 持有 A 的锁，又申请 B 的锁 |
| **不可抢占条件** | 不能强行夺走别人持有的资源 | 不能强行释放别人的锁 |
| **循环等待条件** | 事务之间形成资源等待的环 | T1 等 T2，T2 等 T1 |

#### 死锁的预防（Prevention）

死锁预防的本质是"破坏四个必要条件之一"：

| 方法 | 原理 | 破坏哪个条件 | 优缺点 |
|------|------|:---:|------|
| **一次封锁法** | 事务开始时一次性申请所有需要的锁 | 破坏"请求保持" | 优点：简单，无死锁；缺点：锁持有时间长，并发度低 |
| **顺序封锁法** | 所有事务按预先规定的固定顺序申请锁 | 破坏"循环等待" | 优点：无死锁；缺点：维护顺序困难，事务需求难预测 |

> 注意：**两段锁协议（2PL）不防止死锁**！这是高频考点。

#### 死锁的检测（Detection）

**等待图法（Wait-for Graph）**：为每个事务画一个节点，如果 T1 等待 T2 的锁，画一条 T1→T2 的有向边。如果图中出现**环**，说明存在死锁。

```
等待图例：
  T1 ──→ T2
   ↑      │
   └──────┘
   
T1→T2→T1 形成环 → 存在死锁！
```

**检测时机**：定期检测（如每隔一定时间检查一次等待图），或在事务等待超时时检测。

#### 死锁的解除（Recovery）

| 方法 | 操作 |
|------|------|
| **选一个牺牲者**（Victim Selection） | 选一个事务回滚（通常选开销最小的：修改少、运行时间短的事务） |
| **回滚牺牲者** | 回滚选中的事务，释放它持有的所有锁 |
| **防止饿死** | 同一个事务不能总是被选为牺牲者，需要记录回滚次数 |

#### 死锁预防 vs 检测 vs 解除 对比

| 策略 | 时机 | 方法 | 特点 |
|------|------|------|------|
| **预防** | 死锁发生前 | 破坏必要条件 | 预防永久消除死锁，但并发度降低 |
| **检测** | 运行中 | 等待图找环 | 不阻止死锁发生，但能及时发现 |
| **解除** | 死锁发生后 | 选牺牲者回滚 | 简单粗暴，回滚浪费工作 |

### 13.7 活锁（Livelock）

#### 活锁的概念

**活锁**是指事务虽然没有死锁（没有被永久挂起），但因为某些原因一直在等待、重试，**永远得不到执行机会**。

#### 活锁 vs 死锁

| 对比 | 死锁（Deadlock） | 活锁（Livelock） |
|------|----------------|-----------------|
| **状态** | 事务完全阻塞，无法继续 | 事务一直在动（等待、重试），但无法完成 |
| **现象** | 互相等待，僵住了 | 频繁重试，就是抢不到锁 |
| **类比** | 两辆车在十字路口互不相让 | 一扇门前两人同时想进，同时退让、又同时上前，一直循环 |
| **检测** | 等待图中有环 | 没有环，事务在"活动"但无效 |

#### 活锁的产生场景

多个事务频繁申请 S 锁读数据，写锁申请者（X 锁）一直等待，导致**写事务饥饿**。

#### 活锁的解决方法

**先来先服务（FCFS）策略**：按申请锁的顺序排队，"先排队的事务优先获得锁"，避免某个事务总也抢不到锁。

#### 死锁/活锁对比表

| 对比维度 | 死锁 | 活锁 |
|----------|------|------|
| 事务状态 | 阻塞等待 | 不断重试（在运行，但不前进） |
| 能否自行解除 | 不能，需要外力干预 | 理论上可能自行解除（偶然抢到锁） |
| 检测方法 | 等待图法（检查环） | 超时检测（等太久就说明有问题） |
| 解决方法 | 选牺牲者回滚 | 先来先服务排队策略 |
| 考试频率 | ⭐⭐⭐（高频） | ⭐（偶尔出现） |

**例题 1**：事务的原子性是指（ ）
A. 事务一旦提交，对数据库的改变是永久的
B. 事务中包括的所有操作要么都做，要么都不做
C. 一个事务内部的操作及使用的数据对并发的其他事务是隔离的
D. 事务必须使数据库从一个一致性状态变到另一个一致性状态

> **答案：B**。A 是持久性，C 是隔离性，D 是一致性。口诀："原全不做，隔不干扰，一状态变，持永不变"。

**例题 2**：若事务 T 对数据 R 加了 S 锁，则其他事务对数据 R（ ）
A. 可以加 S 锁，不能加 X 锁　B. 可以加 X 锁，不能加 S 锁
C. 可以加 S 锁，也可以加 X 锁　D. 不能加任何锁

> **答案：A**。S 锁只允许再加 S 锁，不允许加 X 锁。口诀："S 锁让大家一起看，但不让改"。

**例题 3**：关于死锁，下列说法正确的是（ ）
A. 死锁是操作系统中的问题，数据库操作中不存在
B. 防止死锁的方法是禁止两个用户同时操作数据库
C. 当两个用户竞争相同资源时不会发生死锁
D. 只有出现并发操作时，才有可能出现死锁

> **答案：D**。没有并发就没有死锁。死锁的四个必要条件：互斥、请求保持、不可抢占、循环等待。

**例题 4**：在数据库系统中，死锁属于（ ）
A. 系统故障　B. 事务故障　C. 介质故障　D. 程序故障

> **答案：B**。死锁是事务故障的一种。事务故障还包括：运算溢出、违反完整性约束、主动回滚等。

### 13.7 易错陷阱

1. **一致性 vs 原子性**：一致性是"状态正确"（目标），原子性是"要么全做要么全不做"（手段）。
2. **不可重复读 vs 幻读**：不可重复读是 UPDATE 导致的同一行值变化，幻读是 INSERT/DELETE 导致的行数变化。
3. **2PL 保证可串行化但不防死锁**：死锁需要额外的检测和解除机制。
4. **MySQL InnoDB 的 REPEATABLE READ 可通过间隙锁解决幻读**，这是 MySQL 特有的。

### 13.8 记忆口诀

> **ACID**：原全做或全不做，隔并发互不扰，一状态保持对，持提交永不变。
> **并发问题**：丢修改（覆盖写）、脏读（读未提交）、不可重复（同行值变）、幻读（行数变）。
> **锁**：S 锁大家看，X 锁独占改；S 与 S 兼容，X 与谁都不兼容。
> **隔离级别递增**：读未提交最宽松 → 读已提交防脏读 → 可重复读防重复 → 可串行化全防住。

## 知识点 14：数据库备份与恢复

> ⭐⭐中高频 —— 故障类型区分（事务故障/系统故障/介质故障）、恢复策略是概念辨析题常客

### 14.1 故障类型 ⭐

数据库系统中可能发生的故障可分为三类，这是考试概念题的重要考点：

| 故障类型 | 别称 | 含义 | 破坏范围 | 对应恢复策略 |
|----------|------|------|---------|------------|
| **事务故障** | 事务内部故障 | 单个事务自身出错，无法正常完成 | 只影响该事务 | **UNDO**（撤销该事务） |
| **系统故障** | 软故障（Soft Crash） | 系统停转，内存数据丢失，**磁盘数据完好** | 所有正在运行但未提交的事务 | **UNDO**（未完成事务）+ **REDO**（已完成但未写盘事务） |
| **介质故障** | 硬故障（Hard Crash） | **磁盘损坏**，数据库文件被破坏 | 整个数据库或部分数据 | **后备副本 + REDO 日志** |

#### 三种故障一眼区分法

| 故障 | 关键判断词 | 内存数据 | 磁盘数据 | 举例 |
|------|-----------|:---:|:---:|------|
| 事务故障 | "某个事务出错了" | 当事务丢 | 完好 | 死锁、违反约束、运算溢出、主动回滚 |
| 系统故障 | "机器重启/断电了" | **全丢** | 完好 | CPU 故障、断电、OS 崩溃、DBMS 异常终止 |
| 介质故障 | "硬盘坏了" | 全丢 | **损坏** | 磁盘磁头碰撞、磁盘扇区损坏、存储设备故障 |

**关键区别**：系统故障丢**内存**数据，介质故障丢**磁盘**数据。

**考试常考判断题**：
- "死锁属于系统故障" ❌ → 死锁属于**事务故障**
- "断电属于介质故障" ❌ → 断电属于**系统故障**（内存丢，磁盘完好）
- "磁盘损坏后只需重新安装 DBMS" ❌ → 需要**后备副本 + 日志文件**恢复

### 14.2 数据转储（备份）⭐⭐

数据转储就是定期把数据库完整复制到另一个存储介质（磁带、磁盘、云存储等）上。这是数据库恢复的基础手段。

#### 按转储状态分类

| 类型 | 别称 | 操作方式 | 优点 | 缺点 | 适用场景 |
|------|------|---------|------|------|----------|
| **静态转储** | 冷备份（Cold Backup） | 系统停止运行，在无事务运行时做全量备份 | 数据一致性好，简单可靠 | 需要停机，影响业务 | 银行核心系统、非24小时系统 |
| **动态转储** | 热备份（Hot Backup） | 系统正常运行中做备份，同时记录备份期间的日志 | 不停机，不中断服务 | 备份数据可能不一致，需要日志配合恢复 | 互联网应用、电商系统 |

**动态转储的一致性问题**：备份过程中可能有些数据被修改了，导致备份中的数据是"半新半旧"的。解决方法：备份时必须同时记录备份期间的日志，恢复时用日志将备份数据恢复到一致状态。

#### 按转储方式分类

| 类型 | 操作 | 优点 | 缺点 |
|------|------|------|------|
| **海量转储** | 每次备份**全部**数据库 | 恢复简单（一份全量就行） | 耗时长、占用空间大 |
| **增量转储** | 每次只备份**上次备份以来变化的部分** | 时间短、占用空间小 | 恢复复杂（需要全量 + 多个增量） |

#### 转储策略组合

| 策略 | 做法 | 恢复时需要的文件 |
|------|------|---------------|
| **全量备份** | 定期做海量转储 | 只需最新全量备份 + 之后的日志 |
| **全量 + 增量** | 定期做海量转储，期间做增量转储 | 最近全量 + 所有后续增量 + 日志 |
| **全量 + 差异** | 定期做海量转储，期间备份"上次全量以来的变化" | 最近全量 + 最近差异 + 日志 |

**常用策略**：每周日全量备份 + 每天增量备份 + 持续日志备份。

**数据转储典型例题**：

> **例题 1**：在数据库运行过程中，边运行边进行数据备份的方式称为（ ）。
> A. 静态转储  B. 动态转储  C. 海量转储  D. 增量转储
>
> **答案**：B。动态转储（热备份）允许数据库在运行状态下进行备份，无需停机。静态转储需要停机。

> **例题 2**：关于增量转储的叙述，正确的是（ ）。
> A. 增量转储每次备份全部数据库  B. 增量转储的恢复速度比海量转储快  C. 增量转储每次只备份上次转储以来变化的数据  D. 增量转储的数据一致性最好
>
> **答案**：C。增量转储每次只备份变化部分，节省时间和空间，但恢复时需要"全量 + 多个增量"，恢复较慢。A 是海量转储，B 说反了（海量转储恢复更快），D 与数据一致性无关。

> **例题 3**：以下关于静态转储和动态转储的对比，**错误**的是（ ）。
> A. 静态转储需要停止数据库运行  B. 动态转储可以在数据库运行时进行  C. 静态转储的数据一致性比动态转储好  D. 动态转储不需要日志文件配合
>
> **答案**：D。动态转储**必须**配合日志文件——因为备份期间可能有数据被修改，备份中的数据可能不一致，需要日志文件在恢复时修正。A、B、C 都是正确的。

**常见陷阱**：
- 陷阱1：动态转储的数据可能不一致（备份期间有修改），所以**必须配合日志文件**使用。考试常考"动态转储不需要日志"这个错误选项。
- 陷阱2：增量转储节省空间但恢复慢（需要逐个应用增量），海量转储占用空间但恢复快（一份全量即可）。"增量转储恢复更快"是常见错误认知。
- 陷阱3：静态转储 = 冷备份（需停机），动态转储 = 热备份（不需停机）。冷/热指的是数据库是否在运行，不是指温度。

### 14.3 日志文件 ⭐⭐

#### 日志的作用

日志文件是用来记录事务对数据库每一次更新操作的文件。它是数据库恢复的**核心工具**。

**日志文件的两个核心作用**：
1. **事务故障恢复**：通过 UNDO 撤销未完成事务
2. **系统故障恢复**：通过 UNDO 撤销未完成事务 + REDO 重做已完成事务

#### 日志记录的格式

每条日志记录包含以下信息：

| 字段 | 含义 | 示例 |
|------|------|------|
| **事务标识** | 哪个事务执行的操作 | `T1` |
| **操作类型** | 开始/更新/提交/回滚 | `START` / `UPDATE` / `COMMIT` / `ABORT` |
| **操作对象** | 被修改的数据项 | `A` |
| **旧值**（前像） | 修改前的值（用于 UNDO） | `1000` |
| **新值**（后像） | 修改后的值（用于 REDO） | `900` |

**典型日志记录类型**：
```
<T1, START>              ← 事务 T1 开始
<T1, A, 1000, 900>       ← T1 将 A 从 1000 改为 900
<T1, B, 500, 600>        ← T1 将 B 从 500 改为 600
<T1, COMMIT>             ← T1 提交
```

#### WAL 原则（Write-Ahead Logging，先写日志）⭐⭐⭐

**定义**：在把数据修改写入数据库磁盘之前，必须先把对应的日志记录写入日志文件（磁盘）。

```
WAL 原则的写入顺序：
  1. 先把日志记录刷到日志文件磁盘
  2. 再把数据修改刷到数据库磁盘

"先写日志，后写数据"
```

**WAL 为什么重要**：
- 假设备份过程中断电：如果先写数据、后写日志 → 数据写了但没日志记录 → 无法恢复
- 先写日志、后写数据 → 即使数据没来得及写，日志里有记录 → 可以 REDO 重做

**WAL 的两个核心规则**：
1. 事务提交前，其所有日志记录必须先写入磁盘
2. 数据修改写入磁盘前，对应的日志记录必须先写入磁盘

**考试必考点**：
- "日志文件只记录更新操作（INSERT/UPDATE/DELETE），不记录查询操作（SELECT）"
- "WAL = Write-Ahead Logging = 先写日志，后写数据库"

### 14.4 恢复策略 ⭐⭐⭐

不同故障类型对应不同的恢复策略：

| 故障类型 | 恢复策略 | 操作说明 | 需要的工具 |
|----------|---------|---------|-----------|
| **事务故障** | **UNDO** | 反向扫描日志，撤销该事务的所有修改操作（用旧值覆盖新值） | 日志文件 |
| **系统故障** | **UNDO + REDO** | ① UNDO：撤销所有未完成（未提交）的事务；② REDO：重做所有已完成（已提交）但未写入磁盘的事务 | 日志文件 |
| **介质故障** | **后备副本 + REDO** | ① 用最近的后备副本恢复数据库到备份时的状态；② 从日志文件中 REDO 备份后所有已提交的事务 | 后备副本 + 日志文件 |

#### 恢复策略详细操作

**（一）事务故障恢复（只 UNDO）**

步骤：
1. 反向扫描日志文件（从日志末尾往前扫描）
2. 找到该事务的所有更新操作记录
3. 对每条更新记录，执行**反向操作**（用旧值替代新值）
4. 继续反向扫描，直到读到此事务的 START 记录为止

**（二）系统故障恢复（UNDO + REDO）**

步骤：
1. 正向扫描日志，建立两个事务列表：
   - **UNDO 列表**：日志中有 `<Ti, START>` 但没有 `<Ti, COMMIT>` 的事务
   - **REDO 列表**：日志中有 `<Ti, START>` 也有 `<Ti, COMMIT>` 的事务
2. 反向扫描日志，对 UNDO 列表中的每个事务执行 UNDO 操作
3. 正向扫描日志，对 REDO 列表中的每个事务执行 REDO 操作

**（三）介质故障恢复（副本 + REDO）**

步骤：
1. 将最近的后备副本（数据库备份）恢复到新的磁盘上
2. 从日志文件中找出备份时间点之后的所有已提交事务
3. 按时间顺序（正向扫描）对每条日志记录执行 REDO 操作
4. 恢复完成

#### 恢复策略对比速查

| 对比维度 | 事务故障恢复 | 系统故障恢复 | 介质故障恢复 |
|----------|-----------|------------|------------|
| 需要日志文件 | ✅ | ✅ | ✅ |
| 需要后备副本 | ❌ | ❌ | ✅（必备） |
| 有 UNDO | ✅ | ✅（未完成事务） | ❌ |
| 有 REDO | ❌ | ✅（已完成但未写盘事务） | ✅（备份后的全部已提交事务） |
| 扫描方式 | 反向扫描 | UNDO 反向 + REDO 正向 | 正向扫描 |

### 14.5 检查点机制（Checkpoint）⭐⭐

#### 检查点的作用

**大白话**：检查点是"存档点"。有了检查点，系统故障恢复时不需要从头扫描整个日志，只需要从最近的检查点开始扫描，大大缩短恢复时间。

#### 设置检查点的操作

| 步骤 | 操作 | 目的 |
|:---:|------|------|
| 1 | 将日志缓冲区中的所有日志记录写入磁盘 | 确保日志不丢失 |
| 2 | 在日志文件中写入一条 `<Checkpoint, L>` 记录，L 是当前所有活跃事务的列表 | 标记检查点位置 |
| 3 | 将数据缓冲区中的所有修改写入磁盘 | 确保数据持久化 |
| 4 | 记录检查点在日志文件中的地址到"重新启动文件" | 方便下次恢复定位 |

#### 利用检查点的恢复步骤 ⭐

1. 从"重新启动文件"找到最后一个检查点的日志地址
2. 从该检查点开始，正向扫描日志文件
3. 建立 UNDO 列表和 REDO 列表：
   - 初始时，UNDO 列表 = 检查点记录中 L 的所有事务
   - REDO 列表 = 空
   - 扫描过程中：遇到 START → 加入 UNDO 列表；遇到 COMMIT → 从 UNDO 列表移到 REDO 列表
4. 扫描完毕后：
   - UNDO 列表中的事务 → 反向扫描，执行 UNDO
   - REDO 列表中的事务 → 从检查点开始正向扫描，执行 REDO

#### 检查点的恢复优势

```
无检查点：从日志头 ─────────────────→ 日志尾（扫描整个日志）
有检查点：从上一个 Checkpoint ──────→ 日志尾（只扫描检查点之后的部分）
```

**考试重点**：
- 检查点**之前**提交的事务 → 不需要 REDO（数据已经写盘了）
- 检查点**之后**提交的事务 → 需要 REDO
- 检查点之前未提交的事务（在 L 列表中） → 需要 UNDO

### 14.6 数据库镜像 ⭐

#### 镜像的概念

**数据库镜像**是将数据库从一个磁盘自动复制到另一个磁盘（镜像磁盘），保证一个磁盘损坏时另一个磁盘可以立刻接管。

**大白话**：数据库实时"影子分身术"，主数据库写一份，镜像数据库同时写一份。主库坏了，影子立马上岗。

#### 镜像的作用

| 作用 | 说明 |
|------|------|
| **介质故障恢复** | 镜像磁盘上有一份完整的数据副本，无需重装副本和 REDO |
| **提升可用性** | 主磁盘损坏可立即切换到镜像磁盘，几乎无停机时间 |
| **并发读取** | 可以让读操作访问镜像磁盘，减轻主磁盘负担 |

#### 镜像的方式

| 方式 | 操作 | 优点 | 缺点 |
|------|------|------|------|
| **同步镜像** | 每次修改同时写入主磁盘和镜像磁盘 | 数据一致性高 | 写入性能降低 |
| **异步镜像** | 先写主磁盘，延迟写入镜像磁盘 | 写入性能好 | 可能有少量数据不一致（主盘已写但镜像盘未写） |

#### 镜像 vs 备份

| 对比 | 数据库镜像 | 数据库备份 |
|------|-----------|-----------|
| **更新频率** | 实时同步 | 定期执行 |
| **数据时效** | 几乎实时 | 有延迟（上次备份时） |
| **恢复速度** | 秒级切换 | 需要较长时间还原 |
| **存储开销** | 需要双倍磁盘 | 磁带/云存储，成本低 |
| **防误操作** | 不能防（误删数据镜像也删了） | 可以恢复历史版本 |
| **防介质故障** | ✅ 能 | ✅ 能 |

**数据库镜像典型例题**：

> **例题 1**：数据库镜像技术主要用于（ ）。
> A. 提高查询速度  B. 防止介质故障导致的数据丢失  C. 防止用户误操作  D. 提高并发性能
>
> **答案**：B。数据库镜像的核心作用是**介质故障恢复**——主磁盘损坏时，镜像磁盘可以立即接管。镜像不能防止误操作（误删数据镜像也会同步删除），不是主要用来提高查询速度或并发性能的。

> **例题 2**：以下关于数据库镜像的说法，正确的是（ ）。
> A. 镜像可以防止用户误删除数据  B. 同步镜像的写入性能比异步镜像好  C. 镜像数据库与主数据库实时或近实时保持一致  D. 镜像可以替代数据库备份
>
> **答案**：C。A 错（误删除会同步到镜像），B 错（同步镜像需要在两个磁盘都写完后才返回，写入性能较异步差），D 错（镜像不能替代备份——备份可以恢复到历史时间点，镜像只能反映当前状态）。

**常见陷阱**：
- 陷阱1："镜像可以防止误操作"——错！镜像实时同步，误删数据也会同步删除。防误操作要靠**备份**（可以恢复到误删之前的时间点）。
- 陷阱2："镜像可以替代备份"——错！镜像和备份是互补关系：镜像防介质故障（秒级切换），备份防误操作和历史数据恢复（可恢复到历史时间点）。
- 陷阱3："同步镜像和异步镜像没有区别"——错！同步镜像要求两个磁盘都写成功才算完成（性能差但一致性好），异步镜像先写主磁盘再异步写镜像（性能好但可能有延迟不一致）。

### 14.5 例题精讲

**例题 5**：日志文件用于记录（ ）
A. 程序运行过程　B. 数据操作　C. 对数据的所有更新操作　D. 对数据的所有查询操作

> **答案：C**。日志只记录更新操作（INSERT/UPDATE/DELETE），不记录 SELECT。

**例题 6**：系统故障后，恢复时需要对未完成的事务执行（ ）
A. REDO　B. UNDO　C. UNDO+REDO　D. 不需要操作

> **答案：B**。未完成的事务只需 UNDO。已完成事务才需要 REDO。

**例题 7**：介质故障的恢复需要（ ）
A. 只需要日志文件　B. 只需要后备副本　C. 后备副本和日志文件　D. 不需要恢复

> **答案：C**。先恢复后备副本，再根据日志 REDO 后续修改。

**例题 8**：以下关于检查点的说法，错误的是（ ）
A. 检查点可以缩短恢复时间
B. 检查点前已提交的事务不需要 REDO
C. 检查点后的事务一定需要 REDO
D. 系统定期设置检查点

> **答案：C**。检查点后**未完成**的事务需要 UNDO，不是"一定需要 REDO"。

### 14.6 易错陷阱

1. **事务故障只需 UNDO**，系统故障需要 UNDO+REDO。
2. **日志只记录更新操作，不记录查询操作**。
3. **WAL 原则**：先写日志，后写数据库。
4. **介质故障恢复 = 后备副本 + 日志文件**，两者缺一不可。

### 14.7 记忆口诀

> **三种故障**：事务错（死锁），系统挂（断电），介质坏（磁盘损坏）。
> **恢复技术**：转储存副本，日志记修改。先写日志后写库（WAL）。
> **恢复策略**：事务故障只 UNDO，系统故障 UNDO+REDO，介质故障需副本+日志。
> **检查点**：定期设标记，恢复从此起，不扫全日志。

## 知识点 15：数据库应用设计与性能优化

> ⭐⭐⭐必考 —— ER图转关系模式（M:N单独建表）、范式判断是大题必考点

### 15.1 数据库设计的 6 个阶段

| 阶段 | 主要任务 | 产出物 | 依赖 DBMS? |
|------|---------|--------|:---:|
| 1. 需求分析 | 了解用户需求 | 需求说明书、数据流图、数据字典 | 否 |
| 2. 概念结构设计 | 抽象为信息结构 | **ER 图** | 否 |
| 3. 逻辑结构设计 | ER 图 → 关系模式 | 关系模式集合 | 是 |
| 4. 物理结构设计 | 确定存储和索引 | 存储安排、索引设计 | 是 |
| 5. 数据库实施 | 建表、写程序、装数据 | 实际数据库 | 是 |
| 6. 运行与维护 | 监控、调优、备份 | 运行中的数据库 | 是 |

**口诀**：需概逻物实维（需求→概念→逻辑→物理→实施→维护）。

### 15.2 ER 图基本元素

| 元素 | 图形 | 说明 |
|------|------|------|
| 实体 | 矩形框 | 客观存在的事物（学生、课程） |
| 属性 | 椭圆形 | 实体的特性（学号、姓名），码用下划线标出 |
| 联系 | 菱形框 | 实体之间的关系（1:1 / 1:N / M:N） |

**联系的三种类型**：
- **1:1**：一个班级有一个班主任，一个班主任管一个班级
- **1:N**：一个班级有多个学生，一个学生属于一个班级
- **M:N**：一个学生选多门课，一门课有多个学生选

**ER图典型例题**：

> **例题 1**：在 E-R 图中，用来表示"联系"的图形是（ ）。
> A. 矩形  B. 椭圆形  C. 菱形  D. 三角形
>
> **答案**：C。矩形=实体，椭圆形=属性，菱形=联系。这是 E-R 图三大要素的图形符号，必须熟记。

> **例题 2**：在 E-R 图中，如果一个属性可以从其他属性推导出来，这种属性称为（ ），用（ ）表示。
> A. 复合属性，椭圆  B. 派生属性，虚线椭圆  C. 多值属性，双椭圆  D. 原子属性，椭圆
>
> **答案**：B。派生属性（如年龄可从出生日期推算）用**虚线椭圆**表示。复合属性用椭圆表示（可拆分），多值属性用**双椭圆**表示。

> **例题 3**：弱实体在 E-R 图中的表示方式是（ ）。
> A. 矩形  B. 双矩形  C. 菱形  D. 双菱形
>
> **答案**：B。弱实体用**双矩形**表示，弱实体与强实体的联系用**双菱形**表示。弱实体依赖于强实体存在，没有独立的主键。

**常见陷阱**：
- 陷阱1：E-R 图的三大图形符号——矩形（实体）、椭圆（属性）、菱形（联系）——不要记混！考试常有"联系用什么图形表示"这种送分题。
- 陷阱2：E-R 图是**概念模型**的工具，不是逻辑模型。E-R 图独立于 DBMS，与具体数据库无关。
- 陷阱3：属性类型符号要区分——普通椭圆（基本属性）、双椭圆（多值属性）、虚线椭圆（派生属性）、下划线（码/主键）。

### 15.3 ER 图转关系模式（重点）

| 联系类型 | 转换方法 | 示例 |
|----------|---------|------|
| **1:1** | 合并到任意一端，或将联系单独建表 | 班级↔班主任：在班级表加"班主任号"字段 |
| **1:N** | **必须合并到 N 端**，1 端主键作为 N 端外键 | 班级(1)↔学生(N)：在学生表加"班级号"外键 |
| **M:N** | **必须单独建表**，包含两端主键+联系属性 | 学生(M)↔课程(N)：建"选课表(学号, 课程号, 成绩)" |

**M:N 转换示例**：
```
学生表（学号, 姓名）           ← 实体
课程表（课程号, 课程名）        ← 实体
选课表（学号, 课程号, 成绩）    ← M:N 联系，主键 = (学号+课程号)
```

### 15.4 规范化理论（重点）

**函数依赖**：X → Y 表示"知道 X 就能唯一确定 Y"。如"学号→姓名"。

**三种特殊依赖**：
- **完全函数依赖**：(学号, 课程号) → 成绩，单独学号和课程号都不能确定成绩
- **部分函数依赖**：(学号, 课程号) → 姓名，但只需学号就能确定姓名
- **传递函数依赖**：学号 → 系号 → 系主任，系主任传递依赖于学号

**各级范式**：

| 范式 | 核心要求 | 判断口诀 | 违反举例 |
|------|---------|---------|---------|
| **1NF** | 属性不可再分 | "一格一值" | 一个格子里存两个电话号码 |
| **2NF** | 消除非主属性对码的**部分依赖** | "全依赖码" | (学号,课程号)为主键，但姓名只依赖学号 |
| **3NF** | 消除非主属性对码的**传递依赖** | "不依赖非码" | 学号→系号→系主任 |
| **BCNF** | 消除主属性对码的部分和传递依赖 | "所有决定因素都含码" | 3NF 加强版，考试偶尔涉及 |

**范式关系**：1NF ⊃ 2NF ⊃ 3NF ⊃ BCNF（从低到高越来越严格）

**BCNF 经典案例**：R(S, J, T)，S=学生，J=课程，T=老师。每位老师只教一门课(T→J)，一门课有多个老师，学生选课配老师。候选码为(S,J)和(S,T)。但 T→J 说明存在主属性对候选码的部分依赖 → 属于 3NF 但不属于 BCNF。

### 15.5 模式分解 ⭐⭐

模式分解是将一个关系模式分解为多个关系模式，目的是消除数据冗余和操作异常。

#### 分解的目标

| 目标 | 含义 | 大白话 |
|------|------|--------|
| **无损连接分解** | 分解后自然连接能**精确恢复**原关系，既不丢元组也不多出元组 | "拆开了还能拼回去，不多也不少" |
| **保持函数依赖分解** | 分解后各子模式的函数依赖并集**等价于**原函数依赖集 | "原来有哪些约束，拆开后还能推导出来" |

#### 无损连接分解的判断方法

**二分解判定法**（将 R 分解为 R1 和 R2 两个子关系）：

R 被分解为 R1 和 R2，则分解是无损连接的**当且仅当**：
- **(R1 ∩ R2) → (R1 - R2)** 成立，**或者**
- **(R1 ∩ R2) → (R2 - R1)** 成立

即：两个子关系的公共属性，能函数决定其中一个子关系的其余属性。

**判定步骤**：
1. 计算公共属性集 = R1 ∩ R2
2. 计算 R1 独有属性集 = R1 - R2
3. 计算 R2 独有属性集 = R2 - R1
4. 检查公共属性是否能决定 R1 独有属性，或决定 R2 独有属性
5. 如果任何一个成立 → 无损；都不成立 → 有损

**例子**：

```
R(学号, 姓名, 系名, 系主任)，F = {学号→姓名, 学号→系名, 系名→系主任}

分解1：R1(学号, 姓名, 系名)，R2(系名, 系主任)
  公共属性 = 系名
  R1独有 = {学号, 姓名}
  R2独有 = {系主任}
  系名→系主任 ∈ F⁺？✅ 是的（已知 F 中就有）
  → R1 ∩ R2 → R2 - R1 成立
  → 无损 ✅

分解2：R1(学号, 姓名)，R2(系名, 系主任)
  公共属性 = ∅（无公共属性）
  无法判断依赖 → 有损 ❌
```

#### 保持函数依赖的判断

将 R 分解为 R1, R2, ..., Rn，投影到每个子模式的函数依赖集的**并集**，如果等价于原函数依赖集 F，则保持函数依赖。

**判断步骤**：
1. 计算每个子关系 Ri 上的函数依赖投影 π<sub>Fi</sub>(F)
2. 取所有投影的并集 G = π<sub>F1</sub>(F) ∪ π<sub>F2</sub>(F) ∪ ... ∪ π<sub>Fn</sub>(F)
3. 检查 G⁺ == F⁺（闭包等价）

**保持函数依赖 ≠ 无损连接**：
- 一个分解可能无损但不保持函数依赖
- 一个分解可能保持函数依赖但不是无损的
- 我们追求两者兼得

#### 重要结论（考试必考）⭐⭐⭐

| 范式 | 能否保证无损分解？ | 能否保证保持函数依赖？ | 能否两者兼顾？ |
|------|:---:|:---:|:---:|
| **3NF** | ✅ 能 | ✅ 能 | ✅ **总能同时满足** |
| **BCNF** | ✅ 能 | ❌ 不一定 | ❌ 两者不能同时保证 |

**考试核心结论**：3NF 总能实现无损连接且保持函数依赖的分解，BCNF 不一定能保持函数依赖。

**BCNF 不能保持函数依赖的例子**：
```
R(城市, 街道, 邮编)，F = {(城市,街道)→邮编, 邮编→城市}
候选码：(城市, 街道) 和 (街道, 邮编)

由于 邮编→城市，而邮编不是候选码，所以不是 BCNF
分解为 R1(邮编, 城市) 和 R2(街道, 邮编) → 都是 BCNF
但是，(城市,街道)→邮编 这个依赖在两个子关系中都丢失了！无法保持函数依赖！
```

#### 属性闭包的计算方法（求候选码必备）

**属性闭包** X⁺：由属性集 X 通过 F 中的函数依赖能够推导出的所有属性的集合。

**计算步骤**：
1. 初始化 result = X
2. 重复以下步骤直到 result 不再变化：
   - 对于 F 中每条函数依赖 Y→Z
   - 如果 Y ⊆ result，则将 Z 加入 result（result = result ∪ Z）
3. 返回 result 作为 X⁺

**例子**：
```
R(A, B, C, D)，F = {A→B, B→C, C→D}
求 A⁺：
  初始：result = {A}
  第1轮：A→B，A⊆result → result = {A, B}
  第2轮：B→C，B⊆result → result = {A, B, C}
  第3轮：C→D，C⊆result → result = {A, B, C, D}
  无变化 → A⁺ = {A, B, C, D}
  
  所以 A 是候选码（A 能推出所有属性）
```

**用闭包法求候选码**：
- 如果 X⁺ 包含了 R 的所有属性，则 X 是一个超码
- 如果 X 的任何真子集的闭包都不包含所有属性，则 X 是候选码

### 15.6 索引与查询优化

**索引类型**：

| 索引类型 | 特点 | 一个表能有几个 |
|----------|------|:---:|
| 聚集索引（主索引） | 数据按索引顺序物理存储 | 1 个 |
| 非聚集索引（辅助索引） | 索引和数据分开存储 | 多个 |
| 唯一索引 | 索引列值唯一 | 多个 |
| 复合索引 | 多列组合 | 多个 |

**B+ 树索引原理**：
- 数据全在叶子节点，非叶子节点只存索引键
- 叶子节点之间用**双向链表**连接，支持高效范围查询
- 所有叶子在同一层，查询效率稳定
- 数据库索引几乎都用 B+ 树而不是 B 树

**查询优化核心原则**：
- **选择操作尽可能先做**（先过滤再连接，减少数据量）
- 小表驱动大表
- 避免 `SELECT *`，只选需要的列
- WHERE 条件中用索引列，避免在索引列上使用函数
- 复合索引注意**最左前缀原则**

**索引与查询优化典型例题**：

> **例题 1**：关于索引，以下说法**正确**的是（ ）。
> A. 索引一定能加速查询  B. 索引越多越好  C. 对于频繁更新的列，不适合建立索引  D. 索引列不能为 NULL
>
> **答案**：C。频繁更新的列每次更新都要维护索引，开销大，不适合建索引。A 错（查询返回大量行时全表扫描可能更快），B 错（索引多会降低增删改性能），D 错（除主键索引外，普通索引列可以为 NULL）。

> **例题 2**：在数据库查询优化中，以下做法**不合理**的是（ ）。
> A. 在 WHERE 条件中频繁使用的列上创建索引
> B. 在 JOIN 连接列上创建索引
> C. 在 WHERE 条件的索引列上使用函数
> D. 使用覆盖索引避免回表查询
>
> **答案**：C。在索引列上使用函数会导致**索引失效**（如 `WHERE YEAR(日期) = 2024`）。正确做法是 `WHERE 日期 >= '2024-01-01' AND 日期 < '2025-01-01'`。

**常见陷阱**：
- 陷阱1："索引一定能加速查询"——错！如果查询返回超过 30% 的行，全表扫描可能比索引更快（因为回表开销大）。索引适合"大海捞针"式的查询。
- 陷阱2："索引越多越好"——错！每个索引都需要维护（INSERT/UPDATE/DELETE 时更新索引），索引多了反而降低写入性能。
- 陷阱3：索引列上使用函数、表达式、隐式类型转换都会导致**索引失效**。这是考试和面试中最高频的 SQL 优化题。

### 15.7 数据库安全 ⭐

数据库安全是指保护数据库免受非授权访问、恶意破坏和意外泄露。华图/国网将数据库安全性控制的常用方法归纳为**五种**：

#### 数据库安全的五种常用方法（华图口径）

| 层面 | 目标 | 实现方式 |
|------|------|----------|
| **用户标识与鉴别** | 确认"你是谁" | 用户名+密码、生物识别、证书 |
| **存取控制** | 控制"你能做什么" | GRANT/REVOKE 权限管理、角色 |
| **视图机制** | 隐藏敏感数据 | 创建视图只暴露允许访问的列 |
| **审计** | 记录"谁做了什么" | 审计日志（Audit Log） |
| **数据加密** | 防止数据泄露 | 存储加密、传输加密（SSL/TLS） |

#### 用户标识与鉴别

| 方法 | 说明 | 安全程度 |
|------|------|:---:|
| 口令认证 | 用户名 + 密码 | 低（可能被盗或被猜中） |
| 强认证 | 生物识别（指纹、人脸） | 高 |
| 证书认证 | SSL 客户端证书 | 高 |

#### 存取控制（Access Control）⭐⭐

**（一）自主存取控制（DAC, Discretionary Access Control）**

用户对数据对象的权限由数据的所有者自主决定。通过 SQL 的 `GRANT` 和 `REVOKE` 实现。

```sql
-- 授予权限
GRANT SELECT, INSERT ON 学生 TO user1;
GRANT ALL PRIVILEGES ON 学生 TO user2 WITH GRANT OPTION;
-- WITH GRANT OPTION：允许 user2 将权限转授给其他人

-- 回收权限
REVOKE INSERT ON 学生 FROM user1;
REVOKE SELECT ON 学生 FROM user2 CASCADE;
-- CASCADE：级联回收（收回 user2 的权限，同时收回他转授出去的所有权限）
```

**（二）强制存取控制（MAC, Mandatory Access Control）**

系统给每个数据对象和每个用户都分配安全级别，按"上读下写"原则控制：

| 安全级别 | 标记 | 典型用户 |
|----------|------|---------|
| 绝密 | TS（Top Secret） | 最高领导 |
| 机密 | S（Secret） | 高层管理 |
| 秘密 | C（Confidential） | 中层管理 |
| 公开 | U（Unclassified） | 普通用户 |

**MAC 两个核心规则**：
- **不上读**：低安全级别的用户**不能读**高安全级别的数据（防止窃密）
- **不下写**：高安全级别的用户**不能写**低安全级别的数据（防止泄密）

**MAC vs DAC 对比**：

| 对比维度 | DAC（自主存取控制） | MAC（强制存取控制） |
|----------|-------------------|-------------------|
| 权限决定者 | 数据所有者 | 系统安全策略 |
| 灵活程度 | 高 | 低 |
| 安全性 | 较低（用户可能误授权） | 高（用户无法绕过） |
| 适用场景 | 普通商业应用 | 军事、政府部门 |
| SQL 支持 | `GRANT` / `REVOKE` | DBMS 安全配置 |

#### 审计（Audit）

审计是把用户对数据库的所有操作记录下来的机制。审计日志记录"谁、什么时间、做了什么操作"。

```sql
-- 开启审计（Oracle 语法）
AUDIT SELECT, INSERT, UPDATE, DELETE ON 学生 BY ACCESS;

-- 关闭审计
NOAUDIT SELECT ON 学生;
```

#### SQL 注入防御

| 防御方法 | 说明 |
|----------|------|
| **参数化查询**（Prepared Statement） | 使用占位符 `?`，不拼接 SQL 字符串 |
| **输入验证** | 对用户输入进行白名单/黑名单过滤 |
| **最小权限原则** | 应用程序连接数据库的账号只给最少必要权限 |
| **存储过程** | 将数据访问逻辑封装在存储过程中 |

#### 数据库安全综合防护

```
┌──────────────────────────────────────┐
│  第一层：用户标识与鉴别                 │ → 用户名/密码/指纹
├──────────────────────────────────────┤
│  第二层：存取控制                      │ → GRANT/REVOKE + MAC
├──────────────────────────────────────┤
│  第三层：视图 + 加密                   │ → 隐藏敏感列、加密敏感数据
├──────────────────────────────────────┤
│  第四层：审计                         │ → 记录所有操作
└──────────────────────────────────────┘
```

**例题 9**：在数据库设计中，ER 图产生于（ ）
A. 需求分析阶段　B. 概念结构设计阶段　C. 逻辑结构设计阶段　D. 物理结构设计阶段

> **答案：B**。ER 图是概念模型的表示方法。

**例题 10**：ER 图中，一个 M:N 联系转换为关系模式时，该关系模式的码是（ ）
A. N 端实体的码　B. M 端实体的码　C. M 端和 N 端实体的码的组合　D. 重新选取

> **答案：C**。M:N 联系必须单独建表，主键 = 两端主键的组合。

**例题 11**：R(学号, 姓名, 系号, 系主任, 课程号, 成绩)，其中学号→系号，系号→系主任，(学号,课程号)→成绩。R 属于（ ）
A. 1NF　B. 2NF　C. 3NF　D. BCNF

> **答案：A**。候选码为(学号,课程号)。学号→姓名是部分函数依赖（姓名只依赖于学号，不依赖于整个候选码），所以不满足 2NF，最高只到 1NF。

**例题 12**：R(学号, 姓名, 系名, 系主任)，学号→系名→系主任，存在（ ）依赖，不满足（ ）范式。

> **答案**：传递函数依赖，不满足 3NF。

**例题 13**：关于 B+ 树，下列说法正确的是（ ）
A. B+ 树的非叶子节点存储数据记录
B. B+ 树只支持等值查询，不支持范围查询
C. B+ 树的所有叶子节点在同一层
D. B+ 树的叶子节点之间没有连接

> **答案：C**。A 错（数据只在叶子），B 错（链表支持范围查询），D 错（叶子有双向链表）。

### 15.8 易错陷阱

1. **概念结构 vs 逻辑结构**：ER 图是概念结构（独立于 DBMS），关系模式是逻辑结构（依赖关系模型）。
2. **1:N 联系必须合并到 N 端**，不能合并到 1 端。
3. **2NF 和 3NF 的判断**：先找候选码 → 找主属性/非主属性 → 检查依赖。部分依赖不满足 2NF，传递依赖不满足 3NF。
4. **B+ 树 vs B 树**：B+ 树叶子节点有链表，B 树非叶子也存数据，B+ 树更适合范围查询。
5. **3NF 分解一定可以同时满足无损连接和保持函数依赖，BCNF 不一定**。

### 15.9 记忆口诀

> **设计六阶段**：需概逻物实维。
> **ER 转关系**：1:1 随便加，1:N 加 N 端，M:N 单独建，码取两端合。
> **范式递进**：1NF 属性不可分，2NF 消除部分依赖，3NF 消除传递依赖，BCNF 决定因素都是码。
> **B+ 树**：数据全在叶子上，非叶只存索引键，叶子链接成链表，范围查询跑得快。
> **查询优化**：选择先做、投影随后、连接最后，小表驱动大表，索引覆盖最优。

### 16.1 分布式数据库系统（DDBS）

**大白话**：把数据分散存放在多个物理节点上，但让用户感觉像在用"一个"数据库。

#### 基本概念

- **分布式数据库（DDB）**：数据分散存储在计算机网络中的多个物理节点上，逻辑上是一个整体。
- **分布式数据库管理系统（DDBMS）**：管理分布式数据库的软件。
- **分布式数据库系统（DDBS）= DDB + DDBMS**。

#### 两种分布方式（华图重点）

| 类型 | 分布特点 | 大白话 | 别称 |
|------|---------|--------|------|
| **物理分布、逻辑集中** | 数据物理上分散存储，逻辑上是统一的整体 | 数据放在多台机器上，但对用户来说还是一个库 | 集中式（分布式数据库的基本形态） |
| **物理分布、逻辑也分布** | 数据物理上分散，逻辑上也各自独立、自治 | 多个独立数据库通过网络协作，各自有自治权 | 联邦式（Federated） |

#### 分布式数据库的四大特点

| 特点 | 含义 | 大白话 |
|------|------|--------|
| **分布透明性**（独立透明性） | 用户不必关心数据在哪个节点、如何分区、副本如何一致 | 用户写 SQL 时完全不用知道数据存在哪台机器 |
| **集中与自治结合** | 既有全局共享的集中控制，各节点又有局部自治 | 总部统一管理 + 各分部自行决定局部事务 |
| **复制透明性** | 数据副本的更新由系统自动完成，用户无感知 | 多个副本自动同步，用户不用管 |
| **易于扩展** | 增加新节点即可扩展，不影响现有系统 | 加机器就能扩容 |

#### 优缺点对比

| | 内容 |
|------|------|
| **优点** | ①体系结构灵活 ②适应分布式的组织管理 ③经济性好（多台便宜机器替代大机器）④可靠性高（单点故障不影响全局）⑤局部响应快（数据就近访问）⑥易扩展 |
| **缺点** | ①系统开销大（节点间通信开销）②存取结构复杂 ③安全保密性难处理（数据分散，难以统一防护） |

#### 分布式数据库的目标

| 目标 | 说明 |
|------|------|
| **适应性** | 适应分布式环境下的应用需求 |
| **可靠性 / 可用性** | 局部故障不影响整体可用 |
| **充分性** | 充分利用各节点资源 |
| **扩展性** | 支持系统规模的平滑扩展 |

**记忆口诀**：
```
分布式库记两点：
  物理分布逻辑集中（基本），物理逻辑都分布（联邦）
特点四条：分布透明、集中自治结合、复制透明、易扩展
优点记"灵活经济可靠快扩展"，缺点记"开销大结构复杂难保密"
```

### 16.2 对象关系数据库系统（ORDBMS）

**大白话**：在关系数据库的基础上，加入"面向对象"的能力（类、对象、继承、封装），让数据库既能用标准 SQL 操作，又能表达复杂数据。

#### 基本概念

对象-关系数据库管理系统（ORDBMS）**既具备关系数据库的功能，又支持面向对象的特征**，是关系模型与面向对象模型结合的产物。

#### 优点（华图重点：两类优点叠加）

| 优点来源 | 具体优点 | 说明 |
|----------|---------|------|
| **继承关系数据库（RDBMS）的优点** | 透明存储路径 | 用户不关心物理存储细节 |
| | 标准 SQL | 沿用成熟的 SQL 查询语言 |
| | 事务、恢复、完整性 | 具备 ACID、备份恢复、完整性约束机制 |
| **继承面向对象（OODB）的优点** | 表达复杂关系 | 能表示复杂的嵌套、聚合、继承结构 |
| | 封装 | 数据 + 方法封装在一起 |
| | 对象标识（OID） | 每个对象有唯一标识 |
| | 多态 | 同名操作可对不同对象产生不同行为 |
| | 继承 | 子类继承父类的属性和方法 |

**记忆口诀**：对象关系库 = 关系库的"老三样"（SQL + 事务 + 完整性）+ 面向对象的"新五样"（复杂关系、封装、对象标识、多态、继承）。

### 16.3 XML 数据库

**大白话**：专门用来存储、查询、管理 **XML 文档** 的数据库。XML（可扩展标记语言）是一种自描述的结构化文本格式，常用于数据交换。

| 要点 | 说明 |
|------|------|
| **XML** | eXtensible Markup Language，可扩展标记语言，用标签 `<标签>` 描述数据，自描述、与平台无关 |
| **XML 数据库** | 专门存储和管理 XML 文档的数据库，能直接对 XML 结构（元素、属性、层级）进行查询 |
| **两种类型** | ①原生 XML 数据库（Native XML DB，直接以 XML 为存储单位）②支持 XML 的关系数据库（在关系库上加 XML 支持） |
| **典型查询语言** | XPath、XQuery |

**考试提示**：XML 数据库是低频概念题，掌握"XML 是什么 + XML 数据库是什么 + 两种类型"即可，不深入考细节。

### 一、SQL 典型真题（至少 3 道）

#### 真题 1：多表 JOIN + 聚合 + HAVING 综合题

> **题目**：有学生表 `S(sid, sname, age, sex)`，选课表 `SC(sid, cid, score)`，课程表 `C(cid, cname, teacher)`。查询"平均成绩大于 80 分的学生姓名和平均成绩"，按平均成绩降序排列。

```sql
SELECT S.sname, AVG(SC.score) AS avg_score
FROM S
INNER JOIN SC ON S.sid = SC.sid
GROUP BY S.sid, S.sname
HAVING AVG(SC.score) > 80
ORDER BY avg_score DESC;
```

**考点拆解**：
- `INNER JOIN`：学生表关联选课表（只取有选课记录的学生）
- `GROUP BY`：按学生分组，对每个学生的成绩做聚合
- `HAVING`：筛选分组后的聚合结果（不能用 WHERE，因为 AVG 是聚合函数）
- `ORDER BY`：降序排列

**易错陷阱**：`GROUP BY S.sid, S.sname` 中两个字段都要写——因为 `sname` 在 SELECT 中出现了且不是聚合函数的参数，必须出现在 GROUP BY 中（SQL 标准要求）。

---

#### 真题 2：NOT EXISTS 双重否定（关系除法）

> **题目**：查询"选修了所有课程的学生姓名"。

```sql
SELECT sname FROM S
WHERE NOT EXISTS (
    SELECT * FROM C
    WHERE NOT EXISTS (
        SELECT * FROM SC
        WHERE SC.sid = S.sid AND SC.cid = C.cid
    )
);
```

**大白话翻译**：
- 内层 `NOT EXISTS`："不存在一门课程，这个学生选了它" → 这个学生选了所有课程
- 外层 `NOT EXISTS`："不存在一门课程，这个学生没选它" → 选了全部课程

**考点拆解**：
- 这是关系代数中"除法（÷）"的 SQL 实现
- 双重 `NOT EXISTS` 是经典写法，考试大题常考
- `EXISTS` 是关联子查询：内层引用外层 `S.sid` 和 `C.cid`

**易错陷阱**：单层 `NOT EXISTS` 只能判断"存在/不存在"，要表达"全部"必须用双重否定。

---

#### 真题 3：自连接 + LEFT JOIN 找 NULL

> **题目**：有员工表 `Emp(eid, ename, mid)`，其中 `mid` 是上级领导的员工编号（自引用外键）。查询"没有下属的员工姓名"。

```sql
SELECT DISTINCT e1.ename
FROM Emp e1
LEFT JOIN Emp e2 ON e1.eid = e2.mid
WHERE e2.eid IS NULL;
```

**大白话理解**：拿每个员工 e1，去匹配"谁的上司是我"，如果匹配不到（e2.eid IS NULL），说明没人叫他上司。

**考点拆解**：
- 自连接：同一张表起两个别名，自己连自己
- `LEFT JOIN`：保留左表全部行，右表匹配不上的填 NULL
- `WHERE e2.eid IS NULL`：利用外连接"右表全 NULL"来找出"没有匹配"的行

**易错陷阱**：`WHERE e2.eid = NULL`（单等号）是错的！NULL 不能用 `=` 比较，必须用 `IS NULL` / `IS NOT NULL`。

---

#### 真题 4：子查询 + IN + 聚合

> **题目**：查询"比本系平均年龄大的学生"。

```sql
SELECT s1.*
FROM S s1
WHERE s1.age > (
    SELECT AVG(s2.age)
    FROM S s2
    WHERE s2.dept = s1.dept
);
```

**考点拆解**：关联子查询 —— 外层每读一行，子查询就用当前学生的系别去算该系的平均年龄。

### 二、SQL 易错陷阱速查

| 陷阱 | 错误写法 | 正确写法 | 原因 |
|------|----------|----------|------|
| WHERE 中用聚合函数 | `WHERE COUNT(*) > 3` | `HAVING COUNT(*) > 3` | WHERE 在分组前执行，聚合函数还不能用 |
| NULL 比较 | `WHERE col = NULL` | `WHERE col IS NULL` | NULL 代表"未知"，不能用等号比较 |
| NOT IN + NULL | `WHERE id NOT IN (SELECT ...)` | 子查询中排除 NULL 或用 NOT EXISTS | 子查询结果有 NULL 时，NOT IN 返回空集 |
| DELETE 忘加 WHERE | `DELETE FROM 表` | `DELETE FROM 表 WHERE 条件` | 不加 WHERE 会清空整张表 |
| 聚合列与普通列混用 | `SELECT name, MAX(score) FROM SC` | 必须加 `GROUP BY name` | 聚合列和非聚合列不能同时出现在 SELECT 中（除非 GROUP BY） |
| COUNT(*) vs COUNT(列) | 混淆 | `COUNT(*)` 统计行数（含 NULL）；`COUNT(列)` 统计非空值个数 | 算总人数用 COUNT(*)，统计某列有效值用 COUNT(列) |
| 忘记 JOIN 条件 | `FROM A JOIN B` | `FROM A JOIN B ON A.id = B.id` | 没有 ON 条件会退化为笛卡尔积 |

### 三、事务并发高频考点

#### 3.1 四种并发问题对比（必考选择/判断题）

| 并发问题 | 现象 | 发生条件 | 类比 |
|----------|------|----------|------|
| **丢失修改**（Lost Update） | 两个事务同时读同一行，各自修改后提交，后提交的覆盖先提交的 | 没有写锁 | 你我在同一个 Word 文档上各改各的，最后保存的人覆盖了前一个人的修改 |
| **脏读**（Dirty Read） | T1 读到 T2 未提交的修改，T2 随后回滚，T1 读到了"不存在"的数据 | Read Uncommitted | 听到小道消息当真了，结果人家辟谣了 |
| **不可重复读**（Non-repeatable Read） | 同一事务内两次读同一行，**值**不一样（别人 UPDATE 了） | Read Committed 及以下 | 你隔 5 分钟查同一行数据，发现字段值变了 |
| **幻读**（Phantom Read） | 同一事务内两次查同一条件，**行数**不一样（别人 INSERT/DELETE 了） | Repeatable Read 及以下（MySQL InnoDB 除外） | 你隔 5 分钟查同一条件，发现多出了几行 |

#### 3.2 隔离级别速查表（必考填表/选择题）

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 实现方式 | 默认使用 |
|----------|------|-----------|------|----------|----------|
| 读未提交（Read Uncommitted） | 允许 | 允许 | 允许 | 不加锁 | 几乎不用 |
| 读已提交（Read Committed） | 禁止 | 允许 | 允许 | 快照/MVCC | Oracle、PostgreSQL |
| 可重复读（Repeatable Read） | 禁止 | 禁止 | 允许(标准) | MVCC | MySQL InnoDB |
| 可串行化（Serializable） | 禁止 | 禁止 | 禁止 | 表锁/范围锁 | 极少使用 |

**MySQL InnoDB 特殊之处**：在"可重复读"级别下，InnoDB 通过**间隙锁（Gap Lock）+ 临键锁（Next-Key Lock）**解决了幻读问题。所以 MySQL 的"可重复读"实际上对幻读也是禁止的。

#### 3.3 封锁（Lock）核心考点

**锁的兼容矩阵（必考）**：

|  | 已持有 S 锁 | 已持有 X 锁 |
|--|------------|------------|
| 申请 S 锁 | ✅ 兼容 | ❌ 冲突（等待） |
| 申请 X 锁 | ❌ 冲突（等待） | ❌ 冲突（等待） |

**记忆口诀**：S 锁=共享锁=读锁（大家都能读）；X 锁=排他锁=写锁（只能一个人用）。S 只跟 S 兼容，X 跟谁都不兼容。

**两段锁协议（2PL）高频考点**：
- 2PL 规定：事务分两段 —— 扩张阶段（只加锁不解锁）→ 收缩阶段（只解锁不加锁）
- 2PL **保证**可串行化调度
- 2PL **不防止**死锁（死锁需要额外的检测机制）
- 注意区别：一次封锁法（一次性申请所有锁）可以防止死锁，但 2PL 不行

**死锁的预防与检测**：
- 预防：一次封锁法、顺序封锁法
- 检测：等待图（Wait-for Graph），检测到环 → 存在死锁
- 恢复：选一个事务回滚（牺牲者），释放它持有的锁

#### 3.4 事务并发判断速解技巧

**题目类型**："以下调度是否可串行化？"解题步骤：
1. 画出调度序列中每个事务的读/写操作
2. 检查是否存在冲突操作（对同一数据，一个写另一个读/写）且顺序不一致
3. 如果冲突操作形成环 → 不可串行化
4. 如果 2PL 满足 → 一定可串行化

### 四、范式判断技巧

#### 4.1 范式判断三步法（国网大题必考）

**步骤**：
1. **先看 1NF**：有没有列包含多个值？有 → 不满足 1NF，不用往下看
2. **再看 2NF**：找候选码（主键），然后看每个非主属性是否"完全函数依赖"于候选码。如果某非主属性只依赖候选码的一部分 → 不满足 2NF
3. **最后看 3NF**：非主属性之间有没有传递依赖？即 非主属性 A → 非主属性 B → 候选码 这种链？有 → 不满足 3NF

#### 4.2 函数依赖速查

| 依赖类型 | 定义 | 大白话 | 范式关系 |
|----------|------|--------|----------|
| 完全函数依赖 | 非主属性依赖整个候选码，缺任何一个属性都不行 | 必须用完整主键才能确定这个值 | 满足 2NF 的前提 |
| 部分函数依赖 | 非主属性只依赖候选码的**一部分** | 主键的某一部分就够确定这个值了 | 违反 2NF |
| 传递函数依赖 | 非主属性 A → 非主属性 B → 候选码 这种链 | A 不直接依赖主键，而是通过 B 间接依赖 | 违反 3NF |

#### 4.3 范式判断快速模板

**给定关系模式 R(A, B, C, D)，函数依赖集 F = {A→B, B→C, ...}，判断最高满足第几范式。**

```
第1步：求候选码 → 闭包法
第2步：列出所有非主属性
第3步：检查非主属性是否完全函数依赖于候选码（2NF）
第4步：检查非主属性之间是否存在传递依赖（3NF）
```

#### 4.4 范式判断经典例题

> **例题**：关系模式 R(学号, 课程号, 成绩, 教师姓名, 教师职称)，F = { (学号,课程号)→成绩, (学号,课程号)→教师姓名, 课程号→教师姓名, 教师姓名→教师职称 }，候选码为 (学号, 课程号)。
>
> **判断**：
> - 1NF：✅（所有属性原子性）
> - 2NF：❌，因为"教师姓名"只依赖于"课程号"（候选码的一部分），存在部分函数依赖
> - 最高满足 **1NF**

> **例题**：关系模式 R(学号, 姓名, 系号, 系主任)，F = { 学号→姓名, 学号→系号, 系号→系主任 }，候选码为 学号。
>
> **判断**：
> - 1NF：✅
> - 2NF：✅（候选码是单属性，不存在部分依赖问题）
> - 3NF：❌，因为 学号→系号→系主任，存在传递函数依赖
> - 最高满足 **2NF**

#### 4.5 BCNF 判断速解

**BCNF 是 3NF 的加强版**：3NF 只要求非主属性不传递依赖，BCNF 要求**所有决定因素都必须是候选码**。

**判断口诀**：看函数依赖集的**左边**（决定因素）是否都是候选码。如果存在一个函数依赖 `X→Y`，其中 X 不是候选码 → 不满足 BCNF。

**经典 BCNF 例题**：R(S, J, T)，S=学生, J=课程, T=老师，F = { SJ→T, T→J }。候选码为 (S,J) 和 (S,T)。
- 3NF：✅（没有非主属性——所有属性都是主属性）
- BCNF：❌，因为 T→J 中 T 不是候选码
- 最高满足 **3NF**

#### 4.6 范式易错陷阱

| 陷阱 | 错误认知 | 正确认知 |
|------|----------|----------|
| 单属性候选码 = 自动满足 2NF | 以为 2NF 一定满足 | 对！单属性候选码不存在"部分依赖"问题，自动满足 2NF |
| 1NF 是默认满足的 | 忽略检查 | 考试中默认关系都满足 1NF，除非题目明确说某个属性不原子 |
| 3NF 比 BCNF 宽松 | 混淆关系 | BCNF ⊂ 3NF ⊂ 2NF ⊂ 1NF（BCNF 最严格） |
| 认为 NULL 影响范式判断 | 混入无关概念 | 范式判断只看函数依赖，跟 NULL 和具体数据无关 |
| 混淆"传递依赖"和"间接依赖" | 把任何间接关系都叫传递依赖 | 传递依赖特指：非主属性 A → 非主属性 B。如果 A 是主属性则不叫传递依赖（那是 BCNF 的范畴） |

### 六、ER图转关系模式真题

#### 真题 1：M:N 联系转换规则

在 ER 图中，一个学生和课程之间存在 M:N 的"选课"联系。将其转换为关系模式时，正确的是（ ）

A. 在"学生"表中增加"课程号"字段
B. 在"课程"表中增加"学号"字段
C. 单独建立一个"选课"表，包含学号和课程号
D. 将 M:N 联系合并到学生表或课程表中任意一端

> **解析**：M:N 联系**必须单独建表**，新表的主键由两端实体主键的组合构成。如果联系还有自己属性（如"成绩"），也放在这个新表里。1:1 可合并到任意一端，1:N 合并到 N 端。**答案：C。**

#### 真题 2：1:N 联系转换规则

一个班级有多个学生，一个学生只属于一个班级。这种 1:N 联系转换为关系模式时，正确做法是（ ）

A. 在"班级"表中增加"学号"字段，作为外键
B. 在"学生"表中增加"班级编号"字段，作为外键
C. 单独建立一个"属于"表
D. 不进行任何处理

> **解析**：1:N 联系**必须合并到 N 端**，即把 1 端的主键放到 N 端作为外键。这里 N 端是"学生"（多个学生属于一个班级），所以在"学生"表加"班级编号"外键。**答案：B。**

#### 真题 3：SQL GROUP BY + HAVING

有学生表 `S(sid, sname, dept)` 和选课表 `SC(sid, cid, score)`。查询"平均成绩大于等于 80 分的学生学号和平均成绩"，按学号降序排列。正确的 SQL 语句是（ ）

A. 正确答案的 SQL 结构包含：`GROUP BY sid`（按学生分组）→ `HAVING AVG(score) >= 80`（筛选分组后的结果）→ `ORDER BY sid DESC`（降序排列）

```sql
SELECT sid, AVG(score) AS avg_score
FROM SC
GROUP BY sid
HAVING AVG(score) >= 80
ORDER BY sid DESC;
```

**考点拆解**：
- `WHERE` 和 `HAVING` 的区别：WHERE 在分组前过滤行，HAVING 在分组后过滤组
- `WHERE` 中不能使用聚合函数（如 `AVG`、`COUNT`）
- `ORDER BY` 中可以使用 SELECT 中定义的别名（因为 ORDER BY 在 SELECT 之后执行）

**易错陷阱**：如果写成 `WHERE AVG(score) >= 80` 或 `WHERE avg_score >= 80` 都是错误的。

#### 真题 4：事务隔离级别判断题

"读已提交（Read Committed）"隔离级别可以防止的问题是（ ）

A. 丢失修改和脏读　B. 脏读和不可重复读　C. 丢失修改、脏读和不可重复读　D. 所有并发问题

> **解析**：所有隔离级别都防止丢失修改（通过写锁实现）。"读已提交"在前者的基础上额外防止脏读（不读未提交的数据），但不能防止不可重复读和幻读。**答案：A。**

#### 真题 5：事务 ACID 特性判断

银行转账操作中：A 账户扣款 100 元，B 账户加款 100 元。若在 A 扣款成功后系统突然断电，B 未加款，恢复后 A 的扣款被撤销。这体现了事务的（ ）特性；恢复后 A 和 B 的金额在扣款和加款都成功的前提下数据保持正确，体现了事务的（ ）特性

A. 原子性、一致性　B. 一致性、隔离性　C. 持久性、原子性　D. 隔离性、持久性

> **解析**："要么都做、要么都不做"是原子性。A 扣款成功但 B 未加款，恢复后 A 撤销扣款（全部不做），体现**原子性**。A 和 B 总金额在转账前后保持不变，数据从一种正确状态变到另一种正确状态，体现**一致性**。**答案：A。**

**ACID 辨析技巧**（高频考点）：
| 关键词 | 对应特性 |
|--------|----------|
| "要么全做，要么全不做" | **原子性（Atomicity）** |
| "转账前后总金额不变" | **一致性（Consistency）** |
| "并发操作互不干扰" | **隔离性（Isolation）** |
| "提交后数据永不丢失" | **持久性（Durability）** |

#### 真题 6：范式判断——综合题

关系模式 R(学号, 课程号, 成绩, 教师姓名, 教师职称)，函数依赖集为：
F = { (学号,课程号)→成绩, (学号,课程号)→教师姓名, 课程号→教师姓名, 教师姓名→教师职称 }，候选码为 (学号, 课程号)。R 最高满足第几范式？

A. 1NF　B. 2NF　C. 3NF　D. BCNF

> **解析**：第一步：所有属性都是原子的，满足 1NF。第二步：检查非主属性是否完全函数依赖于候选码。(学号,课程号)→成绩 是完全依赖，但 课程号→教师姓名 说明教师姓名只依赖于候选码的一部分（课程号），存在**部分函数依赖**，违反 2NF。所以最高满足 1NF。**答案：A。**

**关键判定**：判断 2NF 时重点看有没有"单属性→非主属性"这种情况。如果候选码是复合的，且有一个非主属性只依赖于候选码的一部分，就违反 2NF。

#### 真题 7：范式判断——传递依赖

关系模式 R(学号, 姓名, 系号, 系主任)，F = { 学号→姓名, 学号→系号, 系号→系主任 }，候选码为 学号。R 最高满足第几范式？

A. 1NF　B. 2NF　C. 3NF　D. BCNF

> **解析**：第一步：满足 1NF。第二步：候选码是单属性，不存在部分依赖问题，自动满足 2NF。第三步：检查是否存在传递依赖。学号→系号→系主任，系主任通过系号传递依赖于学号，且系号和系主任都是非主属性，存在**传递函数依赖**，违反 3NF。所以最高满足 2NF。**答案：B。**

**关键判定**：单属性候选码自动满足 2NF。传递依赖的特征是"主键→非主属性A→非主属性B"这样的链条。

### 模板一：范式判断三步法（选择/大题通用）

**适用题型**：给定关系模式 R 和函数依赖集 F，判断最高属于第几范式。

**解题步骤**：

```
第1步：求候选码
  → 用闭包法：从已知的 F 出发，看哪些属性组合能推出全部属性
  → 单属性能用闭包推出全部 → 该属性就是候选码
  → 复合属性必须是最小组合（任何真子集都不能推出全部属性）

第2步：判断 2NF
  → 找出所有非主属性（不在任何候选码中的属性）
  → 检查每个非主属性是否"完全函数依赖"于候选码
  → 如果候选码是单属性 → 自动满足 2NF（没有"部分依赖"的可能）
  → 如果候选码是复合属性 → 检查是否有非主属性只依赖候选码的一部分
  → 有部分依赖 → 最高 1NF；没有 → 继续判断

第3步：判断 3NF
  → 检查非主属性之间是否存在传递依赖
  → 即：候选码 → 非主属性A → 非主属性B 这样的链
  → 有传递依赖 → 最高 2NF；没有 → 最高 3NF

第4步（可选）：判断 BCNF
  → 检查 F 中每个函数依赖的"左边"（决定因素）是否都是候选码
  → 有一个不是 → 不满足 BCNF
  → 全部都是 → 满足 BCNF
```

**速记口诀**：
```
先找候选码（闭包法）
再查部分依赖（2NF）
后查传递依赖（3NF）
最后看决定因素是不是码（BCNF）
```

### 模板二：ER 图转关系模式三步法（大题必考）

**适用题型**：给定 E-R 图，转换为关系模式。

**转换规则速查表**：

| 联系类型 | 转换方法 | 口诀 |
|----------|---------|------|
| **1:1** | 在任意一端实体对应的表中，加入另一端的主键作为外键。联系属性也放入该表 | "1:1 随便加" |
| **1:N** | 在 **N 端**实体对应的表中，加入 1 端的主键作为外键。联系属性也放入 N 端表 | "1:N 加 N 端" |
| **M:N** | **必须单独建表**，包含两端的主键（作为联合主键）+ 联系自身的属性 | "M:N 单独建，码取两端合" |

**解题步骤**：
```
第1步：识别所有实体 → 每个实体建一张表，主键不变
第2步：识别所有联系 → 判断联系类型（1:1 / 1:N / M:N）
第3步：按转换规则处理每个联系
  → 1:1：选一端加外键
  → 1:N：N 端加外键
  → M:N：单独建表（联合主键 = 两端主键的组合）
第4步：写出最终的关系模式集合
```

**经典例题**：学生 M:N 选课，联系有"成绩"属性。
```
→ 学生表（学号, 姓名, ...）
→ 课程表（课程号, 课程名, ...）
→ 选课表（学号, 课程号, 成绩）  ← 单独建表，主键 = (学号, 课程号)
```

### 模板三：SQL 执行顺序速解法（选择题通用）

**适用题型**：判断题中 SQL 语句哪里写错了，或者问"以下子句的执行顺序"。

**执行顺序模板**：
```
FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT
 (1)     (2)       (3)         (4)        (5)       (6)       (7)
```

**三句口诀搞定所有陷阱**：
1. **WHERE 不用别名，不用聚合**：因为 WHERE 在 SELECT 之前执行，别名还没定义，聚合还没分组
2. **HAVING 用聚合，不用别名**：HAVING 在 GROUP BY 之后，可以用聚合函数，但别名仍不可用（在 SELECT 之前）
3. **ORDER BY 可以用别名**：ORDER BY 在 SELECT 之后执行，别名已定义

**快速判断 SQL 错误的检查清单**：
```
□ WHERE 中有聚合函数？ → 错！改 HAVING
□ WHERE 中用了 SELECT 的别名？ → 错！用原名或表达式
□ GROUP BY 缺了 SELECT 中的非聚合列？ → 错！补上
□ HAVING 中用了非聚合列且没在 GROUP BY 中？ → 错！
□ NOT IN 子查询可能返回 NULL？ → 改 NOT EXISTS
```

### 模板四：事务并发问题一眼辨（选择题/判断题通用）

**适用题型**：给定并发操作序列，判断出现了什么并发问题。

**四个并发问题的关键词速查**：

| 问题 | 关键判断词 | 记忆标签 |
|------|-----------|---------|
| **丢失修改** | 两个事务同时读，各自改，后提交覆盖先提交 | "覆盖了" |
| **脏读** | T1 读到 T2 **未提交**的修改，T2 后来回滚 | "没提交就读了" |
| **不可重复读** | T1 两次读同一行，T2 在中间**修改并提交**，**值**变了 | "值变了" |
| **幻读** | T1 两次查同一条件，T2 在中间**插入/删除并提交**，**行数**变了 | "行数变了" |

**解题步骤**：
```
第1步：画出时间线，标注每个事务的读/写/提交/回滚操作
第2步：看关键区别：
  → T2 有没有提交？没提交 → 可能是脏读
  → T2 提交了，T1 读到的值变了 → 不可重复读
  → T2 提交了，T1 读到的行数变了 → 幻读
  → 两个事务都在写，后来覆盖了 → 丢失修改
第3步：确认答案
```

**隔离级别速查表（倒背如流）**：
```
读未提交 → 防丢失修改（全级别都防）
读已提交 → +防脏读
可重复读 → +防不可重复读
可串行化 → +防幻读（全防）
```

### 模板五：关系代数除运算五步法（大题必考）

**适用题型**：手算 R ÷ S 的结果。

**解题步骤**：
```
第1步：列出 R 中所有 X 值（消除重复）
第2步：列出 S 中所有 Y 值
第3步：对每个 X 值，找出它在 R 中对应的所有 Y 值，形成集合 Y_X
第4步：检查 Y_X 是否包含 S 中的所有 Y 值（即 S ⊆ Y_X）
第5步：满足条件的 X 值就是结果
```

**速记口诀**：除运算 = 找"全才"——X 的 Y 值集合必须包含 S 的全部 Y 值。

**注意**：除运算在 SQL 中用**双重 NOT EXISTS** 实现，考试中如果考题是"写出 SQL"，大概率就是考这个。

### 八、SQL 选择题专项训练（3道）

#### SQL-1：多表连接查询

**[题目]**
设有三个关系表：
- 学生表 S（学号 Sno, 姓名 Sname, 性别 Sex, 年龄 Age）
- 课程表 C（课程号 Cno, 课程名 Cname, 学分 Credit）
- 选课表 SC（学号 Sno, 课程号 Cno, 成绩 Grade）

查询"选修了全部课程的学生姓名"，下列 SQL 语句正确的是（ ）。

A.
```sql
SELECT Sname FROM S
WHERE Sno IN (
    SELECT Sno FROM SC
    GROUP BY Sno
    HAVING COUNT(*) = (SELECT COUNT(*) FROM C)
)
```

B.
```sql
SELECT Sname FROM S
WHERE Sno = (
    SELECT Sno FROM SC
    GROUP BY Sno
    HAVING COUNT(*) = (SELECT COUNT(*) FROM C)
)
```

C.
```sql
SELECT Sname FROM S, SC
WHERE S.Sno = SC.Sno
GROUP BY Sname
HAVING COUNT(*) = (SELECT COUNT(*) FROM C)
```

D.
```sql
SELECT Sname FROM S
WHERE Sno IN (
    SELECT Sno FROM SC
    WHERE COUNT(*) = (SELECT COUNT(*) FROM C)
    GROUP BY Sno
)
```

**[答案]** A

**[解析]**
- 核心思路：先找出"选修课程数 = 总课程数"的学生学号，再查姓名。
- 选项 A 正确：子查询中按 Sno 分组，用 `HAVING COUNT(*) = (子查询查总课程数)` 筛选出选了全部课程的学生，外层用 IN 匹配。
- 选项 B 错误：子查询可能返回多行，单用 `=` 会报错，必须用 `IN`。
- 选项 C 错误：`GROUP BY Sname` 如果学生同名会导致计数错误，应按 `Sno` 分组；且缺少对未选课学生的处理。
- 选项 D 错误：`WHERE` 子句中不能使用聚合函数 `COUNT(*)`，`HAVING` 专用于分组后过滤。

#### SQL-2：子查询

**[题目]**
在 S-SC-C 关系模式中，查询"没有选修'数据库'课程的学生姓名"，下列 SQL 正确的是（ ）。

A.
```sql
SELECT Sname FROM S
WHERE Sno NOT IN (
    SELECT Sno FROM SC
    WHERE Cno = (
        SELECT Cno FROM C WHERE Cname = '数据库'
    )
)
```

B.
```sql
SELECT Sname FROM S
WHERE Sno IN (
    SELECT Sno FROM SC, C
    WHERE SC.Cno = C.Cno AND Cname != '数据库'
)
```

C.
```sql
SELECT Sname FROM S
WHERE NOT EXISTS (
    SELECT Sno FROM SC
    WHERE Cno = '数据库'
)
```

D.
```sql
SELECT Sname FROM S
WHERE Sno NOT IN (
    SELECT Sno FROM SC
    WHERE Cno IN (
        SELECT Cno FROM C WHERE Cname = '数据库'
    )
) OR Sno NOT IN (SELECT Sno FROM SC)
```

**[答案]** A

**[解析]**
- 选项 A 正确：双层嵌套子查询，内层先查到"数据库"课程的 Cno，中间层查出选了该课程的学生学号，外层用 `NOT IN` 排除这些学生。
- 选项 B 错误：`Cname != '数据库'` 表示选了非数据库课程的学生也会被包括，没有排除"只选了数据库但没选其他课"的学生，逻辑有漏洞。
- 选项 C 错误：`NOT EXISTS` 子查询中 `WHERE Cno = '数据库'` 缺少与外表 S 的关联条件（应为 `WHERE SC.Sno = S.Sno AND ...`），且 Cno 是编号不是名称。
- 选项 D 错误：存在逻辑冗余，`OR` 后面的条件已经是 `NOT IN` 的超集，而且表述不够简洁。

#### SQL-3：GROUP BY + HAVING 聚合查询

**[题目]**
在 SC（学号, 课程号, 成绩）表中，查询"平均成绩大于 80 分且至少选修了 3 门课程的学生学号"，正确的 SQL 是（ ）。

A.
```sql
SELECT Sno FROM SC
WHERE AVG(Grade) > 80 AND COUNT(*) >= 3
GROUP BY Sno
```

B.
```sql
SELECT Sno FROM SC
GROUP BY Sno
HAVING AVG(Grade) > 80 OR COUNT(*) >= 3
```

C.
```sql
SELECT Sno FROM SC
GROUP BY Sno
HAVING AVG(Grade) > 80 AND COUNT(*) >= 3
```

D.
```sql
SELECT Sno FROM SC
GROUP BY Sno
WHERE AVG(Grade) > 80
HAVING COUNT(*) >= 3
```

**[答案]** C

**[解析]**
- 选项 C 正确：`GROUP BY Sno` 按学号分组，`HAVING` 子句同时用 `AND` 连接两个条件（平均成绩 > 80 且 选课数 >= 3），逻辑完全正确。
- 选项 A 错误：`WHERE` 子句中不能使用聚合函数（AVG、COUNT），聚合函数的过滤必须放在 `HAVING` 中。
- 选项 B 错误：用了 `OR` 而非 `AND`，题目要求两个条件同时满足。
- 选项 D 错误：语法错误，`WHERE` 必须出现在 `GROUP BY` 之前，且 `WHERE` 中不能使用聚合函数。

### 九、ER 图转关系模式选择题专项训练（2道）

#### ER-1：1:1 和 1:N 联系转换

**[题目]**
某公司 ER 图中，实体"部门"和实体"经理"之间是 1:1 联系，实体"部门"和实体"员工"之间是 1:N 联系。以下关于关系模式转换的描述中，正确的是（ ）。

A. 部门和经理合并为一个关系模式，部门与员工各自独立，并在员工关系中添加部门编号作为外键

B. 部门、经理、员工各自独立，在经理关系中添加部门编号作为外键，在员工关系中添加部门编号作为外键

C. 部门、经理、员工各自独立，在部门关系中添加经理编号作为外键，在员工关系中添加部门编号作为外键

D. 将部门、经理、员工三实体合并为一个关系模式

**[答案]** C

**[解析]**
- 选项 C 正确，转换规则如下：
  - **1:1 联系**：可将任意一端的主键放到另一端作为外键。通常在"部门"中添加"经理编号"作为外键（一个部门只有一个经理，一个经理管一个部门），这样更自然。
  - **1:N 联系**：将"1"端（部门）的主键放入"N"端（员工）作为外键。即在员工关系中添加"部门编号"。
- 选项 A 错误：1:1 联系不一定合并，合并会导致数据冗余和更新异常，一般建议独立建表后加外键。
- 选项 B 错误：在经理关系中加部门编号是 1:N 的做法（N 端放外键方向反了），1:1 联系应是部门端放经理外键。
- 选项 D 错误：三实体功能完全不同，合并违反第三范式，会产生大量冗余。

---

#### ER-2：M:N 联系转换

**[题目]**
学生和课程之间是 M:N 联系（一个学生可选多门课，一门课可被多个学生选），该联系还有"成绩"属性。转换成关系模式时，正确的做法是（ ）。

A. 将"成绩"属性添加到学生关系中，课程关系不变

B. 将"成绩"属性添加到课程关系中，学生关系不变

C. 新建一个"选课"关系模式，包含学生的主键、课程的主键以及成绩属性，主键由学生主键和课程主键共同组成

D. 新建一个"选课"关系模式，包含学生的主键、课程的主键以及成绩属性，再单独添加一个"选课编号"作为主键

**[答案]** C

**[解析]**
- 选项 C 正确，M:N 联系的转换规则：
  - 必须**新建一个独立的关系模式**（即中间表）。
  - 包含两端实体的主键作为外键，同时作为该关系模式的**联合主键**。
  - 联系自带的属性（如"成绩"）也放入该关系模式中。
- 选项 A、B 错误：M:N 联系不能将属性放到任意一端实体中，因为一个学生有多个成绩（对应多门课），一个课程有多个学生成绩，放到任一端都会产生冗余。
- 选项 D 错误：虽然也创建了独立关系模式，但不应随意添加自增主键。联合主键（Sno, Cno）本身就是最自然的候选键，额外添加代理键违反了 ER 图转换的标准做法。

### 十、事务并发场景判断题专项训练（3道）

#### 并发-1：脏读

**[题目]**
设有两个事务 T1 和 T2 并发执行，操作流程如下：
- T1：读取账户 A 的余额为 1000 元
- T2：将账户 A 的余额修改为 2000 元（尚未提交）
- T1：再次读取账户 A 的余额，读到 2000 元
- T2：因某种原因回滚（ROLLBACK），A 余额恢复为 1000 元

该并发场景出现的问题是（ ）。

A. 丢失修改（Lost Update）
B. 脏读（Dirty Read）
C. 不可重复读（Non-repeatable Read）
D. 幻读（Phantom Read）

**[答案]** B

**[解析]**
- 脏读的定义：一个事务（T1）读取了另一个事务（T2）**尚未提交的修改数据**，而 T2 后来回滚，导致 T1 读到的数据是"脏"的（不存在的、无效的）。
- 本题中 T1 读到了 T2 未提交的 2000 元，但 T2 回滚后实际余额是 1000 元，T1 读到了"脏数据"，典型脏读。
- A（丢失修改）：两个事务先后修改同一数据，后提交的覆盖了先提交的修改。本题没有覆盖。
- C（不可重复读）：同一事务内两次读取同一数据，结果不同，是因为另一个事务**提交了**修改。本题 T2 没提交。
- D（幻读）：同一事务内两次查询，第二次多出或少了一些行（INSERT/DELETE），不是同一个数据的值变化。

---

#### 并发-2：不可重复读

**[题目]**
T1 和 T2 并发执行，操作流程如下：
- T1：读取账户 A 的余额为 1000 元
- T2：将账户 A 的余额修改为 2000 元，并**提交（COMMIT）**
- T1：再次读取账户 A 的余额，读到 2000 元

该并发场景出现的问题是（ ）。

A. 脏读
B. 丢失修改
C. 不可重复读
D. 幻读

**[答案]** C

**[解析]**
- 不可重复读的定义：同一事务（T1）内两次读取同一数据行，**结果不同**，原因是另一个事务（T2）在两次读取之间**修改并提交了**该数据。
- 与脏读的区别：脏读读的是未提交数据，不可重复读读的是**已提交**数据——两次读到的是两次不同的已提交值。
- 本题 T2 修改并提交后，T1 再次读取得到不同值，典型不可重复读。
- 不可重复读的解决办法：将隔离级别提升到 **Repeatable Read**（可重复读），MySQL 默认就是这个级别。

---

#### 并发-3：丢失修改

**[题目]**
T1 和 T2 并发执行，操作流程如下：
- T1：读取账户 A 的余额为 1000 元
- T2：读取账户 A 的余额为 1000 元
- T1：将余额减去 100 元，写入 900 元
- T2：将余额加上 200 元，写入 1200 元
- 最终余额为 1200 元，T1 的扣款操作被覆盖消失

该并发场景出现的问题是（ ）。

A. 脏读
B. 丢失修改（Lost Update）
C. 不可重复读
D. 幻读

**[答案]** B

**[解析]**
- 丢失修改的定义：两个事务先后读取同一数据并进行修改，**后提交的事务覆盖了先提交事务的修改**，导致先提交的修改丢失。
- 本题中 T1 的 -100 操作（结果是 900）被 T2 的 +200 操作（结果是 1200）覆盖，T1 的修改完全丢失，典型丢失修改。
- 丢失修改的解决办法：
  - 使用**排他锁（X锁）**：T1 读取时加锁，T2 必须等 T1 提交后才能读取。
  - 使用**乐观锁**：加版本号字段，更新时检查版本号是否被修改。
- 注意：丢失修改是**写-写冲突**，与脏读、不可重复读、幻读（都是读-写冲突）本质不同。

### 十一、范式判断选择题专项训练（2道）

#### 范式-1

**[题目]**
设有关系模式 R（A, B, C, D），其函数依赖集 F = {A→B, B→C, A→D}，且 A 是主键。该关系模式最高属于（ ）。

A. 1NF
B. 2NF
C. 3NF
D. BCNF

**[答案]** B

**[解析]**
- 判断步骤：
  1. **1NF**：所有属性都是原子值（不可再分），满足。基本都满足。
  2. **2NF**：检查是否存在**非主属性对主键的部分函数依赖**。主键是单属性 A，不存在部分依赖（部分依赖只在主键是组合键时才可能出现），所以满足 2NF。
  3. **3NF**：检查是否存在**非主属性对主键的传递函数依赖**。
     - 已知 A→B, B→C，且 B 不是主键（主键是 A），C 是非主属性。
     - 存在 A→B→C 的传递链，即 C 传递依赖于主键 A。
     - 违反了 3NF 定义，所以**最高是 2NF**。
- 选项 C（3NF）错误：存在传递依赖。
- 选项 D（BCNF）错误：BCNF 要求每个决定因素都包含候选键，B→C 中 B 不是候选键，不满足。
- 分解方法：将 R 分解为 R1(A, B, D) 和 R2(B, C)，可达到 3NF 甚至 BCNF。

---

#### 范式-2

**[题目]**
设有关系模式 R（学号, 课程号, 成绩, 教师名），函数依赖集 F = {（学号, 课程号）→成绩, 课程号→教师名}，主键为（学号, 课程号）。该关系模式最高属于（ ）。

A. 1NF
B. 2NF
C. 3NF
D. BCNF

**[答案]** A

**[解析]**
- 判断步骤：
  1. **1NF**：所有属性都是原子值，满足。
  2. **2NF**：检查是否存在**非主属性对主键的部分函数依赖**。
     - 主键是（学号, 课程号），是组合键。
     - 非主属性有：成绩、教师名。
     - 存在 课程号→教师名，即教师名只依赖于主键的一部分（课程号），不需要学号参与。
     - 这是典型的**部分函数依赖**，违反了 2NF。
     - 所以**最高只是 1NF**。
- 部分依赖的危害：数据冗余（同一门课每选一次就要重复存教师名）、更新异常（换老师要改很多行）、插入异常（新课没学生选时无法插入教师名）、删除异常（删除最后选课学生时教师信息丢失）。
- 分解方法：拆分为 R1（学号, 课程号, 成绩）和 R2（课程号, 教师名），消除部分依赖，达到 3NF / BCNF。

### 十二、数据库设计阶段顺序判断题

**[题目]**
数据库设计的正确步骤顺序是（ ）。

A. 需求分析 → 概念结构设计 → 逻辑结构设计 → 物理结构设计 → 数据库实施 → 数据库运行和维护

B. 需求分析 → 逻辑结构设计 → 概念结构设计 → 物理结构设计 → 数据库实施 → 数据库运行和维护

C. 概念结构设计 → 需求分析 → 逻辑结构设计 → 物理结构设计 → 数据库实施 → 数据库运行和维护

D. 需求分析 → 概念结构设计 → 物理结构设计 → 逻辑结构设计 → 数据库实施 → 数据库运行和维护

**[答案]** A

**[解析]**
- 数据库设计六阶段（标准流程）：
  1. **需求分析**：弄清用户要什么数据、什么功能，产出数据字典、数据流图。
  2. **概念结构设计**：将需求抽象为概念模型，典型工具是 **ER 图**（实体-联系图），与具体 DBMS 无关。
  3. **逻辑结构设计**：将 ER 图转换为具体 DBMS 支持的关系模式（表结构），进行**规范化**处理（消除冗余、达到 3NF 等）。
  4. **物理结构设计**：为关系模式选择存储结构、存取方法（如索引、聚簇等），与具体 DBMS 和硬件相关。
  5. **数据库实施**：建表、写代码、录入数据、调试。
  6. **数据库运行和维护**：上线后监控、备份、调整。

- 常见混淆点：
  - 概念设计 vs 逻辑设计：概念设计是画 ER 图（抽象），逻辑设计是转成表（具体）。**概念在前，逻辑在后。**
  - 逻辑设计 vs 物理设计：逻辑设计决定"有什么表"，物理设计决定"表怎么存"。**逻辑在前，物理在后。**
- 选项 B 错误：概念与逻辑顺序颠倒。
- 选项 C 错误：需求分析应在最前面。
- 选项 D 错误：物理与逻辑顺序颠倒。
